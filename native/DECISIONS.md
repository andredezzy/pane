# Engineering decisions log

Dated record of choices made while building the native shell — what was decided, why, and what was rejected. Newest last.

## 2026-10-26

- **Pinned Chromium 156.0.8078.48**, the newest Mac stable on chromiumdash today. Ardia's patch series targets 156.0.8078.47, one patch release behind, so its patches should apply with little or no fuzz.
- **Native data root is `~/Library/Application Support/com.pane.desktop/`** (ADR 0004): it collides with none of the Electron app's directories (`@pane/veil`, `@pane/desktop`, `Pane`).
- **Checkout via a shallow git clone of the tag plus an unmanaged `.gclient`** (`--no-history --shallow`), rather than the official source tarball, which is Linux-oriented and skips Mac-only deps and hooks.
- **Patches are applied and reversed with saved copies** (`~/chromium/.applied`) instead of resetting the checkout, so `src/pane` and build outputs are never touched by a reset.
- **Chrome for Testing 156.0.8078.48** (`~/chromium/cft`) is used only to validate the scenario runner before the first engine build exists; it is never shipped or patched.
- **Dropped `enable_nacl` from the gn args**: Chromium 156 no longer declares it (NaCl is gone), and gn warned the arg had no effect.
- **The Metal toolchain is a separate Xcode 27 component**: ANGLE's Metal shaders need `xcrun metal`, which Xcode 27 does not install by default. Installed with `xcodebuild -downloadComponent MetalToolchain` (no admin rights needed); `native/README.md` lists it as a prerequisite.
- **Engine user data dir is `<data root>/Engine`, profiles are `<data root>/Engine/<profile id>`**: `ProfileManager::IsAllowedProfilePath` only accepts profile directories whose parent is the user data dir, so `<data root>/Profiles/<id>` (the plan's first sketch) would be refused. Pane's own JSON state stays at `<data root>/`.
- **Kernel panic during the first engine build (watchdog timeout, 01:41 local)**: `watchdog timeout: no checkins from watchdogd in 93 seconds`, panicking thread a `clang` from the build. The build ran ~18 compile jobs while Spotlight (`mds`) indexed the fresh 500k-file checkout; a jetsam event 40 min earlier showed memory pressure during the dependency sync. Fixes:
  - **The checkout lives in `~/chromium.noindex`** (Spotlight skips `.noindex` directories), and `~/chromium` is a symlink to it, so every path in the plan and the scripts still works. Chromium's own Mac build docs recommend keeping the checkout out of Spotlight.
  - **`build.sh` caps compile jobs** at two thirds of the cores (12 of 18 here, override with `PANE_BUILD_JOBS`) under `nice`, leaving the system headroom. A utility-QoS clamp was tried first and dropped: it cut throughput ~5× (≈80 vs ≈430 Siso steps/min, a ~9 h build), while the 12-job cap alone holds load near 19 with memory 86% free.

## 2026-10-26 — Phase 1 (PaneCore.framework in host mode)

- **The framework is `PaneCore.framework`, branded Pane**: `chrome/app/theme/chromium/BRANDING` carries the Pane names and `com.pane.desktop`, which also names the helpers `Pane Helper (…)` and the framework bundle `com.pane.desktop.framework`. The framework's own name is not derived from branding everywhere, so patch 0001 sets it in each place that builds it: `chrome/BUILD.gn` (`chrome_framework_name`), `chrome/common/chrome_constants.cc`, `chrome/app/chrome_exe_main_mac.cc`, `content/public/app/BUILD.gn` (libaperitif's install name), and `chrome/browser/web_applications/os_integration/mac/BUILD.gn` (app_mode_loader).
- **Exports are explicit**: `chrome/app/framework.exports` lets `_OBJC_CLASS_$_Pane*`, `_OBJC_METACLASS_$_Pane*` and `_Pane*` through, and `chrome/app/framework.order` must list every one of them by name, in order — `verify_order.py` fails the build otherwise. Every new exported class or constant goes into `framework.order`.
- **One seam into Chrome's startup, not many patches**: `ChromeMain` (patch 0002) builds `pane::PaneMainDelegate`, a `ChromeMainDelegate` subclass from `//pane`. It plugs in `pane::ContentBrowserClient` (a `ChromeContentBrowserClient` subclass), which adds `pane::BrowserMainExtraParts` when hosted. Later hooks (renderer client, command-line switches per renderer) go through these subclasses instead of new patches. `//pane` is a dependency of `//chrome:chrome_dll` and includes `chrome_main_delegate.h` with `nogncheck` (it lives in that target).
- **Host mode is the `--pane-hosted` switch**, added by `PaneBrowserApplication +runWithDelegate:` along with `--no-startup-window --no-first-run --no-default-browser-check` and the engine's `--user-data-dir` (unless one is given). Patched Chrome code reads it through the header-only `pane/common/host.h`: no main menu (`chrome_browser_main_mac.mm`), Dock reopen posted as a notification instead of opening a Chrome window (`app_controller_mac.mm`), and pages reported to DevTools as `page` (`chrome_devtools_manager_delegate.cc`; Phase 2's hidden `Browser` makes them real tabs, which Chrome reports as pages on its own).
- **Lifetime needs no Pane keep-alive**: Chrome's AppController already keeps the process alive without windows and releases that on quit; a Pane keep-alive would have blocked Quit. Each `PaneBrowserContext` holds a `ScopedProfileKeepAlive` (`kBrowserWindow`), released with every page at `PostMainMessageLoopRun`, before Chrome destroys profiles.
- **The app decides page visibility** (`PaneWebContents.visible`): pages are created hidden like background tabs; setting `visible` calls `WasShown` and unhides `WebContentsViewCocoa`, which Chromium hides for contents created hidden (Chrome's own view host unhides it when attaching a tab; the arc-engine notes record the same for Arc). Without the explicit show, `WebContentsImpl` ignores occlusion updates until a page was first shown for real, so a page whose window starts covered stays blank.
- **The app's view hierarchy is layer-backed** around pages, as in Chrome's own windows.
- **Screen locked during the unattended run (since ~04:20 local)**: macOS hides every window from accessibility and refuses input, so the window screenshot, the accessibility read and a real Cmd+Q cannot be proven now. Verified instead: the page is `visible`, laid out at the content area's size (1060×820), and composited by the engine (a CDP capture of it shows the full page); `WebContentsViewCocoa` is unhidden with Chromium's `CALayerHost` attached; graceful shutdown leaves no helper. Under the lock the window shows the page's background color but not its content, while stock Chrome's views windows paint. The `hosted` scenario re-checks everything, including the visual parts, the moment the screen is unlocked (see HUMAN-CHECKLIST), and a content_shell build — Chromium's reference embedder using the same standalone compositor path — confirmed the artifact: under the same lock it also shows only the page's background color (`evidence/phase-1/control-content-shell-locked.png`).
- **Keychain**: under the locked session the ad-hoc signed app cannot read or create its "Pane Safe Storage" item (`-25320`), so Chrome reports "Encryption is not available" and keeps cookies unencrypted for that run. Phase 5 (cookie migration, os_crypt naming) must settle how the item is created; stock Chrome from the same build shows the same message.

## 2026-10-26 — Phase 2 (browser core)

- **One hidden Chrome `Browser` per (window, profile)**, backed by `pane::HostedBrowserWindow` (adapted from Ardia's `ac_browser_window`, Apache-2.0), so pages, popups and extensions see real tabs. Chrome-made browsers (for example from an extension's `chrome.windows.create`) still get Chrome's own window until Phase 4 routes them.
- **Popups become tabs** in the opener's profile, inserted right after the opener: `HostedWebContentsDelegate` rewrites window dispositions to `NEW_FOREGROUND_TAB`, as the Electron app does with `setWindowOpenHandler`.
- **Closing or quitting does not report tab removals**: `WindowHost` skips `didRemoveTab` while a tab strip closes all its tabs, the window closes, or the engine quits. Without this the app saw every tab leave at Cmd+Q and saved empty profiles. `didRemoveTab` now means "this tab closed", and session restore is the app's (it persists its own `profiles.json`, as the Electron app does).
- **The app saves at `browserApplicationWillShutDown:`** (new optional delegate method, called from `PostMainMessageLoopRun`) rather than at `NSApplicationWillTerminateNotification`, which Chromium's quit path does not reliably post.
- **`TabBridge` unregisters its observers in `WebContentsDestroyed()`**, not in its destructor: by the time user data is destroyed, `WebContentsImpl` has already emptied its user-data map, so `FindTabHelper::FromWebContents` returned null, the bridge stayed in `FindTabHelper`'s observer list, and `~FindTabHelper` hit the `CheckedObserver` use-after-free CHECK at every quit.
- **Renderer-crash reports reach the app one task later**: an app that reloads inside `PrimaryMainFrameRenderProcessGone` relaunched the renderer while the process's other observers were still being told it died, and `extensions::RendererStartupHelper::OnRenderProcessLaunched` CHECK-failed. Posting the callback lets every observer see the exit first.
- **Scenarios drive the app through a test-only automation channel** (`PANE_AUTOMATION_DIR`, `native/app/Pane/Automation/Automation.swift`): JSON commands in `in/`, replies with a state snapshot in `out/`. Commands call the same `BrowserController` methods the UI calls; key presses are real `NSEvent`s posted to the app's event queue, so they go through event monitors and menu key equivalents like typed keys. CDP stays for reading pages; CUA for anything the screen must show. Without `PANE_AUTOMATION_DIR` the channel does not exist.
- **Shifted menu shortcuts use uppercase key equivalents** (`"T"` with ⌘ for ⇧⌘T), the form Interface Builder stores: a typed ⇧⌘T arrives as `"T"`, which a `"t"` + Shift item does not match.
- **The theme sets `NSApp.appearance`**, and Chromium's `NativeThemeMac` follows the app's effective appearance into `prefers-color-scheme` with no engine change (`theme.json`: light, dark, and system each match).
- **Locked-screen limits found in Phase 2**: while the screen is locked the window counts as occluded, so Chromium hides the selected page once occlusion tracking is live (after its first real show) and sends it no visual updates; a zoom change then shows in the engine's zoom level but not yet in the page's `devicePixelRatio`. `shortcuts` asserts the engine level always and the page ratio whenever the page is visible, and re-runs on an unlocked screen. The switcher picture under the lock is an offscreen render of the app's views (`switcher.png`), which shows the app UI but not page pixels.
- **Hosted mode returns early from `-[AppController setLastProfile:]`** (patch 0002): Chrome built no main menu, so the bookmark and history menu bridges had no menu (`BookmarkMenuBridge` CHECK-failed on a null root) and the shared menu command state was never created (a null dereference). Both fired when deleting a profile made Chrome switch its last-used profile. The method's remaining work only syncs Chrome's own menus.
- **`deleteContext:completion:` completes when Chrome has marked the profile for deletion** (`ProfileManagerObserver::OnProfileMarkedForPermanentDeletion`), not when the request is made. Only then is the deletion durable: Chrome first closes the profile's browsers (asynchronously), and a quit before that point used to leave the profile and its data in place. The directory itself goes once the profile is destroyed, or in Chrome's startup cleanup.
- **Deleting a profile opens its context first** when it was not opened this session, so engine data from earlier sessions is deleted too; the app tracks pending deletions until the engine confirms.
- **macOS logs a simulated `EXC_GUARD` fault report** (`ExcUserFault_Pane-*.ips`) during downloads: IconServices faults inside `-[NSWorkspace setIcon:forFile:options:]` while Chrome badges the downloading file's icon with its progress. Not a crash; stock Chrome does the same.


## 2026-10-26 — Phase 3 (Chrome UI hooks)

- **Every Chrome dialog, bubble, and menu of a Pane tab is a request object the app answers** (`public/PaneDialogs.h`): JavaScript dialogs (and beforeunload, form resubmission), permission requests, HTTP and proxy authentication, context menus, file choosers, external protocols, unresponsive pages. Each reaches the app through a delegate method and is answered once; the engine withdraws it (`didDismissRequest:`) when Chrome takes it back. The app shows them as sheets on its window, one at a time and only for the selected tab, as Chrome's tab-modal dialogs do (`DialogPresenter`).
- **Hook points** (patch `0004-pane-ui-hooks`, declared in `pane/browser/ui/ui_hooks.h`): `CreatePermissionPrompt`, `LoginHandler::Create`, `ExternalProtocolHandler::RunExternalProtocolDialog`, DevTools docking in `DevToolsWindow`, `PrintViewManagerBase::ScriptedPrint` (for the app's print callback), and `chrome::ShowDeviceChooserDialog`. JavaScript dialogs, the context menu, unresponsive pages, form resubmission, and screen-capture requests need no patch: they are `WebContentsDelegate` methods `HostedWebContentsDelegate` overrides. File dialogs go through `ui::SelectFileDialog::SetFactory`, which catches every file dialog Chrome opens for a window: inputs, File System Access pickers, Save As.
- **Kept from Chrome by decision**: the certificate warning page (it is web content in the tab, not a window), and the picture-in-picture player (`VideoOverlayWindowViews`). The player has to host the video's compositor frame (a viz surface), which AppKit cannot show without Chromium's compositor, and AVKit's picture-in-picture only plays AVFoundation media. The app is told when it opens and closes.
- **Off, as in the Electron app**: Chrome's password manager and autofill (prefs per profile; Pane relies on extension password managers), device choosers (USB, HID, serial, Bluetooth: declined at once), screen capture (`getDisplayMedia` declined), Cast (`MediaRouter` feature off). Also off: Glic (Gemini in Chrome) and the testing field trials (`disable_fieldtrial_testing_config = true`), which put items in the menu bar (Omnibox Everywhere's "Search with Chromium"). Chromium's testing field trials switch on experimental features in non-official builds; Pane ships Chromium's defaults, as official builds do.
- **Print uses the system print panel** (`--disable-print-preview`), from ⌘P and `window.print()`.
- **DevTools dock beside the tab in the app's window**, and undocked DevTools open in a window of Pane's: Chrome's DevTools `Browser` gets a `HostedBrowserWindow` in an engine-owned window (`devtools_window_host.mm`) that shows only the DevTools page. Chrome builds that Browser before it can join a window, so it joins a task later.
- **Fullscreen fills the app's window** (sidebar and toolbar step aside); Chrome's "Press Esc" bubble is replaced by the app's hint, and Esc leaves fullscreen wherever focus is.
- **Closing a tab waits for Chrome**: the app removes a loaded tab when Chrome reports it closed, so a page's beforeunload can keep it. Unloading a profile closes pages at once (`closeImmediately`, no beforeunload).
- **A crash loop shows the app's sad tab**: the first renderer crash reloads the page; another within a minute shows the sad tab with Reload.
- **AppKit's window restoration is off** (`ApplePersistenceIgnoreState`): Pane restores its own session, and AppKit's "reopen windows?" alert after a crash blocked the app.
- **Spellcheck comes up as each profile is added**: `SpellcheckService` hands dictionaries only to renderers created after it exists; Chrome creates it through sync, which Pane does not run.
- **Ardia's hooks (task 3.2)**: `chromium-password-bubble-hook` and `chromium-autofill-address-bubble-window` are not needed (password manager and autofill are off); `chromium-device-chooser-hook` is adapted as `g_pane_device_chooser`, which declines; `chromium-cast-dialog-hook` is not needed (Media Router off); `chromium-side-panel-hook` belongs to Phase 4 (extension side panels); the `chromium-devtools-*` seam is replaced by Pane's own docking hooks, which also cover undocked DevTools.
- **Testing on a locked screen**: scenarios pass `--disable-backgrounding-occluded-windows` while the screen is locked (Chromium's switch for this exact case): macOS reports the window occluded and Chromium would hide its pages, which stops visual updates and the hang monitor. A sheet is clicked with CUA on an unlocked screen, else through the automation channel, which calls `performClick` on the same NSButton. macOS 27 runs open and save panels out of process (`-[NSSavePanel ok:]` throws "not implemented"), so locked-screen runs answer a file chooser beside its panel. Chromium ignores an unresponsive page while a debugger is attached, and mouse input never arms its hang monitor (mouse events are non-blocking), so the hang scenario attaches no CDP and types a key into the page.
- **Incident: a scenario opened the user's Mail app** (07:08 local). The external-protocol scenario first used a `mailto:` link, which Chrome opens without asking (by design), so macOS opened Mail with an unsent compose window to `pane-scenario@example.invalid`. Mail was not running before; it was quit at once (SIGTERM, 07:10). Nothing was sent. The scenario now uses `maps:`, which always asks, and answers Cancel; it checks Maps did not open. A HUMAN-CHECKLIST entry asks to look for a stray draft.


## 2026-10-26 — Phase 4 (extensions)

- **Chrome's extension system runs extensions, one per profile**; the app shows their toolbar actions, popups, install prompts, and management (`public/PaneExtensions.h`, `pane/browser/extensions/`). Install prompts come from Chrome's `ExtensionInstallPrompt` (patch `0005-pane-extensions`) and show as the app's sheet. Ardia's `chromium-extension-install-prompt-hook` was evaluated and adapted that way; Ardia's hidden-window hooks (`chromium-hidden-window-current-window`, `chromium-extension-window-hidden`) are not needed: each profile's tabs live in a hidden `Browser` of Pane's window (Phase 1), which Chrome already counts as the current window for popups and service workers.
- **`chrome.windows.create` opens a tab in the extension's profile**, as the Electron app did: Pane has no popup windows, and Chrome's new `Browser` is folded into the profile's (`ForwardToPaneWindow`). `chrome.tabs.update({active: true})` selects the tab in the app (`browserWindow:didActivateTab:` is now followed, except for Chrome's pick as a tab closes, where the app picks the next tab itself).
- **An action's title, badge, icon, and popup are per tab**: the engine reports them again when the profile's selected tab changes (a `BrowserTabStripTracker`). Chrome's `ExtensionActionIconFactory` keeps the first default icon it returns, which is a blank placeholder when asked before the icon file loaded (NordPass's showed blank); the bridge starts its factories over once an icon loads.
- **A popup's page sizes itself, as in Chrome**: auto-resize is enabled on the popup's main frame as it becomes the main one (`RenderFrameHostChanged`), since its first document commits in a new frame. The page sits on an opaque white canvas in the popover; straight on the popover's material it was blended with it (vibrancy) and a dark popup turned near black.
- **Some extensions turn their popup off until the user signs in**: 1Password clears its popup seconds after installing, so its button opens its welcome page in a tab, as in Chrome. The scenario presses the button and checks whichever the extension chose.
- **Quit outranks a remote debugging client**: Chrome started without a window (`--no-startup-window`) with `--remote-debugging-port` holds a keep-alive for the client until it closes the browser. Pane's quit releases it (`ChromeDevToolsManagerDelegate::AllowBrowserToClose` at app-terminating), so Quit Pane quits under the scenarios too. Pane launched normally has no such keep-alive.
- **Scenarios keep Chromium off the login keychain** (`--use-mock-keychain`): a freshly signed build asks for the keychain password for "Chromium Safe Storage" on every launch. The shipped app's keychain item and signature are Phase 5 (product name, stable signature).
- **CUA reads pages only with full accessibility on**: Chrome builds a page's accessibility tree, with its actions, once an assistive app turns it on (VoiceOver asks the app for its role and sets `AXEnhancedUserInterface`; Chrome waits two quiet seconds). cua-driver does neither, so scenarios do it (`tools/ax-activate.swift`) before clicking a page's button, such as the Web Store's Add to Chrome; the click is then a real, trusted press with user activation.
- **Found by the unlocked-screen runs** (fixed, each with a scenario check): the address field kept the previous tab's address while it had focus (`navigation`); the toolbar's Reload and ⌘R did not bring back a sad tab (`sad-tab`); "Quit Pane" under the scenarios (above). The spelling check had used "helo", which macOS accepts: no word was flagged on any screen, locked or not, and stock Chrome for Testing flagged none either; it now uses "recieve" (`context-menu`).


## 2026-10-26 — Design fidelity (the Electron app and Paper)

- **The reference is the Electron app's renderer, which the Pane file in Paper documents** (`01 · Foundations` to `06 · Lock screen`; tokens, spacing, radii, type, elevation, every screen in light and dark). Paper was read through the Paper app's local MCP server (read-only: screenshots, styles, tokens), and the Electron app was measured live: its built bundle run on a throwaway data directory with remote debugging, element boxes read with `getBoundingClientRect`, and the native app's frames read from its accessibility tree. The two agree to the point on the sidebar, toolbar, page area, settings, and the profile sheet (`native/evidence/design/`, with pixel diffs of each screen in both themes).
- **The design layer** (`Views/Theme.swift`, `Views/Controls.swift`): the CSS tokens as light/dark pairs, lucide icons from their own SVG paths (the Electron app's icon set; ISC, `native/NOTICE`), and packages/ui's Button, Input, Switch, and Separator with the same variants and sizes. Corners are circular, as CSS draws them, not Apple's continuous curve.
- **CSS details the native views reproduce**: line boxes (text-sm is a 20px line, an inline label in a 16px block takes a 24px line, and its margin does not apply), border-box widths (a 1px border widens a chip or an outline button by 2px), collapsing margins (the New tab row sits 4px under the last tab, not 8), box-shadows drawn outside the element, and `flex-1` sharing width before borders.
- **Text is drawn without font smoothing** (`AppleFontSmoothing` 0 in the app's registered defaults), as the Electron UI's `-webkit-font-smoothing: antialiased`; with it SwiftUI text was visibly heavier. Web pages render the same either way (Chromium draws them).
- **Window chrome**: traffic lights at (12, 12) in the sidebar's 39px header (Electron's `trafficLightPosition`), the content under the hidden title bar, 1280 × 800 by default (900 × 600 at least). The title bar container spans the top 40px, over the toolbar; real clicks there still reach the toolbar and the header (`window-chrome` scenario). AppKit's title bar is left alone in full screen.
- **Surfaces as the Electron app's**: the toolbar inside the content panel (the page 43px down it, where Electron's view sits), the profile chip, the address field's loading bar, the profile sheet as a 360px side panel with a black 40% scrim, the uninstall confirmation as the app's dialog (black 60%), find at the window's top right, the switcher's 320px panel. Chrome's own dialogs (alerts, permissions, sign-in, file choosers) stay system sheets (Phase 3); the Electron app has none of its own for them.
- **Kept from Paper over the Electron app**: unloaded tabs at 60% opacity (Paper's TabItem spec). The Electron app sets the class, but the drag code's inline `opacity: 1` overrides it, so its unloaded tabs never dim.
- **Native additions, drawn in the same language**: Settings › Extensions is per profile (a profile select, Update all, and Pinned and Enabled switches on each card, task 4.4), and its uninstall message names the profile. Not yet in the native app, so not in its screens: the Electron app's Browser, Memory & disk, Security, and Updates settings, the profile sheet's fingerprint and proxy fields, the update pill, the proxy dot, and the lock screen (all Phase 5 rows in `docs/native/parity.md`).
- **Found while comparing** (fixed): the HTTP sign-in sheet's fields had no width (an `NSStackView` in the alert sized each empty field to its content; now constrained, and `http-auth` checks the widths on screen); the profile sheet's clip removed its shadow; the find field only showed text typed into it (it now shows the window's query, and searches again only when the query changes).


## 2026-10-26 — Phase 5 (Pane features)

- **5.1 Per-profile proxy**: the engine sets Chrome's own per-profile prefs, `proxy` (fixed servers) and `webrtc.ip_handling_policy` (`PaneBrowserContext.proxyRules`, `webRTCIPHandlingPolicy`); a profile's pages open only after both are applied. A SOCKS proxy with credentials goes through the app's relay (`Network/SocksRelay.swift`, ported from `proxy-relay.ts` onto Network.framework, SOCKS5 with RFC 1929 or SOCKS4a upstream), since Chromium cannot authenticate to SOCKS. An HTTP or HTTPS proxy's challenge is answered with the profile's credentials through the Phase 3 hook, without a prompt; asked again within five seconds (wrong credentials), the user gets the sheet instead of a loop. The connection test (`Network/ProxyTest.swift`) fetches the same IP echo as `proxy-test.ts` through the proxy with URLSession's proxy configurations, SOCKS through the relay (URLSession has no SOCKS4), and feeds the sidebar's dot. Chrome names a proxy challenger with its scheme (`http://host:port`), which `PaneDialogs.h` now says.
- **Observed**: Chrome's own background requests (`accounts.google.com`, `www.google.com`) go out per profile, through its proxy. The Electron app makes none; whether to turn them off belongs with the fingerprint work (5.2), which owns what a profile reveals.
- **5.2 The fingerprint lives in Blink and the browser, not in script** (patch `0006-pane-fingerprint`). The app builds each profile's `EngineFingerprint` (PaneKit) and hands it to the engine before the profile opens (`-[PaneBrowserApplication setFingerprint:forContextIdentifier:]`).
  - **Browser side**: content gets per-context hooks, `GetUserAgentForBrowserContext` and `GetUserAgentMetadataForBrowserContext`. Every place that asked for the global User-Agent now uses them:
    - renderer init;
    - navigations, redirects included;
    - service and shared workers;
    - the per-profile Client Hints delegate;
    - the profile's network context, for prefetches and the browser's own requests.
  - **Languages** use Chrome's own prefs: `intl.selected_languages`, from which `LanguagePrefs` derives `intl.accept_languages`. Setting the derived pref alone was reverted at once.
  - **Renderer side**: each renderer of the profile gets the renderer half of the fingerprint as `--pane-fingerprint`. A renderer never serves two profiles. Blink's `PaneFingerprint` reads it once and reports:
    - navigator.platform, hardwareConcurrency, deviceMemory, and maxTouchPoints;
    - the screen rectangles, colorDepth, and isExtended, plus devicePixelRatio;
    - WebGL's unmasked vendor and renderer;
    - canvas noise on getImageData, toDataURL, toBlob, and convertToBlob, the same noise on every path;
    - audio noise on an OfflineAudioContext's rendered buffer, before `oncomplete`;
    - the speech voices.
  - **Time zone**: the fingerprint's zone becomes the renderer's host time zone. The system's changes no longer replace it, and DevTools' override still works on top.
  - **Locale**: it becomes the embedder locale of `LocaleController`, so it is the default locale of Intl. The renderer's `--lang` is unchanged, because a locale without a resource pak would crash it.
  - Every surface is a native function, in every frame and worker, from the page's first script.
- **Where 5.2 differs from the Electron spoof, on purpose**:
  - **GREASE brand order**: it is Chromium's current one, a permutation seeded by the major version (`GetRandomOrder`). The Electron port's insertion index matches older Chrome only; it agrees for 136 and 156 by chance and not for 157. PaneKit checks the derivation against the `Sec-CH-UA` that Google Chrome 120, 124, 131, and 136 sent. The scenario checks that the GREASE brand equals the engine's own.
  - **Full version list**: it carries the engine's full version. The native User-Agent is reduced (`Chrome/156.0.0.0`), while the Electron one was full.
  - **Device memory**: it is reported in Chrome's buckets, a power of two from 0.25 to 8.
  - **Speech voices**: they are hidden only when the claimed platform is not macOS, since the host's voices are a Mac's. The Electron app always hid them.
  - **No script stubs**: chrome.app, loadTimes, csi, plugins, and storage estimates are Chrome's own, so they need no stubs.
  - **No Worker wrapper**: every worker reads Blink directly, including the module and cross-origin workers that Electron's wrapper skipped.
  - **The noise seed and algorithms are the Electron app's**, so a migrated profile draws the same canvases.
- **A changed fingerprint reaches navigations and new renderers at once**; an open page keeps its renderer's values until it reloads in a new process. Reopening the profile's tabs on a change is part of the profile sheet's fingerprint editor (5.6).
- **Known gaps, as in the Electron app**:
  - WebGPU's adapter info;
  - the CSS `device-width` and `resolution` media features;
  - `window.outerWidth` against a smaller claimed screen;
  - the `Sec-CH-Device-Memory` header.
- **Service workers' own fetches** carry no UA Client Hints in Chrome; an unfingerprinted profile's carry none either. They carry only the User-Agent, which is the profile's.
- **5.3 No Google sign-in workaround** (the user's decision). The Electron app's fallback for Google rejecting its engine is gone: a real Chrome to sign in, a session transfer page, and Sign out of Google in the profile menu. It was a workaround for the Electron engine, and no browser has one. Google accepts the native engine, with and without a fingerprint: `phase-5/google.json` loads the identifier page, never `/rejected`. A version built in this session was removed before it shipped. What stays of it is the engine's read-only cookie API (`PaneCookies.h`, also the cache size and trim of 5.4), which scenarios use.
- **Open: Chrome's own requests to Google.** They were observed in 5.1 (`accounts.google.com`, `www.google.com`, per profile, through its proxy) and are still on. They carry the profile's own User-Agent now (5.2), and Google accepted the engine with them. Finding their sources and turning off those the Electron app never made is a task of 5.6 in the plan.
- **5.4 Sleep releases a tab's page, as in the Electron app.**
  - The page closes and the tab stays, dimmed. Selecting the tab navigates it again, so its back and forward history does not survive. Chrome's in-place discard (`WebContents::Discard`) would keep the history, but on desktop it sits behind a disabled feature (`kWebContentsDiscard`), and Chrome's own discard replaces the tab's WebContents. Neither is worth the risk for parity.
  - Freezing is not used: the Electron scheduler and CONTEXT.md have no frozen state.
- **5.4 The scheduler is PaneKit's port of `sleep-scheduler.ts`**, with every case of its tests, an injectable clock, and the app's timer ticking it every minute. `PANE_TIME_SCALE` speeds the clock up for the `sleep` scenario.
  - **Protected tabs**: audible (`PaneWebContents.audible`, Chrome's audio indicator), DevTools open, and, beyond CONTEXT.md's list, picture-in-picture. A floating video would otherwise vanish while it plays silently.
  - **Recent interaction** is protected by construction, as in the Electron app: a tab's clock starts only when it leaves the selection.
  - **Trim** removes the HTTP cache, Cache Storage, and service workers: Chrome's `BrowsingDataRemover`, as the Electron app's `clearData(cache, serviceWorkers)`. Cookies, local storage, and IndexedDB stay. The size it checks against the budget is the HTTP cache's (`ComputeHttpCacheSize`), as Electron's `getCacheSize`.
- **Fixed from the Electron scheduler**: a hidden profile's tabs are all in the background. With tab sleep sooner than unload, which the defaults (15 and 30 minutes) are, tab sleep always drains a hidden profile before its unload is due. The unload branch then never runs, and the profile was never trimmed. The native scheduler treats a hidden profile whose last tabs just slept as unloaded, and trims it. Two PaneKit tests cover it. Without an unload setting, nothing is trimmed, as before.
