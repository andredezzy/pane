# Building Pane

Pane is its own build of Chromium: Chromium's loader and helpers, and `Pane Framework.framework`, which holds Chrome's `chrome/` layer and the `//pane` tree, Pane's code, its UI drawn in C++ with Views, as Chrome's own is. gn builds all of it. Why: `docs/adr/0004-native-shell-on-own-chromium-framework.md` and `docs/adr/0124-one-ui-in-views-on-every-os.md`. What was decided, and why: the ADRs in `docs/adr/`, one per subject.

## Layout

- `pane/` — the `//pane` tree, symlinked into the checkout as `src/pane`, linked into `Pane Framework.framework`: the launch (`app/`), the model and the data's formats and rules (`model/`: the lock, the vault's sequences, the data's lock, and the panic wipe's order, each system's own steps in `_mac`/`_win` halves, Windows' engine folder as the vault's place and its secret under DPAPI and the TPM's guard of the PIN; the Mac's encrypted volume, Keychain, and earlier Panes' paths in `model/mac/`), the files' encryption (`encryption/`), the layer over Chrome's Browsers (`browser/`), the UI (`ui/`), the update check and install (`updates/`), the scenarios' channel (`automation/`), and what a renderer runs (`renderer/`). A header's platform files sit beside it, `<thing>_mac.cc` and `<thing>_win.cc`, and `<thing>_mac.mm` only where an Objective-C class or header leaves no choice (ADR 0124)
- `chromium/` — what Pane does to Chromium
  - `CHROMIUM_VERSION` — the pinned Chromium stable tag
  - `args/` — gn args per build config
  - `patches/` — `series` (apply order), `MANIFEST` (each touched Chromium file → its owning patch), the patches
  - `prebuilt-engines.tsv` — the engine archive each engine key names, and `UPGRADING.md`, the upgrade routine
- `scripts/` — `sync.sh`, `apply-patches.sh`, `build.sh`, `make-patch.sh`, `preflight.sh`, `fetch-crlset.sh`, `package.sh`, `dist.sh`, Windows' `package-win.sh` and `windows-engine-files.sh`, the checks `check-os-flags.sh` and `compile-windows.sh`, `test-asan.sh` (the model's sanitized tests), and the prebuilt engine's `engine-key.sh`, `fetch-engine.sh`, `publish-engine.sh`
- `packaging/` — what packaging reads: `VERSION`, the entitlements (`signing/`), the dmg's resources (`dmg/`, with `make-background.swift` and `make-volume-icon.swift`, which make its background and volume icon), the icon (`icon/`: `AppIcon.icon`, the bundle's, which `package.sh` compiles; the window's renders; and `make-icons.swift`, which makes the icons from them, Windows' `.ico` files among them), and what Windows' app folder holds (`windows/pane.release`)
- `tests/` — the scenario runner (`run.ts`, its libraries in `lib/` and its Swift tools in `tools/`), two builds' benchmarks in turns (`ab.ts`), fixtures (`pages/`), scenarios that check (`scenarios/`), what measures and never judges (`benchmarks/`), a held test copy for a pass by hand (`rigs/`), and what the test VM alone runs (`vm/`)
- `third_party/` — code Pane adapts; `NOTICE` gives origins and licenses
- `docs/` — this guide, `human-checklist.md` (what only a person can do or verify), `qa/`, reports of passes by computer use, `adr/`, one record per subject, `benchmarks/`, measured comparisons of Pane builds with their raw data and how to rerun them, and `growth/`, the media Pane is shown with outside the app
- `evidence/` — gitignored output of acceptance checks

## Chromium checkout

The checkout lives outside the repo, at `~/chromium` (override with `CHROMIUM_ROOT`): `depot_tools/` and `src/`. Keep it out of Spotlight — here `~/chromium` is a symlink to `~/chromium.noindex`, which Spotlight skips; indexing a fresh checkout during a build starved the system into a kernel panic once. It needs full Xcode plus its Metal toolchain (`xcodebuild -downloadComponent MetalToolchain`), an APFS volume, and ~100 GB free.

```bash
scripts/sync.sh            # depot_tools, src at CHROMIUM_VERSION, deps, hooks, //pane link
scripts/apply-patches.sh   # apply patches/series (no-op when unchanged)
scripts/build.sh           # out/Release, target `chrome` (args/release.gn)
```

Every script is safe to re-run. The first sync and the first build take hours; later builds are incremental. The checkout syncs Windows' dependencies and Chrome's PGO profiles too (ADR 0007); to compile for Windows, sync once with `PANE_WIN_TOOLCHAIN_DIR` naming the folder that holds the toolchain's zip, packaged from a Visual Studio install (Chromium's `docs/windows_build_instructions.md`, Packaging), which stays outside the repo. Moving to a newer Chromium is a routine: `chromium/UPGRADING.md`.

## Patches

Edit files in `~/chromium/src`, list each touched file in `patches/MANIFEST` with its owning patch, then regenerate the patch with `scripts/make-patch.sh <patch-name>`. A file belongs to exactly one patch, so a patch is the diff of its own files against the pinned tag.

## Engine unit tests

```bash
bun run test   # scripts/build.sh pane_unittests, then ~/chromium/src/out/Release/pane_unittests
```

`pane_unittests` checks what `//pane` decides without a browser: the model (`pane/model`, with a twin of each of the Swift app's PaneKit tests that its code still has, `docs/benchmarks/panekit-tests.md`; the lock with the PIN's guard on a TPM in memory, `StandInPinGuard`, and the vault on Windows' place, on every system, and on Windows the lock's answer to each code the chip's provider gives, `app_lock_win_unittest.cc`), the Mac's vault and every earlier Pane's data (`pane/model/mac`, with real disk images), Windows' own on Windows (os_crypt's key under DPAPI, read back by Chromium's own reader, and the TPM's guard on the computer's chip: only the right PIN is typed, and `PinGuardWinTest.DISABLED_AWrongPinIsRefused` types a wrong one when asked for by name, `--gtest_also_run_disabled_tests`, in the test VM), the formats every profile file is written in (`pane/encryption`, ADR 0121: the key registry, the SQLite VFS through journals, WAL, kills, Raze and Recovery, and the stream and whole-file codecs), which launch may open which data (`pane/app`, ADR 0012), Windows' installer's on Windows (`pane/installer`, ADR 0127: the payload, an update's staging, its swap and rollback, the helper's wait and what it ends, and the uninstall's removal, which refuses every folder but the install's own), and the UI's own rules (`pane/ui`: the command table, the Lock's triggers, the design's curves, radii, and colors, the favicons). CI never builds Chromium, so these run locally, before committing an engine change. Run over the test VM's SSH, as its administrator, Windows' `ScopedTempDir` makes its folders in `%SystemRoot%\SystemTemp`, not `%TEMP%`: a test that needs one in the temporary folder makes it under `GetTempDir()`. Run as a scheduled task, in the console's session, it starts below normal priority, which base's test suite refuses at once (`Check failed: !IsProcessBackgrounded()`): the task raises its own priority to normal first, and the tests inherit it.

```bash
bun run test:asan   # scripts/test-asan.sh: out/ASan, then ~/chromium/src/out/ASan/pane_model_unittests
```

The model's tests run under AddressSanitizer too, with DCHECKs on, as PaneKit's sanitized runs did: `pane_model_unittests` holds `pane/model`'s and the Mac's vault's tests alone, over `//base` and `//crypto`, apart from `pane_unittests`' network stack, built in `out/ASan` from `chromium/args/asan.gn` (release.gn's args with `is_asan` and `dcheck_always_on`, and Chrome's PGO profile off, which was made without DCHECKs). gn generates for that one target, so its first build compiles `//base`, ICU, BoringSSL, and the model, a few minutes at 6 jobs, never the browser. ThreadSanitizer doesn't build on the Mac.

## Scenarios

```bash
bun tests/run.ts --binary <path to browser executable> --out <dir> [--foreground] [--user-launch] <scenario or path>...
```

The runner serves `tests/pages` on 127.0.0.1, launches the binary with remote debugging, runs each scenario, and writes `<scenario>.json` plus `report.json` into `--out`. `PANE_SCENARIO_STDERR=1` shows the binary's log. A scenario fails after `--timeout` seconds (600). Whatever it launched is quit, and the directories it took (`context.tempDir`) are removed, with any process still using them. Each entry records whether the screen was locked and the checks it deferred; `report.json`'s `complete` is true only when every check ran.

**Two runs' renders.** `bun tests/rigs/compare-renders.ts <run A's --out> <run B's --out>` compares every PNG the two runs wrote, every byte of every pixel, and lists each render that differs with its parts (each part's box, its pixels, its largest difference); it exits 0 only when both hold the same renders, each identical. Two runs of one build, behind, in one appearance, give identical renders (ADR 0128): a copy's pointer is the channel's, not the user's, the time of day it shows the runner's (`PANE_SHOWN_TIME`), its carets don't blink, the runner's servers keep their ports (`tests/lib/ports.ts`), and a rig renders what loads once it has loaded, a download held at a set share, and a scroll once its overlay scroll bar is gone; so what the comparer lists between two builds is theirs. A run's scenarios are imported as each starts: a run of a build to compare runs from a checkout of its tests that nothing edits meanwhile.

`bun run test:runner` runs the runner's own unit tests (`bun test`, `tests/**/*.test.ts`): what its libraries decide from bytes alone, as the audit's reading of a file. They need the Mac or Windows, as the runner does.

Scenarios for the Pane app (`lib/pane.ts`) give it throwaway data (`PANE_DATA_DIR`) and a throwaway home (`lib/browser.ts`'s `homeEnvironment`: on the Mac `HOME` and `CFFIXED_USER_HOME`, so its caches, HTTP storage, Downloads, and Crashpad's database are not the user's Pane's; on Windows `PANE_HOME_DIR`, below), and drive it through its automation channel (`PANE_AUTOMATION_DIR`, `pane/automation/`, ADR 0018), which, with every `PANE_` hook, works only under `--use-mock-keychain` (`pane/model/test_hooks.h`), where none of the user's data opens; the engine passes Chromium no switch of a launch without it but Pane's own. A launch whose data lies in the temporary folder, by `PANE_DATA_DIR` or under a home of its own, runs on the mock keychain alone, and the mock keychain only there: either without the other exits with 1 before it reads anything (`pane/app/test_copy.h`, ADR 0012), so a test copy reopened without the switch never reaches the user's Keychain. The channel's commands: JSON commands that call what the UI calls, key presses and clicks posted through the platform's own event path, and a state snapshot with every reply. CDP reads pages; `lib/computer-use.ts` covers what only the screen shows: what a check reads of it, through the system's accessibility as a screen reader reads it (the Mac's AX tree, Windows' UI Automation, `lib/uia.ts`), needs an unlocked session alone (`canReadUI()`), and what it drives on the Mac Aside Computer Use too (`canDriveUI()`), or the checks defer. Scenarios run on a Mac in use, so the app never takes the front from the app its user is in: what needs Pane in front (keys a panel takes, a page's fullscreen, Quit Pane?) defers unless `--foreground` allows it, which an idle Mac can, or the user's word (Rigs, below). Preferences are the one thing they still share with the user's Pane: cfprefsd keeps them by bundle ID and ignores a fixed home, and a copy under another bundle ID would ask again for what macOS granted Pane (pasting from other apps), which closes its menus. So a run sets Chromium's `LastRunAppBundlePath` to the build, which the user's Pane resets when it next starts.

**The Mac and Windows.** One runner serves both, and one file of it tests for the OS, `tests/lib/platform.ts`: ADR 0124's rule in the runner's form. What each system does its own way sits in a module that holds both sides and picks one through `bySystem`: `lib/processes.ts` (ps and pgrep; Windows' process table through PowerShell, a process's group as its oldest living ancestor, another process's environment read from its PEB, and `taskkill /F /T`), `lib/tools.ts` (the Swift tools in `tests/tools`, Caps Lock's indicator, a window's capture, the appearance, the volume's disk images, LaunchServices, what makes a stand-in Pane, quarantine or the Mark of the Web and what a download keeps of its page, crash dumps and Crashpad's database, the data folder's privacy (its mode or its ACL) and what an indexer may take of it (Spotlight's or the not-indexed attribute), a byte search of files, and a file held so no write replaces it, `holdFile`: Finder's Locked flag on the Mac, where a read-only mode wouldn't stop an atomic replace, a handle with no delete sharing on Windows), `lib/computer-use.ts` (the screen's lock, `CGSSessionScreenIsLocked` or LogonUI.exe running; the UI driven through Aside on the Mac, and on Windows pressed through UI Automation as Narrator's user presses it, Invoke, else Expand: the menu bar's commands under "Pane ⌄", a dialog's buttons), `lib/uia.ts` (UI Automation's own client, uiautomationcore, compiled once into a DLL: a window's control view in Narrator's order, with each element's type, name, value, description, and the states Narrator says; a press by name; and the process's windows, their client areas, and their screens, in DIPs), `lib/browser.ts` (the app's home, its folder, the bundle or `chrome.exe`'s, its resources, and URLs handed to it as another app hands them), `lib/windows.ts` (the app's windows on screen; what a screen reader reaches of them, `accessibilityTree`; its menus as drawn, Views' less their shadow on Windows; and where its content starts, the frame's on the Mac, the client area's on Windows), `lib/pasteboard.ts` (the clipboard), and `lib/signposts.ts`. A Windows side with nothing behind it yet throws `<what>: no Windows side yet (<item>, …)`, naming the item of the plan that brings it and what it waits on, so nothing there passes for working. Pane's shortcuts are pressed with `PRIMARY`: ⌘ on the Mac, Ctrl on Windows, as the command table gives them there, and those that differ by more with `KEYS` (Back and Forward, Alt+Left and Alt+Right on Windows; Developer Tools' second key, F12; Quit's, Exit's Alt+F4 there, alone, as Ctrl+Q runs nothing on Windows; ADR 0019). What else differs in what Pane shows comes from `lib/pane.ts` by system: where the window's controls sit (`trafficLightsInPlace`: the Mac's lights, or Windows' caption buttons in the panel's corner, ADR 0126) and where Close is pressed (`windowCloseAt`), the frame's top edge that resizes (`TOP_RESIZE_EDGE`, 5 points on Windows), and the word for Quit (`QUIT_WORD`, Exit there).

**Where each runs.** On both, unless a scenario says otherwise in its own `export const notOnWindows`: `{ macOnly }`, whose subject Windows doesn't have, or `{ needsDesign }`, which Windows does its own way, not designed yet, each with its reason. There the runner reports it `SKIP`, the reason in its entry's `notRun`; a `needsDesign` one defers all of it too, so the report isn't `complete`. The Mac's alone: ADR 0122's four (`migration`, `identifier-move`, `files-migration`, `files-migration-large`), every row of its table a Mac Pane's data, since no Pane was published for Windows before the Views line's 0.21.0; `applescript` (ADR 0112); `data-volume` (ADR 0113: Windows has no volume, U5); `memory-guarded` (the hardened runtime's refusal: Windows' promise lets a process of the user's read Pane's memory while it is unlocked, U5); and the rig `views-start`. None waits on Windows' design now: `update-install`, the last, runs there since W7's third part, on stand-in installers it builds from the run's own app folder. A scenario kept off Windows may call the Mac's tools itself; every other, and every module in `lib/`, goes through the modules above.

**On Windows** (the test VM for behavior, a real PC for frames, U6): Bun, PowerShell, and `openssl` (Git for Windows') on the path; the runner started in the console's session, since what starts over SSH shows no window (the VM's `lab/run-interactive.ps1` runs a script there); `--binary <folder>\chrome.exe`, `out/Win`'s files laid out as `packaging/windows/pane.release` names them (`scripts/package-win.sh`'s folder, or `windows-engine-files.sh`'s list); and a printer, which the system's print dialog needs (the VM's own PDF printer won't install, 0x800f0922, so it has one on `FILE:`). - **A test copy** is `PANE_DATA_DIR` in the temporary folder with `--use-mock-keychain`, as on the Mac (`pane/app/data_launch_win.cc`), and its **home** the folder `PANE_HOME_DIR` names in the temporary folder: Chromium reads the user's folders from the shell on Windows, which no variable moves, so a test copy takes them under it (the Desktop, AppData, Start's folder, Documents, Downloads, `PathService`'s overrides), and its App icon follows the shortcuts there alone (ADR 0089). - **A PIN** is set up through the PIN screen by a launch before the one that checks it (`setPinBeforeLaunch`), no Windows Pane having kept the Electron app's hash, and goes through **the computer's TPM**, as a user's does (ADR 0113): the scenarios' derivation of a guarded key asks the chip for its share, with the PIN (`lib/engine-key.ts`), and lists its keys (`pinGuardKeys`). A wrong PIN counts in the chip's lockout and in Windows' own for a standard user, which refuses every authorization after 4 failures in 480 minutes by default; `security` types 16. So the scenarios that type wrong PINs run in the test VM, whose chip is swtpm's (the VM folder's own `scripts/start.sh`, outside the repo; `PANE_VM_TPM=0` boots it with none), with that lockout raised by policy there (`HKLM\SOFTWARE\Policies\Microsoft\TPM`: `StandardUserAuthorizationFailureDuration` 1, `…IndividualThreshold` and `…TotalThreshold` 200), and its state put back from its copy (`tpm-ca/`) when its own count nears 31. - **The channel** hands each key, click, move, and scroll to the window's own dispatch, never to the system's input, so a run behind the user's windows works (ADR 0018); its keys include the arrows, Home, End, and F6, for `focus-groups`; `hitTest` asks the window's dispatcher; `nativeWindows` lists the process's windows by role (Views' menus are `MenuHost`, the system's dialogs the sheet or the app-modal panel); `modal` reads Windows 11's print dialog, the shell's, by its frame; the state's `alert` reads Pane's own alert where it draws the system's (Delete profile's, Paper 11.13 A) as it reads the Mac's sheet, `clickModalButton` presses its buttons, and `about` reads About Pane's lines (11.15 A); `systemEvent` sends Pane's own message window what Windows sends at a display's sleep and a session's lock. A toast's click is a launch there, not a command: `clickNotification` (`lib/browser.ts`) starts the binary with the toast's `--notification-launch-id`, as Windows' helper starts it, on the test copy's data, which a running Pane takes through its process singleton (ADR 0109); on the Mac it is the channel's, as macOS's center hands it. The engine reads the computer's time zone alone there, so `changeSystemTimeZone` says it can't, and `fingerprint` defers that check. `dispatchKey` hands a key to the window's widget, past the window's own traversal of Tab, which Views' focus manager does as the window's handler before it (W8d): a check that moves the keys by Tab presses a real one in front, or gives the control a screen reader's focus behind (`screenReaderFocus`), as `screen-reader` does for an extension's prompt.
- **In front, or behind.** Windows gives keys to the active window alone, and the window's shortcuts run only while it is (`Window::CanHandleAccelerators`), where the Mac's menu bar takes a posted key in the background: a scenario that presses one needs `--foreground` there, which the VM, where no one works, always allows. - **The user's launch.** A scenario's launch names its engine's folder with `--user-data-dir`, which the user's never does: there chrome_elf takes `%LOCALAPPDATA%\Pane\User Data` by itself (ADR 0121). `--user-launch` runs Pane's launches without the switch, as the user's, its data a folder named `Pane` and `LOCALAPPDATA` its parent, so chrome_elf names the data's engine folder as it names the user's. Its keys go only to a window proven in front. It runs in the test VM alone, as `user-launch.ts` does, and refuses where Pane is installed or its data is there.

Now and then a test copy's renderer outlives its browser there (1 of 346 browsers in W8's second part, 3 in its last part's whole run, 2 in W8e's, 3 in W9c's): Windows has ended it, its exit code set, but its teardown under the x64 emulation of Windows on ARM never finishes (one thread waiting in the kernel, `xtajit64se.dll` loaded), so nothing can stop it, `tests/vm/user-launch.ts` reads it as a running Pane, and it holds the app's folder, from the install as from `out/Win`: restart the VM before either, and before `update-install` alone after a whole run. ## Rigs

A person's pass, by computer use, runs on a test copy `tests/rigs/` holds open, on throwaway data, and never on the user's Pane:

```bash
bun tests/run.ts --binary <copy of Pane>/Contents/MacOS/Pane --out <dir> --timeout 7300 tests/rigs/qa-hold.ts  # PIN 1234; ends at <dir>/qa-stop
bun tests/rigs/qa-send.ts <dir>/qa-session.json <command> [json]                                               # setup, through the automation channel
bun tests/rigs/front.ts guard [idle seconds]                                                                   # exit 3 unless the Mac is that idle and unlocked
bun tests/rigs/front.ts <dir>/qa-session.json <step>...                                                        # keys and captures
bun tests/rigs/frame-timing.ts <dir>/qa-session.json <out.mov> <seconds> <step>...                             # when the picture changed, from a recording
```

Taking the front needs the user's word in the session, or the Mac idle 10 minutes with its screen unlocked (`front.ts guard`). `front.ts` checks before each key that the test copy's pid is the frontmost app's and that no input but its own has come, and stops with exit 3 at the first sign of the user: nothing the user's gets keys. It captures the test copy's window, never the screen.

## Testing as a person would

Scenarios prove the mechanics; a person checks what they see and do. A release candidate gets this pass too, driven by computer use, in light and dark, with every finding fixed and checked again the same way. Reports go in `docs/qa/<subject>/`, naming their screenshots, which stay in `evidence/`.

The rig: Aside Computer Use for presses, keys, menus, and the front (`tests/lib/computer-use.ts`, one `aside mcp --computer-use` server per run, Pane's identifier alone allowed), the runner's own reads for the window list and the accessibility tree (`tests/lib/windows.ts`), `screencapture -l <window id>` for stills, `screencapture -v` for motion, `tests/rigs/qa-hold.ts` to hold a test copy open, and `tests/rigs/qa-send.ts` for setup only, never in place of the input under test. A test copy shares the user's Pane's name and identifier, so Aside is given its bundle's path, which binds that copy alone, and only while it runs: asked for an app that isn't running, Aside opens one, and LaunchServices may open another Pane. Before each action the windows Aside holds are proved the copy's (`windows --owned`), and what it prints of an app is never written out. Its background actions keep their own pointer, the user's still; `front`'s real input holds the user's mouse and keyboard until the steps end, so it follows the rules above for the front.

**Taking the screen.** The Mac is in use, so:

- **Always a test copy,** through the scenario harness, on throwaway data. Never the user's Pane, `/Applications`, the user's data, or the user's accounts.
- **Background first.** Whatever accessibility does on a window not in front runs at any time.
- **The front, only when allowed:** the user has said so in the session, or the Mac has been idle at least 10 minutes with its screen unlocked (`HIDIdleTime` from `ioreg -c IOHIDSystem`, `CGSSessionScreenIsLocked`). Say first what will run, for how long, and that any key or click stops it. Check again before each step, stop at the first sign of the user, and put back the app that was in front.
- **Before every key, prove the target:** the frontmost app's pid is the test copy's, immediately before each key. Nothing of the user's gets keys, and only windows proven to be the test's get captured. `tests/rigs/` has the guard.
- **A click's outcome, unrecorded.** While a window is captured (ScreenCaptureKit, `screencapture -v`), macOS marks it as shared, and about half the real presses on it are lost, on the Swift app's window as on this one's: judge what a click did on a run that records nothing, and record motion in a run of its own.
- **If neither comes within a working day,** ask once.

**The checklist:**

1. **Lock and unlock:** the PIN typed with real keys, a wrong one, wrong ones in Settings, ⌃⌘L, the menu, the idle lock with time scaled, the PIN screen against Paper 07.1 to 07.9, the tab that showed comes back, keypress to first frame from a recording.
2. **Real browsing,** on throwaway profiles: public sites that need no account, the sign-in fixture surviving a relaunch and a lock, address suggestions after a relaunch, a download through the UI, an extension from the Web Store.
3. **What changed:** the screens a release touches against their boards, each compared by pixel with the last release.
4. **An older Pane's data:** 07.8 for 0.15.2's data, and nothing changed.
5. **The files from another app,** in Terminal, on test data only: `strings` and `sqlite3` on History, Cookies, Local Storage, an IndexedDB file, and a cache file.
6. **Speed as felt:** recordings of the same page loads on the last release and the candidate, timed frame by frame.
7. **Open items in `docs/human-checklist.md`** an agent may do.

**Timing a motion from a recording:** keep every frame that changed at all, and read each frame's progress against a settled frame from before the change. A spring's last frames move less than a pixel, so a recorder that skips small changes ends early, and calibrating on its last frame scales the whole curve: that read the profile morph 10% fast once, while a trace of Chromium's frames put every one at its spring. A Chromium window's captured times are the window server's samples, about every 9 ms on a 120 Hz display and up to a frame behind its presentation, not the display's.

## App

```bash
scripts/package.sh   # packaging/build/Pane.app: the engine's bundle, Chromium's loader and Pane's UI in its framework, signed
scripts/dist.sh      # packaging/release/Pane-<version>-arm64.dmg: package.sh (stripped), then the dmg
```

For a pass of the edit loop, `~/chromium/src/out/Release/Pane.app` runs as built, without `package.sh`; `security`, `lock-while-open`, and `data-volume` need a package, which carries the volume's watchdog beside the loader.

The app's version lives in `packaging/VERSION`, its only source: the bundle's version keys, Settings, the update check, and the dmg's name all come from it.

**Windows** (W7: Pane's own install, ADR 0127):

```bash
PANE_BUILD_PLATFORM=windows-x64 scripts/build.sh chrome   # out/Win, cross-built here, pane_setup.exe with it; its engine key in out/Win/pane-engine.key
scripts/package-win.sh   # packaging/build/windows/Application, its payload Pane-<version>-x64-app.7z, then packaging/release/Pane-<version>-x64.exe
```

`package-win.sh` lays out the app's folder as an install puts it at `%LOCALAPPDATA%\Programs\Pane\Application`, flat, with no version folder: the engine's files `packaging/windows/pane.release` names (Chromium's installer's list less its Start tiles' logos, and Pane's skies and icon files), `pane-version` from `packaging/VERSION`, and the CRLSet, which it refuses to go without, as `dist.sh` does. Then it compresses the folder's contents with the checkout's 7-Zip as Chromium's installer archive is (LZMA with BCJ2), each file on its own so the install writes each as it reads it, and makes the installer: `pane_setup.exe` (`//pane/installer`, which `build.sh` builds with `chrome` on Windows), the payload after it, and a trailer naming the payload's place, size, unpacked size, SHA-256, and version. The installer copies the folder to `%LOCALAPPDATA%\Programs\Pane\Application`, has chrome.exe register Pane with Windows (`--pane-register`), and closes as Pane's first window paints; the same `pane_setup.exe`, kept in the folder, is the uninstall's helper. `out/Win` runs as built for a scenario's `--binary`, without a version or a CRLSet.

## Prebuilt engine

The app packages without a Chromium checkout from a prebuilt engine, as Ardia's does, for a commit whose engine archive is published:

```bash
PANE_ENGINE_OUT="$(scripts/fetch-engine.sh)" scripts/package.sh
```

`chromium/prebuilt-engines.tsv` names, for the engine key (`engine-key.sh`: the git trees of `CHROMIUM_VERSION`, `args`, `patches`, and `pane`) and a platform, the SHA-256 of its archive in the `engine-<key:12>` release: the Mac's (`mac-arm64`) `PaneCore-<chromium>-<key:12>.zip`, and Windows' (`windows-x64`) `PaneCore-<chromium>-<key:12>-windows-x64.zip`, which `PANE_WIN_ENGINE_OUT="$(scripts/fetch-engine.sh windows-x64)" scripts/package-win.sh` packages. `fetch-engine.sh` downloads and verifies it into `packaging/build/engines.noindex/`, out of Spotlight, which would register its bundle, carrying Chromium's version, as the newest copy of Pane's identifier. A checkout whose engine sources changed has no prebuilt: build the engine. `publish-engine.sh [mac-arm64|windows-x64]` archives one platform's engine into `packaging/release/`, publishes it on the prerelease, and overwrites that platform's line. Archiving refuses an engine that `build.sh` did not record the current key for (the out dir's `pane-engine.key`): one built before a change to the engine's sources, or from a checkout whose tag, patches, or `//pane` were not this repo's.

## Reading a crash report

A release strips its executables, so a crash report (`~/Library/Logs/DiagnosticReports/Pane-*.ips`) names addresses, not functions. Its symbols are published: PaneCore's, beside the engine archive in the `engine-<key:12>` prerelease (`PaneCore-<chromium>-<key:12>.dSYM.zip`), where `<key>` is the copy's `PaneEngineKey` (`plutil -extract PaneEngineKey raw Pane.app/Contents/Info.plist`). Unzip it, check that its UUID (`dwarfdump --uuid`) is the report's `Pane Framework` image's, and resolve each frame against that image's load address:

```bash
atos -arch arm64 -o "Pane Framework.dSYM/Contents/Resources/DWARF/Pane Framework" -l <load address> <address>...
```
