# A page's dialogs are drawn in the window

A page's dialogs are SwiftUI views drawn in the app's window, not `NSAlert` sheets, because a sheet held the main thread, Chromium's UI thread, some 280 ms as it attached, and a dialog in the window shows within a few milliseconds of its request. They are the page's requests the app answers (ADR 0021): JavaScript alert, confirm, and prompt, Leave and Reload site, form resubmission, permissions, HTTP and proxy sign-in, opening another app, and the unresponsive page. `DialogPresenter` (`app/Pane/Browser/DialogPresenter.swift`) still queues them and holds them behind the lock, and the file chooser stays the system's panel. This was P1 of the architecture review of 2026-10-28.

`DialogView` (`app/Pane/Views/DialogView.swift`) draws them as Paper's 04.15 to 04.23 draw those sheets, light and dark: 260 points wide, the title and the message at 13, the fields, then 28-point capsule buttons, the default blue (two side by side, the default on the right; three stacked, the default on top); the gray panel at 95% with a hairline edge and its 0 16 48 shadow. It sits centered on the window, its top at three eighths of its height (Paper's 300 of 800), raised to fit; a long message scrolls. The corners are `Squircle`s on the design's radius scale (DESIGN.md › Shape, ADR 0057): 29 for the panel, 7 for a field. The font is the system's in place of Paper's Inter, as everywhere in the app.

A 4 ms timer on the main thread measured both, over `dialog-alert`, `dialog-confirm`, `dialog-prompt`, and `permission-prompt`: `beginSheetModal` held the thread 270 to 284 ms, and its largest gap after a request was 278 to 317 ms. The dialog is now in the view tree 2 to 6 ms after the request; the largest gap in the next 250 ms is 6 to 12 ms, and 24 to 32 ms when a prompt's field takes the keyboard (AppKit's text field setup, which the sheet also did inside its 280 ms). Later gaps in those runs line up with the scenario's own accessibility reads.

Esc dismisses, as Chrome's dialogs do (Cancel, Wait, and a permission's dismissal), and Return presses the default, both through the one key monitor (ADR 0079). The sheet gave a permission no way to be dismissed: Esc left it open. `permission-prompt` checks that Esc leaves the site free to ask again, and it failed before; `dialog-confirm` checks Return and Esc. Other keys never reach the page under a dialog, and a field keeps its typing. The page under it takes no click; the sidebar and the toolbar still work, as with Chrome's tab-modal dialogs, and switching tabs puts the dialog back in line, as before. A field that took the keyboard gives it back to the page.

The fields are AppKit's (`NSTextField` in the SwiftUI dialog), read as the dialog answers, as the alert's were, so a value set through accessibility (VoiceOver, Voice Control, the scenarios' CUA) counts; a SwiftUI field took only typed text. `http-auth` measures the dialog's fields (`dialogFieldWidths`), not a sheet's: 222 points each.
