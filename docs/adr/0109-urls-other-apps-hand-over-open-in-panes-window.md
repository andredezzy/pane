# URLs other apps hand over, and a site's notification clicked, open in Pane's window, and their sign-ins stay in macOS's sheet

What another app hands Pane opens as new tabs in its window, in the order given, in the profile in use, the last one selected: a link clicked in Mail or Slack with Pane as the default browser, a file opened with Pane, `open -a Pane <url>`. The bundle registers http, https, and file, and the HTML and image types, as Chrome's does. Until then only a URL on the command line opened (`Pane https://…`). Launch Services delivers the others to Chrome's AppController (`-application:openURLs:`), which opened them in a Browser of Chrome's, behind Pane's window and never seen. The research comparing Pane with Aside and Dia found it: both open such links in their own window.

Patch 0002 has a hosted engine's AppController post `PANE_OPEN_URLS_NOTIFICATION` (`pane/common/host.h`) instead, as it already does for reopen. Pane's UI hears it (`AppEvents`, `pane/ui/app/app_events_mac.mm`) and opens the web pages and files among them through the path the command-line URL takes (`UiApp::OpenLaunchURLs`), so they wait behind the PIN lock as it does, and shows the window again if it was closed. A Dock click, the reopen, shows it too: a window the user closed opens anew, its selected tab's page made again (`UiApp::ShowWindow`). The Swift app's `showWindow()` ordered front a window the close had already destroyed, so by its code (read, not run) a closed window never came back until Pane quit.

**Another launch of Pane hands its pages over too, on every system** (W4, 2026-11-13). On Windows another app opens a link by starting Pane with it, as the shell starts a default browser, and a second Pane on the same data, a terminal's on the Mac too, hands its command line to the running one through Chromium's process singleton, then quits. Chrome's own callback took it (`ChromeBrowserMainParts::PostBrowserStart`) and, Pane's launch being `--no-startup-window`, opened nothing: on Windows no link another app handed reached Pane, and `Pane <url>` from a terminal on the Mac opened nothing either. `AppEvents` gives the singleton Pane's callback instead (`ChromeProcessSingleton::Unlock`, which replaces the one it held: as Pane listens, before Chrome's own, for what came while Pane started, and again once Chrome's start is over, before the main loop runs, `BrowserMainExtraParts::PreMainMessageLoopRun`). The pages it names, read as Chrome reads a launch's arguments (`HandedPages`, `pane/ui/app/handed_pages.h`: a URL, or a file's path relative to the other launch's folder, read off the UI thread; search terms left out), open as the Apple Events' do, and one that names none shows the window, as the Dock's reopen does. The web pages and files filter is one for both paths (`AppEvents::OpenURLsHanded`).

**On Windows, Pane is the default as its user makes it** (W8, 2026-11-16, in the test VM on Windows 11 26100). Windows lets an app open Default apps but never set itself, and Pane's UI shows nothing about the default browser on either system: this record asks for none, and ADR 0114 rejected asking at launch. The install puts Pane in Default apps (ADR 0127), whose page offers "Make Pane your default browser" with Set default, which makes Pane the default for http, https, .htm, and .html (Windows keeps the choice under `UserChoiceLatest\ProgId`, `PaneHTM`), and .pdf has its own picker (`PanePDF`). The first link and the first .html after it, Windows asks once, Pane as Default app, Always or Just once, as it does for any browser while other new handlers are listed. Then a link another app opens starts a closed Pane with it, in its "Personal" profile, and goes to a running Pane as a new tab (one browser process), through the process singleton above; the .html and the .pdf open in Pane, the PDF in Chrome's viewer; and Explorer shows Pane's own document icons (ADR 0089, 11.12.2). Measured by a probe of the round's (`evidence/views-migration/runs/p5-w8b-notes.md`), the VM's own input answering Windows' pickers, which UI Automation's root doesn't reach.

**A site's notification clicked in the system's center reaches the site** (the user's call, 2026-11-16; W8d, `evidence/views-migration/runs/p5-w8d-notes.md`): its service worker hears `notificationclick`, and the page it opens or focuses comes up in Pane's window, in the notification's profile. On Windows the click is a launch: `notification_helper.exe`, Chromium's toast activator, starts `chrome.exe --notification-launch-id=<id>` (`--notification-inline-reply` with a reply), which a running Pane takes through the process singleton above, and which starts a closed one. Until then a user's launch dropped the switch before the hand-over, and Pane's callback read pages alone, so the click showed the window and the site heard nothing (ADR 0010). Every launch now keeps the two switches (`kPanesOwnSwitches`, `pane/app/engine_switches.cc`), and `AppEvents` gives a launch that carries one to the UI, which reads the id as Chrome's own handler reads it (`NotificationClickOf`, `pane/ui/app/notification_click_win.cc`, Chromium's `NotificationLaunchId`: a click, a button, a reply, a close, or the settings item), shows the window but for a close, opens the notification's profile through `ProfileContexts::With`, the one way a profile reaches the engine, and hands the click to the step that follows Chrome's own load, `NotificationDisplayServiceImpl::ProfileLoadedCallback` (`ForwardNotificationClick`). Chrome's handler itself (`NotificationPlatformBridgeWin::HandleActivation`) loads the profile through the profile manager, outside Pane's lock, its keys, its fingerprint, and its proxy, so Pane never calls it. A launch that carries the switch takes it out of its own command line before Chrome's startup reads it (`TakeNotificationSwitches`, `BrowserMainExtraParts::PreProfileInit`), since that startup opens the notification's profile (`CreateInitialProfile`, `GetStartupProfilePath`) before the PIN, and gives it to the UI as it starts (`UiApp::Start`).

**Behind the lock the click shows the PIN, and the site hears it once the PIN is in** (`UiApp::HandNotificationToSite`): nothing of the notification's profile opens in the engine before, as a launch's URLs wait (ADR 0042, 0113); a lock that comes first holds it again, and a profile deleted since hears nothing. Since W10g neither system's center keeps a profile's notifications once the profile has closed (below): a click that meets the lock is one that lands as the lock comes, and a closed Pane opens at its Lock with the click held only for a notification a crash left in the center. Until then Windows kept a toast in its center through a lock and after Exit, to be clicked so. **On the Mac** macOS's center hands the click to the browser itself (Chrome's center delegate, in the browser for a banner or in its alerts helper for an alert, then over mojo to `ProcessMacNotificationResponse`), and Chrome's handler hands it to Pane's UI (the user's call, 2026-11-16; W8e): a hunk in `chrome/browser/notifications/mac/notification_utils.cc` (patch 0004, ADR 0004) calls `g_pane_notification_response` (`pane/ui/app/notification_center_mac.h`), which the Mac's `AppEvents` sets, and which reads the click as Chrome's handler reads it (`NotificationClickOf`, `notification_click_mac.cc`) and gives it to `NotificationClicked`, Windows' way. Chrome's handler loaded the profile itself (`DoProcessMacNotificationResponse` → `ProfileManager::LoadProfile`), outside Pane's lock and its keys, with no seam of Chromium's before it, and behind the lock that load never ended on the closed data, so the profile never opened again after the PIN (W8d, measured by handing the click in as the center hands it). Chrome closes a profile's notifications in the center as the profile shuts down, by its id (`NotificationPlatformBridgeMac::DisplayServiceShutDown`), which a lock and a quit do to every profile, and a crash's go as Pane next starts (below), so the center keeps none to click behind the lock or with Pane closed: only a click that lands as the lock comes, or on a notification a crash left there before Pane starts again, meets the lock, and it waits for the PIN as Windows' does.

**Windows' toasts are Pane's only while Start holds its shortcut** (W10f, 2026-11-18, `evidence/views-migration/runs/p6-w10f-notes.md`). Chrome sends a site's notifications to Windows' center only while Start's `Pane.lnk` names Pane's toast activator (`NotificationPlatformBridgeWin`, asked as each profile opens), as the install makes it; a person who deletes it gets them in Chrome's own center instead, a popup of Pane's process at the screen's corner, which the Lock takes away (ADR 0116). Pane doesn't make the shortcut again: the install does, at a reinstall's repair. A test copy's Start folder is its home's (ADR 0089), where its first launch makes the install's `Pane.lnk` (`MakeStartShortcut`, `TakeTestCopyHome`): from W10a, which gave it that folder, until then its toasts went to Chrome's center even from the install, and `notification-click`'s Lock found its profile held there and quit Pane. Left then for the user's call: with the shortcut in place, Windows' own banner showed the site's words beside the PIN screen for its few seconds after a Lock, and a `requireInteraction` toast stayed on the screen, in Windows' center, through the Lock and after Exit (below).

**A profile's notifications leave the system's center as the profile closes, at every Lock and at Exit, on both systems** (the user's call, 2026-11-18, the threat model; W10g, `evidence/views-migration/runs/p6-w10g-notes.md`). Chrome's Mac bridge takes them out of macOS's center as the profile shuts down, by the profile's id, at a Lock and at quit alike (`NotificationPlatformBridgeMac::DisplayServiceShutDown`); Windows' took none (its `DisplayServiceShutDown` is empty), so a site's words stayed in Windows' center, readable without the PIN, through a Lock and after Exit, and on the screen beside the PIN for a banner's few seconds, a `requireInteraction` one until dismissed. Each profile's notifications now leave every center through one step: Pane's own service of the profile (`ProfileNotifications`, `pane/browser/profiles.cc`, made with it) hears what the profile shows from Chrome's display service and closes each through it (`NotificationDisplayService::Close`), as a site's own close does, whatever center holds it: Windows', macOS's, or Chrome's own. `CloseProfile` runs it before the profile's hold goes, at every Lock (Lock Pane, Windows' lock, the idle time; ADR 0116) and for a profile turned off; the service's `Shutdown`, the profile's last moment, runs it again (a deletion, Exit's teardown, what showed as the profile closed). Chrome's own close keeps its Windows bridge's bookkeeping: that bridge checks every 10 minutes that the toasts it showed are still in Windows' center and reports each one gone as closed by its user, loading the profile through Chrome's profile manager, outside Pane's lock and keys, so a toast taken out behind its back would have had it load a locked profile. Windows removes a toast that isn't there with no error, so one its user dismissed leaves the bookkeeping too. At Exit, once the quit can't be cancelled, every toast of Pane's AppUserModelID leaves Windows' center (`windows::ClearToasts`, in a task the thread pool's end waits for; `pane/browser/browser_main_extra_parts_win.cc`), a crash's leftovers with them; the bridge's bookkeeping goes with the process. A sign-out ends Pane with the session, a restart and a shutdown the same way, and Windows kept a toast through a sign-out for the next sign-in: Pane's window takes them out as it hears the session end (`WM_ENDSESSION`, `pane/ui/window/frame_win.cc`), since none of Exit's steps run then (Chrome's own session end, `chrome::SessionEnding`, never notifies the app's termination either). On the Mac the step comes a moment before Chrome's bridge's own close, which then finds nothing: one message per notification shown that session, to a service already running. The cost, the user's, on both systems: a notification shown before a Lock can't be clicked after it, and its site finds it gone after the PIN (a profile's notification database drops, as it opens, what the center no longer lists: `PlatformNotificationContextImpl`). A crash closes nothing: its notifications stayed in the center, readable without the PIN, until the next Exit on Windows, or the profile's next close on the Mac, until they went as Pane next starts (below).

**A crash's notifications leave Windows' center as Pane next starts** (the user's call of 2026-11-18, finished; W10h, `evidence/views-migration/runs/p6-w10h-notes.md`). As the next launch's browser starts, before any profile opens, every toast of Pane's AppUserModelID leaves Windows' center (`BrowserMainExtraParts::ClearLeftoverNotifications`, `windows::ClearToasts`, from `PreProfileInit`): in the process that holds Pane's data alone, since a second launch hands its command line over through the process singleton and exits in `PostEarlyInitialization`, before the browser's main parts; and before Chrome's bridge is made, at the Default profile's load, which follows. That bridge takes into its 10-minute check, as it starts, each toast it finds of an AppUserModelID it already knows (`InitializeExpectedDisplayedNotification`), and would report each one gone as closed by its user, loading the profile outside Pane's lock: this Chromium's starts knowing none, so it took none of a crash's (measured: after a crash and a launch with the crash's two toasts still in Windows' center, the site's `getNotifications()` listed neither after the PIN, and with them taken out behind its back no profile loaded in the 11 minutes after), but Chromium's own test of that start models one that takes them, and a Chromium that read Pane's AppUserModelID at its start would, so the clear is done first: since W10i it starts with the browser's start (`PreEarlyInitialization`), on the thread pool, whose threads are COM's, and the initial profile's load waits for it if it isn't done (`PreProfileInit`), so nothing is left for any start to take. A crash's toast clicked with Pane closed still starts Pane at its Lock with the click held for the PIN, and the site hears it: Windows takes the clicked toast out of its center as it starts Pane, and the others go. The cost, the user's: a crash's other notifications can't be clicked once Pane has started again, and their sites find them gone after the PIN (as a Lock's); and, as W10h ran it on the UI thread, the clear's time before the PIN screen's first frame, 18.5 to 49.5 ms in the test VM (median 29 over 24 launches), whose x64 emulation times nothing as a real PC does; since W10i the UI thread waits only for what is left of it at the initial profile's load (its trace's `waitedMs`, beside `PaneWindow.firstFrame`), not yet measured in the VM.

**And macOS's centers, by a hunk in Chrome's Mac bridge** (the user's call, 2026-11-19, W10h's option b; W10i, `evidence/views-migration/runs/p6-w10i-notes.md`). On the Mac Chrome's bridge, made at the Default profile's load, starts both centers' services at once, each taking every notification its center holds into its own 10-minute check ("restarted after a crash"), and every close of the bridge's takes a loaded profile, where none of the crash's is loaded before the PIN; an alert (`requireInteraction`) lives in the alerts helper's center, which only a process of the helper's bundle reaches. So a crash's notifications stayed in macOS's centers through the next launch and its PIN, until that profile next closed. A hunk in `chrome/browser/notifications/mac/notification_platform_bridge_mac.cc` (patch 0004, ADR 0004) closes, as the bridge is made, right after its two dispatchers have started their services, the notifications of each profile `g_pane_notification_profile_ids` names (`pane/ui/app/notification_center_mac.h`), by its id, in both centers (`CloseNotificationsWithProfileId`). Pane sets the hook as the browser starts, before the initial profile (`BrowserMainExtraParts::ClearLeftoverNotifications`, the Mac's half): the data's profiles' ids, as the engine's folder names their links into the volume, which stay while it is detached (`DataVolume::ProfileIds`), read before the key opens, with no profile loaded. Each service handles a message only once it has taken its center's notifications into its list (`MacNotificationServiceUN::Bind`), so the close drops them from it too: its 10-minute check finds none gone, and nothing is reported closed to a site. Only this data's profiles: a test copy's are its own random ids, never the user's Pane's (ADR 0012), and Default, which every copy has, shows none and is never named. Measured on a test copy, the Mac's screen locked so no one could click the alert: a banner and an alert shown, the browser killed, the next launch locked with Default alone loaded; on the engine before both were still listed after the PIN, with the hunk neither, its close sent 203 ms before the PIN screen's first frame (`mac-crash-probe.ts`, kept in the round's evidence, `evidence/views-migration/runs/p6-w10i-mac-probes/`); and `notification-click`'s Mac part, a banner a kill left, none after the next launch's PIN. A crash's notification clicked with Pane closed starts Pane, which holds the click for the PIN as before (read in the code; no click goes to macOS's center on the user's Mac). The cost, the user's: as on Windows, a crash's notifications can't be clicked once Pane has started again, and their sites find them gone after the PIN; and one more Chromium file in the patches (98 to 99). At quit the bridge's own close of every notification (`~NotificationPlatformBridgeMac` → `CloseAllNotifications`) reaches neither service, which a test copy's quit would otherwise share with the user's Pane: the bridge goes with the browser process's object, after the thread pool, which runs the banners' service, and the IO thread, whose end terminates the alerts helper, have ended (measured, ADR 0012), so a quit's close is each profile's own.

Chrome opens them in the last profile used; Pane's profile in use is the one whose tab is selected, and on a first launch with none, the "Personal" profile it makes.

**Another app's sign-in is not handed over.** Pane's bundle does not say it supports `ASWebAuthenticationSession` (`ASWebAuthenticationSessionWebBrowserSupportCapabilities`, which Chromium's Info.plist sets and `scripts/package.sh` removes). An app that signs its user in through one (Slack, Zoom, Notion, and others) gets macOS's own sign-in sheet, whatever the default browser, as with Dia, which leaves the key out too.

With the key, macOS handed such a sign-in to the default browser, and Chrome's `AuthSessionRequest` (`chrome/browser/mac/auth_session_request.mm`) opened it in a popup Browser of its own. Pane's window hosts every popup Browser by moving its tab into the profile's Browser and closing the popup (ADR 0014, `ForwardToPaneWindow`), but the request keeps the popup's Browser to close the page when the sign-in ends: by then it is gone, so a completed or cancelled sign-in reached a freed Browser. The same research found it, reading the code; no scenario had covered it.

What was rejected:

- **A function the app sets in the engine, called by the AppController:** chrome/ may not depend on //pane (`host.h` is header-only for that), and a notification is how the AppController already reaches the hosted app.
- **The first profile, as the command-line URL used:** Chrome opens them where the user is.
- **Chrome's own handler for a toast's click** (`HandleActivation`), or Chrome's startup reading the switch: each loads the profile through the profile manager, the startup's before the PIN.
- **On the Mac, without a patch:** taking a closed profile out of Chrome's profile list, so the load refuses (its observers read that as the profile deleted); wrapping macOS's center delegate (a banner's click alone: an alert's comes from the helper's process).
- **Asking the center what it shows at the close (`GetDisplayed`) and closing that:** Windows' bridge answers on its own sequence, a hop that Exit's teardown can't wait for, and reads only the AppUserModelIDs its own process showed; on the Mac it is a round trip to macOS's center at every Lock for what Chrome's bridge closes anyway.
- **Taking a profile's toasts out of Windows' history directly at the Lock**, by the profile's id, a crash's with them: Chrome's bridge would find them gone at its next 10-minute check and load the locked profile, outside Pane's lock, to tell the site they closed.
- **On the Mac, //pane alone** (W10h's option a): banners taken out by Pane's own `UNUserNotificationCenter` code, by their user data dir, and alerts by a second alerts helper of Pane's own beside Chrome's. Both race the start of Chrome's own services, so a notification Chrome's service took in before Pane's removal would be reported closed at its 10-minute check, held for the PIN, and its profile opened to tell its site; it costs a second helper process at every launch; which of two helpers of one bundle macOS hands an alert's click to is unknown; and a second banner service in the browser would take the process's one center's delegate from Chrome's.
- **Closing every notification of the bundle as Pane starts** (the services' `CloseAllNotifications`): a test copy's start would take the user's own Pane's (ADR 0012).
- **A hunk in Windows' bridge's `DisplayServiceShutDown`**, as the Mac's closes: Windows' patches are at their 7 (ADR 0004), and Chrome's display service lets //pane close them.
- **The launch's clear on the thread pool, unwaited**: it races the bridge's start on another sequence, and a start that took a crash's toasts before the clear would make its 10-minute check load the crash's profile outside the lock. It runs there since W10i, and the initial profile's load waits for it; W10h ran it on the UI thread, before the PIN screen's first frame.
- **Clearing a crash's toasts at the PIN**, once Pane knows its profiles: the site's words stay readable in Windows' center until someone types the PIN.
- **Keeping a sign-in's popup a window of Chrome's:** a window of Chrome's look among Pane's, and the only one.
- **A sign-in in a tab of Pane's window, with the request patched to find the tab's Browser:** Chrome's security team requires the sign-in's address to show and not be editable ("must not be changed without consultation with the security team"), and a tab's address bar is editable.

How it is checked:

- **The open-urls scenario** hands a running Pane a page and a file through Launch Services (`tests/tools/open-urls.swift`, without activating it), which sends them as an Apple Event each: both open in the profile in use, the last one selected, and no other window shows.
- **A cold launch** (`open -n -g -a packaging/build/Pane.app <url>` with a throwaway home and data directory) delivered the URL while the engine started; on the Swift app it opened once the engine had started, in the "Personal" profile made for it.
- **The security scenario** hands one over behind the PIN lock: nothing opens until the PIN does, then it opens after the launch URL.
- **On Windows**, `open-urls` and `security` hand theirs to a second launch, as the shell hands a default browser's (`handURLs`, `tests/lib/browser.ts`), in the test VM; `HandedPagesTest` reads a launch's arguments as Chrome does, web pages and files alone.
- **`notification-click`'s last part on Windows** (W10f): the copy's own Start shortcut, which its first launch made, deleted; the profile opened again; a notification shown in Chrome's own center (a new window of the process); a Lock leaving Pane locked and running, the data closed, and the popup gone (ADR 0116).
- **`notification-click`** on both systems: a site's notification shown by its service worker once Pane's prompt allowed it, and clicked with Pane open, opens the worker's page as a new tab of the notification's profile, selected; one that focuses its page, from another profile shown, selects that page. Locked, the profiles go and the data closes, and a click behind the lock leaves Pane locked, its window shown, the profile not in the engine (the state's `engineProfiles`) and the data closed, and the page opens once the PIN is in, on both systems (on the Mac since W8e's hunk, handed in as the center hands a click that lands as the lock comes; before, the profile never opened again). On Windows the runner reads Windows' center too (`centerToasts`, the history of the AppUserModelID the copy's Start shortcut names): the profile's toasts, a `requireInteraction` one among them, listed before the Lock and none of them after it; a crash (the browser killed) leaves its two toasts there, a plain one and a `requireInteraction` one, and a click on the plain one with Pane closed, the toast's launch, opens Pane locked, Windows' center holding nothing of Pane's at its first state (W10h), the profile not loaded, then the page after the PIN; and after Exit none of Pane's is left (W10g). `EngineSwitchesTest.KeepsAToastsActivationForPanesUiAlone` keeps the switches, for the UI alone.
- **The VM's install at a Lock and at Exit** (W10g): a site's toast, plain and `requireInteraction`, out of Windows' center by the first sample after Lock Pane (2.4 and 3.7 s), Windows' own lock (5.9 s, its lock screen showing nothing of Pane's), and the idle time (as its Lock came), and after Exit (5.9 s, no process left), the center then holding Windows' own notifications alone, and Pane locked and running after each Lock; on the engine before, the same toast stayed through 91 s after Lock Pane, beside the PIN screen, and after Exit. A sign-out with Pane open left the toast in Windows' center for the next sign-in until Pane's window took it out at the session's end.
- **The VM's install after a crash** (W10h): a site's two toasts, plain and `requireInteraction`, in Windows' center, the browser killed; Pane launched again from Start: nothing of Pane's in the center by the first sample, 3.9 s on (the window at 2.9 s), Pane at its PIN screen, the profile's folder unwritten until the PIN; launched again by the crash's leftover invoked in Windows' notification center (UI Automation): nothing of Pane's left by the first sample, Pane locked, and the site's page the click opens asked for 2.3 s after the PIN. On the engine before, both toasts stayed in the center through the launch and the PIN, until Exit. A test copy so: none at the next launch's first state, the clear traced (`PaneEngine.leftoverNotificationsCleared`); on the engine before, the site's `getNotifications()` listed neither toast after the PIN, and with them taken out of the center behind Chrome's back no profile loaded in the 11 minutes after (the bridge took neither in as it started).
- **In the test VM**, real toasts of the installed Pane clicked in Windows' notification center through UI Automation (W8d): open, the site's page came up as a new tab, selected, the window in front; locked, the PIN came forward with no renderer, and the page opened after it; closed, the helper's launch opened Pane at its Lock, and the site's page was asked for 2.5 s after the PIN's first digit.
- **`plutil -p Pane.app/Contents/Info.plist`** of a packaged app lists no `ASWebAuthenticationSessionWebBrowserSupportCapabilities`.
