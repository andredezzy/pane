# URLs other apps hand over, and a site's notification clicked, open in Pane's window, and their sign-ins stay in macOS's sheet

What another app hands Pane opens as new tabs in its window, in the order given, in the profile in use, the last one selected: a link clicked in Mail or Slack with Pane as the default browser, a file opened with Pane, `open -a Pane <url>`. The bundle registers http, https, and file, and the HTML and image types, as Chrome's does. Until then only a URL on the command line opened (`Pane https://…`). Launch Services delivers the others to Chrome's AppController (`-application:openURLs:`), which opened them in a Browser of Chrome's, behind Pane's window and never seen. The research comparing Pane with Aside and Dia found it: both open such links in their own window.

Patch 0002 has a hosted engine's AppController post `PANE_OPEN_URLS_NOTIFICATION` (`pane/common/host.h`) instead, as it already does for reopen. Pane's UI hears it (`AppEvents`, `pane/ui/app/app_events_mac.mm`) and opens the web pages and files among them through the path the command-line URL takes (`UiApp::OpenLaunchURLs`), so they wait behind the PIN lock as it does, and shows the window again if it was closed. A Dock click, the reopen, shows it too: a window the user closed opens anew, its selected tab's page made again (`UiApp::ShowWindow`). The Swift app's `showWindow()` ordered front a window the close had already destroyed, so by its code (read, not run) a closed window never came back until Pane quit.

**Another launch of Pane hands its pages over too, on every system** (W4, 2026-11-13). On Windows another app opens a link by starting Pane with it, as the shell starts a default browser, and a second Pane on the same data, a terminal's on the Mac too, hands its command line to the running one through Chromium's process singleton, then quits. Chrome's own callback took it (`ChromeBrowserMainParts::PostBrowserStart`) and, Pane's launch being `--no-startup-window`, opened nothing: on Windows no link another app handed reached Pane, and `Pane <url>` from a terminal on the Mac opened nothing either. `AppEvents` gives the singleton Pane's callback instead (`ChromeProcessSingleton::Unlock`, which replaces the one it held: as Pane listens, before Chrome's own, for what came while Pane started, and again once Chrome's start is over, before the main loop runs, `BrowserMainExtraParts::PreMainMessageLoopRun`). The pages it names, read as Chrome reads a launch's arguments (`HandedPages`, `pane/ui/app/handed_pages.h`: a URL, or a file's path relative to the other launch's folder, read off the UI thread; search terms left out), open as the Apple Events' do, and one that names none shows the window, as the Dock's reopen does. The web pages and files filter is one for both paths (`AppEvents::OpenURLsHanded`).

**On Windows, Pane is the default as its user makes it** (W8, 2026-11-16, in the test VM on Windows 11 26100). Windows lets an app open Default apps but never set itself, and Pane's UI shows nothing about the default browser on either system: this record asks for none, and ADR 0114 rejected asking at launch. The install puts Pane in Default apps (ADR 0127), whose page offers "Make Pane your default browser" with Set default, which makes Pane the default for http, https, .htm, and .html (Windows keeps the choice under `UserChoiceLatest\ProgId`, `PaneHTM`), and .pdf has its own picker (`PanePDF`). The first link and the first .html after it, Windows asks once, Pane as Default app, Always or Just once, as it does for any browser while other new handlers are listed. Then a link another app opens starts a closed Pane with it, in its "Personal" profile, and goes to a running Pane as a new tab (one browser process), through the process singleton above; the .html and the .pdf open in Pane, the PDF in Chrome's viewer; and Explorer shows Pane's own document icons (ADR 0089, 11.12.2). Measured by a probe of the round's (`evidence/views-migration/runs/p5-w8b-notes.md`), the VM's own input answering Windows' pickers, which UI Automation's root doesn't reach.

**A site's notification clicked in the system's center reaches the site** (the user's call, 2026-11-16; W8d, `evidence/views-migration/runs/p5-w8d-notes.md`): its service worker hears `notificationclick`, and the page it opens or focuses comes up in Pane's window, in the notification's profile. On Windows the click is a launch: `notification_helper.exe`, Chromium's toast activator, starts `chrome.exe --notification-launch-id=<id>` (`--notification-inline-reply` with a reply), which a running Pane takes through the process singleton above, and which starts a closed one. Until then a user's launch dropped the switch before the hand-over, and Pane's callback read pages alone, so the click showed the window and the site heard nothing (ADR 0010). Every launch now keeps the two switches (`kPanesOwnSwitches`, `pane/app/engine_switches.cc`), and `AppEvents` gives a launch that carries one to the UI, which reads the id as Chrome's own handler reads it (`NotificationClickOf`, `pane/ui/app/notification_click_win.cc`, Chromium's `NotificationLaunchId`: a click, a button, a reply, a close, or the settings item), shows the window but for a close, opens the notification's profile through `ProfileContexts::With`, the one way a profile reaches the engine, and hands the click to the step that follows Chrome's own load, `NotificationDisplayServiceImpl::ProfileLoadedCallback` (`ForwardNotificationClick`). Chrome's handler itself (`NotificationPlatformBridgeWin::HandleActivation`) loads the profile through the profile manager, outside Pane's lock, its keys, its fingerprint, and its proxy, so Pane never calls it. A launch that carries the switch takes it out of its own command line before Chrome's startup reads it (`TakeNotificationSwitches`, `BrowserMainExtraParts::PreProfileInit`), since that startup opens the notification's profile (`CreateInitialProfile`, `GetStartupProfilePath`) before the PIN, and gives it to the UI as it starts (`UiApp::Start`).

**Behind the lock the click shows the PIN, and the site hears it once the PIN is in** (`UiApp::HandNotificationToSite`): nothing of the notification's profile opens in the engine before, as a launch's URLs wait (ADR 0042, 0113); a lock that comes first holds it again, and a profile deleted since hears nothing. Windows keeps a toast in its center through a lock and after Exit (Chrome's bridge there closes none as a profile closes), so its user can click one with Pane locked or closed, and a closed Pane opens at its Lock with the click held. **On the Mac** macOS's center hands the click to the browser itself (Chrome's center delegate, in the browser for a banner or in its alerts helper for an alert, then over mojo to `ProcessMacNotificationResponse`), and Chrome's handler hands it to Pane's UI (the user's call, 2026-11-16; W8e): a hunk in `chrome/browser/notifications/mac/notification_utils.cc` (patch 0004, ADR 0004) calls `g_pane_notification_response` (`pane/ui/app/notification_center_mac.h`), which the Mac's `AppEvents` sets, and which reads the click as Chrome's handler reads it (`NotificationClickOf`, `notification_click_mac.cc`) and gives it to `NotificationClicked`, Windows' way. Chrome's handler loaded the profile itself (`DoProcessMacNotificationResponse` → `ProfileManager::LoadProfile`), outside Pane's lock and its keys, with no seam of Chromium's before it, and behind the lock that load never ended on the closed data, so the profile never opened again after the PIN (W8d, measured by handing the click in as the center hands it). Chrome closes a profile's notifications in the center as the profile shuts down, which a lock does to every profile, and all of them at quit (`NotificationPlatformBridgeMac`), so the center keeps none to click behind the lock or with Pane closed: only a click that lands as the lock comes, or on a notification a crash left there, meets the lock, and it waits for the PIN as Windows' does.

Chrome opens them in the last profile used; Pane's profile in use is the one whose tab is selected, and on a first launch with none, the "Personal" profile it makes.

**Another app's sign-in is not handed over.** Pane's bundle does not say it supports `ASWebAuthenticationSession` (`ASWebAuthenticationSessionWebBrowserSupportCapabilities`, which Chromium's Info.plist sets and `scripts/package.sh` removes). An app that signs its user in through one (Slack, Zoom, Notion, and others) gets macOS's own sign-in sheet, whatever the default browser, as with Dia, which leaves the key out too.

With the key, macOS handed such a sign-in to the default browser, and Chrome's `AuthSessionRequest` (`chrome/browser/mac/auth_session_request.mm`) opened it in a popup Browser of its own. Pane's window hosts every popup Browser by moving its tab into the profile's Browser and closing the popup (ADR 0014, `ForwardToPaneWindow`), but the request keeps the popup's Browser to close the page when the sign-in ends: by then it is gone, so a completed or cancelled sign-in reached a freed Browser. The same research found it, reading the code; no scenario had covered it.

What was rejected:

- **A function the app sets in the engine, called by the AppController:** chrome/ may not depend on //pane (`host.h` is header-only for that), and a notification is how the AppController already reaches the hosted app.
- **The first profile, as the command-line URL used:** Chrome opens them where the user is.
- **Chrome's own handler for a toast's click** (`HandleActivation`), or Chrome's startup reading the switch: each loads the profile through the profile manager, the startup's before the PIN.
- **On the Mac, without a patch:** taking a closed profile out of Chrome's profile list, so the load refuses (its observers read that as the profile deleted); wrapping macOS's center delegate (a banner's click alone: an alert's comes from the helper's process).
- **Keeping a sign-in's popup a window of Chrome's:** a window of Chrome's look among Pane's, and the only one.
- **A sign-in in a tab of Pane's window, with the request patched to find the tab's Browser:** Chrome's security team requires the sign-in's address to show and not be editable ("must not be changed without consultation with the security team"), and a tab's address bar is editable.

How it is checked:

- **The open-urls scenario** hands a running Pane a page and a file through Launch Services (`tests/tools/open-urls.swift`, without activating it), which sends them as an Apple Event each: both open in the profile in use, the last one selected, and no other window shows.
- **A cold launch** (`open -n -g -a packaging/build/Pane.app <url>` with a throwaway home and data directory) delivered the URL while the engine started; on the Swift app it opened once the engine had started, in the "Personal" profile made for it.
- **The security scenario** hands one over behind the PIN lock: nothing opens until the PIN does, then it opens after the launch URL.
- **On Windows**, `open-urls` and `security` hand theirs to a second launch, as the shell hands a default browser's (`handURLs`, `tests/lib/browser.ts`), in the test VM; `HandedPagesTest` reads a launch's arguments as Chrome does, web pages and files alone.
- **`notification-click`** on both systems: a site's notification shown by its service worker once Pane's prompt allowed it, and clicked with Pane open, opens the worker's page as a new tab of the notification's profile, selected; one that focuses its page, from another profile shown, selects that page. Locked, the profiles go and the data closes, and a click behind the lock leaves Pane locked, its window shown, the profile not in the engine (the state's `engineProfiles`) and the data closed, and the page opens once the PIN is in, on both systems (on the Mac since W8e's hunk, handed in as the center hands a click that lands as the lock comes; before, the profile never opened again). On Windows, with Pane closed, the toast's launch opens it locked, the profile not loaded, then the page after the PIN. `EngineSwitchesTest.KeepsAToastsActivationForPanesUiAlone` keeps the switches, for the UI alone.
- **In the test VM**, real toasts of the installed Pane clicked in Windows' notification center through UI Automation (W8d): open, the site's page came up as a new tab, selected, the window in front; locked, the PIN came forward with no renderer, and the page opened after it; closed, the helper's launch opened Pane at its Lock, and the site's page was asked for 2.5 s after the PIN's first digit.
- **`plutil -p Pane.app/Contents/Info.plist`** of a packaged app lists no `ASWebAuthenticationSessionWebBrowserSupportCapabilities`.
