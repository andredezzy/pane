# Every profile's data is encrypted on disk, under a key the PIN releases

> **Extended by [ADR 0115](0115-nothing-outside-the-volume-names-a-page.md)**: what the engine and macOS kept outside the volume goes, what earlier Panes left there is erased at launch, and only a scenario's launch takes Pane's test hooks; **by [ADR 0116](0116-pane-locks-while-open.md)**: Pane also locks while open, and the volume detaches behind the PIN screen; **by [ADR 0114](0114-pane-identifier-is-xyz-roundedcorners-pane.md)**: the data root and the caches are under `xyz.roundedcorners.pane`; **and by [ADR 0121](0121-every-profile-file-encrypted-under-its-own-key.md)**: inside the volume every file a profile writes is encrypted again, under a key only Pane's processes hold, which closes "Code running as the user while Pane is unlocked" below and reverses "Encrypting each of Chromium's stores" under what was rejected; the volume's passphrase moves on from the one derived here, which keeps an earlier Pane out.

Everything Pane keeps of a profile is encrypted on disk: its tabs, cookies, site data, and caches. Without the data key nothing of it reads from the disk, and with a PIN set the key opens only with the PIN. It was the user's call (2026-10-30), after a test listed every profile's name and open tabs from `profiles.json` while the lock was set and no PIN had been typed.

What the test found, before this decision:

- **`profiles.json` was plain JSON** (`app/PaneKit/Sources/PaneKit/PersistedFile.swift`): each profile's name and tabs, with their addresses, titles, and favicons, open to any process of the user's.
- **The engine's profile folders were plain too, but for the cookies.** `DIPS` names the sites the user interacted with, `Network Persistent State` the hosts reached, and `Local Storage`, `IndexedDB`, and `Session Storage` hold the sites' data under their origins. The caches, which hold the pages themselves, sit under `~/Library/Caches` (ADR 0006).
- **The PIN guarded the window, not the files** (ADR 0042). `security.json`'s bcrypt hash also let anyone with a copy try every PIN offline, where the panic wipe never counts.

How it works:

- **One encrypted volume holds every profile's folder** (`DataVolume`, `pane/model/mac/data_volume.h`; the app's side, its sequences and its waits, is `DataVault`, `data_vault.h`). It is a sparse bundle in the data root (`Data.sparsebundle`, a terabyte at most and sparse) whose APFS volume is encrypted with a passphrase the data key derives, as FileVault encrypts a volume: in the kernel, its files' contents and names alike. The image attaches with its volume locked; once the key opens, the volume unlocks (`diskutil apfs unlockVolume`) and mounts at `Engine/Volume` through Disk Arbitration, in Pane's process and out of the Finder (`nobrowse`), its root the user's alone (0700).
- **It is made once**, at the key's first open, after the key is saved: an image with no file system (`diskutil image create blank`, where macOS has it; hdiutil's `-layout NONE` before), an empty APFS container on it (`newfs_apfs -C`), and in that one volume, born encrypted with the passphrase, which `diskutil apfs addVolume` reads from stdin (`DataVolume::AttachOrMake`). No plain volume is ever made. An image whose making a quit cut short, with no container or no volume yet, holds nothing, and the next open finishes it; only an image just made, or one diskutil finds no container on, is formatted. On a loaded Mac each part shows a moment after the tool that made it returns: the device for `newfs_apfs`, its container, the volume for the unlock, and the disk for DiskArbitration's mount. Each is asked again while it isn't there yet, up to 10 s, which CI's runners needed past 3; a wrong passphrase or a locked volume fails at once (0.19.1).
- **`Engine/<profile id>` and the profile's caches' folder are links into it** (`~/Library/Caches/<identifier>/Engine/<profile id>`). Chromium allows a profile wherever its path's parent is the user data dir, comparing the paths as given (`ProfileManager::IsAllowedProfilePath`), and derives the caches' folder from the path alone (`GetUserCacheDirectory`), so the links need no patch.
- **The volume is inside the engine's user data dir** because the network service's sandbox allows only that and the caches' folder, by their resolved paths (`GetNetworkContextsParentDirectory`, `content/browser/sandbox_parameters_mac.mm`). Beside it, at the data root, the cookies and the HTTP cache did not open: the `migration` scenario's page saw its local storage and none of its cookies.
- **It fails closed.** Until the volume is mounted the links lead nowhere and the empty mount point is read-only (0500): a write into a profile fails rather than creating a plain folder. A mounted volume is kept only if macOS reports it encrypted (else `VolumeError::NotEncrypted`): a plain one put in its place unlocks with nothing and mounts, so its image detaches before anything is written, and no profile opens.
- **`profiles.json` is sealed in place**, AES-GCM over its JSON, bound to its name (`pane/model/sealed_file`), with each proxy's password in it. It opens without the volume, so the window shows the profiles and their tabs while the volume opens; it loads off the UI thread, on the model store's own sequence (`ModelStore`), and the vault waits for it before it looks for plain folders and finishes the attach. A plain one an earlier Pane wrote is read once and sealed, with the proxy passwords it kept apart (ADR 0037's `proxy-passwords.json`, or the Keychain item before it), whose store then goes.
- **One data key seals both**: 256 random bits, with a key per use through HKDF (`pane/model/data_key`). It is kept only sealed, under a key HKDF-SHA256 derives from the engine's "Pane Safe Storage" secret, which the engine already reads at every launch, so an update still asks once (ADR 0037). With a PIN, the derivation takes the PIN too, stretched with PBKDF2-HMAC-SHA256 at OWASP's 600,000 rounds (64 ms on this Mac, where bcrypt at cost 10 takes 40), with a salt of its own at every seal.
- **The sealed key tells another secret from a wrong PIN**: it keeps a check of the secret (HMAC-SHA256, cut to 128 bits). Without it, an engine key replaced would make every PIN look wrong, and the fifth would wipe the data. Another secret shows the lock's line for an unreadable key, and counts no attempt.
- **The PIN is checked by opening the data key**, and the bcrypt hash goes. A PIN set before this is checked once more against its hash, which then goes. The count and the wipe stay ADR 0042's. Change and Remove check the PIN with the secret this session already read, so they ask the Keychain nothing.
- **The sealed key is written twice**, atomically: in `security.json`, and in its copy beside the volume, `Data.security.json`. Losing both loses the data; a second copy sealed the same way weakens nothing. A new key is written before the volume it opens is made (`AppLock::OnOpened`): made first, a quit between them left a volume no saved key opens, which the next launch shows as a key lost.
- **Setting, changing, or removing the PIN reseals the data key** and nothing else: no data moves, nothing restarts.
- **Pane makes the engine's Keychain item when it has none and no key is sealed yet**, at the data key's first open (`SafeStorage::DataSecret`), before any of Pane's profiles opens, as Chromium makes it (16 random bytes, in base64, `keychain_password_mac.mm`): a fresh install needs the data key first. ADR 0037 rejected this because a migration would then not hand over the Electron app's key; by this point the migration has run. A migration whose key macOS could not ask for (a locked session) is no longer retried: its sites stay signed out. Once a key is sealed Pane never makes a new secret, which would not open it.

What the engine opens on its own:

- **Chromium starts on its Default profile.** At startup it opens the profile Local State names as used last (`GetStartupProfile`, `chrome_browser_main.cc`), and the ones open last as its fallback: Pane's, before the PIN, outside every gate of Pane's. With an earlier Pane's plain data, it opened the profile the move was copying. Before the engine starts, Pane names Default instead and no profiles open last (`pane/model/local_state`); Pane restores its own session.
- **The segmentation platform is off** (`SegmentationPlatform`, `SegmentationPlatformUkmEngine`, in `pane/app/engine_switches.cc`). Its database at the user data dir's root (`segmentation_platform/ukm_db`) kept the addresses of the pages visited, outside the volume: the `security` scenario found a page's address there. An earlier engine's copy is erased at launch, as the panic wipe erases.
- **Everything else at the engine's root holds none of the browsing**: `Local State` names no profile and no site outside Google's infrastructure, and the `Default` profile, where Pane never browses, has no history, downloads, or favicons (counted on this Mac, 2026-10-30). The `security` scenario's search for a page's address and a value it stored covers the whole data root.

Launch and unlock:

- **The engine still starts before the PIN.** Pane's launch runs inside it (`PaneMainDelegate`, ADR 0010), and the PIN is asked in Pane's window.
- **The image attaches first, before the engine starts** (`PrepareData`, `pane/app/data_launch_mac.cc`), with its volume locked and its watchdog: while the engine starts and the PIN is typed. One that fails is attached again once the key opens, a crash's leftovers cleared. `diskutil image attach --noMount` where macOS has it (26 and later), since hdiutil's attach is deprecated there, and hdiutil before.
- **The data's lock decides which Pane holds the image** (`DataLock`, `pane/model/mac/data_lock.h`): a `flock` on `Pane.lock` in the data root, taken before the attach, which the system lets go of with its process, a crash included, and which the processes Pane starts do not keep. Another Pane started on the same data, as from a terminal, hands its URLs over through the engine's singleton and quits, and leaves the image alone. The attach had counted on a Pane running to keep its image from a second attach, as hdiutil does; diskutil hands back the attached image's devices instead, and the second Pane's watchdog detached the first's volume as it quit, so the first's pages stopped loading (`data-volume`). A Pane started while the last one quits waits for the lock, which that one lets go of once it has detached the image.
- **The model starts with its settings alone**; the profiles come once the key opens. Until then, and while an earlier Pane's data moves in, nothing runs (`UiApp::InteractionAllowed`), as behind the lock.
- **The key opens off the main thread**, and the volume's unlock and mount start there, at once (`DataVault::MakeAttacher`): without a PIN at launch, with one as the PIN is checked, while the lock slides away (0.35 s, ADR 0042). After an update, the Keychain's one prompt now comes before the profiles show.
- **A profile's context opens only once the volume is mounted** and the profile's folders and links are in place (`ProfileContexts::With`, `DataVault`): the single way a profile reaches the engine.
- **The volume never outlives Pane.** After the engine stops, the image detaches by its device, once an attach still under way has finished (the first launch's making of the image, say: a quit in it had left the image attached, after Pane and before its watchdog), which takes it whole (a detach by the mount point can unmount the volume and leave the image attached), waiting a moment for the engine's helpers (the network service keeps the cookies open), then forcing. A watchdog, `pane-volume-watch` (`pane/model/mac/volume_watch_main.cc`, built with the engine, carried in its archive, and packaged beside the loader in `Contents/MacOS`), starts once per Pane, as the image first attaches, wakes once when Pane's process ends (kqueue's `NOTE_EXIT`, nothing polls), and detaches the image, found by its path, on whichever device it then has: a lock detaches it and the unlock attaches it again, and until 0.18.1 each unlock started another watchdog, kept until the quit. It detached 321 ms after its process ended. A quit that detached the image ends it, so it never wakes: from 0.18.1 it took the data's lock for its `hdiutil info`, which found nothing, and a Pane started in those 250 ms found the lock taken and attached its image only once the key opened, 250 ms later to the first page (`benchmark-unlock`, `security`). It runs in a session of its own (`setsid`), ignoring the hangup of the terminal Pane was started from: a kill of Pane's process group had ended both, and left the volume mounted and unlocked. The image keeps the most it has ever held: APFS reuses the blocks a deletion frees, which stay encrypted, and they go when the wipe erases the image. Compacting it, as Pane did at every quit and lock until 0.18.1, gave nothing back: `hdiutil compact` reclaims 0 bytes on an image of 200 GB, 500 GB, or 1 TB, with 8 or 64 MB bands, encrypted or not, measured with 1 GB written and deleted (2026-11-06); only a 10 GB image gave any back. It cost a tool's start (65 ms) that an unlock waited for, so it went. A smaller image was rejected: it would cap a profile's data. Waiting for that detach spins the main run loop with the engine gone, so what Chromium left on a timer goes first: the 2 s it waits after an assistive app asks for the accessibility tree aborted Pane at the quit from 0.14 to 0.17, which `data-volume` now checks. A device remembered from an attach that failed, or from one a lock overtook, is detached only while `hdiutil` still lists Pane's image on it: a volume refused as not encrypted is detached at once, and its number goes to the next disk attached, which the quit had then taken with it (0.19.1, `data-volume`'s decoy).
- **Measured on this Mac** (M5 Pro, 2026-10-30), `benchmark-unlock`, five runs each, medians, against the build before this:
  - From the PIN to the first page painted: 255 ms before, 474 and 492 ms now (+225; two sets of five). After the PIN's stretching, the unlock and the mount take 209 to 221 ms.
  - From launch to the first page without a PIN: 340 ms before, 612 and 636 ms now (+280).
  - Isolated, attaching an image takes 250 to 280 ms, unlocking its volume 170 to 190 ms, and mounting it through Disk Arbitration 47 to 62 ms.
  - The first launch, which makes the volume: from the attach's start to the volume mounted, 1,470 to 1,537 ms over three runs; from launch to the volume mounted, 1.86 to 1.92 s. Its steps: the image 70 ms, its attach 170, the container 100, finding it 90, the encrypted volume 880, the unlock 190, the mount 50.

Moving the data in:

- **An earlier Pane's plain profile folders move into the volume** before any profile opens, file by file, each staged for the panic wipe's erase only once its copy is whole, so a move a quit cuts short copies that folder again. Their caches are dropped, and rebuild. The move follows the data, not the launch: plain folders found at any open move in.
- **Three states on screen change**, drawn in Paper and approved by the user (2026-10-30) on the Lock screen page (ADR 0058):
  - **07.5, the move's progress**: "Encrypting your data", the update's bar (`pane/ui/design/update_status`) at the numpad's width, and "Once, after this update", in place of the dots and the numpad, on the PIN screen's panel (`pane/ui/lock/lock_screen_view`). With no PIN to ask first, it shows from the first frame; after the PIN the screen crossfades into the move, and sinks once it ends.
  - **07.6, an unreadable key**: "Pane can't read the key to your data. / Quit, then restore security.json.", in two lines, no longer saying to remove the file. The dots and the numpad show at 40%, since the lock takes no keys then. When the Keychain gives no secret, its second line asks to open Pane again and allow its keychain item (07.7, drawn while building, approved by the user, 2026-10-30). On Windows, DPAPI giving no secret is a state of its own (`PinEntry::UnreadableReason::kDpapiRefused`, beside the Keychain's `kKeychainDenied`, the launch naming its system's, `AppLock::System::no_secret`), on 07.7's lines until the user approves W5's 07.7.1 (W4).
  - **07.8, the data won't open**: "Pane can't open your encrypted data. / Quit, then open Pane again.", on the same dimmed panel, when the volume would not attach once the key opened: a damaged image, a plain volume in its place, another Pane holding the data past the wait. The lock shuts and takes no keys; with a PIN, the panel that slid away comes back (approved by the user, 2026-10-31). Before it, nothing showed, and the pages never loaded.

The panic wipe:

- **The data key goes first.** Nothing left on this Mac opens the volume or the sealed file after that, the SSD's old blocks included; a copy made earlier with `security.json` is as safe as the Keychain and the PIN made it. The image is detached, and the volume and the files deleted, the image without random passes, which protect nothing more inside it. The fresh Pane seals a key of its own.

What stays outside, and why:

- **`settings.json`**: the lock's theme and the Dock icon show before the PIN (ADR 0001, ADR 0089), and it names no profile, site, or tab (the user's call, 2026-10-30).
- **`security.json`, its copy, and `migration.json`**: the lock and the wipe read them before any key.
- **`deletions.json`**: it names only profile ids, which Engine's links name anyway.
- **`Engine/`'s own files**, as above.
- **Pane's preferences**: the window's frame. The open panel's last folder, which AppKit keeps there, is removed at quit.
- **Nothing of the update check**: its requests send and keep no cookie and no cache (`Updater::RequestFor`, `pane/updates/updater.cc`). The Swift app's had moved from `URLSession`'s shared and default sessions to ephemeral ones, and what those had kept in Pane's caches folder goes at launch (`RemoveSessionCaches`, ADR 0115).

On Windows (U5, the user's call of 2026-11-13; W3):

- **No volume.** One needs elevation, so every profile's folder is the engine's own, `Engine\<id>`, and each file a profile writes is encrypted under its Engine key instead (ADR 0121); names, sizes, and times show at rest, no name naming a site (patch 0010's numbered buckets). The data root is `%LOCALAPPDATA%\Pane`, the user's alone by its ACL, and carries `FILE_ATTRIBUTE_NOT_CONTENT_INDEXED`, which NTFS gives everything made in it, in place of Spotlight's markers. With no volume, the vault's place is the engine's folder (`pane/model/folder_place`): the key opens the data at once, a deleted profile's folder goes, and a lock's close lets the engine's processes forget their keys once every profile has closed; nothing holds a file open against it.
- **The secret is os_crypt's**: the 256-bit key Chromium seals its cookies under, in `Engine\Local State` under DPAPI (`os_crypt.encrypted_key`), read before the engine starts (`pane/model/engine_secret_win.cc`), and made there as Chromium makes it when none is there and no key is sealed, so Chromium takes it as its own (`os_crypt_async::InitWithExistingKey`, checked in `EngineSecretTest`). Only the Pane holding the data's lock makes it (`DataLock`, `LockFileEx` there): two first launches at once can't seal under one key and leave the other in Local State. One DPAPI won't open is never written over; the lock shows its unreadable key. A test copy's is the mock keychain's fixed secret, as on the Mac.
- **With a PIN, the TPM guards it**, as Windows Hello guards its own (`PinGuard`, `pane/model/pin_guard_win.cc`). Setting or changing the PIN makes a key the chip holds through CNG's Microsoft Platform Crypto Provider, RSA 2048 for decrypting, whose own PIN is the PIN, set before the chip makes it and used silently, with no Windows UI; 32 random bytes, sealed under it with RSA-OAEP and SHA-256, are the seal's share, and the sealing key is HKDF-SHA256 over the secret and the share, the PIN's PBKDF2 stretch its salt, under an info of its own. security.json keeps the key's name and the sealed share under `key.tpm`, so every open knows which seal it is: the Mac's seals never have one, and keep every byte (ADR 0122). DPAPI gives the secret to any process of the user's, and four digits stretched by PBKDF2 alone fall in minutes; with the share, nothing on disk can be tried offline, and the guesses are bounded twice. The chip's dictionary-attack lockout locks at 31 failures (`tpmtool`'s Max Auth Fail on the test VM's chip) and forgets one every 10 minutes. Before it, **Windows keeps a lockout of its own for a standard user**, as Pane runs (Group Policy's Trusted Platform Module Services: Standard User Lockout Duration, Individual and Total Lockout Threshold; measured in the test VM on 2026-11-13 with none set): after 4 failed authorizations in its window, 480 minutes by default, that user's TPM authorizations are all refused, the right PIN's too, the record kept in the registry through restarts (`HKLM\SYSTEM\CurrentControlSet\Services\TPM\AuthorizationFailure`). An administrator isn't held by it.
- **Opening it.** Another secret is told before the chip is asked (`IsSealedUnder`), so it counts no attempt, here or in the chip, and shows the lock's unreadable key. A wrong PIN is the chip's refusal (NTE_PERM): it counts at the lock as ever, in the chip, and in Windows' count. A lockout, either one (NTE_AUTHENTICATION_IGNORED from the chip, TPM_E_PCP_AUTHENTICATION_IGNORED from the provider), refuses every PIN, the right one too, and says nothing of the PIN: it counts nothing at the lock or in Settings, and the dots shake; its own words are W5's to draw. And **a seal the chip guards never wipes** (below): its count stops at the last attempt before a wipe. A key gone (NTE_BAD_KEYSET) or a chip cleared loses what it guarded, as a forgotten PIN does, and the lock shows 07.6's lines, in the Mac's words until W5 draws Windows' (they tell the user to restore security.json, where the chip's key is what is gone). No chip for a seal that took one, as when the TPM is turned off in the firmware, shows the same lines and loses nothing: the PIN opens the data once the chip is back. The lock keeps the two apart (W4): a key deleted or a chip cleared (`PinGuard::Refusal::kGone`, opened as `kGuardGone`) and no chip or a provider refusing (`kNoChip`, `kRefused`, opened as `kGuardUnavailable`), each a reason of its own on the PIN screen (`PinEntry::UnreadableReason`), so W5's 07.6.1 and 07.6.2 can say which; both keep 07.6's lines until the user approves those.
- **Without a TPM 2.0, a seal that never had the chip** takes the PIN's stretch alone, and security.json has no `tpm`: the system's TPM Base Services see no TPM 2.0 (`kNoChip`, as Chromium's own hardware check asks them, `base::win::EvaluateWin11HardwareRequirements`). **Any other refusal makes no seal**: a lockout (four wrong PINs by any process of the user's bring one about), a chip that is there and refuses for another reason (`kRefused`), and, for a seal that had the chip, even its absence: setting or changing the PIN then keeps the earlier seal, which the earlier PIN still opens, and the dots shake, its words W5's. Until W4 (2026-11-13), every refusal but a lockout sealed the new PIN with its stretch alone and said nothing, so a refusal a process of the user's could bring about left the PIN to offline guesses.
- **Each key is named by its data folder** ("Pane data key <8 bytes of the folder's SHA-256> <8 random bytes>"), so a reseal deletes the earlier ones once the new seal is on the disk, and the panic wipe deletes them all; a test copy's never meet the user's.
- **The panic wipe deletes the chip's keys first**, whichever seal it wipes (a seal the chip guards never wipes, but one without it can outlive an earlier seal's keys): at the fifth wrong PIN at the lock, before the save that drops the data key, so a copy of security.json made earlier opens nothing after, and again at the next launch if the wipe is due. ADR 0042 has the wipe's processes there.
- **A test copy's PIN goes through the computer's chip**: a scenario's wrong PINs count in its lockout and in Windows' (`security` types 16), which is why they run in the test VM, whose TPM is swtpm's and whose policy raises Windows' standard-user thresholds for the scenarios (`docs/building.md`).
- **On Windows, four wrong PINs wait rather than wipe** (the user's call, 2026-11-13, asked with W3's report): Windows' standard-user lockout, which U5's question didn't weigh, bounds the guesses at 4 per 8 hours where the question named the chip's 32 per 10 minutes, and keeps the owner out as long after 4 typos (Settings' among them), so the lock's fifth wrong PIN never comes there. Rejected: a wipe at the fourth wrong PIN in 8 hours, Windows' count mirrored, which would lose the data to typos where the lockout already bounds a guesser. Past the fourth the lock says to try again later, in words W5 draws, and nothing goes; the Mac's wipe stays at the fifth. **W4 made it the seal's rule** (the user's call, carried out with W5's review, 2026-11-13): the lock's count is saved and never ages while Windows' window does, so once its 8 hours freed a slot, the next wrong PIN would have been the lock's fifth, and it would have wiped. Now a seal the chip guards counts wrong PINs up to the last attempt before a wipe and stays there, in one code path that tests the seal, not the system (`AppLock`); a seal without the chip, the Mac's and a Windows' with no TPM 2.0, keeps the fifth wrong PIN's wipe (ADR 0042). On a guarded seal the PIN screen shows no attempts left and no "Last attempt. All data will be erased." (the user's call, approved in Paper, 07.1.1 and 07.10): nothing is wiped, and Windows' own count, which ages and takes Settings' tries too, isn't Pane's to read (`AppLock::AttemptsTowardWipe`, by the same test of the seal); a seal without the chip keeps both lines.

What it cannot cover:

- **Code running as the user while Pane is unlocked.** The volume is mounted, and any process of the user's reads it, as it reads any app's files under FileVault. The hardened runtime, ad-hoc too, keeps injected libraries and debuggers out of Pane (ADR 0115).
- **A short PIN, against someone with the files and the Keychain secret together.** Offline the panic wipe never counts, and a few digits fall in seconds to hours whatever the stretching. A key that never leaves the Mac, in its Secure Enclave, needs the data protection keychain, so it waits for a Developer ID too.
- **What macOS keeps on its own**: a site's notifications, if any, in its notification database; and plain copies in Time Machine backups or local snapshots made before this (none on this Mac: no destination, no snapshots).

What was rejected:

- **Sealing only `profiles.json`**: the engine's folders name the same sites.
- **Keeping the caches out of the volume**: they hold the pages themselves (the user's call).
- **A volume only while a PIN is set** (the user's call, 2026-10-30): a profile without a PIN would stay in the clear; setting the PIN would copy its data in and leave the plain blocks on the SSD, and removing it would write everything back in the clear; and either would restart the engine.
- **Encrypting each of Chromium's stores** (the disk cache, SQLite, LevelDB, blobs): a patch in every storage layer, to carry through every upgrade (ADR 0008).
- **The PIN before the engine starts, with all of `Engine/` in the volume**: nothing may touch the application before Chromium creates it.
- **The volume beside `Engine/`**: the network service's sandbox does not reach it.
- **Encrypting the image itself** (`hdiutil create -encryption AES-256`), the first build's: its attach, with the image's own key derivation and a cipher in `diskimages-helper`, came after the key and took about 600 ms in Pane, so the first page came 873 ms after the PIN.
- **Mounting through `diskutil`**: 200 ms to start, where Disk Arbitration in Pane's process takes 50. `unlockVolume -mountpoint` mounts in one step, but in the Finder: it takes no `nobrowse`.
- **hdiutil's image with a plain APFS volume, the encrypted one added beside it and the plain one deleted**, the first build's: 3.5 s, and a quit before the delete left a plain volume that the next open mounted, in the clear.
- **`newfs_apfs -E`**, a container and an encrypted volume in 386 ms: it takes the passphrase on its command line, which the user's other processes can read, or from a terminal alone.
- **Making the image before the engine starts**: the lock takes an image with no key for a key lost, and a fresh install has no key until the Keychain gives the secret.
- **Opening the key and the volume before the engine starts, without a PIN**: measured, it gained nothing, since the image's attach, the unlock, and the mount follow one another whatever starts them.
- **A volume per profile**: an attach each, and a mount per profile.
- **An APFS volume in the Mac's own container**: a change to the Mac's disk for an app's data, which would outlive the app.
- **A Keychain item of the data key's own**: a second prompt at every update, which ADR 0037 removed.
- **A slower stretching of the PIN**: a few digits do not hold offline at any cost the unlock can wait for. The Keychain secret is what keeps a copy shut.
- **A watchdog that polls** (`kill -0` in a loop) or waits with `caffeinate -w`: one wakes the Mac every second for Pane's life, the other holds off its idle sleep.
- **Proxy passwords sealed apart from `profiles.json`**, as ADR 0037 kept them: the sealed file holds them as safely, and one place is less to keep in step.

How it is checked:

- **Before building** (2026-10-30), a scenario on the 0.13.1 build, in a throwaway home on the mock keychain, found that a profile whose folder is a link into a mounted volume loads through it, keeps the link, and writes nothing in the clear once the volume is detached; and that with the volume detached, opening the profile fails without writing.
- **`pane_unittests`**, PaneKit's tests ported, with more since:
