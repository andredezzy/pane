# On Windows Pane installs and updates itself: one folder in %LOCALAPPDATA%\Programs\Pane\Application, staged beside it and swapped whole once Pane has exited, with no launcher at launch

Pane on Windows is installed and updated by Pane's own code, as on the Mac (ADR 0092), not by Chromium's installer (decided 2026-11-15, after weighing Chromium's installer and a launcher of Pane's own: What was rejected, below). The app is one folder, `%LOCALAPPDATA%\Programs\Pane\Application`, laid out flat, apart from the data in `%LOCALAPPDATA%\Pane` (ADR 0121), so the panic wipe and the disk audits never meet it. Shortcuts and Pane's ProgIDs start its `chrome.exe`, which loads the `chrome.dll` beside it where no version folder is (`chrome/app/main_dll_loader_win.cc`): nothing more runs at launch. An update stages the new version beside the folder and a small helper swaps the two once Pane has exited, through Chromium's `WorkItemList`, which rolls back; the install window and the uninstall dialog are Pane's own, drawn in Paper (11.12.1 to 11.12.18). It takes no patched file but chrome.exe's icon (ADR 0004).

## Why

- **Chromium's installer needs a version of its own for every release.** `setup.exe` installs the highest version folder and only repairs a running install of the same version, so each Pane release would need its own 4-part Chromium version, a patched `chrome/VERSION`, which the Mac's engine shares: its framework's version folder, `publish-engine.sh`'s check, a new engine key and both engines rebuilt at every release, and a made-up version shown to Google's update servers, DevTools, and Installed apps. With `chromium_strings.grd`, `chrome_exe.rc`, and `setup_main.cc` (its Crashpad and histograms, ADR 0115), at least 4 more patched files where Windows had 2 left.
- **Its traps:** App Paths `chrome.exe`, shared with an installed Chrome; Chrome's 6-hour restart of a Pane with no Browser open, a locked one; the app inside the data root; an uninstall that deletes `User Data` alone; no window while installing.
- **Pane's own keeps the Mac's design** (stage beside, swap after exit, a detached helper finishes, a launch cleans up), packages each release from the engine archives as CI does on the Mac (ADR 0049), shows the web Chromium's real version, and costs nothing at launch.

## The package (2026-11-15, commit `220a9c7`)

- **What the folder holds** is `packaging/windows/pane.release`: the engine's files Chromium's installer packs (`chrome.release`'s `[GENERAL]`, `[HIDPI]`, `[SNAPSHOTBLOB]`, and `[DXC]`) that Pane's build has, without Chromium's Start tiles' logos; Pane's skies and icon files beside chrome.dll (ADR 0089); `pane-version`, Pane's version (ADR 0044); and Chrome's CRLSet (ADR 0040). `scripts/package-win.sh` lays it out from `out/Win` or an engine archive (`scripts/windows-engine-files.sh` lists the engine's part), refuses a package without a CRLSet, as `dist.sh` does, and compresses the folder's contents as Chromium's installer archive is (7-Zip's LZMA with BCJ2) into the payload Pane's installer will carry, `packaging/release/Pane-<version>-x64-app.7z`: 278 files, 472 MB, 130 MB compressed.
- **Each system takes its own file** from a release that carries both: the Mac's `-arm64.dmg`, Windows' `-x64.exe` (ADR 0002).
- **The engine archives** gain a platform column, Windows' archive the engine's files the folder holds (ADR 0049).
- **Nothing writes into the folder but an install and an update:** what Pane's launch logs before Chrome sets its logging up goes to the system's log and stderr, the Mac's default, where Windows' own default was a `debug.log` beside chrome.exe (`pane_main_delegate.cc`); Hunspell's dictionaries are kept in the data (ADR 0040).

## The installer, the registration, and the uninstall (2026-11-15, commit `6d66278`)

- **`Pane-<version>-x64.exe` is Pane's own small program with the payload after it:** `pane_setup.exe` (`//pane/installer`), which draws the boards' window itself with Direct2D and DirectWrite, the payload not being unpacked yet, and `package-win.sh` appends the payload and a 104-byte trailer (offset, size, unpacked size, SHA-256, version, a magic), read past an Authenticode signature if one is added. The same program, kept in the app folder, is the uninstall's helper.
- **The payload is the folder with each file compressed on its own** (7-Zip's LZMA with BCJ2, `-ms=off`): 134 MB where the first part's solid archive was 130 MB. The copy then writes each file as it reads it, with no temporary copy of the whole folder, and the bar follows the bytes. It is read with Chromium's `SevenZipReader` over the mapped file rather than `installer::UnPackArchive`, which can neither say how far it has got nor stop; its SHA-256 is checked beside the copy, and a payload that doesn't match is refused.
- **Nothing half-done (11.12.7):** the copy goes to `Programs\Pane\Installing-<tag>` and is renamed into place only whole; a reinstall moves the earlier folder aside (`Removing-<tag>`) and puts it back if registering fails; Close while copying stops it; a first install that stops leaves no `Programs\Pane`, nor `Programs` if it made it. Before copying, in the boards' order: a newer Pane installed (`pane-version`) is kept; an open Pane is asked to exit as Alt+F4 asks, its command line handed through Chromium's process singleton (`--pane-exit`), so Pane's own Exit Pane? asks first (ADR 0053); the space needed is the unpacked size twice and 64 MB, for the update staged beside it.
- **Registering is chrome.exe's,** `--pane-register=first|repair`, handled before the engine starts (`pane/app/install_switches_win.cc`), so the installer carries none of Chromium's installer code but the reader. ShellUtil makes Start's shortcut, and the desktop's at a first install alone (call A), each naming the AppUserModelID Chromium gives a per-user install, `Pane.` and a hash of the install's path, which is the window's too, so the taskbar groups them; Default apps' entries on Chromium's model in Pane's words (`installer::SetTranslationDelegate`): the ProgIDs `PaneHTM` and `PanePDF` naming `PaneHTM.ico` and `PanePDF.ico`, http and https, Chromium's file types and `.pdf`, no App Paths; the uninstall entry (Rounded Corners, `pane-version`, `Pane.ico`, `NoModify`, `NoRepair`, its UninstallString `chrome.exe --pane-uninstall`); and the toast activator's `LocalServer32`. The toast's menu item says "Go to Pane notification settings" (`OverrideLocaleStringResource`).
- **The install window closes as Pane's first window paints (11.12.6):** the first launch carries `--pane-installed=<event>`, which Pane sets after its window's first frame (`FirstWindowPainted`), and which `SetEngineSwitches` keeps, as it keeps `--pane-wipe-after`. Past 20 s with no window, "Pane couldn’t be installed", Pane installed all the same, and Try again opens it again; a launch an open Pane takes counts as opened.
- **The uninstall (call B):** Installed apps runs chrome.exe `--pane-uninstall`, which copies the helper to `%TEMP%` and starts its dialog. Uninstall waits for Pane to exit (Exit Pane, as above), then chrome.exe `--pane-unregister=keep|erase` takes every registration off: the shortcuts, through ShellUtil, and a pin's file the taskbar doesn't list, whose target is going anyway; Default apps' entries; the uninstall entry; the toast activator; and `HKCU\Software\Pane`, whole with the data, or all but the data's `PreferenceMACs` without it (ADR 0121). Ticked, the data goes the panic wipe's way first, the chip's keys before the files, the bar told each file erased (ADR 0042, 0113). Then the helper removes the app folder, and its own copy as it exits (a hidden `cmd` loop, as Squirrel does). Its last screen, "Pane is uninstalled", says "Pane and its data are gone from this PC." when the data went with it, "Your data stays in %LOCALAPPDATA%\Pane, for when Pane is installed again." when it stays, and nothing of data when there was none, where it used to say the data stayed (2026-11-16, commit `f475f04`, as the user asked, the dialog having shown no data box then since the installer's commit); with no data to keep, `HKCU\Software\Pane` goes whole too, where its preference MACs had outlived it, naming nothing (`Unregister`).
- **Call D:** when the sky Pane shows changes, and at launch, `DockIcon` rewrites the icon of Start's and the desktop's shortcuts and of each pin naming Pane's chrome.exe, on the shell's COM thread at USER_VISIBLE. Not after startup, nor at BEST_EFFORT: Chromium holds both until a page has loaded or 3 minutes have gone, and a Pane with no profile open, or on its Lock, loads none.
- **The shortcuts stay Pane's** (2026-11-16, commit `fcd50d3`). - **What a screen reader reads:** a UI Automation provider of the installer's own (`uia_element.cc`), which Narrator, NVDA, and JAWS read: the window a dialog named by the screen's title, its message the description, a new screen said as it shows; the box a check box, its size and line the description; the buttons and the bar Windows' own, the bar 0 to 100, its percent. ## The update (2026-11-15, commit `4fb6caa`)

- **Where it goes:** `Programs\Pane\Update`, beside `Application` (`pane/installer/update_folder.h`): `<version>.partial` while it unpacks, `<version>` once whole, `<version>.download` naming the installer it came from, `<version>.removing` while it goes, `Swapping` holding the old app during the swap, and `not-installed`, a failed swap's mark. A launch keeps the newest whole version newer than the one running, with its installer, reads the mark once and deletes it, and removes everything else, the installers of what goes too, and the helper copies an earlier exit left in `%TEMP%`, each only by its exact name (`pane-update-helper-` and 8 hex digits, holding the helper alone).
- **Staging (11.12.11):** once the installer matches the release's SHA-256, Pane reads its payload where it lies, as the installer reads it (its trailer, its SHA-256, its version the offer's), and never runs it: unpacked off the UI thread by the installer's own reader into `<version>.partial`, checked (`pane-version`, chrome.exe, the helper), and renamed whole, while the pill holds its full bar. Only the installed Pane stages, the one running from `%LOCALAPPDATA%\Programs\Pane\Application`; a test copy only where a scenario asks (`PANE_UPDATE_INSTALL=1`, its folder in the temporary folder laid out as an install). A newer release replaces what is staged (ADR 0092), renamed `.removing` first, so a quit in between leaves a leftover, never a staged copy.
- **A release withdrawn after it staged** (2026-11-20; ADR 0092's rule, both systems): a check whose latest release is older than the version staged takes the staged folder, its record, and its installer in Downloads away, as a newer one's does, so no exit installs it; a check that fails keeps them. Windows has one more way in: the version the last exit left staged (a swap E rolled back, or a session that ended), which the launch keeps and offers before its check answers. The launch's check takes it away too, whichever of the two comes first (`Updater::KeptFromLastExit` reads the check's latest when the check came first), and E's line goes with it. A quit that comes before the removal has begun runs it itself (`Updater::InstallAtQuit`), since the next launch would keep the folder again and offer it, at a launch whose check might fail. Measured in the test VM before the fix (W10m): 0.21.91 staged beside an install of 0.21.90, GitHub's live latest 0.21.1, the pill gone at the launch's check, and the staged version left in place, which an exit installs (read in the code).
- **The swap, at any exit (11.12.14):** Alt+F4, Exit Pane, and the window's Close install it; Restart to update exits on purpose, with no Exit Pane?. At its exit Pane copies the staged version's `pane_setup.exe` into `%TEMP%` (a folder a running program is in can't be renamed) and starts it with `--pane-swap`, hidden, out of the browser's job where the job lets it go, in it where it doesn't (the job outlives Pane). The helper holds every process running from the app folder by its handle, waits up to 2 min for the browser and 1 s for the rest, takes in what they started since, and ends what outlived the browser (an idle renderer, as the test VM's rounds of 2026-11-14 and 2026-11-15 found). A user's own Exit leaves none (2026-11-16, commit `fcd50d3`: ten Exits of an installed Pane through Exit Pane? and the window's Close, on two builds, every renderer, the GPU process, and the utilities gone before or with the browser, nothing left 30 s on), so the end is for what a crash or another program leaves. Of 2,915 helpers of 346 launches the test VM's watcher saw over that audit's three rounds, most of them test copies', one outlived its browser, a test copy's: a renderer Windows had ended (its exit code set, Windows deleting it) whose teardown under Windows on ARM's x64 emulation never finished (one thread waiting in the kernel, `xtajit64se.dll` loaded). Nothing ends such a process (`TerminateProcess` is refused, as for any process already terminating), and it holds the app folder until Windows restarts, so on Windows on ARM a swap could meet one and fail as E below, the next exit after a restart installing; a PC of Pane's own architecture runs no emulator (U6). It changes nothing where Windows is ending the session (`SM_SHUTTINGDOWN`; Pane starts no helper at a sign-out, as Chromium's own swap waits, `browser_shutdown.cc`) or where a Pane was opened again meanwhile: the next exit installs. Then one `MoveTreeWorkItem` in a `WorkItemList`: the app aside into `Swapping`, the staged folder in its place, everything moved back on any failure. For Restart to update the new Pane opens with the old one's arguments, in front where the old one was; for a plain exit nothing opens. Last, the old app goes (tried for 10 s: Defender reads the files a moment after), with the installer, its record, the mark, the update folder, and the helper's own copy as it exits (the uninstall's `cmd` loop), once the new version has registered (below).
- **The moment between the two moves,** when `Application` stands empty, is the swap's cost, as section 4 of the research weighed it: Windows renames no folder over another, and Chromium's own swap has the same moment for chrome.exe (`setup_main.cc`). A power loss in it leaves Pane's shortcuts naming nothing, the old app in `Swapping`, the new one in `Update\<version>`, and the installer still in Downloads, which installs it again.
- **An update registers as a reinstall does** (2026-11-20, W10m): until then the swap wrote no registration, and only the installer's `--pane-register` writes Installed apps' entry, so after the published 0.21.0 updated itself to 0.21.1 in the test VM (W10l), Installed apps still read 0.21.0, with 0.21.0's size. Now, once the swap is done and the old app, the installer, and the update folder have gone, the helper runs the new version's chrome.exe with `--pane-register=repair`, 60 s at most, as a reinstall's: the installer and the helper start chrome.exe through one helper (`pane/installer/chrome_exe.h`'s `RunChrome` and `RegisterWithWindows`). The entry then names the new version, its size, and the day, and the toast activator, Default apps, and Start's shortcut are written again by the version they name. It runs behind Restart to update's window, which waits on none of it. Only the install's own folder registers (`IsInstalledAppFolder`, which chrome.exe's `--pane-register` checks too): a scenario's copy leaves Windows' registration as it was, and says so in its notes. A registration that fails, or doesn't end, is noted and undoes nothing: the new version is in place and may be running, and the next install or update writes the registration whole again.
  - **The date** is the update's: Chrome's installer writes `InstallDate` at every install and update with the version and the size (`install_worker.cc`'s `AddUninstallShortcutWorkItems`; `setup_main.cc` overwrites even an MSI's at an update), so Installed apps' line says when the version it names came, and Pane's does the same (rejected, below: keeping the first install's).
  - **Beside the Pane it opened:** the registering chrome.exe hands nothing to the running Pane, since chrome.exe's fast path to an open window takes `--profile-directory` alone (`chrome_exe_main_win.cc`'s `AttemptFastNotify`), and Pane's delegate runs the switch before any process singleton exists (`pane_main_delegate.cc`); it takes no data lock (only the unregister does) and reads `settings.json`, which Pane replaces atomically, for the shortcuts' sky. Start's shortcut is made again (`CREATE_ALWAYS`) naming the same chrome.exe, AppUserModelID, toast activator, and sky, so what names it stays; the desktop's is replaced only where it is (`REPLACE_EXISTING`), so one the user deleted stays deleted (11.12.3's A); the taskbar's pins are files of their own, which the registration never writes. Where Windows holds Start's shortcut mapped as it reads it for the new window's taskbar button (ADR 0089), its write fails, and the registration with it: the entry is written before the shortcuts, Start's shortcut stays the one before, which names the same, and the helper notes the failure.
- **E (11.12.14):** a swap that fails rolls back, leaves its mark, and opens the old Pane again for Restart to update; that launch alone shows "The update didn’t install last time. Pane tries again when it exits." above the pill, which still offers Restart to update, and Settings' row says the same words, which no board draws; the next exit tries again. In the VM what fails it is a file in the app folder that another program holds open without sharing its deletion.
- **Exit and install (11.12.11, 11.12.13),** where Pane can't install it: run from another folder, a test copy, a file it may not stage, or a staging that failed. Settings says "Version 0.21.1 is downloaded. Its installer opens when Pane exits." The click exits Pane, which opens the installer as it goes (`ShellExecuteEx` with `--pane-after=<pid>`), and the installer shows nothing until that chrome.exe and what ran from the app folder have gone: in the VM its window showed 0.16 s after Pane had gone.
- **The Mark of the Web** (ADR 0002): the verified installer carries none, so Exit and install runs it with no question from SmartScreen; an unverified one keeps Chromium's own mark (`ZoneId=3`, `HostUrl=about:internet`), written before it reaches Downloads, so SmartScreen asks before it runs, and Pane never stages it.
- **The uninstall** names its window "Uninstall Pane" on the taskbar, the install's staying "Pane Installer" (11.12.9), and removes the update folder too, which it left, and `Programs\Pane` with it. With "Also delete Pane’s data" ticked, its line names the button that erases, "Erased for good once you press Uninstall and delete: nothing can bring it back." (the user's call, 2026-11-17, 11.12.9 B redrawn; the checklist run by hand on Windows found it naming "Uninstall" beside a button titled "Uninstall and delete"), which `windows-install` reads.
- **Only the install's own folder is ever removed or unregistered** (a defect of the installer's commit, found while 11.12.10.1 was drawn from the code; fixed in commit `4fb6caa`): `chrome.exe --pane-uninstall` run from a copy or a build's folder showed "Pane isn’t installed where Windows says" with Try again, since that folder holds a chrome.exe, and Try again had that chrome.exe unregister the install, then deleted every file of that folder. That failure now offers Close alone, and everything that deletes or unregisters checks again, each time, that the folder is `%LOCALAPPDATA%\Programs\Pane\Application`, compared as NTFS compares names (`IsInstalledAppFolder`): the dialog's start, its buttons, the removal itself (`pane/installer/removal.h`) before the unregister and again before the files, and chrome.exe's `--pane-register` and `--pane-unregister`, so another folder's chrome.exe neither takes the install's registrations away nor points them at itself. The update's helper swaps only the install's own folder or a scenario's copy in the temporary folder, checked as it reads its command line and again as it starts.
- **An uninstall that fails can always be finished:** the unregister takes Installed apps' entry away last, and only where every other step went, so one that failed leaves the app untouched and runs again from Installed apps ("Something went wrong while removing it ({code}). Try again."); once unregistered, a file another program holds no longer leaves a "Try again" with no button: Try again removes what is left without chrome.exe, and the words say where it is, "Some of Pane’s files are still in %LOCALAPPDATA%\Programs\Pane ({code}). Try again, or delete that folder.", a fifth line beside the four approved, for the user's look with 11.12.10.1 redrawn. Closed while it erased, a failure brings the window back to say so.
- **The helper never ends another Pane:** once the exiting browser has gone, a browser still running from the folder (another launch's, on data of its own) or a process none of Pane's started defers the swap with nothing ended, the mark left; only then is what outlived the browser ended.
- **The release workflow** packages Windows' installer in CI from the Windows engine archive, as it packages the dmg (ADR 0049), where `chromium/prebuilt-engines.tsv` names a `windows-x64` engine for the tagged commit's key: the checkout's own 7-Zip from Chromium's package store (`infra/3pp/tools/7z/mac-arm64`, `version:3@26.03`, as DEPS pins it, its SHA-256 checked), `fetch-engine.sh windows-x64`, `package-win.sh`, the provenance attested, and `Pane-<version>-x64.exe` published in the same release as the dmg. ## What was rejected

- **Chromium's `mini_installer` and `setup.exe`** (above).
- **A stub launcher over `app-<version>` folders** (Squirrel's shape): one more process at every launch. It was the fallback had the swap after exit failed in the VM; the swap passed there (commit `4fb6caa`).
- **MSIX:** it needs a trusted signature, so it can't carry an unsigned alpha (U6).
- **The app inside the data root,** `%LOCALAPPDATA%\Pane`: the panic wipe and the audits would meet it.
- **`installer::UnPackArchive`** for the payload (2026-11-15): it reads the archive from its start, reports nothing as it goes, and can't stop; a solid payload needs the whole folder in a temporary file before the first file is written.
- **Dynamic annotation (`IAccPropServices`)** for what a screen reader reads: MSAA's alone, and in the VM it read nothing at all.
- **Running the downloaded installer to stage an update** (2026-11-15): it would need a silent mode of its own, and Windows would weigh each update's file as it runs; Pane reads the payload itself.
- **Staging an unverified installer:** nothing vouches for what it holds. It goes through Exit and install, where SmartScreen asks.
- **Waiting for the browser alone:** a renderer that outlives it holds the folder, and the swap fails.
- **Keeping the first install's date after an update** (2026-11-20), an `InstallDate` already there left as it is: the line would date one version and name another, where Chrome's dates the version it names.
- **The update's registration before the new Pane opens** (2026-11-20): Restart to update's window would wait for a second chrome.exe, under the test VM's emulation its first run of the swapped-in files.
- **Registering a scenario's copy:** its registration would name a folder in the temporary folder in the user's own Installed apps, Default apps, and Start, which chrome.exe refuses for any folder but the install's.
