# Extensions' keyboard shortcuts work as in Chrome, and are changed on Chrome's own shortcuts page

An extension's keyboard shortcuts (`chrome.commands`) work as in Chrome and in Aside. A command's shortcut sends `onCommand` with the active tab, and the action's (`_execute_action`) works as a click on the action: its popup, or `action.onClicked`. They work with the page focused, and with the address field being edited. They change on Chrome's own page, chrome://extensions/shortcuts, in the profile's tab, which the extensions page's Keyboard shortcuts opens (the user's D3, Paper 10.3, ADR 0062): set, cleared, and moved from another extension by Chrome's own rules.

Running them:

- **The registry:** `pane::ExtensionShortcuts` (`pane/browser/extensions/extension_shortcuts.h`) is Chrome's `ExtensionKeybindingRegistry`, one per Browser, owned by its `BrowserExtensions`. It keeps every enabled extension's active shortcuts as Chrome's views registry does, and the action's beside them, which Chrome's toolbar keeps itself. Pane's window has one FocusManager for all its Browsers, so none registers with it: the window asks the shown profile's registry for each chord. It stands as its profile's `registry_for_active_window`, so the shortcuts page's `setShortcutHandlingSuspended` pauses it while a field records.
- **The window:** a chord (⌘, ⌃, or ⌥) runs ahead of the page (`Window::PreHandleKeyboardEvent`) and ahead of a view of Pane's (`ExtensionKeys`, the address being edited), as in Chrome a shortcut goes before the page (ADR 0079). A command goes through the registry, which grants the active tab, as Chrome does; the action's runs as a press of its button.
- **What stays the browser's:** a key the menu bar holds stays the menu's, as Chrome's own shortcuts stay Chrome's, and the lock screen, Quit Pane?, and the other overlays take their keys first: behind the lock no extension shortcut runs. Chrome's page checks a key only against other extensions', so one of the menu bar's typed there is refused after the fact, with no message on the page, as Paper 10.3's note asks: `ShortcutRefusal` (`pane/ui/extensions/shortcut_refusal.h`) watches Chrome's `CommandService` and gives the command back the key Chrome took off it for the new one, or none, and the page shows that key again. A key a manifest suggests is refused the same way.

**On Windows, Chrome's Windows rules** (W4, 2026-11-13): an extension's keys are those Chromium's own commands parse there, a manifest's `default` or `windows` suggestion, never its `mac`, whose Command and MacCtrl mean nothing on Windows; Chrome's shortcuts page refuses Ctrl+Alt there, which AltGr types with; a chord of Ctrl or Alt runs ahead of the page and the address field as on the Mac; and the keys refused as the menu bar's are the command table's Windows column (Ctrl+T, Ctrl+W, F11, Alt+Left, ADR 0019), which `ShortcutRefusal` reads as it reads the Mac's.

Comparing Pane's Extensions page with Aside's (the user's request: keep parity with stable browsers) found that no key reached the shortcuts, and a probe extension confirmed it. The first build made the keys the extensions suggest work, with Chrome's own rules settling the conflicts between extensions, and nothing could change them. Pane's own Keyboard shortcuts dialog came next, drawn in Paper (09.8 to 09.12) and built in the Swift app, with Chrome's macOS field rules and messages and a message naming the menu bar's item a key belonged to. It shipped from 0.13 to 0.19, and Chrome's page replaced it with the move to Views, as Pane's Extensions page went (ADR 0062); its tests (`ExtensionShortcutTests`, `KeyRoutingTests`) went with PaneKit, since the glyphs, rules, and messages they checked are Chrome's page's now (`docs/benchmarks/panekit-tests.md`).

What was rejected:

- **The page's pre-handling alone** (`PreHandleKeyboardEvent`): it sees only keys sent to a page, so a shortcut typed in the address field would do nothing. In Chrome and Aside it works there too.
- **Clearing with `RemoveKeybindingPrefs`:** an update of the extension would bring its suggested key back. Chrome's Clear goes through `UpdateKeybindingPrefs`, which keeps the command the user's.
- **A message on Chrome's page for a refused key:** Chrome's page has none for it, and Paper 10.3 has the engine refuse the key with no message, the page showing the key it gives back.

How it is checked:

- **The `extension-shortcuts` scenario,** with a probe extension (`tests/pages/extensions/commands`) that suggests ⌘⇧Y for a command and ⌘⇧U for its action, and a second (`tests/pages/extensions/commands-second`) suggesting ⌥⇧K. With a page focused, ⌘⇧Y runs the command for the active tab and ⌘⇧U the action; with the address field being edited, ⌘⇧Y runs too. On Chrome's shortcuts page, in the profile's tab, it reads the probes' commands and keys, sets a key, moves ⌥⇧K from the second probe (nothing runs while the field records, the window's shortcuts paused with the page's), clears one, and types ⌘T, which is refused: the field gives back the key it had, and ⌘T stays Pane's New Tab in the window.
- **Other scenarios:** `shortcuts`, `key-precedence`, `extension-details`, `extension-context-menus`, `extensions-menu`, `extension-management`, `tabs-api`, `security`, and `smoke`.
