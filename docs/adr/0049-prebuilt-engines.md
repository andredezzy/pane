# Prebuilt engines are matched by key and published as prereleases, and CI packages the app from them and never builds Chromium

The app is packaged from a prebuilt engine, found by a key of the engine's sources, so CI, releases, and a Mac without a Chromium checkout package Pane without building Chromium. The model is Ardia's, an Arc-like Chromium browser for the Mac. `scripts/engine-key.sh` hashes the git trees of what the engine is built from: `chromium/CHROMIUM_VERSION`, `chromium/args`, `chromium/patches`, and `pane` (`//pane`). Ardia hashes its whole `engine/` tree; Pane's sources sit in `chromium/` and `pane/`, apart from the scripts, which do not change the engine. A checkout whose engine sources have uncommitted changes has no key. `chromium/prebuilt-engines.tsv` names the key of the engine at that commit and the archive's SHA-256, and `scripts/fetch-engine.sh` downloads and verifies it from the `engine-<key:12>` release. It was a table of every key until the review of 0.18.0: HEAD read only its key's line, a tag reads its own tree's, and the release's name follows from the key, so one overwritten line does. The archive, `PaneCore-<chromium>-<key:12>.zip`, is the engine's bundle, stripped, with the volume's watchdog beside it, so a fetched engine stands in for `out/Release` as `PANE_ENGINE_OUT`.

**Pane's UI is part of the engine** (ADR 0124): `//pane` holds it, so a change to the UI changes the engine's key, and every release is packaged from an engine this Mac built and published (the user's U4). Until the cutover the UI was a Swift app built on the engine, and the engine changed only with `//pane`'s bridge and Chromium; an app commit then needed no engine of its own.

An archive is the engine built from its key's sources. `scripts/package.sh` once named an archive by the checkout's key and checked only the bundle's Chromium version, so an engine built before the last `//pane` commit, or with other patches applied, was archived as the current engine. Now `scripts/build.sh` writes the key of what it built into `out/<Config>/pane-engine.key` after each successful build of `chrome`: the working tree's key (`engine-key.sh --worktree`), which equals HEAD's once those sources are committed as built. It records none when the checkout is not at `CHROMIUM_VERSION`, the applied patches are not the series (`apply-patches.sh --check`), `src/pane` links to another clone, or the sources changed during the build. `publish-engine.sh` refuses an engine with no record or another key, and checks the bundle is the pinned Chromium version. It also makes the archive, which took an app build while `package.sh` made it (`PANE_ENGINE_ARCHIVE`), until the same review. A stand-in checkout with stand-in `gn` and `autoninja` exercised each case without Chromium.

Engines are published as prereleases named `engine-<key:12>`, apart from the app's releases, since the update check reads `releases/latest`, which skips prereleases. `scripts/publish-engine.sh` publishes one (the user's call, after CI went red on an engine no one had published; archiving, uploading, and adding its TSV line had been three steps by hand). It archives the engine unless `packaging/release` holds its archive, publishes it as the prerelease, never the latest (`--latest=false`), tagged at the commit that last changed the engine's sources, which must be on GitHub first, and checks GitHub's digest of the upload against the archive's SHA-256; it uploads PaneCore's symbols beside it (ADR 0047). Only then does it overwrite the TSV's line, for the caller to commit, so the TSV never names an engine CI cannot fetch. Run for an engine the TSV names, it changes nothing (`chromium/UPGRADING.md`, step 6).

The first published is `engine-0d0a01f8c703` (PaneCore 157.0.8103.15, 164 MB), the engine of the native app on `main`. No engine before it was published, each having changed again first; `4c2b8172f926`, archived locally after an engine change, never was. With the Chromium checkout moved aside, the app was fetched, verified, built from scratch, and packaged in 21 s, and passed `smoke`.

**CI.** CI packages the app from the engine archive its engine sources name and never builds Chromium, which takes hours and some 100 GB; engines are built on a developer's Mac. The Release workflow (`release.yml`) checks the tag, fetches the engine, runs `scripts/dist.sh`, attests the dmg, and publishes it (ADR 0051). The repo's other gates run in `gates.yml`, on a Linux runner: ESLint, Biome (`ci`), the scenario runner's typecheck, knip, and `scripts/check-os-flags.sh` (ADR 0124), on pushes to `main` and every pull request. Biome checks every tracked file, so no paths filter fits it. Electron's binary is not downloaded, since no gate runs the migration scenario.

What needs a Chromium checkout runs on the developer's Mac before each push and tag, never in CI (AGENTS.md): `pane_unittests`, `gn check` for the Mac and Windows, Windows' compile of the shared code (`scripts/compile-windows.sh`), `clang-format`, and the scenarios a change touches. Chromium's build treats every warning in `//pane` as an error.

Until the move to Views, CI built the Swift app too. The App workflow (`.github/workflows/app.yml`, with its composite action `.github/actions/setup-app-build`, which installed XcodeGen, pinned by its release zip's SHA-256, and fetched the engine, cached by key) ran PaneKit's tests, built and packaged the app on pushes and pull requests that touched it, and from 0.13.0 ran PaneKit's tests under the Thread and Address Sanitizers, built the package with warnings as errors, and launched it through ten scenarios (`smoke`, `hosted`, `quiet`, `navigation`, `profiles-isolation`, `restore`, `open-urls`, `security`, `crlset`, and `files-encrypted`). It went when `main` became the Views line (the user's D1, 2026-11-08), whose every UI commit changes the engine key, so CI could build no app on it; `release.yml` kept PaneKit's sanitized and strict runs until PaneKit went with the cutover to Views (ADR 0124).

The runner is GitHub's `xcode-27` image (macOS 27 and Xcode 27, in preview), whose tools packaging runs: `actool` for the icon, `codesign`, `hdiutil`, and dmgbuild. actionlint does not know the preview label yet, so `.github/actionlint.yaml` names it; if GitHub renames the label when the image leaves preview, both change.

What CI runs is pinned. Every action is pinned by commit, its version beside it, and Dependabot bumps them, and the scenario runner's packages, each week in one pull request per ecosystem (`.github/dependabot.yml`). Only a tag on `main` publishes: `release.yml` fetches the whole history and refuses a tag whose commit is not on it, since every Pane's update check offers the latest release at once. A tag on `swift` published too while the Swift line shipped its fixes from there, until 0.20.0 (ADR 0124, D1).

A missing engine fails its own step. `main`'s first native run failed on a missing PaneCore, its reason far up the log: the setup action wrote `fetch-engine.sh`'s output within `echo`'s arguments, so an unpublished engine left the fetch green and `PANE_ENGINE_OUT` empty. The fetch now fails its own step, and its message names the `engine-<key:12>` prerelease to publish and the script that publishes it.

Before they ran on GitHub, the workflows were checked locally. actionlint with shellcheck passes. Every step of the app's passed in a fresh clone with no Chromium checkout, on an engine served from a local folder laid out as GitHub serves release assets. On GitHub, `main`'s first green run took 3 min 37 s.
