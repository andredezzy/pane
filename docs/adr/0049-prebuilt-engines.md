# Prebuilt engines are matched by key and published as prereleases, and CI builds the app on them and never builds Chromium

The app builds on a prebuilt engine, found by a key of the engine's sources, so CI, releases, and a Mac without a Chromium checkout build Pane without building Chromium. The model is Ardia's, an Arc-like Chromium browser for the Mac. `engine/scripts/engine-key.sh` hashes the git trees of what the engine is built from: `engine/CHROMIUM_VERSION`, `engine/args`, `engine/patches`, and `engine/pane` (`//pane`). Ardia hashes its whole `engine/` tree; Pane's also holds its scripts, which do not change the engine. A checkout whose engine sources have uncommitted changes has no key. `engine/prebuilt-engines.tsv` names the key of the engine at that commit and the archive's SHA-256, and `engine/scripts/fetch-engine.sh` downloads and verifies it from the `engine-<key:12>` release. It was a table of every key until the review of 0.18.0: HEAD read only its key's line, a tag reads its own tree's, and the release's name follows from the key, so one overwritten line does. The archive, `PaneCore-<chromium>-<key:12>.zip`, is the engine's bundle, stripped, with `PaneCore.framework` at its top for the linker, so a fetched engine stands in for `out/Release` as `PANE_ENGINE_OUT`.

An archive is the engine built from its key's sources. `engine/scripts/package.sh` once named an archive by the checkout's key and checked only the bundle's Chromium version, so an engine built before the last `//pane` commit, or with other patches applied, was archived as the current engine. Now `engine/scripts/build.sh` writes the key of what it built into `out/<Config>/pane-engine.key` after each successful build of `chrome`: the working tree's key (`engine-key.sh --worktree`), which equals HEAD's once those sources are committed as built. It records none when the checkout is not at `CHROMIUM_VERSION`, the applied patches are not the series (`apply-patches.sh --check`), `src/pane` links to another clone, or the sources changed during the build. `publish-engine.sh` refuses an engine with no record or another key, and checks the bundle is the pinned Chromium version. It also makes the archive, which took an app build while `package.sh` made it (`PANE_ENGINE_ARCHIVE`), until the same review. A stand-in checkout with stand-in `gn` and `autoninja` exercised each case without Chromium.

Engines are published as prereleases named `engine-<key:12>`, apart from the app's releases, since the update check reads `releases/latest`, which skips prereleases. One engine serves every app release until the engine changes. `engine/scripts/publish-engine.sh` publishes one (the user's call, after CI went red on an engine no one had published; archiving, uploading, and adding its TSV line had been three steps by hand). It archives the engine unless `app/release` holds its archive, publishes it as the prerelease, never the latest (`--latest=false`), tagged at the commit that last changed the engine's sources, which must be on GitHub first, and checks GitHub's digest of the upload against the archive's SHA-256; it uploads PaneCore's symbols beside it (ADR 0047). Only then does it overwrite the TSV's line, for the caller to commit, so the TSV never names an engine CI cannot fetch. Run for an engine the TSV names, it changes nothing (`engine/UPGRADING.md`, step 6).

The first published is `engine-0d0a01f8c703` (PaneCore 157.0.8103.15, 164 MB), the engine of the native app on `main`. No engine before it was published, each having changed again first; `4c2b8172f926`, archived locally after an engine change, never was. With the Chromium checkout moved aside, the app was fetched, verified, built from scratch, and packaged in 21 s, and passed `smoke`.

**CI.** CI builds and packages the app on the prebuilt engine its engine sources name and never builds Chromium, which takes hours and some 100 GB; engine builds stay on a developer's Mac. The App workflow (`.github/workflows/app.yml`) runs PaneKit's tests, takes the engine key, fetches the engine by it (cached by key), and runs `engine/scripts/package.sh`, on pushes to `main` and pull requests that touch `app/`, `engine/`, `third_party/`, `tests/`, `package.json`, `bun.lock`, or the workflow and its setup. The Release workflow (`release.yml`) builds the dmg the same way (ADR 0051). Both share one composite action, `.github/actions/setup-app-build`, which installs XcodeGen and fetches the engine.

The runner is GitHub's `xcode-27` image (macOS 27 and Xcode 27, in preview), the toolchain the app is built with. `macos-26` would default to Xcode 26.6, which the app has never been built with. actionlint does not know the preview label yet, so `.github/actionlint.yaml` names it; if GitHub renames the label when the image leaves preview, both change.

What CI runs is pinned. XcodeGen is its 2.46.0 release zip, checked by SHA-256 as `dist.sh` checks dmgbuild, so two builds of one tag generate the same project; it had been Homebrew's latest. Every action is pinned by commit, its version beside it, and Dependabot bumps them, and the scenario runner's packages, each week in one pull request per ecosystem (`.github/dependabot.yml`). Only a tag on `main` publishes: `release.yml` fetches the whole history and refuses a tag whose commit is not on `main`, since every Pane's update check offers the latest release at once.

A missing engine fails its own step. `main`'s first native run failed on a missing PaneCore, its reason far up the log: the setup action wrote `fetch-engine.sh`'s output within `echo`'s arguments, so an unpublished engine left the fetch green and `PANE_ENGINE_OUT` empty. The fetch now fails its own step, and its message names the `engine-<key:12>` prerelease to publish and the script that publishes it.

Since 0.13.0 the App workflow also launches what it builds, as Chromium's and Brave's CI test theirs: PaneKit's tests run again under the Thread and Address Sanitizers, the package builds with warnings as errors, and the packaged app runs the scenarios that need nothing beyond the runner's own fixtures (`smoke`, `hosted`, `quiet`, `navigation`, `profiles-isolation`, `restore`, `open-urls`, `security`, `crlset`, and `files-encrypted`), keeping their evidence for 7 days when one fails. Before, nothing launched the app in CI.

The repo's other gates run in `gates.yml`, on a Linux runner: ESLint, Biome (`ci`), the scenario runner's typecheck, and knip, on pushes to `main` and every pull request. Biome checks every tracked file, so no paths filter fits it. Electron's binary is not downloaded, since no gate runs the migration scenario.

Before they ran on GitHub, the workflows were checked locally. actionlint 1.7.9 with shellcheck passes. Every step of the app's passed in a fresh clone with no Chromium checkout, on an engine served from a local folder laid out as GitHub serves release assets. The new `run:` steps ran with GitHub's env files emulated: the XcodeGen install with the right and a wrong SHA-256, and the main check on `main`'s commit and on that of `native-shell`, the native app's branch then. On GitHub, `main`'s first green run took 3 min 37 s.
