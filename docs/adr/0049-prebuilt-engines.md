# Prebuilt engines are matched by key and published as prereleases

The app builds on a prebuilt engine, found by a key of the engine's sources, so CI, releases, and a Mac without a Chromium checkout build Pane without building Chromium. The model is Ardia's, an Arc-like Chromium browser for the Mac. `engine/scripts/engine-key.sh` hashes the git trees of what the engine is built from: `engine/CHROMIUM_VERSION`, `engine/args`, `engine/patches`, and `engine/pane` (`//pane`). Ardia hashes its whole `engine/` tree; Pane's also holds its scripts, which do not change the engine. A checkout whose engine sources have uncommitted changes has no key. `engine/prebuilt-engines.tsv` names, per key, the GitHub release that carries the engine and the archive's SHA-256, and `engine/scripts/fetch-engine.sh` downloads and verifies it. The archive, `PaneCore-<chromium>-<key:12>.zip`, is the engine's bundle, stripped, with `PaneCore.framework` at its top for the linker, so a fetched engine stands in for `out/Release` as `PANE_ENGINE_OUT`.

An archive is the engine built from its key's sources. `engine/scripts/package.sh` once named an archive by the checkout's key and checked only the bundle's Chromium version, so an engine built before the last `//pane` commit, or with other patches applied, was archived as the current engine. Now `engine/scripts/build.sh` writes the key of what it built into `out/<Config>/pane-engine.key` after each successful build of `chrome`: the working tree's key (`engine-key.sh --worktree`), which equals HEAD's once those sources are committed as built. It records none when the checkout is not at `CHROMIUM_VERSION`, the applied patches are not the series (`apply-patches.sh --check`), `src/pane` links to another clone, or the sources changed during the build. `PANE_ENGINE_ARCHIVE=1 package.sh` refuses an engine with no record or another key, before it builds the app, and checks the bundle is the pinned Chromium version. A stand-in checkout with stand-in `gn` and `autoninja` exercised each case without Chromium.

Engines are published as prereleases named `engine-<key:12>`, apart from the app's releases, since the update check reads `releases/latest`, which skips prereleases. One engine serves every app release until the engine changes. `engine/scripts/publish-engine.sh` publishes one (the user's call, after CI went red on an engine no one had published; archiving, uploading, and adding its TSV line had been three steps by hand). It archives the engine unless `app/release` holds its archive, publishes it as the prerelease, never the latest (`--latest=false`), tagged at the commit that last changed the engine's sources, which must be on GitHub first, and checks GitHub's digest of the upload against the archive's SHA-256. Only then does it add the TSV line, for the caller to commit, so the TSV never names an engine CI cannot fetch. Run for an engine the TSV names, it changes nothing (`engine/UPGRADING.md`, step 6).

The first published is `engine-0d0a01f8c703` (PaneCore 157.0.8103.15, 164 MB), the engine of the native app on `main`. No engine before it was published, each having changed again first; `4c2b8172f926`, archived locally after an engine change, never was. With the Chromium checkout moved aside, the app was fetched, verified, built from scratch, and packaged in 21 s, and passed `smoke`.
