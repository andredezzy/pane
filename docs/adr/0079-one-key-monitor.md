# The overlay on top takes a key first, and Chrome's order decides the rest

The overlay on top answers a key before anything under it, and the rest of a key's way is Chrome's: the focused view, the page first or the app first, then the window's accelerators and the menu bar's. Pane has no key monitor of its own: Views and Chrome's own hooks give each layer its turn.

- **The overlay on top holds the keys** while it shows, its Esc and Return its own: the PIN screen (digits, Delete, Esc, Return; ⌘Q passes, ADR 0042), Quit Pane? (ADR 0053), and the App icon picker (ADR 0089). A page's dialog and the extensions menu stand aside for the PIN screen.
- **A page's dialog takes Esc and Return** ahead of whatever has the keys, the address included, from a handler on the window's root view, since on the Mac Views hands a key to the focused view before the FocusManager's accelerators, and the address takes Esc and Return itself. It stands aside while the switcher, Quit Pane?, or the App icon picker shows over it (ADR 0021).
- **The switcher keeps the focus where it was**: its Esc and Ctrl's release come from the page through `Window::PreHandleKeyboardEvent` and from Views through a handler ahead of the focused view (`Window::SwitcherKeys`).
- **An extension's shortcut runs from the window** ahead of the page (`PreHandleKeyboardEvent`) and ahead of a view of Pane's (`ExtensionKeys`, the address being edited), never one of the command table's keys. While Chrome's shortcuts page records one, the page has every key first, the window's reserved ones too (ADR 0098).
- **The command table** (`pane/ui/app/commands.cc`) is the window's FocusManager's accelerators and the menu bar's key equivalents, and page first or app first is `PreHandleKeyboardEvent`, as Chrome reserves its keys (ADR 0019).

Before, the PIN screen's, Quit Pane?'s, the extensions', and the switcher's key monitors in the Swift app each decided alone, in an order AppKit does not document. The Swift app then had one monitor (`KeyRouter`) that offered each key to the overlays that showed in the order they were drawn, topmost first, as a pure function of what showed (PaneKit's `KeyRouting`). The Views app keeps that order without a monitor, and `KeyRouting`'s tests went with PaneKit (ADR 0098).

`key-precedence`, where the run lets Pane take the front (ADR 0012), opens the extensions menu and Quit Pane? over it, and presses Esc twice. Before, one Esc closed the menu hidden under the panel and Quit Pane? stayed; now Quit Pane? goes first, then the menu. The menu can only open first: with Quit Pane? up, a press on the puzzle lands on its scrim, which closes it and opens nothing under it. It also checks Quit Pane? over the App icon picker. `shortcuts`, `views-keys`, and the command table's tests (`pane/ui/app/commands_unittest.cc`) check the rest of the way.
