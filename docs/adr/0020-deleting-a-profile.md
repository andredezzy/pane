# Deleting a profile is durable before it completes, and asks no page

> **Refined by [ADR 0113](0113-profile-data-encrypted-under-a-key-the-pin-releases.md)** — a delete cut short is finished when the data volume next opens, no longer before the engine starts — **and by [ADR 0116](0116-pane-locks-while-open.md)**: a lock waits for a delete under way, and its folder goes at the next open.

A profile's delete completes only once Chrome has marked the profile for deletion, it is recorded on disk until then, and no page of the profile can hold it back, so a quit, a crash, or a page never leaves a deleted profile's data behind. `deleteContext:completion:` calls back from `ProfileManagerObserver::OnProfileMarkedForPermanentDeletion`, not when the request is made: Chrome first closes the profile's browsers, asynchronously, and a quit before that point used to leave the profile and its data in place. Chrome then removes the profile's link under `Engine/`, and Pane its folder in the data volume (`DataVault.remove(profile:)`).

The app removes the profile from its model at once and lists it in `deletions.json` (PaneKit `ProfileDeletions`) until the engine confirms. A delete cut short by a quit, a crash, a lock, or a context that would not open is finished at the next open of the data volume, a launch's or an unlock's, once it is mounted and before any profile opens: `ProfileDeletions.purge`, from `DataVault`, removes the profile's links (ADR 0006), any plain folder an earlier Pane left, and its folder in the volume. An id that is not one folder name is dropped, never followed. The panic wipe erases the file with the rest (ADR 0042). A profile not opened this session has its context opened first, so the engine data of earlier sessions goes too.

Deleting asks no page (B4 of the engine review, 2026-10-28). Chrome's deletion closes the profile's Browsers with beforeunload, and a page answering "Stay" cancelled it, left the profile loaded with no context, and withheld the completion until quit. `deleteContext` now closes every page of the profile, in every window, without beforeunload, before Chrome's sequence. Today's app does not reach the old failure: it releases every page it knows before deleting, and a page it does not know has no delegate, so its beforeunload is accepted unasked. `profile-lifecycle` still arms a page with beforeunload before deleting its profile, and checks that nothing asked and the engine confirmed.

A context that will not open fails its callers (arch B2 and safety B10, 2026-10-27). `openContext`'s failure dropped the waiters with a log line: the selected tab had no page and no sad tab, and a deleted profile stayed "deleting" with its engine data on disk. `withContext` now hands its callers nil. The tab shows the sad tab, whose Reload selects it again and so retries the open; a tab opened in the background is marked the same; and the delete stops waiting, leaving its folder to the next launch. `profile-lifecycle` opens a profile the engine refuses (an id with a slash): its tab shows the sad tab, and its delete leaves nothing pending. It also finishes, at a relaunch, a delete that `deletions.json` still lists. The same work found that `openContext` never called back for a 300-character id (too long a path). Profile ids are UUIDs, so nothing reached it, and the engine now answers every open (ADR 0017).
