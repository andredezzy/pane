# A profile can keep no history: its pages, their icons, and its downloads, and turning it off clears what it kept

The user's request (2026-11-04): each profile chooses whether it saves its history. Aside and Chrome have no such control, only Chrome's `SavingBrowserHistoryDisabled` policy, so Firefox's "Remember browsing and download history" is the reference, and the user chose what it keeps out: pages and downloads, over pages alone.

Save history is a switch in the profile sheet (ADR 0120), on by default. `BrowserProfile.savesHistory` holds the choice, and a profile from before it, which has none in its file, kept its history and still does.

What off keeps out, through `PaneBrowserContext.savesHistory`, kept in the profile's prefs:

- **The pages it visits and the visited-link colours drawn from them:** Chrome's own `history.saving_disabled`, the policy's pref. The policy leaves explicit access to history open, so `chrome.history.addUrl` would still write: patch 0009 makes it succeed and keep nothing.
- **Their icons:** `ContentFaviconDriver::IsOffTheRecord` answers yes (patch 0009), since the icon's mapping names the page it was found on. The page still shows its icon.
- **Its downloads:** `DownloadHistory` records none (patch 0009), extensions' included. The file still downloads, and the download still shows while Pane runs. Chrome adds a download to History once it is done, but for a page being saved, whose row is written as it begins and which a clear skips while in progress: that row goes at its next update.
- **What Chrome learns from its visits:** the sites' engagement scores and the media engagement counts, whose keys in `Preferences` name each site, and the loading predictor's hosts and origins (`Network Action Predictor`). The policy touches none of them, and a clear of history alone left the scores, so patch 0009 keeps each off, a media session opened before the switch included, and the clear takes Chrome's site usage data too. Looking for each visit's host in every file of the profile found them (2026-11-05), after the first version had shipped checking only the `History` and `Favicons` databases.

- **A running download:** Chrome caches each one on disk while it runs, with its URL, page, and path, in `shared_proto_db`'s leveldb log, which a deletion does not rewrite, so a clear and a relaunch left the page named there. Off, a new download skips that cache (patch 0009), so a crash loses the offer to resume it, which is the row off keeps out; on, it stays, since it is what brings an interrupted download back after a crash, and `History` has no row until it ends. Each open of a profile that is off removes the log first (`DataVolume.prepare`), which takes what it ran while it was on, and what an earlier engine left. A profile turned off while open keeps those bytes until then: they are in the encrypted volume, marked deleted, and nothing but this log's format reads them.

The tabs stay: they are the profile, not its history, and they come back after a quit. So do its cookies and site data (`Cookies`, `Cache`, `Code Cache`, `Local Storage`, `Session Storage`), and a tab still goes back and forward within itself. Those name the sites too, the HTTP cache each resource's whole URL: they are what the sites themselves stored and what a page needs to load fast, as Chrome's Clear browsing data and Firefox's choice treat them. All of it is in the encrypted volume (ADR 0113).

Turning it off clears what the profile kept, through `clearHistory`: Chrome's Clear browsing data, with Browsing history and Download history. As there, an open tab keeps its page and loses its back and forward list. Cookies stay, so the profile stays signed in. Save says what it does: "Keeps no pages or downloads. Saving clears what it kept." appears only on a profile that kept its history until this edit, since a new one, or one already off, has nothing to clear.

A closed profile turned off opens to clear, at once, as the sheet said it would, and closes again once it has, unless something came to use it meanwhile. Turned on, it waits to open. The profile's opening makes the model and the engine agree before any of its pages load (`BrowserController.applyHistory`). The engine's pref is the choice it last had, written a few seconds after the change, and it cannot say whether the clear finished, so the model owes the clear itself: `BrowserProfile.clearsHistory` turns on with the choice, in the same save, and off 15 s after the engine says the clear is done, since it says so before its 10-second commit reaches the disk (a crash in that gap lost the deletion, `profile-history` found). A lock or a quit before then, or a crash, clears at the next open, whichever of the two landed. Off in the model with the pref on also clears, for a file from before `clearsHistory`; so a new profile with history off runs one clear as it first opens, of nothing.

Rejected:

- **Pages alone, the policy as it stands.** The download list and the icons' database would still name where the profile went.
- **An off-the-record profile.** It keeps no cookies either, so it would never stay signed in, which is what a profile is for.
- **Clearing only at the next open.** What Save said was cleared would stay on disk until then.
- **Keeping the tab's back and forward list through a clear.** That would be a Pane of its own over Chrome's remover, and those entries are part of what the profile kept.

Checked by `tests/scenarios/profile-history.ts`, against the engine's own `History` and `Favicons` databases and, a host of its own to each visit, every file of the profile but its site data: on, 2 pages, 1 icon, 1 download, and the records by site; off from the start, none, the page's icon showing and the file downloaded; turned off, all gone, the cookie and the tab still there, and nothing new after, nor after the quit that closes its pages; turned on, pages again; `chrome.history.addUrl` keeping a page only where history is on; the choice after a quit; a closed profile clearing and closing again; a crash right after the Save made up as the profile opens (the engine's trace shows `setSavesHistory` at that open); and a clear still owed with the pref already off, which runs at the open (`clearHistory` in the trace). `ProfileDraftTests`, `BrowserModelTests`, and `PersistenceTests` check the choice's way through the form, the model, and the file.
