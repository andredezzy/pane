# Every Chrome dialog, bubble, and menu of a tab is a request the app answers: a page's dialogs drawn in the window, file choosers and printing in the system's panels

Every dialog, bubble, and menu Chrome would show for a Pane tab reaches the app as a request object, and the app answers it: in host mode Chrome shows no UI of its own (ADR 0004), so the app decides how each request looks. The requests are declared in `engine/pane/public/PaneDialogs.h`: JavaScript dialogs (beforeunload and form resubmission among them), permission requests, HTTP and proxy authentication, context menus, file choosers, external protocols, and unresponsive pages. Each reaches the app through a delegate method and is answered once. The engine withdraws a request (`didDismissRequest:`) when Chrome takes it back, and when its page goes (ADR 0017). The few surfaces that stay Chrome's are ADR 0022's.

The app shows the requests one at a time, and only for the selected tab, as Chrome's tab-modal dialogs do (`app/Pane/Browser/DialogPresenter.swift`): switching tabs puts a dialog back in line, and behind the PIN lock they wait (ADR 0042). A lock while Pane is open closes every page, which withdraws its requests (ADR 0116).

**The seams.** Chrome's UI reaches the app through the hooks of `engine/patches/0004-pane-ui-hooks.patch`, declared in `engine/pane/browser/ui/ui_hooks.h`: `CreatePermissionPrompt`, `LoginHandler::Create`, `ExternalProtocolHandler::RunExternalProtocolDialog`, DevTools docking in `DevToolsWindow` (ADR 0024), `PrintViewManagerBase::ScriptedPrint` for the app's print callback, and `chrome::ShowDeviceChooserDialog`. JavaScript dialogs, the context menu, unresponsive pages, form resubmission, and screen-capture requests need no patch: they are `WebContentsDelegate` methods, which `HostedWebContentsDelegate` overrides. File dialogs go through `ui::SelectFileDialog::SetFactory`, which catches every file dialog Chrome opens for a window: file inputs, File System Access pickers, and Save As.

Ardia's hooks (task 3.2) were weighed against these seams. `chromium-password-bubble-hook` and `chromium-autofill-address-bubble-window` are not needed, with the password manager and autofill off, and neither is `chromium-cast-dialog-hook`, with the Media Router off (ADR 0022). `chromium-device-chooser-hook` is adapted as `g_pane_device_chooser`, which declines. `chromium-side-panel-hook` was left for extension side panels, which never came: Pane's Browsers have no side panel UI (patch 0003). The `chromium-devtools-*` seam gives way to Pane's own docking hooks, which also cover undocked DevTools.

**A page's dialogs are drawn in the window.** They are SwiftUI views in the app's window, not the `NSAlert` sheets they began as, because a sheet held the main thread, Chromium's UI thread, some 280 ms as it attached, and a dialog in the window shows within a few milliseconds of its request (P1 of the architecture review of 2026-10-28). They are JavaScript alert, confirm, and prompt, Leave and Reload site, form resubmission, permissions, HTTP and proxy sign-in, opening another app, and the unresponsive page. `DialogView` (`app/Pane/Views/DialogView.swift`) draws them as Paper's 04.15 to 04.23 draw those sheets, light and dark: 260 points wide, the title and the message at 13, the fields, then 28-point capsule buttons, the default blue (two side by side, the default on the right; three stacked, the default on top); the gray panel at 95% with a hairline edge and its 0 16 48 shadow. It sits centered on the window, its top at three eighths of its height (Paper's 300 of 800), raised to fit; a long message scrolls. The corners are `Squircle`s on the design's radius scale (DESIGN.md › Shape, ADR 0057): 29 for the panel, 7 for a field. The font is the system's in place of Paper's Inter, as everywhere in the app.

A 4 ms timer on the main thread measured both, over `dialog-alert`, `dialog-confirm`, `dialog-prompt`, and `permission-prompt`: `beginSheetModal` held the thread 270 to 284 ms, and its largest gap after a request was 278 to 317 ms. The dialog is now in the view tree 2 to 6 ms after the request; the largest gap in the next 250 ms is 6 to 12 ms, and 24 to 32 ms when a prompt's field takes the keyboard (AppKit's text field setup, which the sheet also did inside its 280 ms). Later gaps in those runs line up with the scenario's own accessibility reads.

Esc dismisses, as Chrome's dialogs do (Cancel, Wait, and a permission's dismissal), and Return presses the default, both through the one key monitor (ADR 0079). The sheet gave a permission no way to be dismissed: Esc left it open. Other keys never reach the page under a dialog, and a field keeps its typing. The page under it takes no click; the sidebar and the toolbar still work, as with Chrome's tab-modal dialogs. A field that took the keyboard gives it back to the page. The fields are AppKit's (`NSTextField` in the SwiftUI dialog), read as the dialog answers, as the alert's were, so a value set through accessibility (VoiceOver, Voice Control, the scenarios' CUA) counts; a SwiftUI field took only typed text.

**File choosers and printing stay the system's panels.** A file chooser opens the system's open or save panel. Printing goes straight to the system print panel, from ⌘P and from a page's `window.print()`, and never to Chrome's print preview: the engine starts Chrome with `--disable-print-preview` (`engine/pane/browser/browser_application.mm`), so printing shows the Mac's own panel and no Chrome UI. The engine tells the app as a page starts printing (`webContentsWillPrint:`, through the hook on `ScriptedPrint`), which only the scenarios read. Behind the PIN lock the menu's Print… does not run (ADR 0042).

How it is checked:

- Each kind of request has its scenario: `dialog-alert`, `dialog-confirm`, `dialog-prompt`, `dialog-beforeunload`, `dialog-form-resubmission`, `permission-prompt`, `http-auth`, `proxy-auth`, `context-menu`, `file-chooser`, `external-protocol`, and `hung-renderer`. `dialog-tab-closed` checks that a pending dialog goes with its tab.
- `permission-prompt` checks that Esc leaves the site free to ask again, which failed with the sheet; `dialog-confirm` checks Return and Esc. `http-auth` measures the dialog's fields (`dialogFieldWidths`): 222 points each.
- `print` opens the panel from `window.print()` and from ⌘P and cancels it, and the page goes on.
