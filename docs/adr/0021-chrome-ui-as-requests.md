# Every Chrome dialog, bubble, and menu of a tab is a request the app answers: a page's dialogs drawn in the window, file choosers and printing in the system's panels

> **On the Views line** (`docs/plans/views-migration.md`, What Chrome asks for): no request objects. Chrome's hooks call Pane's Views UI directly (`pane/ui/dialogs`): the JavaScript dialogs, Leave and Reload site, and form resubmission through `HostedWebContentsDelegate`'s dialog manager, sign-in through `pane::ContentBrowserClient::CreateHttpAuthCoordinator` (a `LoginTabHelper` and a `LoginHandler` of Pane's, as Chromium's own browser test injects them), so patch 0004's `login_handler_views.cc` hunk is gone; another app through the same hook; the hung page through the delegate. Each is one `PageDialog` on the alert's card, shown by `PageDialogs` one at a time, the selected tab's alone, behind the Lock none, as `DialogPresenter` did, and timed from the hook to its frame ("Page dialog", "Permission prompt"). A permission request still comes through `set_view_factory_for_testing`, now installed by the Views controller: Chromium 158 has no production seam for it, since `PermissionPrompt::Create` asks `PermissionsClient::CreatePrompt`, whose one instance is Chrome's own `ChromePermissionsClient` (a private constructor, made in `BrowserProcessImpl`'s), which makes only Chrome's chip and bubble. Esc and Return reach the dialog ahead of whatever has the window's keys, the address included, as the key monitor gave them. File choosers are Chrome's stock panels (U2), sheets on the window; printing is unchanged; Chrome's own tab-modal dialogs show over the content area, the window's one `WebContentsModalDialogHost` for every tab, as `WebUIBrowserWindow`'s.

> **On the Views line** (`docs/plans/views-migration.md`, What Chrome asks for, second half): the page's context menu is no request: `HostedWebContentsDelegate::HandleContextMenu` hands it to the window, which builds Chrome's own `RenderViewContextMenu` (U2), the Mac's NSMenu, and takes off its model what Pane can't support before it shows (`pane/ui/page/page_context_menu`, ADR 0058); `dialogs.mm`, `dialogs_internal.h`, and `PaneDialogs.h` are gone.

Every dialog, bubble, and menu Chrome would show for a Pane tab reaches the app as a request object, and the app answers it: in host mode Chrome shows no UI of its own (ADR 0004), so the app decides how each request looks. The requests are declared in `pane/public/PaneDialogs.h`: JavaScript dialogs (beforeunload and form resubmission among them), permission requests, HTTP and proxy authentication, context menus, file choosers, external protocols, and unresponsive pages. Each reaches the app through a delegate method and is answered once. The engine withdraws a request (`didDismissRequest:`) when Chrome takes it back, and when its page goes (ADR 0017). The few surfaces that stay Chrome's are ADR 0022's.

The app shows the requests one at a time, and only for the selected tab, as Chrome's tab-modal dialogs do (`app/Pane/Browser/DialogPresenter.swift`): switching tabs puts a dialog back in line, and behind the PIN lock they wait (ADR 0042). A lock while Pane is open closes every page, which withdraws its requests (ADR 0116).

**The seams.** Chrome's UI reaches the app through the hooks of `chromium/patches/0004-pane-ui-hooks.patch`, declared in `pane/browser/ui/ui_hooks.h`: `LoginHandler::Create`, and `ExternalProtocolHandler::RunExternalProtocolDialog`. DevTools docking goes through a controller of Pane's (ADR 0024), and, until the same review, `chrome::ShowDeviceChooserDialog` (ADR 0022). The print callback's hook went in the review of 0.18.0, under ADR 0004's rule: only the scenarios read it, and `print` checks the panel itself. A permission request needs none, since the review of 0.18.0: `TabBridge` gives each tab's `PermissionRequestManager` the app's prompt (`set_view_factory_for_testing`, under ADR 0004's rule: a test-named API that goes away is a compile error at an upgrade, as a conflict would be). JavaScript dialogs, the context menu, unresponsive pages, form resubmission, and screen-capture requests need no patch either: they are `WebContentsDelegate` methods, which `HostedWebContentsDelegate` overrides. File dialogs go through `ui::SelectFileDialog::SetFactory`, which catches every file dialog Chrome opens for a window: file inputs, File System Access pickers, and Save As.

Ardia's hooks were weighed against these seams. `chromium-password-bubble-hook` and `chromium-autofill-address-bubble-window` are not needed, with the password manager and autofill off, and neither is `chromium-cast-dialog-hook`, with the Media Router off (ADR 0022). `chromium-device-chooser-hook` was adapted as `g_pane_device_chooser`, which declined, until content settings took that over (ADR 0022). `chromium-side-panel-hook` was left for extension side panels, which never came: Pane's Browsers have no side panel UI (patch 0003). The `chromium-devtools-*` seam gives way to Pane's own controller, and undocked DevTools to a window of its own (ADR 0024).

**A page's dialogs are drawn in the window.** They are SwiftUI views in the app's window, not the `NSAlert` sheets they began as, because a sheet held the main thread, Chromium's UI thread, some 280 ms as it attached, and a dialog in the window shows within a few milliseconds of its request. They are JavaScript alert, confirm, and prompt, Leave and Reload site, form resubmission, permissions, HTTP and proxy sign-in, opening another app, and the unresponsive page. `DialogView` (`app/Pane/Views/DialogView.swift`) draws them as Paper's 04.15 to 04.23 draw those sheets, light and dark: 260 points wide, the title and the message at 13, the fields, then 28-point capsule buttons, the default blue (two side by side, the default on the right; three stacked, the default on top); the gray panel at 95% with a hairline edge and its 0 16 48 shadow. It sits centered on the window, its top at three eighths of its height (Paper's 300 of 800), raised to fit; a long message scrolls. The corners are `Squircle`s on the design's radius scale (DESIGN.md › Shape, ADR 0057): 29 for the panel, 7 for a field. The font is the system's in place of Paper's Inter, as everywhere in the app.

A 4 ms timer on the main thread measured both, over `dialogs`, and `permission-prompt`: `beginSheetModal` held the thread 270 to 284 ms, and its largest gap after a request was 278 to 317 ms. The dialog is now in the view tree 2 to 6 ms after the request; the largest gap in the next 250 ms is 6 to 12 ms, and 24 to 32 ms when a prompt's field takes the keyboard (AppKit's text field setup, which the sheet also did inside its 280 ms). Later gaps in those runs line up with the scenario's own accessibility reads. Any sheet costs that on this macOS, even an empty `NSPanel`, and neither `animationBehavior = .none` nor a shorter `animationResizeTime` or `NSWindowResizeTime` changes it.

Esc dismisses, as Chrome's dialogs do (Cancel, Wait, and a permission's dismissal), and Return presses the default, both through the one key monitor (ADR 0079). The sheet gave a permission no way to be dismissed: Esc left it open. Other keys never reach the page under a dialog, and a field keeps its typing. The page under it takes no click; the sidebar and the toolbar still work, as with Chrome's tab-modal dialogs. A field that took the keyboard gives it back to the page. The fields are AppKit's (`NSTextField` in the SwiftUI dialog), read as the dialog answers, as the alert's were, so a value set through accessibility (VoiceOver, Voice Control, the scenarios' CUA) counts; a SwiftUI field took only typed text.

**File choosers and printing stay the system's panels.** A file chooser opens the system's open or save panel. Printing goes straight to the system print panel, from ⌘P and from a page's `window.print()`, and never to Chrome's print preview: the engine starts Chrome with `--disable-print-preview` (`pane/browser/browser_application.mm`), so printing shows the Mac's own panel and no Chrome UI. Behind the PIN lock the menu's Print… does not run (ADR 0042).

How it is checked:

- Each kind of request has its scenario: `dialogs`, `permission-prompt`, `http-auth`, `proxy-auth`, `context-menu`, `file-chooser`, `external-protocol`, and `hung-renderer`. `dialog-tab-closed` checks that a pending dialog goes with its tab.
- `permission-prompt` checks that Esc leaves the site free to ask again, which failed with the sheet; `dialogs` checks Return and Esc. `http-auth` measures the dialog's fields (`dialogFieldWidths`): 222 points each.
- `print` opens the panel from `window.print()` and from ⌘P and cancels it, and the page goes on.
