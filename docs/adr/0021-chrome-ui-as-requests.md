# Every Chrome dialog of a tab is Pane's, drawn in its window through Chrome's own seams, and its menu, file choosers, and printing are Chrome's and the system's

Every dialog Chrome would show for a Pane tab is Pane's, drawn in the window (`pane/ui/dialogs`): JavaScript's alert, confirm, and prompt, Leave and Reload site, form resubmission, a site's permission request, HTTP and proxy sign-in, opening another app, and the unresponsive page. Adding an extension asks in Pane's dialog too (ADR 0056). The page's right-click menu is Chrome's own, a file chooser the system's panel, and printing the system's print panel. In host mode Chrome shows no window of its own (ADR 0004); the few surfaces that stay Chrome's are ADR 0022's.

**The seams.** Chrome's hooks call Pane's views directly, each through a seam Chromium already has where there is one (ADR 0004):

- Pane's Browsers' `WebContentsDelegate` (`HostedWebContentsDelegate`, `pane/browser/ui/web_contents_delegate.cc`) hands over the JavaScript dialogs, Leave and Reload site among them, through its dialog manager (`JavaScriptDialogs`), the form resubmission warning, the unresponsive page, and the context menu. It declines screen capture (ADR 0022).
- Sign-in goes through Pane's browser client's `CreateHttpAuthCoordinator` (`SignInCoordinator`, `pane/ui/dialogs/sign_in.h`): a `LoginTabHelper` and a `LoginHandler` of Pane's, as Chromium's own browser test injects them. Patch 0004's hunk on `login_handler_views.cc` went with it.
- A permission request comes through `PermissionRequestManager::set_view_factory_for_testing`, set on each tab's page as the app takes it in (`PermissionPrompt::Install`). Chromium 158 has no production seam for it: `PermissionPrompt::Create` asks `PermissionsClient::CreatePrompt`, whose one instance is Chrome's own `ChromePermissionsClient` (a private constructor, made in `BrowserProcessImpl`'s), which makes only Chrome's chip and bubble, anchored in a `BrowserView`. Under ADR 0004's rule a test-named API that goes away is a compile error at an upgrade, as a conflict would be.
- Opening another app goes through the one hook patch 0004 keeps for a dialog (`g_pane_external_protocol_dialog`, `pane/browser/ui/ui_hooks.h`), and adding an extension through patch 0005's (ADR 0056): Chromium has no view factory for either. Each answers "not handled", which keeps Chrome's dialog, where Pane can't ask: with no window of Pane's, or for a profile that isn't one of Pane's.
- Chrome's own tab-modal dialogs show over the content area: the window's one `WebContentsModalDialogHost` serves every tab, as `WebUIBrowserWindow`'s does (`WindowHost`, `HostedBrowserWindow::GetWebContentsModalDialogHostFor`).

**One at a time, the selected tab's.** `PageDialogs` (`pane/ui/dialogs/page_dialogs.h`) shows the dialogs one at a time, and only the selected tab's, as Chrome's tab-modal dialogs show: switching tabs puts a dialog back in line. Behind the Lock, and until the profiles have opened, they wait (ADR 0042); a lock while Pane is open closes every page, which takes its dialogs with it (ADR 0116). A dialog goes once it is answered, when Chrome takes it back, or with its page, and the next shows on the turn after, so one never takes another's place within a call (ADR 0017). A page that asks again while its dialog is up is answered as cancelled, as Chrome answers a dialog it suppresses.

**A page's dialog is drawn in the window, not a sheet.** `PageDialog` (`pane/ui/dialogs/page_dialog`) draws them as Paper's 04.15 to 04.23 and 04.29 do, light and dark, in the look of the macOS alert sheet they began as: 260 points wide, the title in bold and the message at 13, the fields, then 28-point capsule buttons, the default blue (two side by side, the default on the right; three stacked, the default on top), on a gray panel at 95% with a hairline edge and its shadow (`AlertCardLook`). It sits centered on the window, its top at three eighths of its height, raised to fit; a long message scrolls. The corners are superellipses on the design's radius scale (ADR 0057): 29 for the panel, 7 for a field. Each dialog's first frame is timed from its hook ("Page dialog" and "Permission prompt", `pane/ui/interaction_log_mac.cc`).

A sheet held the main thread, Chromium's UI thread, some 280 ms as it attached: a 4 ms timer on the main thread, over `dialogs` and `permission-prompt`, measured `beginSheetModal` holding it 270 to 284 ms, and the largest gap after a request at 278 to 317 ms, where a dialog drawn in the window was in the view tree 2 to 6 ms after its request, the largest gap in the next 250 ms 6 to 12 ms (24 to 32 ms when a prompt's field took the keyboard, AppKit's text field setup, which the sheet also did inside its 280 ms). Any sheet costs that on this macOS, even an empty `NSPanel`, and neither `animationBehavior = .none` nor a shorter `animationResizeTime` or `NSWindowResizeTime` changes it.

**Its keys.** Esc dismisses, as Chrome's dialogs do (Cancel, Wait, and a permission's dismissal, which leaves the site free to ask again), and Return presses the default, ahead of whatever has the window's keys, the address included, from a handler on the window's root view (`RootView::OverlayKey`, ADR 0079). The sheet gave a permission no way to be dismissed: Esc left it open. Other keys never reach the page under a dialog: its first field takes them as it shows, else the dialog does, and Tab goes round its fields. The page under it takes no click, and the sidebar and the toolbar still work, as with Chrome's tab-modal dialogs. Once the dialog goes, the keys go back to what had them, or to the page. The fields are Views' text fields, read as the dialog answers, as the alert's were, so a value set through accessibility (VoiceOver, Voice Control) counts, where a SwiftUI field took only typed text.

**The menu, the file panels, and printing are Chrome's and the system's** (ADR 0124, U2). The page's menu is Chrome's own `RenderViewContextMenu`, the system's menu on the Mac, with what Pane can't support taken off its model before it shows (`pane/ui/page/page_context_menu`, ADR 0096). A file chooser is Chrome's stock dialog, the system's open or save panel as a sheet on the window, for every file dialog Chrome opens: file inputs, File System Access pickers, and Save As. Printing goes straight to the system print panel, from ⌘P (`UiApp::PrintPage`) and from a page's `window.print()`, never to Chrome's print preview: the engine starts Chrome with `--disable-print-preview` (`pane/app/engine_switches.cc`). Behind the Lock Print… does not run, as no command but Quit and Check for Updates… does (ADR 0042).

**What was weighed.** Ardia's hooks, against these seams: `chromium-password-bubble-hook` and `chromium-autofill-address-bubble-window` are not needed with the password manager and autofill off, nor `chromium-cast-dialog-hook` with the Media Router off (ADR 0022). `chromium-device-chooser-hook` was adapted as `g_pane_device_chooser`, which declined, until content settings took that over (ADR 0022). `chromium-side-panel-hook` was left for extension side panels, which never came: Pane's Browsers have no side panel UI (patch 0003). The `chromium-devtools-*` seam gave way to Pane's own controller (ADR 0024). The print callback's hook went in the review of 0.18.0, under ADR 0004's rule: only the scenarios read it, and `print` checks the panel itself.

Until 0.20.0 each of these reached the Swift app as a request object of the engine's Objective-C API (`PaneDialogs.h`: the context menu and the file choosers too), answered once and withdrawn when Chrome took it back (`didDismissRequest:`), and a SwiftUI view drew the dialogs, with AppKit's text fields in them. The Views app has no request objects: Chrome's hooks call its views.

How it is checked:

- Each kind of dialog has its scenario: `dialogs`, `permission-prompt`, `http-auth`, `proxy-auth`, `external-protocol`, and `hung-renderer`; `context-menu`, `file-chooser`, and `print` check the menu and the panels. `dialog-tab-closed` checks that a pending dialog goes with its tab.
- `permission-prompt` checks that Esc leaves the site free to ask again, which failed with the sheet; `dialogs` checks Return and Esc. `http-auth` measures the dialog's fields: 222 points each.
- `print` opens the panel from `window.print()` and from ⌘P and cancels it, and the page goes on.
- `tests/rigs/views-dialogs.ts` times a dialog's and a permission prompt's first frames.
