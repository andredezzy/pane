# Every file a profile writes is encrypted under a key only Pane's processes hold

The user's requirement (2026-10-31): none of Pane's content can be seen without the PIN. ADR 0113 encrypted every profile at rest, and ADR 0116 locked Pane while open, but while Pane is unlocked the volume is mounted, and any process running as the user read the profiles' files: history, site storage, caches, preferences. ADR 0115 listed that gap. This closes it inside the engine: a process that reads files, even with Full Disk Access, finds only ciphertext, while Pane is unlocked as much as while it is locked. It reverses ADR 0113's rejection of encrypting each of Chromium's stores, which weighed a patch in every storage layer against an upgrade's cost; `docs/qa/engine-file-encryption/` has what its passes found.

Without a PIN the files are just as encrypted: the data key then opens with the Keychain's secret alone, and macOS asks the user before any other process reads that item.

## The key

- **One per profile**, HKDF-SHA256 of the data key, the profile's id as salt and `Pane engine files` as info (`model::EngineFilesKey`, `pane/model/data_key.h`), apart from the key that seals Pane's own files. Nothing writes it to disk, a command line, or an environment (`engine-keys` looks for it in every form, in `ps -E` and in every file).
- **It reaches the engine with the profile:** `pane::OpenProfile` (`pane/browser/profiles.cc`) registers it before Chromium creates the profile (`pane/encryption/engine_keys`), with the roots a profile's files live under, in each form a path reaches them (`RootsOf`, each OS's in `engine_keys_mac.cc` and `engine_keys_win.cc`): on the Mac the links, and the resolved volume, and the volume by the data directory as Pane was given it (`data_launch_mac.cc`), whose vault writes its markers there while Chromium resolves its own user data dir, so a link in the data directory's path (`/var` is `/private/var`) leaves no form unregistered; on Windows the user data dir as given and as NTFS resolves it (`base::NormalizeFilePath`: long names for short ones, junctions followed, the case on disk). The disk is read for them once per open, in the browser alone; the other processes get them with the keys, so each file's lookup stays string compares.
- **Other processes get it in shared memory**, as os_crypt_async passes its keys, never in a mojo buffer: the network service with each `NetworkContextParams`, the Storage Service before each `Bind*StorageControl`. So each gets it back after a restart, which `engine-keys` checks by killing them.
- **A protected path with no key stops the process.** Chromium deletes or razes a store that fails to open, and a crash loses nothing. So does a path that names a registered profile's folder in a form no root has (a short name, a link or junction, a `\\?\` prefix, a share): a form nothing registered is refused, never written plain. The profiles' ids stay registered past a lock's drop, as the roots do. So does a key that doesn't fit, and a plain SQLite or LevelDB file in a migrated profile.
- **It stays until the lock's detach has succeeded,** profile unloads included: stores still flush as a profile is destroyed. Before that detach, the work Chrome left in its thread pool for the profiles has run (ADR 0116): a lock that came before Chrome's startup was over had left that work held behind it, and at the startup's 3 minutes it met this record's check of a profile's file with no key, which ended Pane. The check stays. Each process then forgets every key and says how many it has left, 0, in the engine's trace (`PaneBrowserApplication.engineKeysDropped`). At quit the keys go with the processes.

## What each store gets

| Store | Treatment | Where |
|---|---|---|
| SQLite (browser, network service) | AES-256-GCM per page, in 32 reserved bytes: a random nonce, the tag, a format and key id | a VFS, `pane/encryption/sqlite_vfs.cc` |
| LevelDB (browser, Storage Service) | AES-256-CTR, a key per file; no text log; no appends to a closed file | `third_party/leveldatabase/env_chromium.cc` |
| Whole files: Preferences, Bookmarks, TransportSecurity, CacheStorage's `index.txt`, and the rest written and read whole | AES-256-GCM | `base/files/pane_file_codec.h`, through `ImportantFileWriter`, `WriteFile` (`file_util_posix.cc`, `file_util_win.cc`), `ReadFileToString` |
| Every Simple cache: HTTP, code, CacheStorage, service workers' scripts, shared dictionaries; the HTTP cache Simple on every OS (below) | Chromium's chunked AES-256-GCM-SIV, keyed entry names | `net/disk_cache/pane_cache_hook.h` |
| IndexedDB's blobs, the origin private file system | the same chunked format, since both are overwritten in place | `storage/browser/file_system/pane_encrypted_stream.cc` |
| Sync access handles | through the browser, as Incognito's: no renderer holds a descriptor or a key | `file_system_access_*` |
| Names | IndexedDB's default buckets by id (`WebStorage/<id>/IndexedDB`); CacheStorage's folders by an HMAC under the profile's key | `file_path_util.cc`, `cache_storage_manager.cc` |
| GPU caches in a profile, blob storage, the Download Service, Network Persistent State, SCT reports, No-Vary-Search's files | not on disk | one condition each |
| Tab restore, Chromium's Keychain-encrypted bookmarks and sessions | off: they name what closed, or open without the PIN | `tab_restore_service_impl.cc`, `engine_switches.cc` |

`//pane/encryption` holds the formats, `core` depending on nothing but `//base` and BoringSSL so that `//sql`, LevelDB, and `//services` can use it.

## What stays plain

- **The data root:** `settings.json`, `security.json` and its copy, `migration.json`, `profiles.json` (sealed), `deletions.json`, `Pane.lock`, and the volume's image.
- **The engine's root,** which Chromium uses before the PIN: `Local State`, `Last Version`, `Variations`, `ChromeFeatureState`, its shader caches, `Safe Browsing`, the crx caches, `NativeMessagingHosts`, and the `Default` profile, holding only Chromium's defaults (ADR 0115).
- **In a profile:** `Extensions/`, installed extensions' public code; empty files and folders; and the file system's `.usage` counts, a magic and a size.

`files-encrypted` searches these too, for every value it planted.

## On Windows

The same formats and hooks, store by store, and what only Windows needs (ADR 0124; no volume there, U5):

- **No volume, no conversion.** No Pane was ever published for Windows, so every profile there starts encrypted: the conversion of an earlier Pane's profiles (`//pane/encryption:migration`) and ADR 0122's paths build on the Mac alone, and no root names a volume.
- **Pane's own data there** (W3, 2026-11-13): the data root is `%LOCALAPPDATA%\Pane`, made at launch and marked `FILE_ATTRIBUTE_NOT_CONTENT_INDEXED`, which NTFS gives what is made in it, in place of Spotlight's markers; the user data dir `User Data` in it (below), a profile at `User Data\<id>` with its caches inside (`pane/model/folder_place`: the vault's sequences, shared, over a place with no volume). The data key is sealed in `security.json` and its copy under os_crypt's DPAPI key and, with a PIN, a key the TPM holds (ADR 0113); `profiles.json` sealed under its files key. A deleted profile's folder goes once the engine has closed its files: NTFS deletes no file still open, so it is tried again for 10 s, then left to deletions.json and the next open. The vault registers its own form of the data folder as a root, as the Mac's does, so a marker it writes in a profile's folder is the profile's.
- **The engine's folder is the one chrome_elf names** (2026-11-14, `evidence/views-migration/runs/p5-w3fix-notes.md`). On Windows Chromium takes its user data dir from chrome_elf alone (`ChromeMainDelegate`'s `InitializeUserDataDir`), which reads `--user-data-dir` from the command line the process started with, never from `base::CommandLine`, where Pane's switches go, then a policy's folder, then the install mode's, `%LOCALAPPDATA%\Pane\User Data` (patch 0001). W3 named its `Engine` in `base::CommandLine` alone, so a launch with no switch on its own command line, as a shortcut, the taskbar, or another app's link starts the user's Pane, kept Chrome's whole user data in `User Data`, every file plain, its Default profile with `History`, `Login Data`, and `Web Data` among them, while the data root got no `Engine`, and the helpers were told `Engine` (`p5-w5c-notes.md`, in the test VM). Every scenario passed the switch, so none met it. Now Windows' engine folder is that very default (`model::EngineFolder`: `User Data` there, `Engine` on the Mac, unchanged), which the launch, the vault, the secret, Local State's reset, and the wipe all name through the one function; and before anything is written the launch asks chrome_elf for its folder and goes on only where it is the data's own (`data_launch_win.cc`): the user's launch gets it by default, a test copy names its own with the switch, and a launch whose command line or policy names another, or a folder chrome_elf couldn't use, exits 1, writing nothing but the empty folder the switch named, which chrome_elf makes as it reads it. Another form of the same folder goes on: its case, its 8.3 name, a junction to it (compared as NTFS resolves them, the existing part of each through `base::NormalizeFilePath`). A second launch that hands Pane a link finds it by the same folder, through `chrome.exe`'s own fast path (`chrome::GetDefaultUserDataDirectory`) or the singleton; the panic wipe's relaunch keeps the command line its launch started with; an update's relaunch is W7's, and can only start Pane on its engine folder. Rejected: Chromium's policy key, which overrides the switch and which a test copy shares with the user's Pane; a patch to chrome_elf's `User Data`; and a relaunch to add the switch, not weighed, with the default already the engine's folder.
- **A lock closes the data** once every profile has closed in the engine: with no volume to detach, every process then forgets its keys (`DataVault::Delegate::VolumeDidDetachAtLock`), and nothing another process holds open holds it up.
- **Names compare as NTFS compares them,** without case, and `/` separates as `\` does (`SameComponent`, `engine_keys_win.cc`): ASCII's case, folded by `base::EqualsCaseInsensitiveASCII`. `FilePath::CompareEqualIgnoreCase` folds all of Unicode, as NTFS does, but needs user32, which the Storage Service's sandbox there (`kService`, win32k locked down) doesn't have, and CHECKs it. A name differing only in another letter's case reads as another form, which the refusal above stops: it fails closed. The Mac compares byte for byte, as ever.
- **`WriteFile` seals a profile's file** in `file_util_win.cc` as in `file_util_posix.cc` (patch 0010); the rest of `//base`'s hooks are in files both share.
- **The HTTP cache is Simple's on every OS:** `--enable-features=DiskCacheBackendExperiment:backend/simple` (`pane/app/engine_switches.cc`). Windows' default is Blockfile (`ChooseCacheType`, `IsSimpleBackendEnabledByDefaultPlatform`) and the experiment's own default is SQL, neither of which Pane's hook reaches, so the group is spelled out. The Mac's default is Simple already. `EngineSwitchesTest.EveryLaunchCachesInSimplesFormat` reads the switches as Chromium does, and fails without the line. Every other cache asks for Simple itself, and the GPU's in a profile stay off.
- **At the engine's root**, before the PIN: the GPU's shader caches are `GrShaderCache` and `ShaderCache` there, in Blockfile's format, and Chrome writes `Last Browser`, its executable's path. A site's notification image waits in `Notification Resources` there for the 12 s the system's toast reads it (Residuals: site notifications).

## An earlier Pane's data

- **The fence comes first.** The first open with this Pane changes the volume's passphrase, before any file converts, so 0.15 to 0.17, whose engine would raze stores it can't read, say "Pane can't open your encrypted data" (Paper 07.8) and open nothing. A change is one call to APFS, so a kill leaves one passphrase or the other, and this Pane tries both.
- **Then each profile converts, in place,** the one a window waits for at once, the others behind it. The HTTP and code caches go and rebuild. Each file goes to a temporary one, is verified by decrypting it, and is renamed over the original: SQLite through `VACUUM INTO`, the rest by its own format, Simple cache entries with their names rekeyed. A kill at any point loses nothing; the next launch goes on. An empty file beside the profile, in the volume, says it is done.
- **A safety copy** of what changes, encrypted whole, comes before the first file converts. Two opens in a row that a kill ended, before any came up, restore it, once: never after one came up, which would take back what was written since, and a quit or a lock is no failure. 0.18.0 counted anything under 5 s as a failure, even past a good open, and rolled healthy profiles back unasked. A restore and a migration never share a folder, a lock's detach waits for both, and a restore that fails leaves the profile refused, tried once. From its third good open it goes, once 0.18.2's repair has read its listing.
- **The panel** is Paper 07.5's, unchanged, past a second, for a profile a window waits for.

## What 0.18.0's migration got wrong, and what 0.18.2 puts right

- **A first party's IndexedDB could move into a third party's bucket.** The migration took every default bucket by the identifier of its origin, and a partitioned storage key parses to the same origin as the first party's, so the last row in key order, a partitioned one if any, took the store. The site then read an empty store, and an embed of it read the site's. A bucket that already held a store got it nested inside. The migration now reads first parties only. **The repair** runs once per profile, before it next opens (`.files-repaired`): the safety copy's listing names the first parties that had a store, and among the partitioned buckets whose store is older than the copy, the last in key order is where it went. It moves back, nested or not. A store the first party has again keeps its place and the other stays too: nothing proves which it wants. **Where the safety copy is gone, the store stays where it is** (the user's call, 2026-11-06): nothing else proves which store moved, and a guess could hide a real one. The release's notes say so. An in-app notice would be new UI.
- **Partitioned file systems were sealed as whole files**, since only `File System` was taken for a stream, where partitioned storage writes `FileSystem`. They read as empty, with the bytes intact: the repair puts each back as a stream, its magic proving what it is.
- **Background Fetch's CacheStorage folder collided with the Cache API's**, nesting one in the other: the hash the folder is named by covers its owner's suffix, which only that hash tells.
- **One malformed store barred its whole profile**, at every launch: VACUUM reads what Chromium never touched. A store SQLite calls `CORRUPT` or `NOTADB` now goes as Chromium's raze would have taken it, with the safety copy keeping it. A bad cache entry goes too. `quick_check`, run with no callback, had been saying yes to anything; it now has to say `ok`, and a copy that fails it while its original passes is this code's failure. A disk too full for the copy still bars the profile: a message for it is new UI.
- **A file over 1 GiB in a whole file's place stopped the process at every launch** (`base::File` reads 2 GiB at most): it stays as it is, in the encrypted volume.

## What can still take a store

- **The quota database resets only when SQLite calls it malformed** (patch 0010, `quota_database.cc`): Chromium resets on any failed open, and that dooms `WebStorage`, where Pane keeps every default bucket's IndexedDB, where Chrome keeps first parties' outside it. Anything else stops the process, which loses nothing. A really malformed quota database still takes IndexedDB with it.
- **A page 1 a crash tore, with a journal to restore it, opens.** SQLite reads the header as it opens, before any playback, and that read failed the open, which reached that reset. It now comes back short, which SQLite takes for an empty header.
- **Past a playback, a WAL's page that won't authenticate is an error.** Zeros read as a malformed database, which Chromium razes.
- **Chromium's cookie key stays the one it was.** 158 made "v10" unavailable on a data directory other than Chrome's default, which sealed every cookie out of reach of the release before it (`KeychainKeyProviderUserDataDirProtection`). It guards one app's data from another copy of Chrome, which Pane's own key does already, so it's off. A session carried from an earlier Pane is what caught it, in `data-volume` then, and in `files-migration` now.
- **A kill between an append's writes leaves a stream's tail readable:** its last chunk may be marked as not the last, and a read tries both marks (`encrypted_cache_file.cc`, one more Chromium file, since a repair at open would race a writer). The mark guards only against someone who truncates the file, whom the threat model leaves out. A power cut can still tear a chunk.

## What may stay plain

`files-encrypted` still searches these for what it planted. Any addition needs its reason here.

- **The data root:** Pane's own files: `settings.json`, readable at the user's call; `security.json` and `Data.security.json`, which hold the PIN's length and the sealed key, and on Windows the TPM key's name and its sealed share; `profiles.json`, sealed; `deletions.json`, which names only ids; `Pane.lock`. The volume's image, `Data.sparsebundle`, on the Mac.
- **macOS's in the volume:** `.fseventsd/no_log` and `fseventsd-uuid`. Its log, which names files that change, is off at every mount.
- **The engine's root** (`Engine/`, on Windows `User Data\`), which Chromium uses before the PIN: `Local State` (on Windows os_crypt's key in it, under DPAPI), `Last Version`, `Variations`, `ChromeFeatureState`, and on Windows `Last Browser`; the GPU's shader caches, `GraphiteDawnCache` and `GPUPersistentCache` (ADR 0115), and on Windows `GrShaderCache` and `ShaderCache`; `Safe Browsing`, `component_crx_cache`, `extensions_crx_cache`, `Webstore Downloads`, `NativeMessagingHosts`; the `Default` profile, holding only Chromium's defaults (ADR 0115), and its caches under `~/Library/Caches`.
- **In a profile:** `Extensions/`, installed extensions' public code; empty files and folders; and the file system's `.usage` counts, a magic and a size: metadata, as a file's size is.

## Residuals

- **A process that writes.** It can change Pane's bundle, which ad-hoc signing does not guard, and steal the key at the next launch; or edit Local State. This waits for a Developer ID (ADR 0048). Nothing here depends on a feature flag or a field trial.
- **Pane's processes' memory, against Apple's inspection tools.** `lldb` is refused, and a program of the user's own gets no task port, on the browser, the network service, and the Storage Service. But `vmmap`, `heap`, `leaks`, `stringdups`, and `sample` run, since Apple's tools carry `com.apple.system-task-ports.read`: they print regions, class names, and stacks, and a value planted in the process is in none of it. The plan had required all of them to fail; measuring showed they don't, on any app, and the user chose on 2026-11-05 to go on with this recorded. `memory-guarded` checks exactly this.
- **Root and the kernel; the screen and Accessibility; Apple Events,** which TCC asks the user for.
- **What the user takes out of Pane:** downloads, print jobs, drags and the clipboard, site notifications.
- **Metadata:** file sizes and times, and the names of installed extensions' folders. Hiding those means encrypting `Extensions/`, a week more, which the plan left to the user.
- **Chromium's preference MACs in Windows' registry** (found 2026-11-14 by the user's launch's check): beside each profile's Secure Preferences, Chromium keeps an HMAC of each tracked preference in `HKCU\Software\Pane\PreferenceMACs\<profile id>` (`RegistryHashStoreContentsWin`, on Windows alone): the profiles' ids and the tracked preferences' names, an installed extension's id among them (`extensions.settings.<id>`), each value an HMAC, never a site or a value of a page. Nothing removes them with a profile or at the panic wipe, and a test copy writes the same key as the user's Pane (624 profile ids in the test VM's). Open: whether Pane removes them.
- **An attach writes.** Starting an earlier Pane on migrated data changes the image's own bands (APFS checkpoints) and its `Engine/` root, as any launch does: no file inside the volume, and not `security.json`, its copy, or `profiles.json`, whose hashes `files-migration` compares.

## What was rejected

- **Interposing file calls with dyld:** whether the hardened runtime honours it is unknown, libSystem's own calls escape it, and it has to emulate POSIX exactly.
- **A Group Container alone** (after a Developer ID): Full Disk Access still reads it.
- **Everything in memory, as Incognito:** the data would be gone at every quit.
- **A SQLCipher fork:** SQLite removed codec support, and a VFS survives upgrades. **XTS for SQLite:** no integrity, and deterministic.
- **IndexedDB's SQLite backend:** it deletes LevelDB data, and has not launched.
- **Dropping keys as each profile closes:** stores still flush as their profile is destroyed.
- **CTR for blobs and the origin private file system,** as the plan first had: an overwrite reuses its keystream.
- **Binding a stream file to its folder,** as the plan first had: it guards only against a process that writes, which is out of scope, and a rename across folders would have stopped a store.
- **Caching page 1's plaintext per file,** as the plan first had: a whole-page read and decrypt costs microseconds, and a stale copy would hide another connection's write.
- **The code cache and shared dictionaries off,** as the plan first had: through the same hook they read as ciphertext, and repeat visits keep them.
- **Resolving each root in every process** (`AddRoots` itself): the sandboxed network service and Storage Service would read the disk for it, where they may not be let; the browser resolves once per open and hands both forms over.
- **Comparing Windows' names with `FilePath::CompareEqualIgnoreCase`:** it CHECKs user32, which the Storage Service lacks there.
- **A form of a path nothing registered passed through as plain, or keyed by the id it names:** a form the registry doesn't know means its model of paths is wrong; a crash shows that, and loses nothing.
- **Windows' HTTP cache left in Blockfile's format,** or the experiment's SQL: a second hook in another backend, where Simple's is there already.

## How it is checked

- **`files-encrypted`**, on this Mac before a push or a tag (CI runs no scenarios): a rich session, with Pane open and unlocked, then every file under the profile, its caches, the data root, the home, and `$TMPDIR`: each in a format of Pane's or on the allow-list, none holding a planted value, no name giving a site away, in clear or as an unkeyed hash. The session's values read back through it all.
- **`files-encrypted`** also lists every file (`inventory.json`), for `chromium/UPGRADING.md`'s step at each new Chromium.
- **`files-migration`**, from each published build it is given (0.15.2 and 0.17.2): killed three times in its first opens, everything still there, nothing plain, and the published build on the migrated data refused, the volume's files unchanged. **`files-migration-large`**: with its panel, and six kills at random points.
- **`engine-keys`**, **`memory-guarded`**, **`volume-unindexed`** (Spotlight: `.metadata_never_index` at every mount, since `mdutil` can't tell on a volume out of the Finder).
- **On Windows** (2026-11-13), in the test VM, the x64 engine under emulation: encryption's own tests on NTFS (the roots through a junction, an 8.3 name, and another case; `\\?\` and a share refused; `WriteFile` sealing; 200 kills mid-journal and mid-WAL, nothing committed lost). `files-encrypted`'s session in a test copy, its data given once by long names and once by 8.3 names, a form's field and a download added: it read back through every store, and `files-encrypted`'s audit (`tests/lib/file-audit.ts`) over the folder, laid out as a Mac's, found 294 files, every profile file in Pane's formats, no value and no name of the site; the HTTP cache Simple and encrypted (9 files, 30 KB); a scan of the user's whole AppData for every value in UTF-8 and UTF-16LE, 11,740 files: none.
