# Pane locks while open: on command, when the Mac sleeps or locks, and after a time without use

ADR 0113 put every profile's data in an encrypted volume the PIN opens, and Pane locked only at launch: once open, the data stayed readable until Pane quit, by anyone at the Mac and by any process of the user's. The user's requirement (2026-10-31) is that none of Pane's content can be seen without the PIN, and their call, of the options drawn in Paper (06.4, 07.9), was the command, the Mac's own sleep and lock, and an idle time.

What changes:

- **Lock Pane** (⌃⌘L, the Pane menu, after Settings) locks at once; without a PIN it is greyed out.
- **Pane locks by itself** (`LockTriggers`, `pane/ui/app/lock_triggers.h`) when the screen locks (`ui::AddScreenLockCallback`), the Mac sleeps, a lid closing it too (`base::PowerMonitor`'s suspend), its displays sleep or another user takes the session (the platform's pair, which nothing in Chromium observes: `lock_triggers_mac.mm`, NSWorkspace's own notifications; `lock_triggers_win.cc`, the console display's power setting, and a session switch locking through Chromium's); and after **Lock after** (Settings, Security: 1 min, 5 min, 15 min, 1 hour, Never; 15 min by default) without use, on a 15-second tick. Pane is in use while it is in front and the computer has input, which then is Pane's (`ui::CalculateIdleTime`), and while a page plays sound or shows in picture-in-picture; behind other apps, its clock runs from when it left the front. No key or mouse monitor of its own (ADR 0079). Each calls the Lock, which keeps the order below. The Swift app's `LockController` listened for `com.apple.screenIsLocked` and read `CGEventSource`'s time since the last event.
- **The PIN screen shows in the same frame** (`UiApp::LockNow`). Behind it, the switcher, Quit Pane? (ADR 0053), and an extension's popup and menu close, every page closes, what changed is written, and the profiles leave the model; behind it no intent acts (`UiApp::InteractionAllowed`, ADR 0042). The data key leaves memory. Each profile then closes in the engine (`pane::CloseProfile`, `pane/browser/profiles.h`, from `ProfileContexts::CloseForLock`): its downloads under way stop as at a quit, the context's hold goes, every page closes without beforeunload, and the profile's Browsers close, which Pane's patch otherwise keeps open without tabs. Chrome then destroys the profile (`DestroyProfileOnBrowserClose`), which closes its databases. What Chrome would keep open past the profile goes with it (below). What Chrome left in its thread pool as the profiles were created and destroyed then runs, its startup ended first if no page has ended it, 5 s at most (`pane/browser/background_work`). Only then does the volume detach, and every process drops its engine keys once it has (ADR 0121). A profile still opening answers only the first Lock that came, so a second Lock never leaves the volume attached.
- **The PIN opens it all again**: the volume attaches, the profiles load, and the tab that showed comes back, still signed in.
- **Only the PIN screen animates** (`pane/ui/lock/lock_screen_view`), on the compositor's own animation, over the window as it already is: behind the rising screen the window is already empty, and behind the falling one the toolbar is already in place. The Swift app's slide had an animation over the whole window, which also animated what changed behind it in the same update: the toolbar going and coming with the profiles.
- **What was under way waits for the lock.** A context still opening as Pane locks closes once it has opened; a profile being deleted is waited for, and its folder goes at the next open. An attach or a move from an earlier Pane still running is waited for before the detach. The PIN typed meanwhile waits for the detach before attaching again. None of it blocks the main thread.
- **A profile still open 10 s after the lock makes Pane quit**, which closes every profile, and the volume detaches after. The detach is never forced while the engine runs. Until 0.18.2 it was, after 1.55 s, and the keys went whether or not it worked: a profile's `closed` fired as its destruction began, before its stores closed (since W3 it waits for two of them, below), so a late flush met a volume that was gone. It now tries for 10 s; past that, the keys stay and Pane quits, and the forced detach waits until the engine has stopped. `lock-while-open` holds a file open through a lock, then past the wait.
- **A profile's close waits for its preferences and its history** (W3, 2026-11-13): `CloseProfile`'s `closed` came at `OnProfileWillBeDestroyed`, which Chrome calls as `~ProfileImpl` begins, before the preferences' last write (posted to the profile's file sequence as it is destroyed) and before the history's databases close (on the history's sequence). A profile opened again at once, as one turned off opens again to cache in memory (ADR 0119), met them still open, and on Windows, which refuses to open a file being replaced and keeps Chrome's databases under an exclusive lock, Chrome showed its profile error for the preferences over the window, a native box whose modal loop runs none of Pane's tasks until it is clicked: 3 times in 14 runs of `profile-history` in the test VM, its stack sampled with cdb. `closed` now comes once the history's backend is destroyed (`HistoryService::SetOnBackendDestroyTask`, run after its databases close) and a task on the profile's file sequence has run past that last write, within the same 10 s (`ProfileDestructionWaiter`, `pane/browser/profiles.cc`); on the Mac the volume's detach follows them too.
- **What Chrome holds of a profile itself goes before the detach, every time.** A lock that came while a profile was still opening, as the system's locks come the moment an unlock has the volume, stuck in one or two `lock-while-open` runs in five: Chrome's shared proto database (leveldb_proto's `shared_proto_db` and its `metadata`), which a profile opens as it starts, stayed open two minutes past a profile that went before it had opened. Its open, once ended, posts the clean-up of obsolete clients 120 s on, holding the database until then, and the provider's Shutdown cancels it; a profile that went first had its Shutdown run before the clean-up was posted, with nothing to cancel. The detach gave up after 10 s and Pane quit. Pane's own service of each profile (`ProfileStores`, `pane/browser/profiles.cc`), whose Shutdown comes as the profile's services shut down, right before its storage goes, makes that clean-up immediate through Chromium's own seam (`LetSharedProtoDatabaseGo`, `pane/browser/proto_databases.h`), and the database closes as its open ends. No Chromium patch.
- **Chrome's held work runs before the keys go.** Chrome posts work that reaches a profile's files as the profile is created and as it is destroyed, much of it BEST_EFFORT (the bounce-tracking `DIPS` database's open; the bookmarks' merged-surface ordering, written as the profile goes), and it holds every BEST_EFFORT task until its startup is over: once a visible page has loaded, else 3 minutes after launch (`BrowserMainLoop`'s fence, `AfterStartupTaskUtils`). A lock that came first, right after an unlock or with no page loading, left that work held behind it: the volume detached, the keys went, and when the 3 minutes ran out the work reached a profile's file with no key, where the encryption's deliberate check (ADR 0121) ended Pane. Every such crash found came at those 3 minutes, in a probe whose locks never let a page finish loading. Once every profile has closed, a lock now ends Chrome's startup if it isn't over, and waits for the thread pool to have run all it holds, 5 s at most (`ProfileContexts::CloseForLock`, `pane/browser/background_work`); the detach and the keys' drop come after. ADR 0121's rule stays as it is. Found with it: Chrome writes a profile's README, at each creation of a profile that has none, in a BEST_EFFORT task, which a loaded Mac held past a lock that had closed the profile and dropped its keys, and the encryption's check ended Pane; `OpenProfile` writes it as it makes the profile's folder, under the key just registered, before the profile loads, so Chrome posts none (`MakeProfileDirectory`).

What was rejected:

- **Forcing the detach after a short wait**, as the first build did: Pane's hosted Browser kept the profile, so its databases stayed open 12 s, and the forced detach pulled them from under the engine. The browser and the network service died of `SIGBUS` on their memory-mapped SQLite files once the PIN opened the data again.
- **Leaving the volume mounted behind the PIN screen**: any process of the user's could read it, which is what the requirement rules out.
- **Locking only the window and keeping the engine's profiles**: their pages, cookies, and caches stay in memory and on a mounted volume.
- **Quitting Pane at every lock**: the window, its tabs, and the place in them would go, where the PIN can bring them back.
- **The window behind the PIN screen animating with it**: the page that opened while the card grew back drew at a size from the way, 757 points tall in a 741-point card, its top under the toolbar.
- **Letting a download finish first**: the data would stay open for as long as the download takes.
- **Waiting out Chrome's own stores past 10 s**: the shared proto database's hold lasts two minutes, with the PIN screen up and the volume still open behind it.
- **A patch to the shared database**, skipping its clean-up once shut down: the user's call is no Chromium patch, and Chromium's own seam does it from `//pane`.
- **Letting it go as Chrome announces the profile's destruction** (`OnProfileWillBeDestroyed`): up to a second can pass before the profile goes, waiting for its renderers, in which a client's first request can still make the database.
- **Relaxing ADR 0121 while the volume is detached**, a profile's path with no key read as plain since nothing is there to read: the encryption's promise would rest on a state the browser tracks, and it holds while locked but not between the PIN's attach and the profile's key.
- **A marker posted after the profile's creation tasks**, a BEST_EFFORT task the lock waits for: it answers once that work has begun, not ended; it comes before what the profile's destruction posts; and Chrome's startup holds it as long as the work.
- **Each service's own signal** (the bounce-tracking service's round trip through its database's sequence): one service of many, and none answers for a profile already destroyed.
- **Ending Chrome's startup at the unlock**, or at launch: Chrome holds that work back so that the first page loads first; at a lock the pages are gone.
- **A longer cap**: the pool emptied within 400 ms at every lock measured; past 5 s the volume would stay mounted behind the PIN screen for work that isn't the lock's.

How it is checked:

- **What locks it by itself**: `lock-while-open` posts the displays' sleep and the session's resign to Pane alone; the screen's lock and the sleep reach every app, the user's own Pane among them, so `pane_unittests`' `LockTriggersTest` covers those, the time without use in front and behind, and the page's sound or picture-in-picture as use. The real events were tried once with the user at the Mac (2026-11-12), on a package's test copy behind a PIN: the screen's lock (⌃⌘Q), the displays' sleep (`pmset displaysleepnow`), the Mac's sleep from the Apple menu, and the lid closing each locked it and detached its volume, and its PIN opened it again; another user's session went untried, the Mac having one account, so the scenario's posted event stands for it.
- **`lock-while-open`**: with a PIN, a signed-in tab, and a 4 MB download under way, Lock Pane's reply already shows the PIN screen. The profiles leave the model, the download is cancelled, and the volume is unmounted and detached 219–322 ms after the command over four runs (the detach itself takes 0.16 s, unforced). The PIN brings back the same tab, its cookie, and its local storage, the volume attaching in 0.59 s. The page then fills its card at its own size (`pageLayout`: the size the engine drew it at against its view's); before the fix, 757 against 741. With Lock after at a minute, and time running 60 times faster (`PANE_TIME_SCALE`), Pane locks by itself while it is behind.
- **Once, on this Mac (2026-10-31)**: `lsof` on the mount point during the lock showed the profile's 113 files open for 12 s before the fix and none 250 ms after the command with it. Chrome's `profile_manager` log showed the last `kBrowserWindow` hold going.
- **`lock-while-open` also locks 8 times the moment an unlock has the volume**, the profile still opening: each detaches within the lock's wait, and the PIN after it finds Pane still running. Before `ProfileStores`, such locks stuck 1 in 11 and 2 in 8, `lsof` finding the browser process alone holding `shared_proto_db`'s 8 files, and a build that waited longer detached 120.2 s after the lock; with it, 40 such locks detached in 132–369 ms (2026-11-11). `pane_unittests`' `SharedProtoDatabaseTest` holds the cause on Chromium's own code, the database's LOCK still held at 119 s and free at 120, and its release at once.
- **`lock-while-open` holds the thread pool's BEST_EFFORT work** 1.5 s from before an unlock (`holdBackgroundWork`, Chromium's fence, the one its startup takes) and locks the moment the unlock attaches, three times: each detaches once that work has run (671–1,364 ms; 20 runs in a row on the hardened package, 2026-11-11), and Pane answers after it. On the code before, the first such lock detached in 246 ms and the held work then stopped Pane (`DIPS`'s open, no key). It also locks a launch the moment its first unlock attaches, before any page has loaded: once the volume has detached the pool holds nothing, where on the code before it still held work 10 s on, to run at the startup's 3 minutes with the keys gone.
- **The user's path, by a probe** (2026-11-11): a launch, the PIN, a tab whose server hasn't answered, Lock Pane, and Pane left locked: on the code before it stopped 176 s after the keys went, 3 minutes after launch, opening `DIPS` with no key; now the PIN opens it after 197 s.
- **A census** (2026-11-11): a build that keeps the keys past the drop and lists every access to a profile's file after it. 223 locks the moment an unlock attached, on the code before: 329 such accesses, from `BookmarkMergedSurfaceOrdering`'s write and `DIPS`'s open, all in the one lock that met the startup's 3 minutes; now, 600 locks so timed: none, the lock's wait for the pool 17.5 ms at the median and 73.7 at most, the detach 128–586 ms.
- **`pane_unittests`' `BackgroundWorkTest`**, on Chromium's thread pool, its fence holding the work: it reaches its profile's file after the drop of a lock that doesn't wait, and with its key when the lock waits; what it posts in turn is waited for; the cap ends the wait.
