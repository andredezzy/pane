# Host mode is one seam into Chrome's startup and the --pane-hosted switch, and Pane's quit outranks Chrome's keep-alives

> **On the Views line** (`docs/plans/views-migration.md`, N3): the keep-alive is `pane::BrowserContext`'s (`pane/browser/browser_context.cc`, plain C++), one per open profile, held by `pane::ProfileContexts` and given to Chrome's close with the profile; `PaneBrowserContext` is gone.

Pane changes Chrome's startup through one seam rather than many patches, and everything Chrome does differently under the app keys off one switch, `--pane-hosted`. The seam is `ChromeMain` (patch 0002), which builds `pane::PaneMainDelegate`, a `ChromeMainDelegate` subclass from `//pane`. It plugs in `pane::ContentBrowserClient`, a `ChromeContentBrowserClient` subclass, which adds `pane::BrowserMainExtraParts` when hosted. Later hooks go through these subclasses instead of new patches, as the command-line switches each renderer gets do (`--pane-fingerprint`, ADR 0038). `//pane` is a dependency of `//chrome:chrome_dll` and includes `chrome_main_delegate.h` with `nogncheck`, since it lives in that target.

`PaneBrowserApplication +runWithDelegate:dataDirectory:` adds `--pane-hosted`, along with `--no-startup-window --no-first-run` and the engine's `--user-data-dir`, unless one is given (ADR 0006). Patched Chrome code reads the switch through the header-only constants of `pane/common/host.h`, so it does not depend on `//pane`. Under it Chrome builds no main menu (`chrome_browser_main_mac.mm`), and a Dock reopen is posted as a notification to the app instead of opening a Chrome window (`app_controller_mac.mm`). Since ADR 0014 the hidden `Browser` behind each window makes the app's pages real tabs, which Chrome reports to DevTools as pages on its own, so the hunk in `chrome_devtools_manager_delegate.cc` that reported them went in the review of 0.18.0. Hosted mode also returns early from `-[AppController setLastProfile:]`, whose remaining work only syncs Chrome's own menus. With no main menu, the bookmark and history menu bridges had no menu (`BookmarkMenuBridge` CHECK-failed on a null root) and the shared menu command state was never created (a null dereference); both fired when deleting a profile made Chrome switch its last-used profile.

Lifetime needs no keep-alive of Pane's. Chrome's AppController already keeps the process alive without windows and releases that on quit; a Pane keep-alive would have blocked Quit. Each `PaneBrowserContext` holds a `ScopedProfileKeepAlive` (`kBrowserWindow`), so Chrome does not unload a profile the app shows, and releases it as the engine shuts down: as quitting starts, while the message loop still runs, with `PostMainMessageLoopRun` as the backstop, before Chrome destroys profiles.

**Quit outranks a remote debugging client.** Pane's windows are the app's, and Quit is the user's call. Chrome started without a window (`--no-startup-window`) and with `--remote-debugging-port` holds a keep-alive for the client until the client closes the browser. Pane's quit releases it: as the app terminates, the engine calls `ChromeDevToolsManagerDelegate::AllowBrowserToClose` (`pane/browser/browser_main_extra_parts.mm`). Pane launched normally has no such keep-alive. The case is the scenarios', which launch the app with remote debugging, and the runs on an unlocked screen found Quit Pane not quitting there.

**The app's view fills the window through `views::NativeViewHost`.** A `paneEmbeddedView` in `bridged_content_view.{h,mm}` once asked it first for clicks and assistive technologies; in the review of 0.18.0 the Widget's contents became a `NativeViewHost` (`pane/browser/ui/window_host.mm`), which stock Views routes to, so both files return to the original (ADR 0004). On one build with and without it, a hit test takes 63 µs against 62 on a page and 82 against 80 in the sidebar, 20,000 calls three times over; the accessibility tree by cua-driver's `get_window_state` is the same 23 elements; element at position answers the same at five points; 60 `setFrame` steps take 1.47 ms each against 1.55, the worst 4.2 against 4.0; local pages load within 0.2 ms. `smoke`, `window-drag`, `window-chrome`, `sidebar-resize`, `dialogs`, and `devtools-undocked` pass. A live resize by the pointer and a VoiceOver pass by a person are owed.

How it is checked:

- **`hosted`:** on an unlocked screen it chooses Quit Pane from the menu, twice since ⌘Q asks first (ADR 0053), and expects the app and every helper to be gone within 5 seconds.
