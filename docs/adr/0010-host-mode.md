# Host mode is one seam into Chrome's startup and the --pane-hosted switch, and Pane's quit outranks Chrome's keep-alives

Pane changes Chrome's startup through one seam rather than many patches, and everything Chrome does differently for Pane keys off one switch, `--pane-hosted`. The seam is `ChromeMain` (patch 0002), which builds `pane::PaneMainDelegate`, a `ChromeMainDelegate` subclass from `//pane`. It plugs in `pane::ContentBrowserClient`, a `ChromeContentBrowserClient` subclass, which adds `pane::BrowserMainExtraParts` to the browser's main parts: they start Pane's data and UI once the browser has started (`OpenData`, `UiApp::Start`). Later hooks go through these subclasses instead of new patches, as the command-line switches each renderer gets do (`--pane-fingerprint`, ADR 0038). `//pane` is a dependency of `//chrome:chrome_dll` and includes `chrome_main_delegate.h` with `nogncheck`, since it lives in that target.

**The launch sets the switch.** `PaneMainDelegate::BasicStartupComplete`, the first of Pane's code in the browser process, before Chrome reads its command line, starts Pane's launch (`pane/app/views_launch.h`): it brings the data up to date and takes its lock (`PrepareData`, ADR 0113), then sets the engine's command line (`pane/app/engine_switches.cc`): `--pane-hosted`, `--no-startup-window`, `--no-first-run`, the features Pane keeps off, and the engine's `--user-data-dir`, unless one is given (ADR 0006). Every browser process runs it, a relaunch's too: until the cutover the Swift app set the switch from outside (`PaneBrowserApplication +runWithDelegate:dataDirectory:`) and the launch ran only without it, so a relaunch that copied the engine's own command line, the switch in it, would have started an engine with no data and no window.

**What the switch turns off.** Patched Chrome code reads it by name, or through the header-only constants of `pane/common/host.h`, so it does not depend on `//pane`, and a Chromium binary run without it, such as Chromium's own tests, keeps Chrome's behavior. Under it:

- Chrome builds no main menu (`chrome_browser_main_mac.mm`): Pane's own menu bar is built from its command table (`pane/ui/app/menu_bar.h`). With no main menu, the bookmark and history menu bridges had no menu (`BookmarkMenuBridge` CHECK-failed on a null root) and the shared menu command state was never created (a null dereference); both fired when deleting a profile made Chrome switch its last-used profile, so `-[AppController setLastProfile:]` returns early, its remaining work only syncing Chrome's own menus.
- A Dock reopen, and the URLs another app hands Pane, are posted as notifications instead of opening a Chrome window (`app_controller_mac.mm`), which Pane's UI hears (`pane/ui/app/app_events.h`, ADR 0109).
- Handoff advertises nothing (patch 0002), and Chrome keeps no crash handler, no histograms on disk, and no account list from Gaia (patch 0008), no GPU cache in a profile (0006), and keeps downloads' requests, closed tabs, and blobs off the disk, and names IndexedDB's folders by bucket (0010): ADRs 0040, 0115, and 0121.

Since ADR 0014 the hidden `Browser` behind each window makes Pane's pages real tabs, which Chrome reports to DevTools as pages on its own, so the hunk in `chrome_devtools_manager_delegate.cc` that reported them went in the review of 0.18.0.

**Lifetime needs no keep-alive of Pane's.** Chrome's AppController already keeps the process alive without windows and releases that on quit; a Pane keep-alive would have blocked Quit. Each open profile's `pane::BrowserContext` (`pane/browser/browser_context.cc`, held by `pane::ProfileContexts`) holds a `ScopedProfileKeepAlive` (`kBrowserWindow`), so Chrome does not unload a profile Pane shows, and gives it to Chrome's close with the profile as quitting starts, while the message loop still runs, before Chrome destroys profiles (`UiApp::Start`).

**Quit outranks a remote debugging client.** Pane's windows are Pane's, and Quit is the user's call. Chrome started without a window (`--no-startup-window`) and with `--remote-debugging-port` holds a keep-alive for the client until the client closes the browser. Pane's quit releases it: as quitting starts, the engine calls `ChromeDevToolsManagerDelegate::AllowBrowserToClose` (`pane/browser/browser_main_extra_parts.cc`). Pane launched normally has no such keep-alive. The case is the scenarios', which launch Pane with remote debugging, and the runs on an unlocked screen found Quit Pane not quitting there.

**Pane's views fill the window.** Each window is a `views::Widget` of Pane's whose root view is Pane's (`pane/ui/window/root_view.h`, ADR 0014), the page in a `views::WebView` among its views, in the window's one compositor. Until the cutover the Widget held the Swift app's `NSView` through a `views::NativeViewHost`, from the review of 0.18.0, when `bridged_content_view.{h,mm}` went back to the original.

How it is checked:

- **`hosted`:** Pane launched with a page shows it in its one window, its window told of the tab (`PaneBrowserWindowDelegate.didInsertTab` in the trace) and the page a DevTools target; on an unlocked screen it chooses Quit Pane from the menu, twice since ⌘Q asks first (ADR 0053), and expects Pane and every helper to be gone within 5 seconds.
- **Every scenario** runs on a launch that set the switch, and fails on a window Chrome makes of its own (`WindowWatcher`).
