# Host mode is one seam into Chrome's startup and the --pane-hosted switch, and Pane's quit outranks Chrome's keep-alives

Pane changes Chrome's startup through one seam rather than many patches, and everything Chrome does differently under the app keys off one switch, `--pane-hosted`. The seam is `ChromeMain` (patch 0002), which builds `pane::PaneMainDelegate`, a `ChromeMainDelegate` subclass from `//pane`. It plugs in `pane::ContentBrowserClient`, a `ChromeContentBrowserClient` subclass, which adds `pane::BrowserMainExtraParts` when hosted. Later hooks go through these subclasses instead of new patches, as the command-line switches each renderer gets do (`--pane-fingerprint`, ADR 0038). `//pane` is a dependency of `//chrome:chrome_dll` and includes `chrome_main_delegate.h` with `nogncheck`, since it lives in that target.

`PaneBrowserApplication +runWithDelegate:dataDirectory:` adds `--pane-hosted`, along with `--no-startup-window --no-first-run --no-default-browser-check` and the engine's `--user-data-dir`, unless one is given (ADR 0006). Patched Chrome code reads the switch through the header-only constants of `engine/pane/common/host.h`, so it does not depend on `//pane`. Under it Chrome builds no main menu (`chrome_browser_main_mac.mm`), and a Dock reopen is posted as a notification to the app instead of opening a Chrome window (`app_controller_mac.mm`). A page that is no tab of Chrome's is reported to DevTools as `page` (`chrome_devtools_manager_delegate.cc`); since Phase 2 the hidden `Browser` behind each window makes the app's pages real tabs, which Chrome reports as pages on its own (ADR 0014). Hosted mode also returns early from `-[AppController setLastProfile:]`, whose remaining work only syncs Chrome's own menus. With no main menu, the bookmark and history menu bridges had no menu (`BookmarkMenuBridge` CHECK-failed on a null root) and the shared menu command state was never created (a null dereference); both fired when deleting a profile made Chrome switch its last-used profile.

Lifetime needs no keep-alive of Pane's. Chrome's AppController already keeps the process alive without windows and releases that on quit; a Pane keep-alive would have blocked Quit. Each `PaneBrowserContext` holds a `ScopedProfileKeepAlive` (`kBrowserWindow`), so Chrome does not unload a profile the app shows, and releases it as the engine shuts down: as quitting starts, while the message loop still runs, with `PostMainMessageLoopRun` as the backstop, before Chrome destroys profiles.

**Quit outranks a remote debugging client.** Pane's windows are the app's, and Quit is the user's call. Chrome started without a window (`--no-startup-window`) and with `--remote-debugging-port` holds a keep-alive for the client until the client closes the browser. Pane's quit releases it: as the app terminates, the engine calls `ChromeDevToolsManagerDelegate::AllowBrowserToClose` (`engine/pane/browser/browser_main_extra_parts.mm`). Pane launched normally has no such keep-alive. The case is the scenarios', which launch the app with remote debugging, and the runs on an unlocked screen found Quit Pane not quitting there.

How it is checked:

- **`hosted`:** on an unlocked screen it chooses Quit Pane from the menu, twice since ⌘Q asks first (ADR 0053), and expects the app and every helper to be gone within 5 seconds.
