# Each profile's proxy is Chrome's own per-profile setting

Each profile's proxy is set in Chrome's own per-profile prefs, so each profile, its own Chrome profile (ADR 0006), goes out through its own proxy. The prefs are `proxy` (fixed servers) and `webrtc.ip_handling_policy`, which keeps the real address from leaking past the proxy, and a profile's pages open only after both are applied. The app sets them as `PaneBrowserContext.proxyRules` and `webRTCIPHandlingPolicy` (`engine/pane/public/PaneBrowserContext.h`), from `app/Pane/Network/ProfileNetwork.swift`.

Chromium cannot authenticate to SOCKS, so a SOCKS proxy with credentials goes through the app's relay (`app/Pane/Network/SocksRelay.swift`), the Electron app's `proxy-relay.ts` ported onto Network.framework, which speaks SOCKS5 with RFC 1929 or SOCKS4a upstream. An HTTP or HTTPS proxy's challenge is answered with the profile's credentials through the engine's authentication request (ADR 0021), without a prompt. Asked again within five seconds, which means the credentials are wrong, the user gets the sign-in dialog instead of a loop. Chrome names a proxy challenger with its scheme (`http://host:port`), as `engine/pane/public/PaneDialogs.h` says. The passwords live in the Keychain, not in `profiles.json` (ADR 0069). The connection test (`app/Pane/Network/ProxyTest.swift`) fetches the same IP echo as the Electron app's `proxy-test.ts` through the proxy, with URLSession's proxy configurations, and SOCKS through the relay, since URLSession has no SOCKS4. Its result is the sidebar's dot.

The safety review (2026-10-27) made a port 1 to 65535 everywhere. A SOCKS proxy with credentials on port 70000 or -1 trapped in the relay's `UInt16(_:)` on Chrome's first connection, and the process died with every profile, while its test clamped the port to 65535 and passed. PaneKit's `ProxyConfig.port(_:)` is the one check: the paste shortcut and the profile sheet use it, and the relay and the test throw "bad proxy port" on anything outside `ProxyConfig.ports`. The sheet refuses to save a proxy that has a host and no valid port, with the error under the row, as the name's is; it used to save it as no proxy, and the profile went direct. The test button shows the same message in red. The `proxy` scenario sets port 70000 on a SOCKS5 profile with credentials: its test fails, its page does not load, and the other profiles keep theirs. The paste shortcut (`host:port:user:password` on one line) keeps the rest of the line as the password, so `host:port:user:p:ss` keeps `p:ss`; it took only `parts[3]`, as the Electron app did.

A proxy changed while its profile's context opens is applied too. The context's first apply read the proxy once and awaited its relay, and a change meanwhile found no context to apply to, so pages loaded with the old rules while the sidebar's test showed the new proxy green. `ProfileNetwork.apply` now repeats until the proxy it applied is the profile's current one, which also settles two applies running at once on the newest. Routing the change through `withContext`, as the review suggested, was rejected: it would open the contexts of profiles nobody opened. The window is narrower than the automation channel's 100 ms poll, and five tries through it did not hit it before the fix either, so no scenario proves it.

Chrome's own background requests (`accounts.google.com`, `www.google.com`) also went out per profile, through its proxy, where the Electron app made none. Whether to turn them off went to the fingerprint work, which owns what a profile reveals. They are off, with the requests the browser made itself past every profile's proxy (ADR 0040).
