# Each profile's proxy is Chrome's own per-profile setting, and its password is never kept in the clear

> **Partly replaced by [ADR 0122](0122-pane-upgrades-only-from-the-last-0-18-x.md)** — the separate stores of the passwords, and a plain `profiles.json`, are no longer read. `proxy` checks the sealed file alone.

Each profile's proxy is set in Chrome's own per-profile prefs, so each profile, its own Chrome profile (ADR 0006), goes out through its own proxy. The prefs are `proxy` (fixed servers) and `webrtc.ip_handling_policy`, which keeps the real address from leaking past the proxy, and a profile's pages open only after both are applied. The app sets them as `PaneBrowserContext.proxyRules` and `webRTCIPHandlingPolicy` (`engine/pane/public/PaneBrowserContext.h`), from `app/Pane/Network/ProfileNetwork.swift`.

Chromium cannot authenticate to SOCKS, so a SOCKS proxy with credentials goes through the app's relay (`app/Pane/Network/SocksRelay.swift`), the Electron app's `proxy-relay.ts` ported onto Network.framework, which speaks SOCKS5 with RFC 1929 or SOCKS4a upstream. An HTTP or HTTPS proxy's challenge is answered with the profile's credentials through the engine's authentication request (ADR 0021), without a prompt. Asked again within five seconds, which means the credentials are wrong, the user gets the sign-in dialog instead of a loop. Chrome names a proxy challenger with its scheme (`http://host:port`), as `engine/pane/public/PaneDialogs.h` says. The connection test (`app/Pane/Network/ProxyTest.swift`) fetches the same IP echo as the Electron app's `proxy-test.ts` through the proxy, with URLSession's proxy configurations, and SOCKS through the relay, since URLSession has no SOCKS4. Its result is the sidebar's dot.

A port is 1 to 65535 everywhere. A SOCKS proxy with credentials on port 70000 or -1 trapped in the relay's `UInt16(_:)` on Chrome's first connection, and the process died with every profile, while its test clamped the port to 65535 and passed. PaneKit's `ProxyConfig.port(_:)` is the one check: the paste shortcut and the profile sheet use it, and the relay throws "bad proxy port", and the test "bad port", on anything outside `ProxyConfig.ports`. The sheet refuses to save a proxy that has a host and no valid port, with a red ring around the field, as the name's has (ADR 0120); it used to save it as no proxy, and the profile went direct. The test shows the port's message beside its button, on red. The `proxy` scenario sets port 70000 on a SOCKS5 profile with credentials: its test fails, its page does not load, and the other profiles keep theirs. The paste shortcut (`host:port:user:password` on one line) keeps the rest of the line as the password, so `host:port:user:p:ss` keeps `p:ss`; it took only `parts[3]`, as the Electron app did.

A proxy changed while its profile's context opens is applied too. The context's first apply read the proxy once and awaited its relay, and a change meanwhile found no context to apply to, so pages loaded with the old rules while the sidebar's test showed the new proxy green. `ProfileNetwork.apply` now repeats until the proxy it applied is the profile's current one, which also settles two applies running at once on the newest. The window is narrower than the automation channel's 100 ms poll, and five tries through it did not hit it before the fix either, so no scenario proves it.

Chrome's own background requests (`accounts.google.com`, `www.google.com`) also went out per profile, through its proxy, where the Electron app made none. Whether to turn them off went to the fingerprint work, which owns what a profile reveals. They are off, with the requests the browser made itself past every profile's proxy (ADR 0040).

**The password.** A profile's proxy password is in `profiles.json`, sealed with the file under the data key (ADR 0113). In the clear in that file was the Electron app's format. It took two steps before ADR 0113 sealed the whole file, and what they left is read once, when an earlier Pane's plain `profiles.json` is, then deleted.

A Keychain item of their own (2026-10-27):

- **One generic password, "Pane Proxy Passwords", held them all** as JSON by profile id, so macOS asked at most once after an update of an ad-hoc signed build (ADR 0048), not once per profile. Its account is the data directory's path, so a Pane started on another data directory keeps its own (and the former identifier's path, for a data root ADR 0114 moved).
- **It was read at launch only when a proxy signs in** (a username, or a password the file still held), since macOS may ask first, and written only when a password changed, on the save queue (ADR 0068), before the file: a password left `profiles.json` only once the store held it. A password the file still held, the Electron app's or an older Pane's, was read as it was, won over the store, and moved at the first save.
- **If the store could not be read or written** (the user denied it), the passwords stayed in the file for that session rather than be lost, and the store was not asked again until the next launch.

Sealed under the engine's key (2026-10-29), the user's call, after every update asked for the login keychain's password twice, once for "Pane Safe Storage" and once for "Pane Proxy Passwords":

- **Each item names the builds that may read it:** an ad-hoc signature carries no Team ID, so macOS names each build by its code hash, and a new build asks once per item.
- **One answer covers both:** the engine reads "Pane Safe Storage" at every launch, and Pane is the same process, so one Always Allow covers the passwords too. An update asks once. ADR 0113 seals the data key under the same secret, for the same reason, and makes the engine's Keychain item when it has none and no data key is sealed yet.
- **The passwords moved to `proxy-passwords.json`** in the data directory, sealed with AES-GCM under a key HKDF-SHA256 derives from the engine's secret. PaneKit's `ProxyPasswordSeal` seals and opens them, and `ProxyPasswordVault` decides where they are read from; the app gives it the Keychain and the file (`app/Pane/Security/ProxyPasswordStore.swift`, `SafeStorage.engineSecret`).
- **The first launch after it** read the old item once more, its last prompt, sealed what it held, and deleted it. Before the engine had a key, in a fresh install's first moments, the passwords went to the old item and were sealed at a later launch. A key the user denied, or one that did not open the box, left the passwords where they were, and the box stayed for its key.

The panic wipe deletes the sealed file and the old item, the item without asking (ADR 0042). Under `--use-mock-keychain` the store is `mock-keychain.json` in the data directory, so scenarios never touch the login Keychain (ADR 0012).

What was rejected:

- **Routing a proxy's change through `withContext`:** it would open the contexts of profiles nobody opened.
- **Deleting the engine's "Pane Safe Storage" key in the panic wipe:** that key is not scoped by data directory, so a wipe in a Pane on a throwaway data directory would sign the real one out.
- **A certificate of Pane's own, to keep both items' grants across updates:** tried on 2026-10-29 and undone the same day. The partition list macOS keeps on each item (its `partition_id` entry) names an app without a Team ID by its code hash (`cdhash:`), whatever certificate signs it: a test item made through the calls Chromium makes refused the second build of a tool signed with the same certificate (`-25293`), as it refused an ad-hoc one. Developer ID browsers' items (Dia, Aside) carry `teamid:`, which updates keep; a Developer ID would end the prompt altogether (ADR 0048), and it is the user's call for later.
- **Keeping the engine's key out of the Keychain:** the cookies' encryption would no longer keep them from other apps.
- **Pane making the engine's item when it has none:** a migration would then find a key and not hand over the Electron app's (ADR 0043). ADR 0113 makes it once the migration has run.

How the password is checked:

- **PaneKit's tests:** the box opens with its secret alone, and not once changed; an earlier Pane's box opens with the engine's key, and its item reads too; a denied key, or another key's box, reads nothing; and once the profiles are sealed with them, neither the box nor the item stays. Until ADR 0113 they also checked that the vault moved the item's passwords into a box, and kept the item before the engine had a key.
- **Scenarios**, on the mock keychain: `proxy` checks that no password is left in `profiles.json` in the clear, and that the Electron app's plain password signs in without a prompt, moves, and signs in again after a relaunch; `profile-sheet` checks the same for a proxy saved from the sheet. `proxy-auth`, `security`, `migration`, `smoke`, and `restore` pass with it.
- **What only the login Keychain shows**, one prompt per update, was the user's to see at the next update.
