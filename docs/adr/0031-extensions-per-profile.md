# Extensions run on Chrome's extension system, per profile, and their actions and popups behave as Chrome's

> **Refined by [ADR 0115](0115-nothing-outside-the-volume-names-a-page.md)** — a `migration.json` that still lists the extensions as `pendingExtensions` is written again without them at launch.

> **On the Views line** (`docs/plans/views-migration.md`, X1 and X2): each Browser of the window registers Pane's `ExtensionsContainer` (`BrowserExtensions`), which watches the profile's extensions where `ExtensionsBridge` did, its icon factories started over once an icon loads; an action's popup is Pane's bubble drawn to Paper 04.12 in a window of its own (`pane/ui/extensions/action_popup`), Chrome's `ExtensionViewHost` showing the page once loaded, sized within 25 × 25 and 800 × 600 and cut to the screen's room under the button. It closes on Esc in the page or its `window.close()`, a click outside it or another app taking the keys (unless DevTools inspect it or it shows a dialog), the tab changing, as Chrome's does, its extension going, and before its Browser; a second press on its button closes it, as in Chrome, where NSPopover could close and open it again.

> **On the Views line** (`docs/plans/views-migration.md`, X3 and X4): an install's prompt goes from Chrome's hook straight to Pane's dialog (ADR 0056), and a profile's extensions are managed on Chrome's own page in the profile's tab (ADR 0062); the bridge's `PaneExtensionInstallRequest`, `PaneExtensionDetails`, and `PaneExtensionCommand` are gone. An action's popup shows above its button where the screen leaves more room above it than under it, its arrow out of its bottom edge with the tip on the button's top, as NSPopover chose its edge (X2's finding, `pane/ui/extensions/action_popup`).

Extensions run on Chrome's own extension system, so every extension API is Chrome's (ADR 0004), and each profile has its own: a profile is its own Chrome profile (`Engine/<id>`, ADR 0006, a link into the encrypted volume since ADR 0113), with its own extension registry, toolbar, and `Extensions/` folder, and the app keeps each profile's list by its id. The engine hands the app their toolbar actions, popups, install prompts, and management (`pane/public/PaneExtensions.h` and `PaneBrowserContext.h`, `pane/browser/extensions/`), and the app draws them (ADRs 0054, 0056, 0062).

Install prompts come from Chrome's `ExtensionInstallPrompt` (`chromium/patches/0005-pane-extensions.patch`), and the app shows them as its own (ADR 0056); Ardia's `chromium-extension-install-prompt-hook` was evaluated and adapted that way. Ardia's hidden-window hooks (`chromium-hidden-window-current-window`, `chromium-extension-window-hidden`) are not needed: each profile's tabs live in a hidden `Browser` of Pane's window (ADR 0014), which Chrome already counts as the current window for popups and service workers.

The Electron app's extensions do not come over with the migration (ADR 0043). NordPass showed first what they carried: its Continue froze in a migrated profile and works on a fresh install, where it took a test address to Nord Account's sign-up page, so the freeze comes from the extension data the migration copied. Electron lacked APIs NordPass uses (`contextMenus`, `privacy`, `webNavigation`; its login page renders blank there), so that data is from a half-working extension. Reinstalling NordPass in that profile clears it; the vault itself is on NordPass's servers. Then the user reported an extension installed in one profile showing in several others. The engine was not sharing them. The Electron app had installed each extension once and loaded it into every profile, so the migration listed it as pending in all of them (`migration.json`), and each profile installed it as it opened, with Chrome's prompt answered for the user. On the user's data, NordPass was the Electron app's only extension: five profiles had it, each installed seconds after it was opened, and the other six still had it pending.

The migration now leaves extensions behind, and the app reinstalls none (`MigratedExtensions` is gone). A profile adds its own from the Web Store; the extension's saved data is still in the copied partition, so adding it back where it was used finds it. Installing it in one profile chosen for the user was rejected: the Electron app recorded none, and its storage existed in every profile. A `migration.json` written before listed them as `pendingExtensions`, which nothing reads; since ADR 0115 the launch writes it again without them (`ElectronMigration.dropPendingExtensions`). Extensions the migration already installed stay until removed in each profile.

`extensions-per-profile` installs Dark Reader in one profile and checks that another, opened beside it, lists none and has no `Extensions/` entry for it, and that disabling, unpinning, and removing it in the first leave the second's own copy as it was. It passed before the fix too, which rules out the engine and the app's lists. `migration` opens both migrated profiles and expects neither to have the Electron app's extension; before the fix it found it in both.

**Actions and popups.** An extension's toolbar action and its popup behave as they do in Chrome, the browser extensions are written for: the engine keeps Chrome's per-tab action state and popup sizing, and the app shows the popup's page in its own popover (`app/Pane/Extensions/ExtensionPopover.swift`). Where the actions sit, pinned or in the extensions menu, is ADR 0054's.

An action's title, badge, icon, and popup are per tab. The engine reports them again when the profile's selected tab changes, through a `BrowserTabStripTracker` (`pane/browser/extensions/extensions_bridge.mm`). Chrome's `ExtensionActionIconFactory` keeps the first default icon it returns, which is a blank placeholder when asked before the icon file loaded (NordPass's showed blank), so the bridge starts its factories over once an icon loads.

A popup's page sizes itself, as in Chrome: auto-resize is enabled on the popup's main frame as it becomes the main one (`RenderFrameHostChanged`, in `pane/browser/extensions/action_popup.mm`), since its first document commits in a new frame. The page sits on an opaque white canvas in the popover: straight on the popover's material it was blended with it (vibrancy), and a dark popup turned near black. Under the Dark theme the page's view painted nothing at all, so that view alone takes the aqua appearance; the popover around it stays dark, and the page's color scheme follows the theme app-wide.

Some extensions turn their popup off until the user signs in. 1Password clears its popup seconds after installing, so its button opens its welcome page in a tab, as in Chrome. The `password-managers` scenario presses the button and checks whichever the extension chose.

A popup closes with its `Browser`. It held a raw `Browser*` and kept itself alive until closed; it now holds a weak pointer, and the Browser's window closes its popups as it is destroyed, telling the app. The `tabs-api` scenario deletes a profile with its popup open: before, the app died there in each of three runs, on an uncaught exception in NSWindow's restorable-state encoding 130 ms after the popup's close, and now the popup closes with the Browser. The same scenario opens the popup from the extension's worker with `chrome.action.openPopup`. The fix's other half, a Browser that stops counting as Pane's with its window, is ADR 0014's.
