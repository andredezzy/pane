# Extensions run on Chrome's extension system, per profile, and their actions and popups behave as Chrome's

> **Refined by [ADR 0115](0115-nothing-outside-the-volume-names-a-page.md)** — a `migration.json` that still lists the extensions as `pendingExtensions` is written again without them at launch.

Extensions run on Chrome's own extension system, so every extension API is Chrome's (ADR 0004), and each profile has its own: a profile is its own Chrome profile (`Engine/<id>`, ADR 0006, a link into the encrypted volume since ADR 0113), with its own extension registry, toolbar model, and `Extensions/` folder. Each of the window's hidden Browsers registers Pane's `ExtensionsContainer` (`BrowserExtensions`, `pane/ui/extensions/browser_extensions.h`), as Chrome registers its own for its windows and `webui_browser_window.cc` for its WebUI one: it watches the profile's extensions for the window (installs and removals, enabling, pins, site access, each action's title, badge, and icon, and the Browser's active tab), and `chrome.action.openPopup` shows the popup through it. Pane draws the rest: the toolbar's actions and the extensions menu (ADR 0054), the install prompt (ADR 0056), and management on Chrome's own extensions page in the profile's tab (ADR 0062).

Install prompts come from Chrome's `ExtensionInstallPrompt` through patch 0005's hook, straight to Pane's dialog (ADR 0056); Ardia's `chromium-extension-install-prompt-hook` was evaluated and adapted that way. Ardia's hidden-window hooks (`chromium-hidden-window-current-window`, `chromium-extension-window-hidden`) are not needed: each profile's tabs live in a hidden `Browser` of Pane's window (ADR 0014), which Chrome already counts as the current window for popups and service workers.

**The Electron app's extensions do not come over with the migration** (ADR 0043). NordPass showed first what they carried: its Continue froze in a migrated profile and works on a fresh install, where it took a test address to Nord Account's sign-up page, so the freeze comes from the extension data the migration copied. Electron lacked APIs NordPass uses (`contextMenus`, `privacy`, `webNavigation`; its login page renders blank there), so that data is from a half-working extension. Reinstalling NordPass in that profile clears it; the vault itself is on NordPass's servers. Then the user reported an extension installed in one profile showing in several others. The engine was not sharing them. The Electron app had installed each extension once and loaded it into every profile, so the migration listed it as pending in all of them (`migration.json`), and each profile installed it as it opened, with Chrome's prompt answered for the user. On the user's data, NordPass was the Electron app's only extension: five profiles had it, each installed seconds after it was opened, and the other six still had it pending.

The migration leaves extensions behind, and the app reinstalls none. A profile adds its own from the Web Store; the extension's saved data is still in the copied partition, so adding it back where it was used finds it. Installing it in one profile chosen for the user was rejected: the Electron app recorded none, and its storage existed in every profile. A `migration.json` written before listed them as `pendingExtensions`, which nothing reads; since ADR 0115 the launch writes it again without them (`model::DropPendingExtensions`, `pane/model/mac/electron_migration.h`). Extensions the migration already installed stay until removed in each profile.

`extensions-per-profile` installs Dark Reader in one profile and checks that another, opened beside it, lists none and has no `Extensions/` entry for it, and that disabling, unpinning, and removing it in the first leave the second's own copy as it was. It passed before the fix too, which rules out the engine and the app's lists. `migration` opens both migrated profiles and expects neither to have the Electron app's extension; before the fix it found it in both.

**Actions and popups.** An extension's toolbar action and its popup behave as they do in Chrome, the browser extensions are written for. Where the actions sit, pinned or in the extensions menu, is ADR 0054's.

- **Per tab.** An action's title, badge, icon, and popup are per tab, and show for the Browser's active tab; `BrowserExtensions` reports them again when it changes. Chrome's `ExtensionActionIconFactory` keeps the first default icon it returns, which is a blank placeholder when asked before the icon file loaded (NordPass's showed blank), so once any icon has loaded the factories start over (`ActionIcons`, `pane/ui/extensions/installed_extensions.h`).
- **The popup** (`pane/ui/extensions/action_popup`) is the extension's page in Pane's bubble, drawn to Paper 04.12, which the user kept over Chrome's square `ExtensionPopup` (Paper 10.5): a window of its own over Pane's, as the Swift app's `NSPopover` was, an arrow from its top edge whose tip touches the toolbar button, and the page in a frame of the popover's material. Chrome's own popup host (`ExtensionViewHost`) runs the page, and the bubble shows once its first load has finished, as Chrome's does. The page sizes itself, as in Chrome, within 25 × 25 and 800 × 600 (`EnableSizingFromWebContents`), cut to the room the screen leaves under the button, or above it where the screen leaves more room there, its arrow then out of its bottom edge, as `NSPopover` chose its edge.
- **The page sits on white,** as a page's canvas is in Chrome, so a dark popup's page shows on it as it would in a tab. In the Swift app's popover, the page straight on the popover's material was blended with it (vibrancy), and a dark popup turned near black; under the Dark theme its view painted nothing at all until it took the aqua appearance.
- **It closes** on Esc in the page or the page's own `window.close()`, a click outside it or another app taking the keys (unless DevTools inspect it or it shows a dialog), the tab changing, as Chrome's does, its extension going, and before its Browser; a second press on its button closes it, as in Chrome, where `NSPopover` could close and open it again.

Some extensions turn their popup off until the user signs in. 1Password clears its popup seconds after installing, so its button opens its welcome page in a tab, as in Chrome. The `password-managers` scenario presses the button and checks whichever the extension chose.

**A popup closes with its `Browser`.** The Swift engine's popup held a raw `Browser*` and kept itself alive until closed; deleting a profile with its popup open killed the app in each of three runs, on an uncaught exception in NSWindow's restorable-state encoding 130 ms after the popup's close. The popup goes before its Browser (`~BrowserExtensions`). The `tabs-api` scenario deletes a profile with its popup open, and opens the popup from the extension's worker with `chrome.action.openPopup`. The fix's other half, a Browser that stops counting as Pane's with its window, is ADR 0014's.

Until 0.20.0 the engine handed the Swift app the actions, popups, prompts, and management through its Objective-C API (`PaneExtensions.h`, `ExtensionsBridge`, a `BrowserTabStripTracker`), and the app drew them, the popup in an `NSPopover` (`ExtensionPopover.swift`).
