# Pane is a native Swift shell on its own Chromium framework, not Electron or Tauri

> **Being replaced (the user, 2026-11-07):** Pane's UI moves into Chromium as C++ Views, one implementation on Mac and Windows, with no Swift left and no duplicated code. Windows comes into scope. It follows Aside's pattern, with one difference: every profile stays in one window over hidden Browsers (ADR 0014), where Aside overwrites `Browser::profile_` in place. Why: on Windows, a native Swift shell means WinUI, and Dia, the closest such browser, measured about 1.5 s more to its window than Chrome through the same launch, and about 100 MB more in its browser process, with a window for each layer over the page; Aside, in Views, measured about 60 ms more than Chrome and draws in one surface. Measured in a VM on 2026-11-07, without a GPU, so no frame numbers. What it cost is written down: a port of the Swift, and more of `//pane` for each Chromium upgrade to touch. The rule below, that the engine stays faithful to Chromium, stays. Until the cutover this record describes what ships. `docs/plans/views-migration.md` is the migration, and its K3 rewrites this record.

> **On the Views line** (`docs/plans/views-migration.md`, What Chrome asks for): sign-in goes through the seam Chromium keeps for it, `ChromeContentBrowserClient::CreateHttpAuthCoordinator` (`pane/ui/dialogs/sign_in.h`), so patch 0004 drops its `login_handler_views.cc` hunk and keeps DevTools' virtual and the external protocol dialog's hook: the patches edit 92 Chromium files and change 1,020 lines, with 9 files added (93 and 1,034 before).

> **On the Views line** (`docs/plans/views-migration.md`, X1): chrome.action.openPopup reaches Pane's popup through the `ExtensionsContainer` Pane registers for each Browser it hosts (`pane/ui/extensions/browser_extensions.h`), as `webui_browser_window.cc` registers its own, so patch 0005 drops its `extension_action_api.cc` hunk and keeps the install dialog's hook, X3's: the patches edit 91 Chromium files and change 1,004 lines, with 9 files added (92 and 1,020 before).

Pane moves off Electron to the architecture Arc and Dia use: a pure-Swift app (AppKit + SwiftUI) that links Pane's own Chromium build, `PaneCore.framework`, in the same process through an Objective-C embedding API. The app's `main` calls `ChromeMain` and Chromium owns the run loop; each tab's native view sits in the app's own view hierarchy, so tabs of several profiles share one window; Chrome's `Browser` objects still exist behind every window but stay hidden, so extension APIs and Chrome internals keep working while every Chrome-owned UI surface is routed to the app as a delegate callback and drawn natively.

The framework is built from Chromium's `chrome/` layer plus a `//pane` tree, with a small patch series for the framework layout (ADR 0009), a host mode in which Chrome creates no UI of its own (ADR 0010), and the hook seams.

Scope is macOS on Apple Silicon; Windows and Linux are out for now (Dia ships on Mac only, and Arc's Windows port required porting Swift itself). The native app's data root is ADR 0006's, and the Electron data is migrated from a copy, never in place (ADR 0043). The product language in `CONTEXT.md`, the rules in `DESIGN.md`, and ADRs 0001 and 0002 carried over. Each subject since has an ADR of its own, from 0005.

**The engine stays as faithful to Chromium as it can be** (the user, 2026-11-06). Every edit to a Chromium file is carried through each upgrade, so a change goes in `//pane` first, through a seam Chromium already has second, and into a Chromium file only when neither can do it. Cutting a patch of Pane's moves the engine toward the original. Encryption (ADR 0121) and the fingerprint (ADR 0038) stay, as what makes Pane, kept as small as they can be, and a data-loss fix outranks the count.

What was rejected:

- **CEF:** embedding in the app's own NSView forces CEF's Alloy style, which has no extension system (removed in M128), no autofill or password manager, and no Chrome dialogs, covering 167 of the 1,701 methods Arc's app needs; the arc-engine analysis rejected it for Arc for the same reason.
- **The out-of-process design OpenAI uses for Atlas (OWL):** it stays a fallback only.
- **Staying on Electron:** Pane is a browser, Chromium is its substrate, and the shell is native, as Arc's and Dia's are. Pane had stayed on Electron only because the one alternative its July 2026 evaluation weighed was Tauri on WKWebView.
- **Tauri on WKWebView (July 2026):** weighed for its footprint and startup. Every headline feature sits on Chromium's session machinery with no WKWebView path: WKWebView has no extension runtime; fingerprint spoofing needs per-session main-world injection and header rewriting, and WebKit's own fingerprint would betray it; per-profile partitions and proxies need macOS 14 APIs that Tauri/wry does not expose; Google sign-in by CDP cookie import has no cookie-injection API, and Google refuses WKWebView. Tauri's multi-webview, which per-tab views need, is an unstable feature flag with open positioning and rendering bugs. The memory math failed too: the move could only shrink the shell (about 100–130 MB of a 342 MB light session, measured live), while tab content, which grows with use, is the engine's under any webview. Atrium, the closest precedent, tried a WKWebView pane through Tauri and retreated to CEF, adding about 170 MB back plus compositing hacks. Memory is served instead by tab sleep and profile unload (ADR 0041; `CONTEXT.md`: Sleep, Unload, Keep loaded). Revisit only if Pane's identity moves off Chromium-dependent features, or if Tauri stabilizes multi-webview *and* wry exposes per-webview data stores, proxies, and script injection, and even then re-run the memory math.

How it is checked:

- **The count of what the patches edit** (`chromium/patches/*.patch`, each `diff --git` that is not a new file): 121 Chromium files and 1,363 changed lines, with 11 files added, at 0.18.0, and 93, 1,035, and 9 after the review of 0.18.0 cut what `//pane` or a seam could carry. A change that raises it says why.
- **What stays, and why no seam does it** (that review read every hunk):
  - **0001:** `//pane` in `chrome_dll`, the exports, the order check off, and the Keychain's names, which have no gn arg.
  - **0002:** `ChromeMain`'s delegate, and the `AppController` methods (a reopen, opened URLs, the last profile, Handoff) and the main menu, which AppKit's delegate owns.
  - **0003:** a window that stays with no tabs, the window and `WebContentsDelegate` factories, and three places that need a `BrowserView` (toasts, reading mode, the sad tab). `AllowCheckIsTestForTesting` could stand for reading mode's, and was rejected: it also trips `CHECK_IS_NOT_TEST`, which production code holds (`prefetch_container.cc`).
  - **0004:** sign-in, DevTools' one virtual, and the external protocol dialog, whose test delegate would make Pane reimplement six of its behaviors.
  - **0005:** the extension install dialog and `chrome.action.openPopup()`.
  - **0006:** the User-Agent per context, in renderers, navigations, workers, and Client Hints, and what Blink reports, which nothing outside it can change: the fingerprint.
  - **0008:** the crash handler and persistent histograms, which start inside `ChromeMainDelegate` before features are read, the quarantine's URLs, and Gaia's account list.
  - **0009:** a profile that saves no history keeps nothing where Chromium has no per-profile switch: downloads, favicons, engagement, the predictor, and an extension's `history.addUrl`.
  - **0010:** encryption's hooks in each store, and two data-loss fixes (ADR 0121).
- **`docs/benchmarks/native-vs-electron.md`** measures what the move bought: the native app at 0.11.2 against the last Electron release, 0.6.0, on one Mac, by the `benchmark-*` scenarios.
