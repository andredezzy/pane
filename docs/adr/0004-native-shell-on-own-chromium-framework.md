# Native shell on Pane's own Chromium framework

Pane moves off Electron to the architecture Arc and Dia use: a pure-Swift app (AppKit + SwiftUI) that links Pane's own Chromium build, `PaneCore.framework`, in the same process through an Objective-C embedding API. The app's `main` calls `ChromeMain` and Chromium owns the run loop; each tab's native view sits in the app's own view hierarchy, so tabs of several profiles share one window; Chrome's `Browser` objects still exist behind every window but stay hidden, so extension APIs and Chrome internals keep working while every Chrome-owned UI surface is routed to the app as a delegate callback and drawn natively. This supersedes ADR 0003, which kept Electron because the only alternative evaluated was Tauri on WKWebView.

The framework is built from Chromium's `chrome/` layer plus a `//pane` tree, with a small patch series for the framework layout, a host mode in which Chrome creates no UI of its own, and the hook seams. CEF was rejected for the same reason the arc-engine analysis rejected it for Arc: embedding in the app's own NSView forces CEF's Alloy style, which has no extension system (removed in M128), no autofill or password manager, and no Chrome dialogs — covering 167 of the 1,701 methods Arc's app needs. The out-of-process design OpenAI uses for Atlas (OWL) stays a fallback only. Electron, Tauri/wry and WKWebView are out: Pane is a browser, Chromium is its substrate, and the shell is native.

Scope is macOS on Apple Silicon; Windows and Linux are out for now (Dia ships on Mac only, and Arc's Windows port required porting Swift itself). The native app keeps its data in `~/Library/Application Support/com.pane.desktop/`, which collides with no directory the Electron app uses (`@pane/veil`, `@pane/desktop`, `Pane`); the Electron data is migrated from a copy, never in place. The product language in `CONTEXT.md`, the rules in `DESIGN.md`, and ADRs 0001 and 0002 carry over unchanged. Each decision since is an ADR of its own, from 0005.
