# Pane is its own build of Chromium, with its UI inside the engine, not Electron or Tauri

> **On Windows** (`docs/plans/views-migration.md`, W1): the patches edit 91 Chromium files and 1,023 lines, and add 9, from 90, 994, and 9: Windows' `chrome_dll` takes `//pane` (0001, `chrome/BUILD.gn`), its `ChromeMain` builds Pane's delegate (0002, `chrome_main.cc`), and Crashpad, which `chrome_elf` starts there before any switch of Pane's, no longer starts (0008, `chrome_crash_reporter_client_win.cc`, the one file more; ADR 0115). The plan allows 7 more for Windows.

Pane is a browser built as Chromium is, from Chromium's own `chrome/` layer and Pane's `//pane` tree (`pane/`), linked into one framework, Pane's by its branding (ADR 0009), and started by Chromium's own loader and helpers. Its UI is part of that build: C++ with Views, Chromium's own toolkit, calling `chrome/browser` directly as Chrome's own UI does (ADR 0124). Chrome's `Browser` objects still exist behind every window but stay hidden (ADR 0014), so extension APIs and Chrome's internals keep working, while Pane draws every window, and Chrome's own UI stays off (ADR 0010).

It came in two steps. The Electron app gave way, at 0.7.0, to the architecture Arc and Dia use: a native Swift app (AppKit and SwiftUI) that embedded Pane's own Chromium build in the same process through an Objective-C API, its `main` calling `ChromeMain`, each tab's native view in the app's own view hierarchy. That app shipped from 0.7.0 to 0.19.2. Then, at the user's call (2026-11-07), the UI moved into the engine, in Views, one implementation for the Mac and Windows, with no Swift left and no bridge (ADR 0124): measured on Windows, a native Swift shell means WinUI, and Dia, the closest such browser, took about 1.5 s more than Chrome to its window through the same launch, with a window for each layer over the page, where Aside, in Views, took about 60 ms more and draws in one surface. The Swift app, its package PaneKit, the Objective-C API (`pane/public`), and the framework's exports for it are gone from `main`, which the `swift` branch keeps until `main`'s first release (AGENTS.md); the engine's data and formats carried over unchanged (ADR 0122).

The framework is built from Chromium's `chrome/` layer plus `//pane`, with a small patch series: `//pane` in the framework (ADR 0009), a host mode in which Chrome creates no UI of its own (ADR 0010), the hooks for Pane's windows over hidden Browsers (ADR 0014), and the hook seams where Chromium has none.

Scope is macOS on Apple Silicon, where Pane ships; Windows compiles from the same code and comes after the Mac (ADR 0124). The data root is ADR 0006's, and the Electron data is migrated from a copy, never in place (ADR 0043). The product language in `CONTEXT.md`, the rules in `DESIGN.md`, and ADRs 0001 and 0002 carried over from the Electron app. Each subject since has an ADR of its own, from 0005.

**The engine stays as faithful to Chromium as it can be** (the user, 2026-11-06). Every edit to a Chromium file is carried through each upgrade, so a change goes in `//pane` first, through a seam Chromium already has second, and into a Chromium file only when neither can do it. Cutting a patch of Pane's moves the engine toward the original. Encryption (ADR 0121) and the fingerprint (ADR 0038) stay, as what makes Pane, kept as small as they can be, and a data-loss fix outranks the count. Pane's UI calls Chrome's internals directly, so a Chromium upgrade also touches `//pane`: `chromium/UPGRADING.md` counts how much, the standing cost of the UI living in the engine.

What was rejected:

- **CEF:** embedding in the app's own NSView forces CEF's Alloy style, which has no extension system (removed in M128), no autofill or password manager, and no Chrome dialogs, covering 167 of the 1,701 methods Arc's app needs; the arc-engine analysis rejected it for Arc for the same reason.
- **The out-of-process design OpenAI uses for Atlas (OWL):** it stays a fallback only.
- **The native Swift shell, kept on the Mac beside a second UI for Windows,** or ported to Windows on WinUI: two UIs, or a bridge and a toolkit with a window per layer over the page (ADR 0124).
- **Staying on Electron:** Pane is a browser, Chromium is its substrate, and the shell is native, as Arc's and Dia's are. Pane had stayed on Electron only because the one alternative its July 2026 evaluation weighed was Tauri on WKWebView.
- **Tauri on WKWebView (July 2026):** weighed for its footprint and startup. Every headline feature sits on Chromium's session machinery with no WKWebView path: WKWebView has no extension runtime; fingerprint spoofing needs per-session main-world injection and header rewriting, and WebKit's own fingerprint would betray it; per-profile partitions and proxies need macOS 14 APIs that Tauri/wry does not expose; Google sign-in by CDP cookie import has no cookie-injection API, and Google refuses WKWebView. Tauri's multi-webview, which per-tab views need, is an unstable feature flag with open positioning and rendering bugs. The memory math failed too: the move could only shrink the shell (about 100–130 MB of a 342 MB light session, measured live), while tab content, which grows with use, is the engine's under any webview. Atrium, the closest precedent, tried a WKWebView pane through Tauri and retreated to CEF, adding about 170 MB back plus compositing hacks. Memory is served instead by tab sleep and profile unload (ADR 0041; `CONTEXT.md`: Sleep, Unload, Keep loaded). Revisit only if Pane's identity moves off Chromium-dependent features, or if Tauri stabilizes multi-webview *and* wry exposes per-webview data stores, proxies, and script injection, and even then re-run the memory math.

How it is checked:

- **The count of what the patches edit** (`chromium/patches/*.patch`, each `diff --git` that is not a new file): 121 Chromium files and 1,363 changed lines, with 11 files added, at 0.18.0; 93, 1,035, and 9 after the review of 0.18.0 cut what `//pane` or a seam could carry; and 90, 994, and 9 once the UI was in Views, which took three more out: sign-in moved to the seam Chromium keeps for it, `ChromeContentBrowserClient::CreateHttpAuthCoordinator` (`pane/ui/dialogs/sign_in.h`), out of `login_handler_views.cc`; `chrome.action.openPopup()` reaches Pane's popup through the `ExtensionsContainer` Pane registers for each Browser it hosts (`pane/ui/extensions/browser_extensions.h`), as `webui_browser_window.cc` registers its own, out of `extension_action_api.cc`; and `framework.exports` went back to Chromium's, its order check in `chrome/BUILD.gn` with it, once no app linked the framework (ADR 0009). A change that raises it says why. The migration aimed at 89 or fewer, and the user kept 90 (2026-11-11): the next out would be reading mode's hunk in 0003, a `SidePanelUI` seam that hands its 38 or so callers a panel that does nothing.
- **What stays, and why no seam does it** (the review of 0.18.0 read every hunk, and the Views line each it touched):
  - **0001:** `//pane` in `chrome_dll`, and the Keychain's names, which have no gn arg.
  - **0002:** `ChromeMain`'s delegate, and the `AppController` methods (a reopen, opened URLs, the last profile, Handoff) and the main menu, which AppKit's delegate owns.
  - **0003:** a window that stays with no tabs, the window and `WebContentsDelegate` factories, and three places that need a `BrowserView` (toasts, reading mode, the sad tab). `AllowCheckIsTestForTesting` could stand for reading mode's, and was rejected: it also trips `CHECK_IS_NOT_TEST`, which production code holds (`prefetch_container.cc`). A `SidePanelUI` of Pane's, registered for each hosted Browser as `SidePanelUIBase` registers itself, could stand for it too, at the price of about 38 callers getting a panel that does nothing where they now get none: not taken yet.
  - **0004:** DevTools' one virtual, and the external protocol dialog, whose test delegate would make Pane reimplement six of its behaviors, and which has no view factory.
  - **0005:** the extension install dialog, which has no view factory either; its hook calls Pane's dialog (`pane/ui/dialogs/add_extension`).
  - **0006:** the User-Agent per context, in renderers, navigations, workers, and Client Hints, and what Blink reports, which nothing outside it can change: the fingerprint.
  - **0008:** the crash handler and persistent histograms, which start inside `ChromeMainDelegate` before features are read, the quarantine's URLs, and Gaia's account list.
  - **0009:** a profile that saves no history keeps nothing where Chromium has no per-profile switch: downloads, favicons, engagement, the predictor, and an extension's `history.addUrl`.
  - **0010:** encryption's hooks in each store, and two data-loss fixes (ADR 0121).
- **`docs/benchmarks/native-vs-electron.md`** measures what the move off Electron bought: the native app at 0.11.2 against the last Electron release, 0.6.0, on one Mac, by the `benchmark-*` scenarios; **`docs/benchmarks/views-shell.md`** measures the Views UI against the last Swift release, 0.19.2.
