# Extensions' own menu items and site access show where Chrome shows them, and Chrome's reload prompt after a change is declined without a dialog

**An extension's own items.** The items an extension adds with `chrome.contextMenus` show in the page's right-click menu and in its pinned action's, laid out by Chrome's own `ContextMenuMatcher`. The order, the grouping (an extension with several items gets one submenu under its name), titles cut at 75 characters with the selection in them, radio groups, separators, and the action menu's limit of six top-level items are all Chrome's. An item runs through the matcher, so `MenuManager` updates a checkbox's or a radio group's state and sends `onClicked`: a page item with the page, frame, and tab; an action item, as Chrome's does, with the active tab and no page. Before, neither menu showed them: an extension such as a password manager that saves or fills from the right-click menu had no way in.

- **The page's menu** is Chrome's own `RenderViewContextMenu`, the Mac's `NSMenu` (ADR 0058), so its extensions' items are Chrome's, in Chrome's slot, each with its icon; Pane only takes off its model what Pane can't support (`pane/ui/page/page_context_menu`).
- **A pinned action's right-click menu** is Pane's `ActionMenu` (`pane/ui/extensions/action_menu.h`), one `ui::SimpleMenuModel` shown as the system's menu, plain as Aside's, with no icons and in Title Case (Paper 04.13 to 04.13.2). It takes the extension's items in its action's context through a copy of Chrome's `MenuItemMatchesAction`, which is private to `extension_context_menu_model.cc`, and runs each as Chrome's model does. It is made as it is asked for, for the page the action shows on, so it always shows the current choice.

**Its site access.** A pinned action's right-click menu lists the extension's site access, as Chrome's and Aside's do: This Can Read and Change Site Data, a submenu of When You Click the Extension, On <site>, and On All Sites, the current one checked, then Learn More About Site Access. Where the extension can't run on the page, the menu reads Can't Read or Change Site's Data, disabled, instead. View Web Permissions follows Manage Extension. Both rows show only for an extension that asks for site access, by host permissions or activeTab. Paper drew it first: 04.13.1 and 04.13.2, light and dark, approved by the user (ADR 0058).

- **The menu:** its name; the extension's own items; its site access; Remove from Pane and Unpin; then Manage Extension and View Web Permissions. A separator stands between each group.
- **The items** are Chrome's page access items, as `ExtensionContextMenuModel::CreatePageAccessItems` makes them on the path without `kExtensionsMenuAccessControl`, the menu Aside shows. Each carries Chrome's title-case strings and command IDs, with `PermissionsManager` deciding which choices show, which are enabled, and which is checked, for the page's origin. The site is the host without www, as Chrome's `GetCurrentSite`. The apostrophes are typographic, as the app's own text and the boards set them; Chrome's strings use straight ones.
- **Choosing one** goes through `SitePermissionsHelper::UpdateSiteAccess`, while the tab is still at the origin the menu was made for, and only for an extension whose access the user can change. Learn More opens Chrome's help article (`kRuntimeHostPermissionsHelpURL`, support.google.com/chrome?p=enable_extensions) in a new tab of the window, as Chrome's `OpenUrl` does.
- **View Web Permissions and Manage Extension** open the extension's Details on Chrome's own page, chrome://extensions/?id=, in the profile's tab (ADR 0062), whose site list holds the site On <site> grants.

**Chrome's reload prompt is declined.** When an extension's site access changes on a page, Chrome asks to reload it: "Reload this page to apply your updated settings on this site", with Reload and Cancel. Choosing When You Click the Extension put Chrome's own sheet on Pane's window, where Pane's tabs show no Chrome dialog (ADR 0021). Pane declines the prompt at once, as it declines the device choosers (ADR 0022): the page keeps what it has and takes the change at its next load. The seam is `ReloadPageDialogController::AcceptDialogForTesting(false)`, held for the process (`pane/browser/ui/ui_hooks.cc`), which answers Cancel in `ExtensionActionRunner::ShowReloadPageBubble`, the one place Chrome shows the prompt from. It serves both a site access change (`SitePermissionsHelper`) and a click on an action whose blocked scripts need a reload. It replaced a hook of Pane's in `extension_action_runner.cc` in the review of 0.18.0, under ADR 0004's rule; a test-named API that goes away is a compile error at an upgrade, as a conflict would be. Chrome's "added" bubble goes the same way (`ExtensionInstallUI::disable_ui_for_tests`).

Until 0.20.0 the Swift app drew both menus itself, from the items an engine class of Pane's (`ExtensionMenu`) gathered through the same matcher, and the page's menu followed the Electron app's order; the move to Views took Chrome's own page menu, with the user's approval on Paper (ADR 0124, U2).

What was rejected:

- **Matching the items in the app from `MenuManager`'s list:** it would repeat Chrome's matching, grouping, and limits, and drift from them.
- **Listing the action's items in the extensions menu's more menu too:** Chrome's menu there does, but Aside's, which Pane's follows (ADR 0054), does not. An unpinned extension's action items show once it is pinned.
- **Chrome's `ExtensionContextMenuModel` for the action's menu:** it needs a Browser with Chrome's toolbar, and it carries Chrome's other items (Options, Remove with Chrome's dialog, the side panel, Rate it), which Pane's menu draws itself or leaves out.
- **The kExtensionsMenuAccessControl wording** (Ask on Every Visit, Always on <site>): Chrome keeps that feature off on the desktop, and Aside shows the classic wording.
- **Straight apostrophes:** the boards, and every string of the app's, set typographic ones.
- **Chrome's reload sheet:** Chrome's UI on Pane's window, which ADR 0021 rules out.
- **Reloading at once:** it would throw away what the page holds, such as a form being filled, without asking.
- **A reload prompt of Pane's own:** it would be a new design, which Paper draws first (ADR 0058). Until one is drawn and approved, the change waits for the page's next load.

How it is checked:

- **The `extension-context-menus` scenario,** with a probe extension (`tests/pages/extensions/context-menus`) that adds two page items and two action items, and asks for every site:
  - **The page's menu,** Chrome's own, has the probe's two page items in a submenu under its name, in Chrome's slot before View Page Source. Choosing each runs `onClicked` with the page's URL and its tab, and the checkbox shows its new state the next time.
  - **The action's items** come from the menu's own model, which the channel reads (`extensionActionMenu`): Probe action item, then Probe action check, checked. Choosing the first runs `onClicked` for the page's tab, with no page.
  - **The action's site access** reads the submenu with On All Sites checked, and Learn More after the choices. When You Click the Extension leaves the probe without `<all_urls>`, as `chrome.permissions.getAll` reports it. On 127.0.0.1 grants that site alone, and On All Sites gives every site back. After each, the submenu shows the choice checked. On a data: page the menu reads Can't Read or Change Site's Data, disabled.
  - **The reload prompt:** after When You Click the Extension, no window but the main one shows. Before the answer, Chrome's sheet showed there.
- **The `extensions-menu` scenario:** Manage Extension opens the extension's Details.
- **The `context-menu`, `extensions-page-profile`, `tabs-api`, and `smoke` scenarios** pass.
