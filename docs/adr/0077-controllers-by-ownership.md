# The model lives in pane/model and changes only through the controller's intents, and controllers are split by what they own

The browser's state, `model::BrowserModel` (`pane/model/browser_model.h`), is plain C++ that knows no engine, no view, and no file, so its rules run in tests without a browser (ADR 0124). `UiApp` (`pane/ui/app/ui_app.h`) is the controller, and only its intents change the model, each also doing what the change asks of the engine, so the sidebar, the profile sheet, Settings, the menu bar, the switcher, and the automation channel, which calls them in the UI's place (ADR 0018), cannot drift apart. Every intent that acts on the browser asks `InteractionAllowed()` first, wherever it comes from (ADR 0042).

**Controllers by what they own.** `UiApp` owns the model, the window, and the switcher's state, which `TabSwitcherView` draws; `SleepController` runs Sleep, Unload, and Trim (ADR 0041); `ExtensionsUi` the extensions' prompts and shortcuts, while Chrome's own page manages them (ADR 0062); `ProfileContexts` (`pane/browser/profile_contexts.h`) the profiles' contexts, their waiters, and the work a lock waits for, so the lock's ordering is in one place (ADR 0116); and `ModelStore` the files (ADR 0068).

**The model.** `BrowserModel` waits 300 ms after the last change before it saves (`kSaveDelay`), and each save hands a copy of what changed to the store (ADR 0068). A settings change that changes nothing writes nothing (the sidebar's reset to its width, say). Its tests (`browser_model_unittest.cc`) cover insertion after an anchor, removal into the closed tabs, a deleted profile's tabs, the selection and its observers, clamped moves (a negative destination no longer traps), what an edit changed, the timestamps, and the debounced save: one write per burst, only the changed file, nothing for an unchanged tab, `SaveNow` at once, and a failed write asked again. The rules beside it have files and tests of their own: the extensions' prompt text (`extension_text.h`, ADR 0056), the crash loop (`crash_loop.h`, ADR 0027), the switcher (`tab_switcher.h`), the reorder (`reorder.h`, ADR 0066), and the toolbar's progress (`toolbar_progress.h`, ADR 0081).

**One intent per change.** An edit returns what changed (`ProfileChanges`: the proxy, the fingerprint, the history), and the intent applies it, so no second subscriber can silently drop the first. The profile sheet keeps one `ProfileDraft` (`pane/model/profile_draft.h`): what it starts from, what keeps it from saving (the name, then the proxy's host and its port, the first problem shown as a red ring around its field, ADR 0120), and what it saves, which the controller applies. The channel's `createProfile` builds a `ProfileDraft` and calls the same intent as the sheet's Create, spoofing off unless the command asks (`spoof`), so scenarios' pages still see the engine's own values (ADR 0018, ADR 0038).

It came from a review of the Swift app's architecture (2026-10-28), which moved its model into PaneKit, a package that knew no engine and no file, made it read-only outside it, and split a 1,253-line `BrowserController` by what each part owned; behavior stayed as it was, and every scenario (59) passed on the final build. The move to Views ported the model and its rules, with their tests, to `pane/model` (`docs/benchmarks/panekit-tests.md`), and the Swift app's controllers went with it (ADR 0124).
