# The model lives in PaneKit and changes only through the controller's intents, and controllers are split by what they own

The browser's state, `BrowserModel`, lives in PaneKit, where it knows no engine and no file, so its rules run in tests. It is read-only outside PaneKit, and only the controller's intents change it, each also doing what the change asks of the engine, so the sidebar, the profile sheet, Settings, the menu bar, and Automation, which calls them in the UI's place, cannot drift apart. The app's controllers are split by what each one owns. It came from a review of the architecture (2026-10-28). Behavior stayed as it was, and every scenario (59) passed on the final build, against the frozen engine, `complete` in each report.

**Controllers by what they own.** `app/Pane/Browser/BrowserController.swift` went from 1,253 lines to 945, beside `+Intents` (136) and `+Actions` (152). `ExtensionsController` owns each profile's extension list (out of `BrowserModel`, which keeps no `NSImage` or `NSColor`), the puzzle's menu, the more menu, the add and remove popups and their Report abuse box, the toolbar's anchors, the Extensions page's anchor, and the action popover. Seven fields left `WindowState`, and the extension views take it, not the browser controller. `PageRegistry` holds each loaded tab's `WebContents` both ways, its docked DevTools, and the tab an inserted page takes (`opening(_:)`, in place of a `pendingTabID` set and cleared around the call); the controller still decides when a page comes and goes.

Views take what they use where that is clean: Settings takes the settings, the lock, the updater, and the change it makes; the profile sheet the profile and its save; the extension views their controller. The root, the sidebar, the toolbar, and find keep the controller, for its intents. Of the 10 view types that took the whole controller, 7 still do, all intent callers. The feature has its folder: `app/Pane/Extensions/` holds the controller, the popover, the model, the menu, the popups, the page, and the actions, and `VerticalReorder` and `WindowDragArea` joined the view layer's `app/Pane/Views/Components/` (ADR 0070).

**The model in PaneKit.** `BrowserModel` takes its timestamps and its 300 ms save wait from a clock (`BrowserModel.Clock`), and each save hands a copy of what changed to a `persist` closure. `ModelStore` (`app/Pane/Model/ModelStore.swift`), in the app, reads `settings.json`, and `profiles.json`, sealed under the data key with each proxy's password in it (ADR 0113), reading once the passwords an earlier Pane kept apart (ADR 0037). It writes on its utility queue, as ADR 0068 made it: the main thread still only copies. A settings change that changes nothing writes nothing (the sidebar's reset to its width, say). PaneKit's 14 model tests cover insertion after an anchor, removal into the closed tabs, a deleted profile's tabs, selection and its MRU, the selection's observers, clamped moves (a negative destination no longer traps), an edit's proxy and fingerprint changes, the clock's stamps, an unloaded tab's state, and the debounced save (one write per burst, only the changed file, nothing for an unchanged title, `saveNow` at once). Two rules went to PaneKit with the model, each with tests: `ExtensionPromptText` (Add … to Pane?, curled quotes, Report abuse's URL; ADR 0056) and `CrashLoop` (a second crash within a minute shows the sad tab; ADR 0027).

**One intent per change.** `app/Pane/Browser/BrowserController+Intents.swift` changes the model: `createProfile(draft)`, `saveProfile`, `updateProfile`, `setKeepLoaded`, `moveProfile`, `moveTab`, `expandProfile`, `collapseProfile` (collapse unloads), `toggleProfile`, `collapseAll`, `showPage` (it hides the page under Settings and Extensions, which the model's `pageDidChange` did; `toggleSettings` calls it), `changeSettings` (a theme applies at once, ADR 0001), and `presentProfileSheet`.

The single-slot callbacks are gone. An edit returns what changed (`ProfileChanges`: proxy, fingerprint), and the intent applies it, so no second subscriber can silently drop the first. The sleep clocks watch the selection through `observeSelection`, a list (ADR 0041). The lock's `didUnlock` stays one slot: it has one subscriber and is not the model's. The contexts, their waiters, and the work a lock waits for are `ProfileContexts`', which the controller owns, so the lock's ordering is in one place (ADR 0116).

Automation's `createProfile` is the sheet's Create. It made a profile with no fingerprint and no proxy test, where the sheet generated one; it now builds a `ProfileDraft` and calls the same intent, spoofing off unless the command asks (`spoof`), so scenarios' pages still see the engine's own values (ADR 0018, ADR 0038).

The profile sheet keeps one `ProfileDraft`, PaneKit's (`app/PaneKit/Sources/PaneKit/ProfileDraft.swift`): `init(profile:)`, `validate()` (the name, then the proxy's host and its port, through `ProxyConfig.port`, the first problem shown as a red ring around its field, ADR 0120), the proxy it saves, the paste shortcut, and `apply(to:generate:)`. Sixteen `@State`s became five, and 11 tests cover the draft.

**Observation granularity was measured, and left as it is.** The toolbar reads every tab's loading progress, so a background tab's load can run its body. Counted with each body logging itself, 20 background reloads across 5 tabs ran the toolbar's body 8 times, as many as 4 reloads of the selected tab did: SwiftUI coalesces the changes per frame. Per-tab observable objects would save nothing visible. The sidebar's sections and rows, which did run for changes they do not show, take values instead (ADR 0073).
