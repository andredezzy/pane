# Pane's data root is its identifier's folder, with the engine's profiles under Engine

> **Partly replaced by [ADR 0113](0113-profile-data-encrypted-under-a-key-the-pin-releases.md)** — each `Engine/<profile id>`, and its caches' folder, is a link into an encrypted volume attached at `Engine/Volume`, whose image is in the data root — **by [ADR 0114](0114-pane-identifier-is-xyz-roundedcorners-pane.md)**: the data root's and the caches' folders are `xyz.roundedcorners.pane`, no longer `com.pane.desktop` — **and narrowed by [ADR 0115](0115-nothing-outside-the-volume-names-a-page.md)**: `PANE_DATA_DIR` and `--user-data-dir` count only in a scenario's launch, and the data root and its caches are 0700.

The native app keeps its data in `~/Library/Application Support/<identifier>/` (ADR 0004), `com.pane.desktop` until 0.14.0, because that folder collides with none of the Electron app's directories (`@pane/veil`, `@pane/desktop`, `Pane`); the Electron app's data is migrated from a copy, never in place (ADR 0043). Pane's own JSON state (`profiles.json`, `settings.json`, and the others) stays at the root. The engine's user data dir is `Engine/` inside it, and each profile is `Engine/<profile id>`.

The profiles sit directly under the user data dir because Chromium accepts nothing else: `ProfileManager::IsAllowedProfilePath` only accepts profile directories whose parent is the user data dir, so `<data root>/Profiles/<id>`, the plan's first sketch, would be refused. The launch finds the root before the engine starts (`PrepareData`, `pane/app/data_launch_mac.cc`), and Chrome starts with `--user-data-dir=<root>/Engine` unless a scenario's launch names one (`pane/app/engine_switches.cc`); the Swift app handed the engine the root through its Objective-C API (`+runWithDelegate:dataDirectory:`). Chromium keeps a profile's caches at the same path under `~/Library/Caches` (`<identifier>/Engine/<profile id>`), so removing a profile's data means both folders (ADR 0020).

In a scenario's launch, `PANE_DATA_DIR` replaces the root. Every scenario sets it to a throwaway folder, or gives the app a throwaway home to derive it from (`derivedDataRoot`, `tests/lib/browser.ts`, `tests/lib/pane.ts`), so no scenario reads or writes the user's data.
