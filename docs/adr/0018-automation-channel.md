# Scenarios drive the app through a test-only automation channel

> **Narrowed by [ADR 0115](0115-nothing-outside-the-volume-names-a-page.md)**: the channel opens only in a scenario's launch, on the mock keychain (`model::TestHook`), where none of the user's data opens; a process of the user's starting Pane with `PANE_AUTOMATION_DIR` had read every tab of a launch without a PIN. The reason given below for not gating it, that whoever sets a launch's environment can read the data directory itself, ended with ADR 0113's encryption.

Scenarios drive the app through an automation channel (`pane/automation/`) that opens only when `PANE_AUTOMATION_DIR` is set in a scenario's launch (`model::TestHook`, `pane/model/test_hooks.h`; `UiApp` makes it as it starts), so they exercise the app's own paths while a shipped Pane never opens it on the user's data. The runner drops JSON commands into `<dir>/in/<n>.json`, and the app replies, with a snapshot of what shows, in `<dir>/out/<n>.json`. Both sides watch their folder rather than poll it: the app through `base::FilePathWatcher` (kqueue on the Mac, ReadDirectoryChangesW on Windows), the runner through `fs.watch`, with a look every 250 ms in case an event goes missing (`tests/lib/pane.ts`). A command the app can't read yet, or reads empty, stays and is read again 20 ms later, the commands after it waiting their turn: Windows can hold a file just moved into the folder for a moment, and the first scenarios run there each lost their first command to an empty read, answered as an unknown command. Commands call what the UI calls, the controller's intents (ADR 0077), and CDP stays for reading pages, CUA for what only the screen can prove (ADR 0012).

**Input is real.** Keys, clicks, hovers, and scrolls are posted through the platform's event path to the window (`pane/automation/input.h`; on the Mac `NSEvent`s in the app's queue, `native_input_mac.mm`), so what handles the user's handles them: the window's accelerators, the focused view, and the page (ADR 0079). On Windows each is the event the window's message handler makes of Windows' message (`HWNDMessageHandler`: a `ui::KeyEvent` of the key's message, its scan code in it, the modifiers held as its flags, as Views' own test helper builds Windows' keys; a `ui::MouseEvent`), handed to the window's event sink, aura's dispatcher, where `DesktopWindowTreeHostWin` hands a message's (`input_win.cc`): the input method, Views' accelerators and focus, the page. A key's character is posted to the window's queue first, as TranslateMessage posts it, where the input method takes it with the key and drops it if the key was handled. Keys and clicks run after what the channel did before, as the Mac's queue runs them; moves and scrolls at once, as the Mac's go to the window. Never through `SendInput`, which reaches whatever window is in front, nor through Windows' own mouse messages, whose tracking answers a move at once with a leave where the real pointer isn't and drops a scroll over another app's window: a run behind the user's windows works on both systems (ADR 0012). `dispatchKey` hands a key to the window itself, in the background too, its half (`phase`) and the modifiers as keys, so Ctrl's release reaches Views. `menu` chooses an item through the real menu bar, its titles and enabled states brought up to date first, as when it opens, then `performActionForItemAtIndex:`, as a click; it answers whether the item ran, which behind the Lock only Check for Updates… and Quit do. `menuBar` reads every item's title, key, and state. A hover posted over the page goes to the page's view, and one at the window's edge to its frame, not to Views, so a rig leaves the pointer over a part of Pane's own, such as the sidebar's empty list.

**Names are Pane's.** The channel names what has the keyboard, and the parts of the window, by Pane's view ids (`pane/ui/view_ids.h`: `pane.content`, `pane.toolbar.address`, `pane.profileSheet`, `pane.switcher.tab.<id>`, `pane.dialog.field.<n>`), not by a toolkit's classes or a field's placeholder. `frames` gives each named part's place in the window, and `hitTest` says what a press at a point would reach: the page, a view of Pane's, the frame, which moves the window, or the frame's own controls, on Windows as the window's dispatcher finds it (aura's targeter: a page's own window, or Views', which may answer HTCAPTION). `state` reads the rest: the toolbar's controls, the switcher's groups and selection, the dialog showing (`sheet`), those waiting (`pendingRequests`), the app-modal panel (`modal`), and every visible window of the process by its role (`nativeWindows`): on the Mac `NSApp.windows`; on Windows the top-level windows Windows lists, a widget's by its name (Views' menus are `MenuHost`), the system's dialogs (class `#32770`) owned by the window as its sheet while a file panel is asked for, else as the app-modal panel, and the shadows Windows draws for a popup in windows of their own left out, each window's text read as Windows keeps it, asking no window of another thread (`windows_win.cc`).

**Dialogs and panels are answered as a person would.** `clickSheetButton` clicks a page dialog's button for real, at its middle; `fillSheet` fills its fields as accessibility does; `dialogAccessibility` reads what VoiceOver gets of it. `answerFileChooser` answers the system's open or save panel from beside it (`pane/automation/file_panels.h`: the stock panel, behind a listener of the channel's, set only while the channel runs); `modalHost` reads where Chrome's tab-modal dialogs show, and `clickModalButton` presses the print panel's button. On Windows the stock file dialog runs on a thread of its own and stays up once let go of, showing even after the channel's answer: the channel closes it as it shows, as its Cancel does, and starts the next once the one before has ended and given its window back, since Chromium shows one system dialog at a time (a second, while the first was up, ended the browser at `AutoCloseDialogEventHandler`'s check, 2026-11-13; `file_panels_win.cc`). Windows 11's print dialog is the shell's, drawn in its own process over Pane's disabled window (an `ApplicationFrameWindow`, tied to the window by the shell's `ProxyModalWindow`): `modal` reads its title once it has one (a frame closed sooner once left the page's `print()` waiting), and its buttons, XAML's, are no windows, so none is listed and `clickModalButton` takes Cancel as its close button, which cancels it the same way; the others wait on UI Automation.

**What only the scenarios read is read apart from what the app does.** The snapshot is a file of its own (`pane/ui/app/ui_app_snapshot.cc`). The page's menu is held only while it is on its way, shown, or going (`PageContextMenus::held`), so a closed menu is let go with the page its items hold: the Swift app's controller had held the last menu strongly for the channel, which kept a closed menu, its items, and their page alive, and an item could run against a closed tab. `context-menu` checks that the menu is let go once it closes and its items no longer run.

Gating the channel on the PIN lock (ADR 0042) was not done: the channel existed only for scenarios, whoever set a launch's environment could read the data directory itself, and its commands that open or show pages went through what the lock already gated. ADR 0113 encrypted the data, which ended the second reason, and ADR 0115 gated the channel on a scenario's launch instead.

Until 0.20.0 the channel was the Swift app's (`app/Pane/Automation/`), the same JSON in the same folders, read by polling: split by concern into the poller, the commands, one builder for each mouse and key event, and the snapshot, with a probe (`AutomationProbe`) as the controller's view of what only scenarios read. `pane/automation/` replaced it whole.

How it is checked: every scenario (`tests/scenarios/`) runs through it, on the Mac and, those that run on both systems, in the Windows test VM (`docs/building.md`, Scenarios); `context-menu` checks a closed menu's release; `pane_unittests`' `TestHooksTest` checks that a launch off the mock keychain reads no test hook, the channel's directory among them (ADR 0115).
