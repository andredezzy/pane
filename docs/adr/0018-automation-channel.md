# Scenarios drive the app through a test-only automation channel

> **On the Views line** (`docs/plans/views-migration.md`, H1): the channel names what has the keyboard, and what a press would reach, by Pane's view ids (`pane/ui/view_ids.h`: `pane.content`, `pane.toolbar.address`, `pane.profileSheet`), not AppKit's classes or a field's placeholder; `hitTest` also says who takes the press (the page, Pane's views, the frame, which moves the window, or the frame's own controls).

> **Narrowed by [ADR 0115](0115-nothing-outside-the-volume-names-a-page.md)**: the channel opens only in a scenario's launch, on the mock keychain (`TestHooks`), where none of the user's data opens; a process of the user's starting Pane with `PANE_AUTOMATION_DIR` had read every tab of a launch without a PIN. The reason given below for not gating it, that whoever sets a launch's environment can read the data directory itself, ended with ADR 0113's encryption.

> **On the Views line** (`docs/plans/views-migration.md`, H4): a hover the channel posts over the page goes to the page's view, and one at the window's edge to its frame, not to Views, so a rig leaves the pointer over a part of Pane's own (the sidebar's empty list). The toolbar's controls and the update pill's are named in `frames`, and `state.toolbar` reads each control's state, where accessibility read them.

> **On the Views line** (`docs/plans/views-migration.md`, H5): `switcher`, `reloadCrashed`, `setSleepSettings`, `readCacheSize`, and `readCookies` come over; `menu` answers whether an item ran; `frames` names the switcher's rows (`pane.switcher.tab.<id>`) and the sad tab's Reload; `state.switcher` lists the switcher's groups and selection.

> **On the Views line** (`docs/plans/views-migration.md`, H7): `menu` chooses an item through the real menu bar (the NSMenu brought up to date, then `performActionForItemAtIndex:`, as a click), `menuBar` reads every item's title, key, and state, and `dispatchKey` takes a half of a key (`phase`) and the modifiers as keys, so Ctrl's release reaches Views in the background.

> **On the Views line** (`docs/plans/views-migration.md`, What Chrome asks for): `clickSheetButton` clicks a page dialog's button for real at its middle, `fillSheet` fills its fields as accessibility does, `dialogAccessibility` reads what VoiceOver gets of it, `answerFileChooser` answers the system's panel beside it, `typeInPage` hands the focused page a key through the window, `modalHost` reads where Chrome's tab-modal dialogs show, and `clickModalButton` presses the print panel's button; `state` names the dialog showing (`sheet`), those waiting (`pendingRequests`), and the app-modal panel (`modal`); `frames` names the dialog (`pane.dialog`, `pane.dialog.field.<n>`, `pane.dialog.button.<n>`).

Scenarios drive the app through an automation channel that exists only when `PANE_AUTOMATION_DIR` is set, so they exercise the app's own paths while a shipped Pane carries none of it. The runner drops JSON commands into `<dir>/in/`, and the app replies, with a snapshot of its state, in `<dir>/out/`. Commands call the same intents and actions the UI calls (ADR 0077). Key presses are real `NSEvent`s posted to the app's event queue, so they go through the key monitor (ADR 0079) and menu key equivalents as typed keys do. CDP stays for reading pages, and CUA for anything the screen must show (ADR 0012).

The channel is split by concern, in `app/Pane/Automation/`. `Automation.swift` polls and replies. `Automation+Commands.swift` groups the commands by what they drive (profiles, tabs, the page, input, dialogs, extensions, security, updates, the app), with `AutomationCommand` reading the fields. `Automation+Events.swift` builds every mouse and key event, one builder each, where `clickPage` and `typeInPage` had built their own. `Automation+Snapshot.swift` reads the state, and `AutomationProbe.swift` declares the probe.

Test-only state stays out of the shipped types. `AutomationProbe` is the controller's view of what only scenarios read: a page printing, the context menu, downloads, a profile's data going. The controller's probe is nil unless `PANE_AUTOMATION_DIR` is set in a scenario's launch (`TestHooks`, ADR 0115), and held weakly; `Automation` is the probe. The controller's `lastContextMenu`, `contextMenuOpen`, and `pendingDeletions`, and the download notification are gone from the app's own types. Automation holds the context menu weakly: the controller's strong hold had kept a closed menu, its items, and their page alive, and an item could run against a closed tab. `context-menu` checks that the menu is let go once it closes and its items no longer run; before, it stayed held.

Gating the channel on the PIN lock (ADR 0042) was not done. The channel existed only for scenarios, whoever set a launch's environment could read the data directory itself, and its commands that open or show pages go through `select`, which the lock already gates. ADR 0113 encrypted the data, which ended the second reason, and ADR 0115 gated the channel on a scenario's launch instead.
