# The Electron app's data migrates once, from a copy, before anything loads

On the first launch with no native data, before anything loads, Pane migrates the Electron app's data once, from a copy, and never writes the source, so the profiles, tabs, PIN, and site data come over while the Electron app's own data stays as it was (`app/Pane/main.swift`, `app/Pane/Migration/LaunchMigration.swift`, PaneKit's `ElectronMigration`). `migration.json` records the migration, so it runs once.

The source is the shipped Electron app's data: `~/Library/Application Support/@pane/veil`, or `@pane/desktop` (the package's name before its rename on 2026-05-05), whichever's `profiles.json` changed last (`ElectronMigration.defaultSource`). The first version read `~/Library/Application Support/Pane`, and was corrected the same day (Phase 6): `apps/veil/package.json` has no top-level `productName` (electron-builder's `build.productName` names only the bundle), so Electron runs the app under its package name, and the installed 0.6.0 app keeps its data in `@pane/veil`. The scenario had hidden this and the Keychain item's name (below), since its seed set the name to "Pane" and used the mock keychain.

Its JSON files and each profile's partition (`Partitions/profile-<id>`, which Electron names in lowercase) are copied into a staging folder, without caches or the Electron session's own files, and Pane imports from that copy only. The partition becomes the profile's engine directory (ADR 0006), and Chromium moves its root `Cookies` into `Network/` as it opens it. The copy runs on a thread of its own, and one that takes over a second shows a note ("Bringing over your profiles") until it is done, so the first launch never looks hung; the log line gives its duration. The copy replaces a `settings.json` or `security.json` that a cut-short migration left in the data directory, on which the next run used to throw "file exists", and `profiles.json` still moves last, as the commit. Extensions stay behind: each profile adds its own from the Web Store and finds its saved data in the copied partition (ADR 0031).

What stops a migration is `migration.json`, or a `profiles.json` with profiles in it (or one that cannot be read): native profiles are never replaced. An empty list does not, so a launch that made nothing, such as one beside the running Electron app before the fix below, still migrates; writing a record on a fresh install (`noSource`) was not needed for that. The panic wipe keeps `migration.json`, so a wiped Pane never migrates again (ADR 0042).

The migration waits while the Electron app runs, which its `SingletonLock` shows by naming a live process. Until the safety review (2026-10-27) it skipped instead: a first launch beside the running Electron app logged `sourceInUse`, started empty, and saved `profiles.json`, so the next launch found native data and never migrated, and a thrown migration did the same. Now, while the Electron app runs, Pane writes nothing and says so, "Quit the old Pane to continue", in a system alert (`CFUserNotification`, in `app/Pane/Migration/LaunchAlert.swift`, since nothing may touch NSApplication before the engine). It goes on by itself once the Electron app quits, or quits on Cancel. Polling until the pid went, with no word, was rejected: Pane would look hung. The lock's pid must be an Electron app: alive (or `EPERM`, another user's), with `proc_pidpath` naming a bundle that has `Electron Framework.framework` in it, since a stale `SingletonLock` whose pid came back as another process held the migration back for good.

Cookies stay decryptable. The engine's Keychain item is "Pane Safe Storage" with account "Pane" (patch `engine/patches/0001-pane-framework.patch`), where Chromium's would be "Chromium Safe Storage". Electron names its item after the package, "@pane/veil Safe Storage" with account "@pane/veil", because the app's script runs (`app.name = productName || name`) before Electron names the item (`ElectronBrowserMainParts::PostCreateMainMessageLoop`, Electron 41). After migrating, Pane copies the Electron app's key into its own item (`app/Pane/Security/SafeStorage.swift`); macOS asks the user once, and a one-time Allow is enough. The engine keeps a name of Pane's own, and new installs never carry the Electron package's name. Renaming the engine's item to the Electron one was rejected: it fits only one of the two package names, and it needs an engine rebuild. A Deny at macOS's prompt asks again in a system alert ("Keep your sign-ins?": Try Again, or Continue Signed Out), since a Pane without the key signs the migrated sites out for good once the engine makes a key of its own. When the Keychain cannot ask at all (a locked session, `-25320`), `migration.json` keeps `cookieKeyPending`, and a later launch tries again while the engine has no "Pane Safe Storage" item yet (`SafeStorage.hasEngineKey()` reads attributes only, which asks nothing). No scenario verifies the key: scenarios never touch the login Keychain (ADR 0013), and a folder named by `PANE_ELECTRON_DATA_DIR` has no app name, so no key is adopted.

Every scenario launch points `PANE_ELECTRON_DATA_DIR` at a folder that does not exist, so no scenario ever reads the user's Electron data; the generic launcher (`tests/lib/browser.ts`) gives a throwaway `PANE_DATA_DIR` too, since `smoke` had written the real data directory with empty defaults. The `migration` scenario names a throwaway source written by Electron 41 itself (its session API, mock keychain), and starts Pane while Electron 41, run by a second script, holds its single-instance lock on the source for 6 s. Three seconds in, Pane has written nothing and Electron still runs; Pane then migrates once it quits, where it used to start its engine beside it. The Electron data the migration reads is compared byte for byte; the running Electron app rewrites its own root session files, as it always did. PaneKit's `ElectronMigrationTests` cover a fake Electron (a copy of `sleep` in a bundle with Electron's framework), a stale lock naming the test's own process, an empty `profiles.json` with a cut-short migration's files, and the record's `cookieKeyPending`.
