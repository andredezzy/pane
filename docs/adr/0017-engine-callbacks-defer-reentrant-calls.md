# Calls made from inside engine callbacks wait for the next turn

Every delegate call from the engine runs inside Chromium's own dispatch (a page's observer, a tab strip notification, a page's request), so an app call that would destroy a tab or change a tab strip waits for the next turn of the run loop while a callback is live, instead of re-entering Chromium mid-call. `ScopedAppCallback` (`engine/pane/browser/app_callback.h`) marks every call into the app, and `close`, `closeImmediately`, `activateTab:`, the window's `close`, `deleteContext`, and `terminate` run on the next turn while one is live. It replaces `IsNotifyingTabStrip`: before, only tab strip notifications deferred the app's calls (A5 of the engine review, 2026-10-28). `engine/pane/public/PaneBrowserApplication.h` says which calls are safe in a callback: `openTabWithURL:` returns its tab, so it cannot wait, and is not for tab strip callbacks. No scenario proves it: the app makes none of these calls from a callback today, except `activateTab:`, which already waited.

The engine keeps to Chromium's order in two more places, both from Phase 2. Renderer-crash reports reach the app one task later: an app that reloaded inside `PrimaryMainFrameRenderProcessGone` relaunched the renderer while the process's other observers were still being told it died, and `extensions::RendererStartupHelper::OnRenderProcessLaunched` CHECK-failed. Posting the callback lets every observer see the exit first. And `TabBridge` unregisters its observers in `WebContentsDestroyed()`, not in its destructor: by the time user data is destroyed, `WebContentsImpl` has already emptied its user-data map, so `FindTabHelper::FromWebContents` returned null, the bridge stayed in `FindTabHelper`'s observer list, and `~FindTabHelper` hit the `CheckedObserver` use-after-free CHECK at every quit.
