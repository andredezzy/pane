# Pane keeps Chromium's order and its word: what would re-enter Chromium from inside its notifications waits for the next turn, and every request completes or goes with its page

What Pane does from inside one of Chromium's notifications that would re-enter Chromium mid-dispatch waits for the next turn of the run loop. Every open of a profile answers, and every request Chrome holds for a page ends when the page goes, because a request left open hangs something with no word why: a dialog queued for good, a profile that never opens. Both rules came from building the Swift app's engine and a review of it (2026-10-28), and Pane's UI keeps them itself now that it calls Chrome directly (ADR 0124).

**What would re-enter Chromium waits for the next turn.** The controller (`UiApp`) hears Chromium inside its own dispatch: a page's observer, a tab strip's notification, a page's request. So a renderer's death reaches it a task later: a reload inside `PrimaryMainFrameRenderProcessGone` relaunched the renderer while the process's other observers were still being told it died, and `extensions::RendererStartupHelper::OnRenderProcessLaunched` CHECK-failed (ADR 0027). A page's popup is selected, a closed tab's successor chosen, and Chrome's own pick followed on the next turn (ADR 0015), and the page Chrome puts in a discarded tab's place loads on the next (ADR 0041). What an answer to a page's dialog asks next shows on the turn after, never in its place within the call.

**The frame comes first.** A tab's page is made after the frame that answers its selection, once that frame is handed to the display compositor (`AfterFrame`, `pane/ui/after_frame.h`), so a tab chosen only in passing makes none, and the window's title follows that frame too, as AppKit lays its hidden title bar out again at each title (1.7 of a switch's 2 ms; a switch, 16.1 → 10.6 ms to the screen; "Pane" took 1 of ⌘T's 4.6 ms). Hiding the tab left stays where Chromium does it, in the frame's work (`docs/benchmarks/views-shell.md`, ⌘T's first frame). The frame that answers a command or a tab's choice is asked for once it is handled (`FrameHold`, 50 ms at most): asked for at once, the display compositor answers with a frame due at the next refresh, which cc drops when the UI thread reads it past that, and ⌘T's frame then waited for the display link's next call, 6 to 12 ms when it had stopped.

**A page's requests go with it.** `PageDialogs` (`pane/ui/dialogs/page_dialogs.h`) holds every page's request with an observer of its page, so a request goes with its page however it goes (closed, slept, unloaded, discarded), answering nothing, and traces its end (`didDismissRequest`; ADR 0021). Chrome's JavaScript dialog manager is one map for the process, keyed by WebContents, and content's own cancel at destruction never reaches it for a tab Chrome detached: a tab that slept or unloaded with an alert waiting had kept it, the alert queued for good, with a dangling key that would have suppressed the dialogs of a later tab at the same address. A dialog withdrawn as its page goes is not answered: the frames are gone, and content's answer would then read a frame that is not there for DevTools. Permission and authentication requests are withdrawn by their Chrome owners.

**Opening a profile always answers** (`pane::OpenProfile`, `pane/browser/profiles.cc`). An id that is not one folder name fails at once: a 300-character one had never called back, since Chrome loads a new profile from a directory it does not check it made, and without one the preferences fail to load and the segregated pref store waits for both its files forever ("Init observer found at shutdown"). A new profile's folder is made first, off the main thread, and a profile that cannot have one (a full disk, a permission) fails too. Profile ids are UUIDs, so no user's profile reached it.

**Dropped mojo replies complete.** The cookies' read and the cache's size never called back when their pipe closed (the network service restarting, the profile going); their callbacks now run with nothing then (`WrapCallbackWithDefaultInvokeIfNotRun`, `pane/browser/profile_cache.cc`, the automation channel's `readCookies`). The review's other case did not hold: the browsing data remover tells its observers as it is destroyed, even of removals it never finished (`browsing_data_remover_impl.cc`), so a trim always completes.

Until 0.20.0 the rules were the engine's API's, which the Swift app called: `ScopedAppCallback` marked every call into the app, and the app's `close`, `activateTab:`, `deleteContext`, `closeContext`, and `terminate` waited for the next turn while one was live; the bridge withdrew a page's dialogs as it went; and its `TabBridge` unregistered its observers in `WebContentsDestroyed()`, not in its destructor, after `~FindTabHelper` hit the `CheckedObserver` use-after-free CHECK at every quit.

How it is checked:

- **`dialog-tab-closed`**: an alert waiting in a tab that closes, one in a tab that sleeps, and one showing when its tab closes. Before, the slept tab's alert stayed queued (`pendingRequests` 1).
- **`profile-lifecycle`**: the 300-character id shows the sad tab soon after it is selected; before, it never did.
