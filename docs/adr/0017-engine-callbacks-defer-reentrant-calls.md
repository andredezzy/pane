# The engine's API keeps Chromium's order and its word: calls made from inside a callback wait for the next turn, and every promised callback and request completes or goes with its tab

A call that would re-enter Chromium mid-dispatch waits for the next turn of the run loop. Every engine call that promises the app a callback makes it, and every request the engine holds for a page ends when the page goes, because a request left open hangs something with no word why: an alert queued in the app for good, a profile that never opens, a Swift `await` that never resumes. Both rules came from building the shell and a review of the engine (2026-10-28).

**Calls from inside a callback wait for the next turn.** Every delegate call from the engine runs inside Chromium's own dispatch (a page's observer, a tab strip notification, a page's request), so an app call that would destroy a tab or change a tab strip waits for the next turn while a callback is live, instead of re-entering Chromium mid-call. `ScopedAppCallback` (`pane/browser/app_callback.h`) marks every call into the app, and `close`, `closeImmediately`, `activateTab:`, the window's `close`, `deleteContext`, `closeContext` (ADR 0116), and `terminate` run on the next turn while one is live. It replaces `IsNotifyingTabStrip`: before, only tab strip notifications deferred the app's calls. `pane/public/PaneBrowserApplication.h` says which calls are safe in a callback: `openTabWithURL:` returns its tab, so it cannot wait, and is not for tab strip callbacks. No scenario proves it: the app makes none of these calls from a callback today, except `activateTab:`, which already waited.

The engine keeps to Chromium's order in two more places, both from building the shell. Renderer-crash reports reach the app one task later: an app that reloaded inside `PrimaryMainFrameRenderProcessGone` relaunched the renderer while the process's other observers were still being told it died, and `extensions::RendererStartupHelper::OnRenderProcessLaunched` CHECK-failed. Posting the callback lets every observer see the exit first (ADR 0027). And `TabBridge` unregisters its observers in `WebContentsDestroyed()`, not in its destructor: by the time user data is destroyed, `WebContentsImpl` has already emptied its user-data map, so `FindTabHelper::FromWebContents` returned null, the bridge stayed in `FindTabHelper`'s observer list, and `~FindTabHelper` hit the `CheckedObserver` use-after-free CHECK at every quit.

**A tab's pending requests go with it.** Chrome's JavaScript dialog manager is one map for the process, keyed by WebContents, and content's own cancel at destruction never reaches it for a tab Chrome detached: its delegate is gone by then. A tab that slept or unloaded with an alert waiting kept it: no `didDismissRequest`, the alert in the app's queue for good, and a dangling key that would have suppressed the dialogs of a later tab at the same address. The tab's bridge (`pane/browser/ui/tab_bridge.mm`) now withdraws the dialog as its page goes, without answering it: the frames are gone, and content's answer would then read a frame that is not there for DevTools. The unresponsive-page and external protocol requests, which nothing in Chrome takes back either, are withdrawn the same way; permission and authentication requests already were, by their Chrome owners. A withdrawal tells the app (`didDismissRequest`), and `DialogPresenter` takes the request down and out of its queue (ADR 0021). A tab closed through `close` already lost its dialog: Chrome cancels it while the tab still has its delegate.

**`openContext` always answers.** An id longer than a folder name can be (300 characters) never called back. Chrome loads a new profile from a directory it does not check it made; without one, the preferences fail to load, and the segregated pref store (Preferences and Secure Preferences) waits for both files to report themselves initialized, which a failed file store never does (`json_pref_store.cc` sets `initialized_` only on success). Chrome logged "Init observer found at shutdown". The engine now refuses ids over 255 bytes, and makes a new profile's folder itself first, off the main thread, failing a profile that cannot have one (a full disk, a permission), which hung the same way; a profile already loaded skips that hop. An open that completes once quitting started fails as well, instead of holding its profile past the engine's teardown.

**Dropped mojo replies complete.** `getCookies` and `getCacheSize` (`pane/browser/cookies.mm`) never called back when their pipe closed (the network service restarting, the profile going), and their Swift async wrappers never resumed. Their callbacks now run with nothing then (`WrapCallbackWithDefaultInvokeIfNotRun`). The review's other case did not hold: the browsing data remover tells its observers as it is destroyed, even of removals it never finished (`browsing_data_remover_impl.cc`), so `trimCache` always completes.

How it is checked:

- **`dialog-tab-closed`**: an alert waiting in a tab that closes, one in a tab that sleeps, and one showing when its tab closes. Before, the slept tab's alert stayed queued (`pendingRequests` 1).
- **`profile-lifecycle`**: the 300-character id shows the sad tab 105 to 155 ms after it is selected; before, it never did.
