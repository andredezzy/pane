# Chrome makes no request of its own but the extension updater's, and its CRLSet ships with the app

Every request Chrome made on its own, outside the pages, is off: some carried a profile's Google cookies, some went out from the browser itself, past every profile's proxy, with the Mac's real address, and the Electron app made none. They first showed with the per-profile proxy (ADR 0037): Chrome's own background requests to `accounts.google.com` and `www.google.com` went out per profile, through its proxy, and whether to turn them off went to the fingerprint work, which owns what a profile reveals (ADR 0038). A net log of a quiet session then named each source by its traffic annotation.

What is off:

- **The component updater** (`update_client`), with `--disable-component-update`. The on-device AI model's manifest registers itself on demand regardless, and the updater refuses it (`component_updater_service.cc`), so the hunk that made it honor the switch went in the review of 0.18.0: `quiet` and `files-encrypted`'s inventory still hold.
- **The network time check** (`network_time_component`), with the `NetworkTimeServiceQuerying` feature.
- **AI Mode's eligibility check** (`aim_eligibility_fetch`), which carried a profile's Google cookies and country, with the `Aim*` features.
- **The Translate ranker model** (`ranker_url_fetcher`), with the `TranslateRanker*` features. Translate itself is off per profile (`translate.enabled`).
- **The Google account list** (`gaia_auth_list_accounts`), which sent a profile's Google cookies on every launch, from sign-in metrics among other callers: patch 0008 makes `TriggerListAccounts` do nothing when Pane hosts the engine (ADR 0010), and browser sign-in is off per profile (`signin.allowed`). Signing in to Google's websites is unaffected, as the `google` and `extension-management` scenarios show.
- **The preconnect to the default search engine** (`PreconnectToSearch`): a net log of the `crlset` scenario showed connections to `www.google.com` that no page asked for, at start and again while a page showed. No request went out, so the requests in the log never named it.

The switch and the features are set in `pane/app/engine_switches.cc`, the per-profile prefs in `pane/browser/profiles.cc`. The component updater, the network time check, and the on-device AI model were the requests that went out from the browser itself.

The one request Chrome still makes of its own is the extension updater's: as each profile starts, and every five hours or so after, it asks Chrome's update service (`update.googleapis.com`) for newer versions of its Web Store extensions, as every browser does (ADR 0062).

**Pane follows the system's proxy settings without their auto-detection** (the user's call, 2026-11-15). Windows ships with "Automatically detect settings" on, so Chromium asked the network for a proxy at each start, by DHCP and then by DNS (`wpad`), the one request `quiet` still failed on there: anyone on a public network can answer as `wpad` and take the traffic through a proxy of theirs, which sees the sites, HTTPS's content still sealed. Pane keeps Windows' explicit proxy server and its setup script's address, live as Windows changes them, and each profile's own proxy, and drops the detection, on every system. The Mac's auto proxy discovery ships off, so there it changes nothing until a user turns it on. A company network that hands its proxy out by WPAD alone needs the proxy set in the profile, or Windows' setup script named, as the user weighed.

- **A profile's network contexts** take the system's settings through the pipe Chrome's own take (`ProxyConfigMonitor`'s `ProxyConfigClient`, set up in `ChromeContentBrowserClient::ConfigureNetworkContextParams`, which Pane overrides): `DropAutoDetection` (`pane/browser/system_proxy.cc`) takes the detection off what a context starts with and off each change after, for settings Chromium read from the system alone (`ProxyConfig::from_system`, which every system's reading sets and which nothing else reads). A profile's own proxy, a policy's, the command line's (`--proxy-auto-detect` included), and an extension's are not the system's, so they pass as they are, with their precedence. Nothing is kept, and a context still waits for the system's first reading, as Chrome's does.
- **The browser's own network contexts** (Pane's update check, Safe Browsing's lists) take local state's monitor, which no seam reaches: `SystemProxy` keeps local state's `proxy` pref as Chromium's own reading of the system's settings reports them, without the detection: their setup script's address, their servers and bypass list, or direct, in the forms Chrome's prefs read (`ProxyConfigDictionary`). Its value outranks the system's settings in Chrome's reading of the pref (`PrefProxyConfigTrackerImpl::ReadPrefConfig`), and a policy's or the command line's outranks it. It is there before the network service starts (`BrowserMainExtraParts::PreCreateThreads`): the last launch's reading, or direct until the first, which follows within milliseconds; Pane's first update check waits for it (`SystemProxy::WhenRead`).
- **Rejected:** writing the pref for profiles too, as first proposed: Chrome's own reading for a new profile answers its first network context before any pref is set, the system's settings would be kept in every profile's Preferences, and a pref holds a setup script or servers, not both. Following Windows' detection, as Chrome and Edge do.
- **What it leaves:** Safe Browsing's per-profile context (`safe_browsing::NetworkContextService`), made only when Safe Browsing sends something, which `quiet` shows it doesn't, follows the system's settings as Chrome does; so does the browser's own under a policy that names the system's settings (`ProxyMode` "system"); where Windows names a setup script and a server both, the browser's own contexts take the script alone, so a script that fails sends the update check direct where a profile falls back to the server; local state holds Windows' explicit proxy or script address, as Windows' registry does.

**On Windows spellcheck downloads a dictionary for a language Windows lacks** (2026-11-15, commit `4e8b752`). The Mac spellchecks with macOS's spellchecker alone. Windows spellchecks with Windows' own for each language it has, and with Chromium's Hunspell for each it lacks, whose dictionary (`<language>-<version>.bdic`, 6.8 MB for German) Chrome downloads from Google's CDN (`redirector.gvt1.com`) through the profile's own network context, so its proxy, without cookies: never at start, at the first text a page's field holds, which a page with a filled field reaches as it shows. A profile spellchecks the UI's language, which its fingerprint's languages only filter (one that leaves the UI's out turns spellcheck off for the profile), and what the user chooses in the page's Spell check menu. So a language the user picks that Windows lacks downloads its dictionary, as Chromium's annotation names the trigger, and where the UI's own language is one Windows lacks each data folder downloads it with no choice made: twice, in the test VM's German run. The user kept it (2026-11-15), so spellcheck works in that language from the start, over leaving the language unchecked until chosen: only a UI language whose spellchecker Windows lacks meets it, and the request carries no cookie and goes through the profile's proxy. The dictionaries are kept in the engine folder, in Pane's data, where Chromium keeps them on every other system and where its Windows fallback writes one (`KeepDictionariesInUserData`, `pane/browser/browser_main_extra_parts.cc`): beside `chrome.exe` they were in the app's own folder, which an update replaces, so each would download again, and which the panic wipe leaves.

The CRLSet ships with the app:

- **Pane gives up Chrome's component updates**, as the Electron app never had them, so what they kept current comes with each build. The Chrome Root Store is built into the engine. The CRLSet was not, until 2026-10-30: with the updater off, the engine had Chromium's built-in one, which is empty (`net/cert/crl_set.cc`, `BuiltinCRLSet`), and blocked no revoked certificate beyond the static blocklist. The research comparing Pane with Aside and Dia found it: both keep Chrome's CRLSet (`CertificateRevocation/`), fetched by the component updater every few hours.
- **Each build carries Chrome's current CRLSet**, and the engine hands it to the certificate verifier as it starts, before any profile loads: on 2026-10-30, the certificates revoked by 204 issuers, 177 blocked keys, and 9 blocked interception roots (sequence 10872). Pane blocks the certificates Chrome blocks, up to the build's date.
- **`scripts/fetch-crlset.sh` fetches it on the build machine** as Chrome's component updater does. Google's update service names the CRX; the script checks its SHA-256, and its CRX3 signature by the key Chrome pins for CRLSets (`crl_set_component_installer.cc`). `package.sh` puts its `crl-set` in `Contents/Resources`, keeping a day's copy in `packaging/build` for builds without the network, and `dist.sh` refuses a release without one. On Windows `package-win.sh` puts the same file beside chrome.dll (`base::DIR_ASSETS`, `bundled_crl_set_win.cc`) and refuses a package without one (2026-11-15, commit `220a9c7`). `//pane` loads it in `BrowserMainExtraParts::PreProfileInit` (`content::GetCertVerifierServiceFactory()->UpdateCRLSet`), as the component installer would.
- **A CRLSet only adds what fails**: revocations and blocked keys. Past its `NotAfter` (about four days after Google makes it), Chrome still blocks everything in it and only stops treating a certificate it covers as known good (`revocation_checker.cc`). A shipped CRLSet is as fresh as the release, which Pane's cadence (ADR 0005) keeps to days.

What was rejected:

- **Chrome's component updater for the CRLSet alone:** a request of the browser's own to Google, through no profile's proxy.
- **Fetching the CRLSet at launch from the app:** the same request, made by the app.
- **Trusting the CRLSet's download over TLS alone:** the build checks the signature Chrome checks.

How it is checked:

- **The `quiet` scenario** keeps every source off: a quiet session reaches nothing but its local fixtures, and no host but theirs is looked up, preconnected, or connected to; nor is a proxy detected, its net log holding no `PAC_FILE_DECIDER` or `WPAD_` event. In the test VM it failed on the engine of 2026-11-14 with DHCP's and DNS's WPAD, and passes behind and in front since the detection went (2026-11-15, commit `4e8b752`).
- **`pane_unittests`, the proxy:** `WithoutAutoDetectionTest` (a setup script's address, a server and its exceptions, a server for each scheme stay; detection alone is direct; settings not the system's, a profile's own and an asked-for detection, are untouched), `ProxyPrefWithoutAutoDetectionTest` (each form reads back through Chrome's own reading of the pref as the very rules the system gave: one server, a server per scheme with Windows' SOCKS4 and the Mac's SOCKS5, HTTPS, an IPv6 literal, a fallback and direct, `<local>`, `<-loopback>`), `SystemProxyTest` (local state holds direct until the first reading, keeps the last launch's, follows the system live, and a policy's proxy keeps its precedence), `DropAutoDetectionTest` (through the pipe a context takes its settings by).
- **Windows' own settings, in the test VM** (2026-11-15, commit `4e8b752`): with "Automatically detect settings" on throughout, a profile with no proxy of its own and the update check reached nothing as shipped, went through Windows' proxy server within 3 s of its setting, through the proxy its setup script named once set, and nowhere once put back; no detection in the net log.
- **Spellcheck, in the test VM** (the same notes): with the VM's English UI no profile downloaded anything while typing, whatever its fingerprint's languages; choosing German in the page's menu downloaded its dictionary into the engine folder; with a German UI it downloaded with no choice, before any typing.
- **fetch-crlset.sh** refuses a CRX with one byte changed, and one signed by any other key.
- **The `crlset` scenario** finds the CRLSet in a packaged app's bundle, and the sequence the certificate verifier used for a page (its net log) is that CRLSet's, not the built-in 0; on Windows, beside chrome.exe in a package laid out as an install lays it out, in the test VM (`BundledCRLSetWinTest` for its place).
