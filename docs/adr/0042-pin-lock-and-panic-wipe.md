# The PIN lock and the panic wipe are the Electron app's

> **Partly replaced by [ADR 0113](0113-profile-data-encrypted-under-a-key-the-pin-releases.md)** — the PIN opens a sealed data key instead of matching a bcrypt hash, which is checked once more at the first unlock; the panic wipe destroys that key first, and erases the volume's image without passes; and an unreadable key shows 0113's lines (Paper 07.6) — **and extended by [ADR 0116](0116-pane-locks-while-open.md)**: Pane also locks while open, on Lock Pane (⌃⌘L), when the Mac sleeps or locks, and after a time without use, and the PIN screen then rises over the window (0.4 s).

The PIN lock and the panic wipe are the Electron app's, kept on the same `security.json` (`pane/model/security`, `pane/model/mac/app_lock`), so a PIN set in the Electron app unlocks Pane, and the fifth wrong PIN in a row at the lock erases every profile, as it did there. The file holds the PIN's digit count and the failed attempts, and held its bcrypt hash until ADR 0113. A wrong PIN at the lock counts on disk at once, so a quit can't reset the count. In Change and Remove it counts in memory, and the fifth locks Pane, erasing nothing (the user's call, 2026-11-06). Until 0.18.1 those counted on disk too, and since the launch's check read only the count, five wrong PINs in Settings and a quit erased every profile at the next launch, with Pane unlocked the whole time. A wipe is due only once the key has gone, in the same save as the lock's fifth attempt: so a wipe cut short is still finished, and a last attempt on disk with the key still there, which only 0.18.0's Settings left, counts for nothing and leaves the lock its five. `security` checks each. bcrypt is OpenBSD's libc implementation, vendored unmodified in `pane/model/mac/bcrypt/` (its origin and license in `third_party/openbsd-bcrypt`). It checks bcryptjs's `$2b$` and `$2a$` hashes off the main thread (`VerifyPinHash`), and Pane wrote `$2b$` at cost 10, as the Electron app did, until ADR 0113.

**The PIN screen** (`pane/ui/lock/lock_screen_view`, its dots and numpad in `pin_pad`, its logic in `pane/model/pin_entry`) is the Electron app's `page.tsx` and `numpad.tsx`, over the whole window and every overlay but the full screen's hint. While a PIN shows it takes every key (digits, Delete, Esc, Return), so none reaches a page or the window's commands; ⌘Q still quits, at once, from any PIN screen, Settings' too (ADR 0053). Pane adds one thing: Return continues when a new PIN is long enough. The motion is the Electron app's, restored on the user's report that it was missing (2026-10-27): the screen rises as it comes (ADR 0116) and sinks as it leaves (0.35 s, ease-in), on the compositor's own animation (`motion::LockIn` and `motion::LockOut`); a dot fills as its ring fades, and the keys light and fill over 0.15 s; a wrong PIN's shake (±8 then ±6 points over 0.4 s) is skipped when motion is reduced. At launch the screen does not rise, as the Electron app's did over the sidebar: it is in place from the window's first frame, so the profiles never show before the PIN. The keys' hover and press were checked under the real pointer in the front session of 2026-11-12. In the Swift app the screen's slide had vanished unseen as it left, since a view SwiftUI's stack removes drops under the window's content, until it took a z-index over the other overlays.

**The lock is one predicate the app asks,** `UiApp::InteractionAllowed()`: the data open and not locked (2026-10-27). It used to stop keys only: with the mouse, the menu bar opened a tab, DevTools (undocked, in a window the PIN screen does not cover), and the print panel over the lock; a launch URL loaded behind it and set the window's title; and any Chrome dialog would show over it. Behind the lock the menu runs only Quit and Check for Updates…; selecting a tab, showing a page, and every other intent do nothing; the URLs Pane is launched with or handed open on unlock (`UiApp::OpenLaunchURLs`); Chrome's dialogs hold and resume (ADR 0021); an extension's popup closes and its prompt is answered no (`ExtensionsUi::Lock`); the switcher stays shut. `UiApp::AccessDidOpen` lets them go on. Quit Pane? is no part of the predicate: it is not a boundary. Nor is the automation channel (ADR 0018), which opens only in a scenario's launch (ADR 0115) and acts through the same intents, which ask the predicate. `security` starts Pane locked with a URL, hands it another, and clicks the menu bar through the channel's `menu`, which runs an item only when the menu enables it, as a click does. Before, New Tab, Reopen Closed Tab, and Print… ran; now only Check for Updates… does, no tab exists, the title stays Pane, and the URLs open once the PIN is in.

**A `security.json` that does not decode never opens the lock.** A decode error used to give an empty state, so Pane started unlocked and the next save wrote over the damaged file. Now the file is first kept aside as `security.json.damaged`, and `SecurityState::Recover` reads the PIN's bcrypt hash, its length, and the failed attempts from what is left (a cut-short file, or a newer Pane's format after a downgrade); the key comes from the copy beside the volume (ADR 0113). With no PIN left in it, the lock stays shut, takes no keys, and says so on the PIN screen's error line ("Pane can't read the key to your data. / Quit, then restore security.json.", `AppLock::kKeyUnreadable`; it said to restore or remove the file until ADR 0113). Starting unlocked was rejected: the lock is a security boundary, and fails closed. An attacker with the disk could delete the file either way; this is about corruption, so the owner keeps a way back. A wipe still due is read the same way. `security` launches on a cut-short file, whose PIN unlocks, and on garbage, where the lock stays shut and 1234 does nothing; before, both opened unlocked.

**The panic wipe** (`pane/model/mac/panic_wipe`, its process in `panic_wipe_run`) erases the engine's data (every profile, with its extensions, and the encrypted volume, ADR 0113), the app's JSON files, and the engine's caches, which Chromium keeps under `~/Library/Caches` when the data is under Application Support. It deletes the Keychain item where an earlier Pane kept the proxy passwords (`ProxyPasswordStore`), but not the engine's "Pane Safe Storage" key, which is not scoped by data directory (ADR 0037). Symbolic links go without being followed. The erase runs in the instance the wipe starts. The wiped instance kills its helpers (`proc_listpids` of its children, `SIGKILL`), starts Pane again with its own arguments and environment, as the Electron app relaunched, adding their pids and its own (`--pane-wipe-after=<pid>,<pid>…`), and `_exit`s, so nothing of the engine's shutdown writes. Only if that start fails does it erase in place. The next instance, before anything reads the data directory (`PanicWipeAtLaunch`), waits for those pids (30 s at most) and moves each target into `Wiping/<id>/` beside it: a rename on the same volume, `security.json` last, since while it holds the fifth attempt the wipe is still due. Pane starts fresh at once, and a thread of its own overwrites the moved data with random bytes and deletes it: three passes for the profiles, one for the caches, which hold nothing the profile does not. A wipe cut short (a crash, a quit mid-erase, a wiped instance that died before starting the next) is staged or erased at the next launch. What could not be overwritten or deleted is logged and shown in the channel's snapshot (`security.wipe`).

The first port erased in the wiped instance, on its main thread while its engine and helpers still ran, and its restarted child waited for it at most 10 s: a few GB outlasted the cap, so both erased at once and the child's engine could start under the parent's deletes; a crash mid-erase skipped the restart; and the network service could flush cookies after the erase. Erasing in the new instance before its engine starts was rejected: the window would stay away for the whole erase, and the data is equally reachable on disk for those seconds either way. On 1 GB of profile data, measured on the Swift app as this design came in, the fresh instance answered 0.67 s after the fifth PIN, with the data gone at 1.5 s; it had answered at 1.8 s, its window frozen for 1.5 s while the parent erased. `security` checks that the erase reports nothing, nothing is left in `Wiping`, the wiped instance's helpers are gone, and the profile's data with them. `PanicWipeTest.Erases` reads a hard link to the cookies' file after the erase: its bytes are random, so they were overwritten, not only unlinked.

**The wipe erases the Electron app's data too** (the user's call, 2026-10-28). After the migration (ADR 0043), the Electron app's folder (`~/Library/Application Support/@pane/veil`) kept a second, complete copy of every profile's cookies, readable with the key the login Keychain keeps, and five wrong PINs left it. A review had proposed a Settings › Security action instead, behind a confirmation, holding that erasing another app's folder unasked, on a wrong PIN, was not the wipe's to decide; the user chose the wipe. It erases the folder `migration.json` names as its source, and that folder's caches, with the app's own data: staged beside it at once (`@pane/Wiping/`), then three random passes for the data and one for the caches. Only the recorded source goes, and only while it holds the Electron app's `profiles.json`: a record naming the data directory, a folder holding it, or a path of four components or fewer, the root counted (`/`, a volume, a home folder), erases nothing (`PanicWipeTest.RefusesOtherFolders`). `migration.json` stays, so a wiped Pane never migrates again. The Electron app's Keychain item ("@pane/veil Safe Storage") goes too when macOS allows it without asking, off the launch: a prompt would ask whoever typed the wrong PINs, and with the data gone the key opens nothing (`PanicWipeRunTest.ForgetsTheElectronAppsKey`). Nothing else is touched. `security`, in a throwaway directory, gives the wiped Pane a migrated-from folder and a neighbor: before, the folder survived the wipe; now it is gone, and the neighbor and `migration.json` stay.

Until 0.20.0 this was the Swift app's (`AppLock.swift`, `LockScreenView`, and PaneKit's `PinEntry`, `PanicWipe`, and `SecurityState`, bcrypt as its `CBcrypt` target); the Views app's model ported them with their tests (`pane/model/security_unittest.cc`, `mac/pin_hash_unittest.cc`, `mac/panic_wipe_unittest.cc`, `mac/panic_wipe_run_unittest.cc`, `mac/app_lock_unittest.cc`).
