# The PIN lock and the panic wipe are the Electron app's

> **Partly replaced by [ADR 0113](0113-profile-data-encrypted-under-a-key-the-pin-releases.md)** — the PIN opens a sealed data key instead of matching a bcrypt hash, which is checked once more at the first unlock, and the panic wipe destroys that key first.

The PIN lock and the panic wipe are the Electron app's, ported natively onto the same `security.json`, so a PIN set in the Electron app unlocks the native one, and the fifth wrong PIN at the lock erases every profile, as it did there. The file holds the PIN's bcrypt hash and digit count, and the failed attempts. A wrong PIN counts on disk at once, in Change and Remove too, and only the lock wipes. bcrypt is OpenBSD's libc implementation, vendored unmodified as PaneKit's `CBcrypt` target (its origin and license in `third_party/openbsd-bcrypt`). It verifies bcryptjs's `$2b$` and `$2a$` hashes and writes `$2b$` at cost 10, as the Electron app did, off the main thread.

The PIN screen is a native port of the Electron app's `page.tsx` and `numpad.tsx`, its logic in PaneKit (`PinEntry`). While it shows it takes every key, so none reaches a page or a shortcut (ADR 0079); ⌘Q still quits, at once (ADR 0053). Pane adds one thing: Return continues when a new PIN is long enough. The motion is the Electron app's, restored on the user's report that it was missing (2026-10-27). The screen slides down as it leaves (0.35 s, ease-in), now across five frames, with a z-index of 2 over the other overlays: a view a ZStack removes drops under the window's content, where the slide had vanished unseen. The keys fade over 150 ms, and a wrong PIN's shake (±8 then ±6 points over 0.4 s) is skipped when motion is reduced; the keys' hover is unverified on screen. At launch the screen does not slide up, as the Electron app's did over the sidebar: it is in place from the first frame, so the profiles never show before the PIN.

The lock is one predicate the shell asks, `BrowserController.interactionAllowed` (the safety review, 2026-10-27). It used to stop keys only: with the mouse, the menu bar opened a tab, DevTools (undocked, in an engine window the PIN screen does not cover), and the print panel over the lock; a launch URL loaded behind it and set the window's title; and any Chrome dialog would show over it. Behind the lock the menu now runs only Quit and Check for Updates…; selecting a tab and showing a page wait; the launch URL opens on unlock; Chrome's dialogs hold and resume; extension popups close and prompts answer no; the switcher stays shut. `AppLock.didUnlock` (`app/Pane/Security/AppLock.swift`) lets them go on. The quit panel is not part of the predicate: it is not a boundary, and its own monitor takes the keys. Neither is the automation channel (ADR 0018), which exists only when `PANE_AUTOMATION_DIR` is set, for scenarios, and opens or shows pages through `select`, which the lock gates. The `security` scenario starts Pane locked with a URL and clicks the menu bar through the automation command `menu`, which runs an item only when the menu enables it, as a click does. Before, New Tab, Reopen Closed Tab, and Print… ran; now only Check for Updates… does, no tab exists, the title stays Pane, and the URL opens once the PIN is in.

A `security.json` that does not decode never opens the lock. A decode error used to give an empty state, so Pane started unlocked and the next save wrote over the damaged file. Now the file is first kept aside as `security.json.damaged`, and `SecurityState.recover` reads the PIN's bcrypt hash, its length, and the failed attempts from what is left (a cut-short file, or a newer Pane's format after a downgrade). With no PIN left in it, the lock stays shut, takes no keys, and says so on the PIN screen's error line ("Pane can't read its PIN. Quit, then restore or remove security.json.", `PinEntry.unreadable`). Starting unlocked was rejected: the lock is a security boundary, and fails closed. An attacker with the disk could delete the file either way; this is about corruption, so the owner keeps a way back. A wipe still due is read the same way. `security` launches on a cut-short file, whose PIN unlocks, and on garbage, where the lock stays shut and 1234 does nothing; before, both opened unlocked.

The panic wipe erases the engine's data (every profile, with its extensions), the app's JSON files, and the engine's caches, which Chromium keeps under `~/Library/Caches` when the data is under Application Support. It deletes the proxy passwords' Keychain item, but not the engine's "Pane Safe Storage" key, which is not scoped by data directory (ADR 0069). Symbolic links go without being followed. The erase runs in the instance the wipe starts (`app/PaneKit/Sources/PaneKit/PanicWipe.swift`). The wiped instance kills its helpers (`proc_listpids` of its children, `SIGKILL`), starts Pane again with its own arguments and environment, as the Electron app relaunched, adding their pids and its own (`--pane-wipe-after=<pid>,<pid>…`), and `_exit`s, so nothing of the engine's shutdown writes. Only if that start fails does it erase in place. The next instance, before anything reads the data directory, waits for those pids (30 s at most) and moves each target into `Wiping/<id>/` beside it: a rename on the same volume, `security.json` last, since while it holds the fifth attempt the wipe is still due. Pane starts fresh at once, and a utility thread overwrites the moved data with random bytes and deletes it: three passes for the profiles, one for the caches, which hold nothing the profile does not. A wipe cut short (a crash, a quit mid-erase, a wiped instance that died before starting the next) is staged or erased at the next launch. `PanicWipe.erase` returns what it could not overwrite or delete, which the app logs and the automation snapshot shows (`security.wipe`).

The first port erased in the wiped instance, on its main thread while its engine and helpers still ran, and its restarted child waited for it at most 10 s: a few GB outlasted the cap, so both erased at once and the child's engine could start under the parent's deletes; a crash mid-erase skipped the restart; and the network service could flush cookies after the erase. Erasing in the new instance before its engine starts, as the safety review suggested, was rejected: the window would stay away for the whole erase, and the data is equally reachable on disk for those seconds either way. On 1 GB of profile data the fresh instance answers 0.67 s after the fifth PIN, with the data gone at 1.5 s; it answered at 1.8 s before, its window frozen for 1.5 s while the parent erased. `security` checks that the erase reports nothing, nothing is left in `Wiping`, the wiped instance's helpers are gone, and no profile data comes back 3 s later. PaneKit's test reads a hard link to the cookies' file after the erase: its bytes are random, so they were overwritten, not only unlinked.

The wipe erases the Electron app's data too (the user's call, 2026-10-28). After the migration (ADR 0043), the Electron app's folder (`~/Library/Application Support/@pane/veil`) kept a second, complete copy of every profile's cookies, readable with the key the login Keychain keeps, and five wrong PINs left it. The safety review had proposed a Settings › Security action instead, behind a confirmation, holding that erasing another app's folder unasked, on a wrong PIN, was not the wipe's to decide; the user chose the wipe. It erases the folder `migration.json` names as its source, and that folder's caches, with the app's own data: staged beside it at once (`@pane/Wiping/`), then three random passes for the data and one for the caches. Only the recorded source goes, and only while it holds the Electron app's `profiles.json`: a record naming the data directory, a folder holding it, or a path five components or shorter erases nothing (PaneKit tests). `migration.json` stays, so a wiped Pane never migrates again. The Electron app's Keychain item ("@pane/veil Safe Storage") goes too when macOS allows it without asking, off the launch: a prompt would ask whoever typed the wrong PINs, and with the data gone the key opens nothing. Nothing else is touched. The `security` scenario, in a throwaway directory, gives the wiped Pane a migrated-from folder and a neighbor: before, the folder survived the wipe; now it is gone, and the neighbor and `migration.json` stay.
