# Menu shortcuts match the keys as typed, and what Chrome reserves goes ahead of the page

Pane matches its shortcuts against keys as they are typed, so a real key press always reaches them. The menu bar's keys and the window's are one table of `ui::Accelerator`s (`pane/ui/app/commands.cc`), the Swift app's main menu item for item, which the window's FocusManager takes as its accelerators and `MenuControllerCocoa` shows as the menu bar's key equivalents (`pane/ui/app/menu_bar_mac.mm`).

**A shifted shortcut is the uppercase key with ⌘ alone,** the form Interface Builder stores and AppKit reads: `"T"` for ⇧⌘T (Reopen Closed Tab), since a typed ⇧⌘T arrives as `"T"`, which a `"t"` + Shift item does not match. `shortcuts` presses ⇧⌘T as a real key event, through the automation channel (ADR 0018), and checks that the closed tab comes back.

**⌘Q is matched with Caps Lock ignored,** as every accelerator is, so it quits wherever Pane takes every key: at the PIN screen (ADR 0042) and in Quit Pane? (ADR 0053). Before the fix (2026-10-27), ⌘Q with Caps Lock on did nothing at the PIN screen. While an overlay takes every key, the window's key equivalents drop every command of the menu bar's but Quit (`KeyEquivalentsForPane`, `pane/ui/window/frame_mac.mm`), so ⌘Q, Caps Lock on or off, reaches Quit, which quits at once there. `security` presses ⌘Q with Caps Lock at the PIN screen and checks that Pane quits.

**What Chrome reserves goes ahead of the page** (`IsAppFirst`, through `Window::PreHandleKeyboardEvent`), so no page can keep a user in it: ⌘Q, ⌘T, ⌘W, ⇧⌘T, and the switcher's Ctrl-Tab and Ctrl-Shift-Tab, and while the page fills the screen only ⌘Q and Full Screen, as Chrome's `kReservedCommandIds` and its fullscreen rule have it (`IsReservedCommandOrKey`). So ⌘T answers in its own frame, and the address field holds the focus before the next key. Every other key, ⌘L and ⌘F among them, goes to the page first, as in Chrome, then the window's FocusManager and the menu bar, so a key inside that round trip goes to the page. A key behind a command acts on what the command did: a key queued behind ⌘L replaces the address, where one that beat the selection appended to it (`shortcuts`, with both keys in the queue at once).

The Swift app reserved only ⌘T, and sent ⌘Q, ⌘W, and ⇧⌘T to the page first, where a page could take them; the move to Views made them Chrome's, by this record's own reason for ⌘T. The Swift line had lost even ⌘T's reservation in 0.19.0: `8e969e2` dropped the bridge's `preHandleKeyEvent:`, which the Swift still answered. Its ⌘Q matched Caps Lock through its key monitor's routing (ADR 0079).

How it is checked: `pane_unittests`' `CommandsTest` (each key runs one command, Caps Lock or not; what goes ahead of the page, and in fullscreen; ⇧⌘T apart from ⌘T; the menu bar's models from the table), `shortcuts`, and `security`, where the run lets Pane take the front (ADR 0012).
