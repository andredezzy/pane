# Menu shortcuts match the keys as typed, and what Chrome reserves goes ahead of the page

Pane matches its shortcuts against keys as they are typed, so a real key press always reaches them. The menu bar's keys and the window's are one table of `ui::Accelerator`s (`pane/ui/app/commands.cc`), the Swift app's main menu item for item, which the window's FocusManager takes as its accelerators and `MenuControllerCocoa` shows as the menu bar's key equivalents (`pane/ui/app/menu_bar_mac.mm`).

**A shifted shortcut is the uppercase key with ⌘ alone,** the form Interface Builder stores and AppKit reads: `"T"` for ⇧⌘T (Reopen Closed Tab), since a typed ⇧⌘T arrives as `"T"`, which a `"t"` + Shift item does not match. `shortcuts` presses ⇧⌘T as a real key event, through the automation channel (ADR 0018), and checks that the closed tab comes back.

**⌘Q is matched with Caps Lock ignored,** as every accelerator is, so it quits wherever Pane takes every key: at the PIN screen (ADR 0042) and in Quit Pane? (ADR 0053). Before the fix (2026-10-27), ⌘Q with Caps Lock on did nothing at the PIN screen. While an overlay takes every key, the window's key equivalents drop every command of the menu bar's but Quit (`KeyEquivalentsForPane`, `pane/ui/window/frame_mac.mm`), so ⌘Q, Caps Lock on or off, reaches Quit, which quits at once there. `security` presses ⌘Q with Caps Lock at the PIN screen and checks that Pane quits.

**What Chrome reserves goes ahead of the page** (`IsAppFirst`, through `Window::PreHandleKeyboardEvent`), so no page can keep a user in it: ⌘Q, ⌘T, ⌘W, ⇧⌘T, and the switcher's Ctrl-Tab and Ctrl-Shift-Tab, and while the page fills the screen only ⌘Q and Full Screen, as Chrome's `kReservedCommandIds` and its fullscreen rule have it (`IsReservedCommandOrKey`). So ⌘T answers in its own frame, and the address field holds the focus before the next key. Every other key, ⌘L and ⌘F among them, goes to the page first, as in Chrome, then the window's FocusManager and the menu bar, so a key inside that round trip goes to the page. That holds once the page can take the key. A tab just reopened or woken from sleep has no view of its own until its renderer's first frame, its view stays hidden a moment after WebView focuses it (`WebView::SetUpNewMainFrame`), and Chromium drops a key sent to a renderer whose process still starts (`RenderWidgetHostImpl::ForwardKeyboardEventWithCommands`): a key sent then went nowhere, neither to the page nor to the window, whose shortcuts Views skips while a page holds the focus (`WebView::SkipDefaultKeyEventProcessing`). Until the page shows, holds the focus, and its renderer runs, the window's shortcuts take the key (`PageWebView`, `pane/ui/page/page_web_view.h`); on Windows a key the focused window can't take, which aura drops before any handler hears it (`aura::Window::CanAcceptEvent`), goes to Views' content window, where they hear it (`KeysToTheWindow`, `pane/ui/window/frame_win.cc`; W4, 2026-11-13, found with the engine's log at each step of the key's way). There ⌘1's Ctrl+1 right after ⇧⌘T's Ctrl+Shift+T was lost so in about one run of `shortcuts` in four in the test VM, in front, and in none of 10 after; the Mac's menu bar ran ⌘1 first. A key behind a command acts on what the command did: a key queued behind ⌘L replaces the address, where one that beat the selection appended to it (`shortcuts`, with both keys in the queue at once).

The Swift app reserved only ⌘T, and sent ⌘Q, ⌘W, and ⇧⌘T to the page first, where a page could take them; the move to Views made them Chrome's, by this record's own reason for ⌘T. The Swift line had lost even ⌘T's reservation in 0.19.0: `8e969e2` dropped the bridge's `preHandleKeyEvent:`, which the Swift still answered. Its ⌘Q matched Caps Lock through its key monitor's routing (ADR 0079).

**On Windows the same table gives each command Windows' key** (W4, 2026-11-13), a column of keys per system beside the Mac's (`MenusWithKeysOf`; the system by `ThisKeySystem`, `commands_mac.cc` and `commands_win.cc`): Ctrl where the Mac takes ⌘, and Chrome's own Windows keys (`chrome/browser/ui/accelerator_table.cc`) where Ctrl alone would collide or Windows has its own: F11 for Full Screen, since ⌃⌘F is Ctrl+F's there; Ctrl+Shift+L for Lock Pane, since ⌃⌘L is Ctrl+L's (the user's to confirm); Alt+Left and Alt+Right for Back and Forward; F12 beside Ctrl+Shift+I for Developer Tools, where the Mac's second key is ⌥⌘I; Ctrl+Y for Redo; and Alt+F4 beside Ctrl+Q for Quit (ADR 0053). Zoom In shows Ctrl+=, what people type, as Chrome shows it, and takes Ctrl+Shift+= (Ctrl++) and the numpad's + too; Zoom Out shows Ctrl+- and takes Ctrl+Shift+- and the numpad's -, as Chrome's Windows table has them; the Mac's keep ⇧⌘= shown as ⌘+, with ⌘= beside it. What is the Mac's alone (Hide, Hide Others, Minimize) has no key there, and no key is Ctrl+Alt's, which AltGr types with, as Chrome's rule has it. What Chrome reserves goes ahead of the page there too, by the same table.

**Quit's keys reach Quit past an overlay that takes every key, on both systems** (W4): the window registers them at the FocusManager's high priority, which runs them past the overlay's view that holds the focus (the PIN screen's, Quit Pane?'s), and refuses every other command while an overlay takes every key (`Window::AcceleratorPressed`). On the Mac the menu bar had run ⌘Q there, past `KeyEquivalentsForPane`, which still drops the menu bar's other keys; Windows has no menu bar, and Ctrl+Q stopped at the overlay. Chrome's own menus show the table's key (`HostedBrowserWindow::GetAcceleratorForCommandId`: Exit Full Screen's in the page's menu, F11 on Windows), and Views' menus write Windows' keys Windows' way ("Ctrl+T"). Pane's own keyed chips, Quit Pane?'s ⌘Q and the dialogs' ↩, are drawn as on the Mac until Paper draws Windows' (W5).

How it is checked: `pane_unittests`' `CommandsTest` (each key runs one command on each system, Caps Lock or not; what goes ahead of the page, and in fullscreen; ⇧⌘T apart from ⌘T; the menu bar's models from the table; Windows' listing, `WindowsTakesCtrlAndItsOwnKeys`, and the zoom keys, `ZoomKeys`, on every system), `shortcuts`, and `security`, where the run lets Pane take the front (ADR 0012); on Windows, in the test VM, the scenarios that press them, by `PRIMARY` and the keys that differ by more (`KEYS`, `tests/lib/platform.ts`), and `shortcuts` run ten times in front for a key right after a reopened tab.
