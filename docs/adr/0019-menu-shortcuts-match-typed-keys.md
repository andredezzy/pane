# Menu shortcuts match the keys as typed

Pane matches its shortcuts against keys as they are typed, so a real key press always reaches them. A shifted menu shortcut uses an uppercase key equivalent with ⌘ alone, the form Interface Builder stores: `"T"` for ⇧⌘T (Reopen Closed Tab, `app/Pane/MainMenu.swift`), since a typed ⇧⌘T arrives as `"T"`, which a `"t"` + Shift item does not match. `shortcuts` presses ⇧⌘T as a real key event, through the automation channel (ADR 0018), and checks that the closed tab comes back.

⌘Q is matched with Caps Lock ignored, so it quits wherever Pane takes every key: at the PIN screen (ADR 0042) and in Quit Pane? (ADR 0053). Before the fix (2026-10-27), ⌘Q with Caps Lock on did nothing at the PIN screen. The key monitor's routing does it (`KeyPress.isQuit`, ADR 0079; `NSEvent.isQuitShortcut` before), with a PaneKit test. `security` presses ⌘Q with Caps Lock at the PIN screen and checks that Pane quits, where the run lets Pane take the front (ADR 0012).

⌘T is reserved ahead of the page, as Chrome reserves it (`IsReservedCommandOrKey`), so it answers in its own frame, and the address field holds the focus before the next key. ⌘L and ⌘F go to the page first, as in Chrome, so a key inside that round trip goes to the page. A key behind a command acts on what the command did: `selectAll` no longer waits on a dispatch, where a key that beat it appended to the address (`shortcuts`, with both keys in the queue at once).
