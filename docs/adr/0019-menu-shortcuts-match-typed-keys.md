# Menu shortcuts match the keys as typed, and what Chrome reserves goes ahead of the page

Pane matches its shortcuts against keys as they are typed, so a real key press always reaches them. The menu bar's keys and the window's are one table of `ui::Accelerator`s (`pane/ui/app/commands.cc`), the Swift app's main menu item for item, which the window's FocusManager takes as its accelerators and `MenuControllerCocoa` shows as the menu bar's key equivalents (`pane/ui/app/menu_bar_mac.mm`).

**A shifted shortcut is the uppercase key with ⌘ alone,** the form Interface Builder stores and AppKit reads: `"T"` for ⇧⌘T (Reopen Closed Tab), since a typed ⇧⌘T arrives as `"T"`, which a `"t"` + Shift item does not match. `shortcuts` presses ⇧⌘T as a real key event, through the automation channel (ADR 0018), and checks that the closed tab comes back.

**⌘Q is matched with Caps Lock ignored,** as every accelerator is, so it quits wherever Pane takes every key: at the PIN screen (ADR 0042) and in Quit Pane? (ADR 0053). Before the fix (2026-10-27), ⌘Q with Caps Lock on did nothing at the PIN screen. While an overlay takes every key, the window's key equivalents drop every command of the menu bar's but Quit (`KeyEquivalentsForPane`, `pane/ui/window/frame_mac.mm`), so ⌘Q, Caps Lock on or off, reaches Quit, which quits at once there. `security` presses ⌘Q with Caps Lock at the PIN screen and checks that Pane quits.

**What Chrome reserves goes ahead of the page** (`IsAppFirst`, through `Window::PreHandleKeyboardEvent`), so no page can keep a user in it: ⌘Q, ⌘T, ⌘W, ⇧⌘T, and the switcher's Ctrl-Tab and Ctrl-Shift-Tab, and while the page fills the screen only ⌘Q and Full Screen, as Chrome's `kReservedCommandIds` and its fullscreen rule have it (`IsReservedCommandOrKey`). So ⌘T answers in its own frame, and the address field holds the focus before the next key. Every other key, ⌘L and ⌘F among them, goes to the page first, as in Chrome, then the window's FocusManager and the menu bar, so a key inside that round trip goes to the page. That holds once the page can take the key. A tab just reopened or woken from sleep has no view of its own until its renderer's first frame, its view stays hidden a moment after WebView focuses it (`WebView::SetUpNewMainFrame`), and Chromium drops a key sent to a renderer whose process still starts (`RenderWidgetHostImpl::ForwardKeyboardEventWithCommands`): a key sent then went nowhere, neither to the page nor to the window, whose shortcuts Views skips while a page holds the focus (`WebView::SkipDefaultKeyEventProcessing`). Until the page shows, holds the focus, and its renderer runs, the window's shortcuts take the key (`PageWebView`, `pane/ui/page/page_web_view.h`); on Windows a key the focused window can't take, which aura drops before any handler hears it (`aura::Window::CanAcceptEvent`), goes to Views' content window, where they hear it (`KeysToTheWindow`, `pane/ui/window/frame_win.cc`; W4, 2026-11-13, found with the engine's log at each step of the key's way). There ⌘1's Ctrl+1 right after ⇧⌘T's Ctrl+Shift+T was lost so in about one run of `shortcuts` in four in the test VM, in front, and in none of 10 after; the Mac's menu bar ran ⌘1 first. A key behind a command acts on what the command did: a key queued behind ⌘L replaces the address, where one that beat the selection appended to it (`shortcuts`, with both keys in the queue at once). A page that had the keys and goes before the next one comes, as a new tab's does, leaves them to none (`RootView::ShowPage`): WebView makes itself unfocusable then, and Views moved the keys to the next Tab stop, on Windows a button of Pane's, whose focus ring showed until the page took them (W5, 2026-11-14, found by sampling the focus in the test VM).

**Lock Pane's key goes ahead of the page too** (`IsAppFirst`), page fullscreen or not, on both systems: the user's call (2026-11-17), so no page can keep Pane open. A page that kept ⌃⌘L or Ctrl+Shift+L (`preventDefault`) stopped the Lock, on Windows (W9a) and on the Mac (W9b) alike, by real keys: an editor's own key there, Google Docs' and Sheets' align left and Word on the web's bulleted list on Windows, pressed in such an editor, left Pane open. Chrome has no Lock to reserve, so its fullscreen rule, which leaves a fullscreen page every key but Quit and Full Screen, doesn't bind it. Its cost: inside Pane, those editors' Ctrl+Shift+L on Windows and a page's ⌃⌘L on the Mac never reach the page (their toolbars stay). `CommandsTest.LockGoesAheadOfThePage`; `key-precedence` sets up a PIN, has the page keep the key, and presses it as a person does, which needs Pane in front (`Window::CanHandleAccelerators`), so it runs there and defers behind.

The Swift app reserved only ⌘T, and sent ⌘Q, ⌘W, and ⇧⌘T to the page first, where a page could take them; the move to Views made them Chrome's, by this record's own reason for ⌘T. The Swift line had lost even ⌘T's reservation in 0.19.0: `8e969e2` dropped the bridge's `preHandleKeyEvent:`, which the Swift still answered. Its ⌘Q matched Caps Lock through its key monitor's routing (ADR 0079).

**On Windows the same table gives each command Windows' key** (W4, 2026-11-13), a column of keys per system beside the Mac's (`MenusWithKeysOf`; the system by `ThisKeySystem`, `commands_mac.cc` and `commands_win.cc`): Ctrl where the Mac takes ⌘, and Chrome's own Windows keys (`chrome/browser/ui/accelerator_table.cc`) where Ctrl alone would collide or Windows has its own: F11 for Full Screen, since ⌃⌘F is Ctrl+F's there; Ctrl+Shift+L for Lock Pane, since ⌃⌘L is Ctrl+L's (confirmed by the user, 2026-11-17, below); Alt+Left and Alt+Right for Back and Forward; F12 beside Ctrl+Shift+I for Developer Tools, where the Mac's second key is ⌥⌘I; Ctrl+Y for Redo; and Alt+F4 alone for Exit Pane, Windows' Quit: Ctrl+Q runs nothing there, the user's call (2026-11-14, `kCtrlQExitsOnWindows`, ADR 0053). Zoom In shows Ctrl+=, what people type, as Chrome shows it, and takes Ctrl+Shift+= (Ctrl++) and the numpad's + too; Zoom Out shows Ctrl+- and takes Ctrl+Shift+- and the numpad's -, as Chrome's Windows table has them; the Mac's keep ⇧⌘= shown as ⌘+, with ⌘= beside it. What is the Mac's alone (Hide, Hide Others, Show All) is not in Windows' menus, Minimize there has no key, and no key is Ctrl+Alt's, which AltGr types with, as Chrome's rule has it. What Chrome reserves goes ahead of the page there too, by the same table. **Windows' own keys beside the shown ones** (W9a, 2026-11-16, found by hand in the test VM, where F5 did nothing): F5 for Reload, F3 and Shift+F3 for Find Next and Find Previous, Ctrl+F4 for Close Tab (ahead of the page, as Close Tab goes), and Alt+D for the address, hidden beside Ctrl+R, Ctrl+G, Ctrl+Shift+G, Ctrl+W, and Ctrl+L, as Chrome's Windows table has each; the menus show what they showed (`CommandsTest.WindowsKeysOfItsOwn`). **The switcher closes, choosing nothing, as the window leaves the front** (`Window::OnWidgetActivationChanged`, W9a): Ctrl+Esc, Windows' Start, took the front with the switcher up, Ctrl's release, which chooses its tab, went to Start, and the switcher stayed over the page until an Esc in Pane.

**On Windows the menu bar's commands are one menu under the sidebar's "Pane ⌄"** (W5, 2026-11-14; Paper 11.4's A, 11.5, ADR 0126), built from the same table for Windows' keys (`MenusWithKeysOf`): Pane's own items (About Pane, Check for Updates…, Settings…, Lock Pane), then File, Edit, View, Navigate, Tab, and Window as submenus, the root's own models, then Exit Pane, each item enabled, checked, and titled as the Mac's menu bar asks the app (`AppMenuModel`, `pane/ui/app/menu_bar_win.cc`), its keys written Windows' way by Views (`GetShortcutText`). Window's Zoom is Maximize there. Alt alone and F10 open it, as they open Chrome's menu (`AppMenuKeys`, `frame_win.cc`), unless an overlay takes every key. What only the Mac's menu bar does, Pane runs itself there (`platform_commands_win.cc`): the Edit menu on what has the keys, a field of Pane's or the page, Minimize, and Maximize or Restore. The channel chooses from it by the Mac's paths, so a scenario's `menu` reads the same on both systems.

**On Windows, Tab goes as in Chrome,** the user's call (2026-11-14): the toolbar's and the sidebar's buttons take no Tab, as Chrome's toolbar's and tabs' don't (`KeepButtonsOutOfTab`, `pane/ui/design/tab_order.h`, given each as it comes to either), while fields and the page keep it, and the sheets and dialogs their own order. The keys reach the buttons as Chrome's reach its panes (`FocusGroups`, `pane/ui/window/focus_groups_win.cc`): F6 moves them from the page to the address field, the toolbar's first button, the sidebar's first, and back to the page, Shift+F6 the other way, each skipped where it doesn't show; Alt+Shift+T to the toolbar's first button; in the toolbar or the sidebar the arrows, Home, and End move between its buttons (`ButtonsInOrder`: in their order on screen, shown and enabled, a tab's X its row's), and Esc gives the keys back to what had them. None of it while an overlay takes every key, the page fills the screen, or a sheet or dialog has the keys. On the Mac nothing changes: no button takes Tab there, by Views' own rule, and neither F6 nor Alt+Shift+T moves the keys.

**Quit's keys reach Quit past an overlay that takes every key, on both systems** (W4): the window registers them at the FocusManager's high priority, which runs them past the overlay's view that holds the focus (the PIN screen's, Quit Pane?'s), and refuses every other command while an overlay takes every key (`Window::AcceleratorPressed`). On the Mac the menu bar had run ⌘Q there, past `KeyEquivalentsForPane`, which still drops the menu bar's other keys; Windows has no menu bar, and Ctrl+Q stopped at the overlay. Chrome's own menus show the table's key (`HostedBrowserWindow::GetAcceleratorForCommandId`: Exit Full Screen's in the page's menu, F11 on Windows), and Views' menus write Windows' keys Windows' way ("Ctrl+T"). Pane's own keyed chips write Windows' keys there since W5 (Paper 11.6): Alt+F4 on Exit Pane?'s Exit, and Enter where the Mac's chips show ↩ (`SystemWords`, `pane/ui/design/system_words_win.cc`).

How it is checked: `pane_unittests`' `CommandsTest` (each key runs one command on each system, Caps Lock or not; what goes ahead of the page, and in fullscreen, Lock Pane's in both; ⇧⌘T apart from ⌘T; the menu bar's models from the table; Windows' listing, `WindowsTakesCtrlAndItsOwnKeys`, the keys Pane's chips show, `ShownKeys`, and the zoom keys, `ZoomKeys`, on every system), `shortcuts`, `security`, and `focus-groups`, where the run lets Pane take the front (ADR 0012), `TabOrderTest` for the Tab order on both systems; on Windows, in the test VM, the scenarios that press them, by `PRIMARY` and the keys that differ by more (`KEYS`, `tests/lib/platform.ts`), and `shortcuts` run ten times in front for a key right after a reopened tab.
