# Patches apply and reverse from saved copies

`engine/scripts/apply-patches.sh` keeps a copy of each patch it applies in `~/chromium/.applied`, and takes patches out by reversing those copies instead of resetting the checkout, so `src/pane` and the build outputs are never touched by a reset. `.applied/state` records what is applied, in series order, each patch by its SHA-256 and name. A run with the series unchanged does nothing. A run whose applied patches are the start of the series applies the rest. Anything else is reversed first, last patch first, from the copies, and then the whole series applies, so a changed series or a changed patch never needs a reset.

The other scripts in `engine/scripts/` keep the record true, and trust it. `make-patch.sh` regenerates a patch from the files `engine/patches/MANIFEST` assigns it, as their diff against the pinned tag, and records it as applied, since the tree then holds it. `sync.sh` refuses to move the checkout to another tag while patches are applied: their record would no longer describe the tree. `build.sh` records an engine key only when `apply-patches.sh --check` says the applied patches are the series (ADR 0049). A patch that a Chromium upgrade moved is merged three ways from the blobs it was made against; a conflict stops the run with its markers in the files, and once it is resolved and the patch regenerated, the next run continues after the patches already applied (ADR 0005).

A reversal resumes where it stopped (review Q1, 2026-10-27). Each patch now leaves `.applied/state` as it comes out. Before, a reversal stopped by a hand edit failed on the first already-reversed patch on every run after, and only editing `.applied/` by hand got out of it. Proved with two patches and a hand edit: before, the second run failed on `b.txt`; now it finishes.
