# Every engine request answers, or goes with its tab

Every engine call that promises the app a callback makes it, and every request the engine holds for a page ends when the page goes, because a request left open hangs something with no word why: an alert queued in the app for good, a profile that never opens, a Swift `await` that never resumes. The engine review of 2026-10-28 found three such holes (B2, B5, B6), and the engine closes each.

A tab's pending requests go with it (B2). Chrome's JavaScript dialog manager is one map for the process, keyed by WebContents, and content's own cancel at destruction never reaches it for a tab Chrome detached: its delegate is gone by then. A tab that slept or unloaded with an alert waiting kept it: no `didDismissRequest`, the alert in the app's queue for good, and a dangling key that would have suppressed the dialogs of a later tab at the same address. The tab's bridge (`engine/pane/browser/ui/tab_bridge.mm`) now withdraws the dialog as its page goes, without answering it: the frames are gone, and content's answer would then read a frame that is not there for DevTools. The unresponsive-page and external protocol requests, which nothing in Chrome takes back either, are withdrawn the same way; permission and authentication requests already were, by their Chrome owners. A withdrawal tells the app (`didDismissRequest`), and `DialogPresenter` takes the request down and out of its queue (ADR 0021). `dialog-tab-closed` checks an alert waiting in a tab that closes, one in a tab that sleeps, and one showing when its tab closes; before, the slept tab's alert stayed queued (`pendingRequests` 1). A tab closed through `close` already lost its dialog: Chrome cancels it while the tab still has its delegate.

`openContext` always answers (B5, and a hang another review track found). An id longer than a folder name can be (300 characters) never called back. Chrome loads a new profile from a directory it does not check it made; without one, the preferences fail to load, and the segregated pref store (Preferences and Secure Preferences) waits for both files to report themselves initialized, which a failed file store never does (`json_pref_store.cc` sets `initialized_` only on success). Chrome logged "Init observer found at shutdown". The engine now refuses ids over 255 bytes, and makes a new profile's folder itself first, off the main thread, failing a profile that cannot have one (a full disk, a permission), which hung the same way; a profile already loaded skips that hop. An open that completes once quitting started fails as well, instead of holding its profile past the engine's teardown. In `profile-lifecycle`, the 300-character id shows the sad tab 105 to 155 ms after it is selected; before, it never did.

Dropped mojo replies complete (B6). `getCookies` and `getCacheSize` (`engine/pane/browser/cookies.mm`) never called back when their pipe closed (the network service restarting, the profile going), and their Swift async wrappers never resumed. Their callbacks now run with nothing then (`WrapCallbackWithDefaultInvokeIfNotRun`). The review's other case did not hold: the browsing data remover tells its observers as it is destroyed, even of removals it never finished (`browsing_data_remover_impl.cc`), so `trimCache` always completes.
