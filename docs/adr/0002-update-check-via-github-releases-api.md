# Pane checks GitHub's latest release at launch and every six hours, and a dmg that matches the release's SHA-256 leaves quarantine

> **Installing is replaced by [ADR 0092](0092-pane-installs-its-updates.md)**: Pane installs a downloaded update itself at quit; where it can't, the pill says Quit and install, and its click quits Pane and shows the installer once it has gone. The check and the download below still hold.

Pane checks for updates by asking for the repo's latest GitHub Release and comparing versions: no update framework, no update service. The Electron app did the same, having rejected electron-updater: Pane is ad-hoc signed, Squirrel.Mac refuses to update an unsigned app, and its zip and `latest-mac.yml` would have been a publishing duty on every release for an updater that could install nothing. The contract, the `releases/latest` tag and its `-arm64.dmg` asset, is also how every Electron Pane found the native app, and every Swift Pane the Views app (ADR 0122).

**The check.** `pane/updates/updater.cc` checks and downloads through Chromium's system network context, which keeps no cache or cookies, and the rules are `pane/model/updates.h`', with tests. It checks at launch and every six hours after (`kUpdateCheckInterval`), retries a failed check after 5, 15, and 60 minutes, and holds the checking state for 0.8 s, so a click visibly does something. It checked daily until 2026-10-30, when the research into how Aside, Dia, and other Chromium browsers ship security fixes found that Chromium's now come every week, and a new milestone every two weeks: a Pane left open for days must hear of a release within hours. Chrome checks every 4.5 hours, Brave every 3, and Dia every 8. The check is one request to GitHub's API, so six hours costs nothing a user would notice. One source of truth, the `Updater`, serves the sidebar pill, Settings › Updates (whose Check for updates says when the last check completed, in the Mac's own short time format), the lock screen, and Pane › Check for Updates…; a check keeps what is on offer up, and a downloaded update stays downloaded. A build that isn't packaged carries no `PaneVersion` and reads 0.0.0, so the scenarios' stand-in release is 0.0.0 by default.

**The download.** The arm64 dmg downloads to Downloads, at a user's own request's priority: at the default (idle), the file it writes waits behind the fence Chromium keeps on best-effort tasks until startup completes, which a window with no page painted reaches only at a 3-minute failsafe. Its progress shows the average rate since its connection's first bytes, no estimate in the first second, and the ETA's hysteresis (`DownloadETA`), and the pill, Settings, and the Lock hear it at most once a frame. TLS to api.github.com vouches for the release JSON, not for where its links go, so a download must come from the repo's releases (`IsTrustedDownload`): https, github.com on its default port, the `/andredezzy/pane/releases/download/` path (standardized, so `../` cannot leave it), and a plain file name ending in `-arm64.dmg`, which also names the file in Downloads. A release whose dmg fails the check offers no update; GitHub's redirect to its asset host is followed over https.

**A slow connection.** The download leaves a connection that crawls, and goes on from where it got to on a new one (`DownloadPace`, `pane/updates/dmg_download`). The user's Mac showed why (2026-11-04): of the same 135 MB dmg, from the same address and with either curl or the Swift app's URLSession, about one connection in three got 90 to 650 KB/s and the others 26 to 38 MB/s, and each kept its rate, so a download that drew a slow one took half an hour, or looked stuck. Slower than 1 MB/s over 5 s from its first bytes, or with none in 5 s, the connection is left: its setup says nothing of its rate. Each connection is a request of its own on `SimpleURLLoader`, which, unlike the Swift app's URLSession, keeps no resume data, so the rest is asked for by `Range`, with `If-Range` carrying the file's ETag or Last-Modified, its bytes written into one temporary file off the UI thread; the digest still checks the whole file. Each new connection no faster doubles the next window, 10, 20, then 40 s, and after four the download stays, since on a link that is itself slow more would only cost it. If the server refuses to resume (GitHub's signed link expires, an hour after the redirect gives it, measured from its `se` and the token's `exp` on 2026-11-05), the download starts over, once: a 200 to a range request is the whole file again, from the start, any other answer refuses, and from then on the server is asked for no range. A connection that could not resume gives up what it brought, so it is left only while that is under a twentieth of the file, and one that cannot be left spends no switch. One that drops goes on from where it got to, after 2, 4, then 8 s in a row with nothing brought, long enough for a Wi-Fi switch.

**The digest, and quarantine.** GitHub gives each asset's SHA-256 in the release JSON (`digest`), which TLS to api.github.com vouches for. The updater hashes the dmg off the UI thread, in about 0.2 s for 163 MB. A dmg that differs is deleted and the update offered again; only a matching one leaves quarantine (`ReleaseFromQuarantine`, `pane/updates/update_files.h`), so the Pane copied out of it opens like the one it replaces (Sparkle likewise takes an update out of quarantine once its signature checks out). Pane quarantines every file it writes (Chromium's `LSFileQuarantineEnabled`, which the bundle keeps), and macOS refuses a quarantined copy of an app that is not notarized (ADR 0048): "Apple could not verify “Pane” is free of malware", with Move to Trash first and Open Anyway left in System Settings, after every update. It was found running the update path against the real v0.7.0 release: the downloaded dmg carried `com.apple.quarantine`, and the app copied out of it was refused at launch. A release without a digest downloads as before and stays quarantined, so Gatekeeper asks. The Electron app's download of v0.7.0 carried no quarantine, so its users' first native Pane opened too.

Installing was first the user's: the dmg opened and the user dragged Pane to Applications, and silent updates waited for a Developer ID and Sparkle (`docs/human-checklist.md`, 6.2). ADR 0092 replaced that, and rejected Sparkle.

What was rejected:

- **Checking daily, as before:** a security release could wait a day to be offered.
- **Checking every hour or less:** GitHub's API allows 60 unauthenticated requests an hour per address, which many Panes behind one address would share.
- **Keeping the quarantine:** every update would end on a dialog that suggests malware and offers the Trash first.
- **Removing it without the digest:** any file at a trusted URL would skip Gatekeeper.
- **Two connections at once, keeping the faster:** it spends the user's data twice for what one switch gets.
- **Signing with a self-made certificate:** it would also keep the Keychain's grant across updates (ADR 0048), but puts a private key in CI's secrets, the user's call.

How it is checked:

- **The model's tests** (`pane/model/updates_unittest.cc`, the twins of PaneKit's `UpdatesTests`): which release is an update, which downloads are trusted, the SHA-256 from the digest, `DownloadETA`, `DownloadPace`, and the connection rules (`CanResume`, `CanLeaveConnection`, `ReadRangeAnswer`, `DropRetryDelay`).
- **The scenarios:** every launch points at a stand-in release (`PANE_UPDATE_URL`) that serves its downloads from its own host, so a run never reaches GitHub or its rate limit. `updates` adds a throwaway downloads folder and no opening: a dmg that matches the digest leaves quarantine, one that differs is deleted and the update offered again, and one without a digest stays quarantined.
- **The `update-connection` scenario,** its eight cases passing on the Views build as on the Swift's: a stand-in server that crawls on the first connection. The download goes on from where it got to, its bar never going back, and the file matches its digest; a server without ranges, or one that refuses them, gets it from the start, and without ranges far enough in it stays. A server that refuses is asked once, however many of its connections crawl. A connection that starts late at a good rate stays. A connection cut mid-way resumes, and one of unknown length at a good rate is left alone.
- **Against the real release:** on 2026-11-05 the same calls left three connections to v0.17.0's asset 1.2 s in each, answered 200 and then 206 from `release-assets.githubusercontent.com`, and the 135 MB whole matched its digest in 10.4 s; a build that reported 0.16.9 downloaded and staged it in 8.6 s and swapped it in at a quit, nothing left beside it or in Downloads. A build that reported 0.6.9 found v0.7.0 3.4 s after launch, downloaded and verified its 163 MB dmg in 11.4 s, and opened it; the app copied out of it carried no quarantine, opened, and kept the old one's profile and tab. The published Electron 0.6.0, run with a throwaway home, offered v0.7.0 1.6 s after launch and downloaded and opened its dmg. The Views release's real update from the published Swift builds is ADR 0122's.

Revisit with a Developer ID: a notarized app opens quarantined.
