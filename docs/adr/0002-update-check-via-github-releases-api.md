# Update check via the GitHub Releases API

Pane checks for updates by asking for the repo's latest GitHub Release and comparing versions (PaneKit's `Updates`): no update framework, no update service. Installing stays a user action: Pane downloads the dmg and opens it, and the user drags Pane to Applications. The Electron app did the same, having rejected electron-updater: Pane is ad-hoc signed, Squirrel.Mac refuses to update an unsigned app, and its zip and `latest-mac.yml` would have been a publishing duty on every release for an updater that could install nothing. The contract, the `releases/latest` tag and its `-arm64.dmg` asset, is also how every Electron Pane found the native app.

The updater is the Electron app's (`app/Pane/Updates/Updater.swift`): it checks at launch and daily, retries after 5, 15, and 60 minutes, and holds the checking state for 0.8 s; the arm64 dmg downloads to Downloads with the average rate since its first bytes, no estimate in the first second, and the ETA hysteresis (PaneKit's `DownloadETA`), then opens. One source of truth serves the sidebar pill, Settings › Updates, the lock screen, and Pane › Check for Updates…; a check keeps what is on offer up, and a downloaded dmg stays downloaded, the pill's click opening it again. TLS to api.github.com vouches for the release JSON, not for where its links go, so a download must come from the repo's releases (`Updates.isTrustedDownload`): https, github.com on its default port, the `/andredezzy/pane/releases/download/` path (standardized, so `../` cannot leave it), and a plain file name ending in `-arm64.dmg`, which also names the file in Downloads. A release whose dmg fails the check offers no update; GitHub's redirect to its asset host is URLSession's to follow, over https. Scenarios point every launch at a stand-in release (`PANE_UPDATE_URL`) that serves its downloads from its own host, so a run never reaches GitHub or its rate limit, and `updates` adds a throwaway downloads folder and no opening.

Revisit with an Apple Developer ID: silent updates need signing whatever the mechanism, and an updater (Sparkle) belongs to that signing work (`docs/human-checklist.md`, 6.2).
