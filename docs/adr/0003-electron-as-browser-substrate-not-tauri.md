# Electron as the browser substrate, not Tauri

Pane stays on Electron. A full migration to Tauri was evaluated (July 2026) for its footprint and startup wins and deliberately rejected: Pane is a browser, and Chromium is the product substrate, not overhead. Every headline feature sits on Chromium/Electron session machinery with no WKWebView path — the vendored Chrome-extension host (no extension runtime exists in WKWebView), fingerprint spoofing (no per-session main-world injection or request-header rewriting, and WebKit's own engine fingerprint would betray the spoof regardless), per-profile partitions and proxies (the Apple APIs are macOS 14+ and unexposed by Tauri/wry), and Google sign-in via CDP cookie import (no cookie-injection API, and Google actively refuses WKWebView). Tauri's multi-webview — the mechanism per-tab views would need — is an explicitly unstable feature flag with open positioning and rendering bugs.

The performance math also fails on its own terms: the migration could only shrink the shell (~100–130 MB of a 342 MB light session measured live), while tab web content — the part that grows with real use — is engine-mandatory and equal-sized under any webview. The closest real-world precedent, Atrium, attempted a WKWebView browser pane via Tauri multi-webview and retreated to embedding Chromium (CEF), adding ~170 MB back plus native compositing hacks. The memory goal that motivated the evaluation is served instead by the tab-sleep / profile-auto-unload program (see CONTEXT.md: Sleep, Unload, Keep loaded).

Revisit only if Pane's identity moves off Chromium-dependent features, or if Tauri stabilizes multi-webview *and* wry exposes per-webview data stores, proxies, and script injection — and even then, re-run the memory math before re-litigating.
