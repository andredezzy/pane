# Scenarios run on a locked screen and report what they could not prove

Scenarios run on a locked screen as well as an unlocked one, proving what they can another way, and each report says what the lock kept it from proving, so a locked-screen pass is never taken for a full one. A locked session hides every window from accessibility and refuses input, so a window screenshot, an accessibility read, and a real ⌘Q cannot be proven under it; the unattended run of 2026-10-26 found the screen locked from about 04:20 local. The runner (`tests/run.ts`) records in each entry `locked` (the screen was locked at its start or end) and `deferred`, the checks it skipped (`context.defer`), and `report.json`'s `complete` is true only when nothing was deferred (review S8, 2026-10-27). `hosted`, `context-menu`, `switcher`, `extensions-menu`, `sidebar-resize`, and `http-auth` defer what only the screen shows, and `sidebar-reorder` and `sidebar-scroll` have done the same since; the `"deferred: screen locked"` strings scenarios returned before are gone. A check that runs another way on a locked screen is told by `locked`.

Locked, macOS reports the window occluded, and Chromium hides its pages once occlusion tracking is live (after a page's first real show, ADR 0011): no visual updates, and no hang monitor. So while the screen is locked, `launchPane` passes `--disable-backgrounding-occluded-windows`, Chromium's switch for this exact case. A dialog is answered with a CUA click on an unlocked screen, else through the automation channel (ADR 0018), which presses the same button a click would. macOS 27 runs open and save panels out of process (`-[NSSavePanel ok:]` throws "not implemented"), so a locked run answers a file chooser beside its panel. Chromium ignores an unresponsive page while a debugger is attached, and mouse input never arms its hang monitor (mouse events are non-blocking), so `hung-renderer` attaches no CDP and types a key into the page. While a page is hidden, a zoom change shows in the engine's zoom level but not in the page's `devicePixelRatio`, so `shortcuts` asserts the engine level always and the page ratio whenever the page is visible, and re-runs on an unlocked screen. The switcher's picture under the lock is an offscreen render of the app's views (`switcher.png`), which shows the app's UI but not page pixels.

A page left blank under the lock is the lock's artifact, not Pane's. Under it the window shows the page's background color but not its content, while stock Chrome's views windows paint, and a content_shell build, Chromium's reference embedder on the same standalone compositor path, shows only the background color under the same lock too. Phase 1's `hosted` passed locked on what it could prove: the page `visible`, laid out at the content area's size (1060×820), and composited by the engine (a CDP capture of it showed the full page); `WebContentsViewCocoa` unhidden with Chromium's `CALayerHost` attached; and no helper left after a graceful shutdown. It then re-checked everything, the visual parts included, on an unlocked screen, as `docs/human-checklist.md` records.

CUA reads a page only with full accessibility on. Chrome builds a page's accessibility tree, with its actions, once an assistive app turns it on: VoiceOver asks the app for its role and sets `AXEnhancedUserInterface`, and Chrome waits two quiet seconds. cua-driver does neither, so scenarios do it (`tests/tools/ax-activate.swift`) before clicking a page's button, such as the Web Store's install button; the click is then a real, trusted press with user activation.
