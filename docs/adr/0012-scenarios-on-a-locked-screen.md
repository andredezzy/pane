# Scenarios run unattended on the user's Mac: they never reach its apps or its login keychain or take its front, clean up after themselves, wait for conditions, and report what they could not prove

Scenarios run on the Mac the user works on, often unattended and on a locked screen, so the runner (`tests/run.ts`) leaves the user's apps, front, and files as it found them, has each check wait for its condition rather than a fixed time, and reports each check it could not make: a partial pass is never taken for a full one, and a failure is the app's, not the runner's. The rules came from incidents and a review of the runner (2026-10-27). CI runs no scenario (ADR 0049): every scenario runs on this Mac before a push or a tag (AGENTS.md), and a run takes the front only through `run.ts --foreground`, on a Mac whose user allowed it or that is idle.

**What a run reports.** Each entry records `locked` (the screen was locked at its start or end) and `deferred`, the checks the scenario skipped (`context.defer`). `report.json` is written however a scenario ends, and its `complete` is true only when every scenario passed and nothing was deferred. A scenario defers each check that only the screen, or Pane in front, can prove. A check that runs another way on a locked screen, or in the background, is told by `locked` and by `context.foreground`.

**A locked screen, or a window in the background.** A locked session hides every window from accessibility and refuses input, so a window screenshot, an accessibility read, and a real ⌘Q cannot be proven under it; and on an unlocked screen a background test window can be occluded too, the user's windows covering most of it and the system's file panel, out of process, the rest. Scenarios prove what they can another way:

- Occluded, Chromium hides the window's pages once occlusion tracking is live (after a page's first real show, ADR 0011): no visual updates, no hang monitor, and Chrome's `FileSelectHelper` ends the next chooser of a page that isn't visible (`OnVisibilityChanged`). So every run in the background or on a locked screen passes `--disable-backgrounding-occluded-windows`, Chromium's switch for this exact case (`launchPane`, `tests/lib/pane.ts`); one in front runs with Chromium's own occlusion, as the user sees it. Without it, `file-chooser` failed 4 of 4 on 2026-11-11, and `views-dialogs` in dark never had an external app's prompt asked for (five runs in three hours): a page hidden by the user's windows is no subject of any scenario.
- A page's dialog is answered by a real click on its button through the automation channel (`clickSheetButton`, ADR 0018), its fields filled first as a value set through accessibility is, with no accessibility tree of the window; its Esc and Return go through Views' own dispatch without the front (`pressWindowKey`). macOS 27 runs open and save panels out of process (`-[NSSavePanel ok:]` throws "not implemented"), so a run answers a file chooser from beside its panel, the channel's own listener between the panel and Chrome's (`pane/automation/file_panels.h`); the panel's accessory view, a window macOS hosts beside it, counts as the sheet's.
- A key posted into the app's queue reaches the menu bar without the front, so ⌘T, ⌘Q, and Ctrl-Tab run in the background; a key the window itself takes (typing, Esc, Ctrl's release) needs the key window, so without the front a scenario sends it through Views' own dispatch (`dispatchKey`), and a check of a key queued behind another defers.
- A background window can hold the focus on no view: a launching copy is active, its window key, until it hands the front back (below), and while the app is active, Views turns a view's request for the focus in a window that isn't key into an activation (`kMacActivateWidgetOnFocusRequest`), which the app in use wins. Either way Views keeps the view for when the window is key (`FocusManager::RestoreFocusedView`), so a user switching to Pane finds the PIN screen with the keys, but the channel's keys reached a window with none: while the user typed in another app the first PIN of 9 `lock-while-open` runs went nowhere (2026-11-11). The channel's keys to the window (`pinKeys`, `windowKey`, `dispatchKey`) first give the focus back as becoming key does, without the front (`FocusAsKeyWindow`, `pane/automation/automation.cc`), then go through the window's own dispatch. `views-lock` makes the window resign key through its delegate, as AppKit does (`resignKey`), checks the focus is on no view, and types the PIN.
- A press handed to the widget takes the mouse whenever the user's own button happens to be down (`Widget::OnMouseEvent` reads `[NSEvent pressedMouseButtons]`), and the copy then hears the user's release elsewhere, which ended 3 of 120 stress drags: `pointerWindow` and `dragWindow` hand the press, the moves, and the release to the root view, and only the pointer's move to the press to the widget.
- Chromium ignores an unresponsive page while a debugger is attached, and mouse input never arms its hang monitor (mouse events are non-blocking), so `hung-renderer` attaches no CDP and types a key into the page.
- While a page is hidden, a zoom change shows in the engine's zoom level but not in the page's `devicePixelRatio`, so `shortcuts` asserts the engine level always and the page ratio whenever the page is visible.
- The app's own render of its views (`render`) shows its UI but not page pixels, under the lock too: the switcher's picture (`switcher.png`, from `shortcuts`) is one.

A page left blank under the lock is the lock's artifact, not Pane's: under it the window showed the page's background color but not its content, while stock Chrome's views windows painted, and a content_shell build, Chromium's reference embedder on the same standalone compositor path, showed only the background color under the same lock too. `hosted` passes locked on what it can prove: one window of Pane's, the page it was launched with, and the window told of its tab; it defers the page drawn in the window and Quit Pane stopping every helper to an unlocked screen.

CUA reads a page only with full accessibility on. Chrome builds a page's accessibility tree, with its actions, once an assistive app turns it on: VoiceOver asks the app for its role and sets `AXEnhancedUserInterface`, and Chrome waits two quiet seconds. cua-driver does neither, so scenarios do it (`tests/tools/ax-activate.swift`) before clicking a page's button, such as the Web Store's install button; the click is then a real, trusted press with user activation.

**Never the front of the app in use** (2026-10-30). Eight scenarios brought the app in front with `activate(ignoringOtherApps:)`, so whoever worked on the Mac lost their keys to a test Pane mid-run; even the cooperative `activate()` took the front, for 3.4 s of one run while the user was in another app. The automation's `activate` takes the front only when the runner allows it (`run.ts --foreground`, `PANE_AUTOMATION_FOREGROUND`, `MayTakeFront`), and otherwise brings the window forward without the app; without the flag the eight passed with what needs the front deferred, and the user's app stayed in front for all 720 samples of the 72 s. On macOS 27, AppKit also makes a copy the runner starts from the app in front active as it finishes launching, the published 0.19.2 as much as the Views build, and it kept the front for the whole run: a scenario's copy without `--foreground` now hands it back at once to the app it took it from (`pane/ui/app/app_events_mac.mm`), and the user's app stayed in front for every 50 ms sample of a launch. A copy that may not take the front opens the new Pane after Restart to update behind the app in use (`open -g`, `pane/updates/update_installer_mac.cc`). What needs Pane in front (a page's fullscreen, keys only the key window takes) defers without the flag (`bringToFront`, `tests/lib/pane.ts`): `fullscreen` whole, `key-precedence`'s Quit Pane? over the menu, `security`'s ⌘Q with Caps Lock, `app-icon`'s Esc and Return by real keys, and `tabs-api`'s `chrome.action.openPopup`.

**Never the user's apps** (2026-10-26). `external-protocol` first used a `mailto:` link, which Chrome opens without asking, by design, so macOS opened the user's Mail with an unsent compose window. It was quit at once, and nothing was sent. A scenario that opens another app's link uses a scheme Chrome always asks about: `external-protocol` uses `maps:`, answers Cancel, and checks that Maps did not open; its fixed wait is there to prove that nothing opens. `docs/human-checklist.md` asks the user to look for a stray draft.

**Never the login keychain, nor the user's data.** Every scenario launch passes `--use-mock-keychain` (`tests/lib/browser.ts`), so a run never reads or writes the user's login Keychain: a freshly signed build asked for the keychain password for its Safe Storage item ("Chromium Safe Storage" then) on every launch. A Keychain item's access list names the app by its designated requirement, and an ad-hoc signature's is its code hash, which every build changes; only a Developer ID ends those prompts for the shipped app (ADR 0048). The Keychain also failed the first runs under a locked session: the ad-hoc signed app could neither read nor create its item (`-25320`), so Chrome reported "Encryption is not available" and kept cookies unencrypted for that run. Stock Chrome from the same build shows the same message. The shipped app's item is "Pane Safe Storage", account "Pane" (patch 0001), the item the migration fills with the Electron app's key (ADR 0043).

The app's own Keychain use honors the same switch. Under `--use-mock-keychain` the data key is sealed under a fixed secret, not the engine's Keychain item (`SafeStorage::DataSecret`, ADR 0113), so a scenario's data opens with none of the user's, and the proxy passwords an earlier Pane kept apart are read from `mock-keychain.json` in the data directory, not the "Pane Proxy Passwords" item (ADR 0037). Only under the switch does the app take its test hooks (`model::TestHook`, ADR 0115). The two go together, a test copy and the mock keychain (`pane/app/test_copy.h`): a launch whose data lies in the temporary folder, by `PANE_DATA_DIR` or under a home of its own, is a test copy and runs on the mock keychain alone; started without it, as 0.19.1's installer relaunches a scenario's copy (its `PANE_` variables and home, no switch), it exits with 1 before it reads anything, so no test copy reaches the user's Keychain item. The mock keychain runs a test copy alone: on data outside the temporary folder it is refused too, since its fixed secret would seal a key where the user's data has none yet, and a scenario's hooks would reach the user's data. Every other launch is the user's, and opens their data; a test copy reads and writes nothing outside the temporary folder (`PrepareData`). What only the real Keychain shows stays unproven by a scenario: the data key sealed under the engine's secret (ADR 0113), and the migration's adoption of the Electron app's cookie key, since a folder named by `PANE_ELECTRON_DATA_DIR` has no app name, so no key is adopted (ADR 0043). `tests/rigs/views-start.ts` proves both refusals, by `PANE_DATA_DIR` and by a home alone, under a sandbox that denies the Keychain's services and files, and `pane_unittests` the rule, link by link (`LaunchKindTest`).

**The machine as it was.** A scenario owns its temp dirs (`context.tempDir(prefix)`), `launchPane`'s data dir among them. When it ends, pass or fail, the runner detaches the encrypted volumes attached from them (`detachImagesIn`, ADR 0113), kills whatever still uses them, found by the dir in a process's arguments (`tests/lib/processes.ts`), and removes them. The data dir had leaked on every launch, 11 GB in `$TMPDIR`; in a private `$TMPDIR`, six scenarios (`smoke quit security restore profile-lifecycle downloads`) leave nothing. A failed launch kills its app and removes its dirs, and an app that exits before serving DevTools fails it at once: `/usr/bin/false` takes 261 ms to fail, not 60 s. The CDP client rejects pending calls and waiters once its socket closes, and `Browser.close` is skipped for an app that already quit: `quit`'s teardown takes 85 ms, not a 15 s timeout. The teardown also stops the panic wipe's new instance (`security`), which is no child of the runner and had been stopped only if every check before it passed.

**Deadlines.** Each scenario has one: `--timeout`, 600 s by default. A scenario past it fails, its apps and dirs go, and the run goes on. Under `--timeout 3`, a scenario that never returns failed at 3,002 ms, and the next one ran. Rejections a scenario leaves behind are logged, not fatal.

**One copy of each helper.** `tests/lib/targets.ts` finds DevTools targets, in place of five hand-written loops; `waitForExit`, and `launchTraced` with `waitForEntry`, replace hand-parsed traces; there is one `windowsOf`. `tests/lib/tools.ts` builds every Swift tool of the runner's (`tests/tools/`), and builds it again once its source is newer: an edited tool used to keep running its old build from `$TMPDIR`.

**Conditions, not fixed times.** A check waits for what it needs, with `tests/lib/poll.ts` and `PaneApp.settled`. `ubol` loads its page again until the rules block the ads, `sidebar-reorder` reads the order once the drop has changed it, and `hung-renderer` types once the page names itself Hanging. `password-managers` presses its button once no more tabs open (2 s quiet), and branches on what the press opened, since 1Password turns its popup off seconds after installing. Installing from the Web Store clicks its button again, every 3 s, until the install prompt comes: the store wires the button a moment after it shows, and the one click, made as soon as it showed, was lost, so `dark-reader`, `password-managers`, and `ubol` waited out a minute and failed on every run. `sidebar-scroll` reads the rows' frames once the list shows the row and holds still, two reads alike. The fixed waits that stay prove that something does not happen (`quiet`, `migration`, `external-protocol`, `dialogs`' beforeunload, `password-manager-off`, `extensions-per-profile`, `window-chrome`, `sleep`), or let an animation finish before an evidence capture. Two wait for something no signal shows: the spellchecker's verdict (`context-menu`), and the key-status flicker a new tab or a closed popup causes (`extensions-menu`).

**Controls as they are now.** A scenario reads a control again before it acts on it. `extensions-menu` opens the more menu again before pressing a row: it had failed twice when the window gave up key status mid-run (an extension's tab or popup taking it while the app is not frontmost), which closes the menu, as it should (ADR 0054). `clickControl` (`tests/lib/cua.ts`) reads an accessibility element again and presses, up to three times, when it was built anew between the read and the press (kAXErrorInvalidUIElement, -25202), as SwiftUI's were and a page's can be, and for that error alone. A scenario also clicks where the controls are now: when the sidebar widened to Aside's 260 points (ADR 0060), `window-chrome`'s click at the old back position landed on Collapse all. It clicks back at (281, 29) and Collapse all at (236, 19.5).

**The app's own clock.** A check times from the moment the app's clock starts. `sleep` timed a background tab's sleep from the last tab's opening, most of a second after the tab before it had started the clock by taking the selection, so the check passed or failed on where the scheduler's one-second ticks fell, from build to build.

**On Windows too.** The runner runs on Windows, and these rules hold there; it ran first in the Windows test VM on 2026-11-13, each scenario that runs on both systems passing or its failure named with what it waits on (`docs/building.md`, Scenarios). One file of it tests for the OS (`tests/lib/platform.ts`); what the Mac does with its own tools, the screen's lock read from `ioreg`, a home fixed for Foundation, the processes from ps and pgrep, a window's capture, sits in a module with a Windows side too. On Windows:

- **Never the front, never the user's input.** The channel hands each key, click, move, and scroll to Pane's window's own dispatch (ADR 0018), never to the system's input, which reaches whatever window is in front (`SendInput`), so a run behind the user's windows works and takes nothing from them; a press captures none of the user's pointer, Views capturing only while a real button is down. Windows gives keys to the active window alone, and the window's shortcuts run only while it is (`Window::CanHandleAccelerators`), where the Mac's menu bar takes a posted key in the background: a scenario that presses one needs Pane in front there (`--foreground`), which the test VM, where no one works, always allows, so the VM runs the suite both ways. In front the page's menu is the platform's to show (`PageContextMenus::Run`), which on Windows is W4's, so `context-menu` and `extension-context-menus` pass there only behind.
- **The lock** is LogonUI.exe running, and the UI is never driven by `lib/cua.ts`, whose tree is macOS's (Windows' is UI Automation's, W8's with Narrator).
- **A home of its own.** Chromium reads the user's folders from the shell there, which no variable moves, so a test copy takes them under the folder `PANE_HOME_DIR` names in the temporary folder: the Desktop, AppData, Documents, Downloads (`pane/app/data_launch_win.cc`), as a fixed home gives them on the Mac.
- **Quit ends the process.** A scenario's launch, with remote debugging and no startup window, holds DevTools' keep-alive, which Chrome lets go only at `Browser.close`, and Chrome on Windows exits only once no keep-alive holds it: Pane's quit lets it go too (`browser_main_extra_parts_win.cc`), so a scenario's copy quits as a user's, who never has remote debugging (ADR 0115).
- **The computer's time zone** is the system's alone there: the engine reads it from the registry when Windows says it changed (ICU reads no TZ on Windows), so no zone changes for Pane alone, and `fingerprint` defers its check of Automatic following it.
- **Chrome's words.** Chromium title-cases its menus on the Mac alone (its strings' `use_titlecase`): a scenario compares Chrome's words in either case (`sameTitle`), and the channel chooses an item by its title in either case.

A Windows side with nothing behind it yet throws, naming the item that brings it (W3's data, W5's menu bar, W7's install, W8's UI Automation, U5's volume, U6's frames), so nothing there passes for working. Each scenario says itself where it doesn't run (`export const notOnWindows`), the Mac's alone or Windows' design to come, and a run there reports it rather than running it; one whose Windows design is to come counts as checks not made, so that run isn't `complete`.
